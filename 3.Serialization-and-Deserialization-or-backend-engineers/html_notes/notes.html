Serializzazione, il linguaggio condiviso di macchine.

Un client JavaScript e un server Rust non hanno nulla in comune a livello di tipi di dati. La serializzazione è comunque il modo in cui parlano: entrambi convertono i loro dati nativi da e per un formato concordato per il viaggio attraverso la rete. Questo manuale copre l'intera idea, la barriera linguistica, lo standard comune, i formati testo e binario, JSON in modo approfondito, il modello mentale OSI e l'intero viaggio di andata e ritorno client<->server, con codice funzionante in Go e Python.

01

La barriera linguistica

Una tipica applicazione web è costituita da due macchine in luoghi diversi, connesse tramite Internet. Il cliente: il frontend, spesso un'app JavaScript (React, Angular, Vue) in esecuzione in un browser come Chrome, comunica con un servitore, il backend, che può essere eseguito su localhost o in un punto remoto in AWS, GCP o Azure. Comunicano tramite alcuni protocolli di rete: HTTP (API REST tradizionali) o gRPC o WebSocket. Questo manuale presuppone HTTP/REST, poiché è ancora il più comune.

Ecco il problema. Il client potrebbe essere JavaScript e il server potrebbe essere Rust e questi due linguaggi gestiscono i dati completamente diverso:

  • JavaScript è dinamico e non compilato, i tipi sono sciolti e decisi in fase di esecuzione.
  • Ruggine è compilato ed estremamente rigoroso riguardo ai tipi.

Pertanto, quando un client JavaScript invia un oggetto simile { name: "..." } nel corpo della richiesta, il server Rust non può capire nativamente una struttura dati JavaScript, i suoi tipi di dati non assomigliano a quelli di JavaScript. Lo stesso problema si svolge al contrario per la risposta. Due macchine, due mondi interni incompatibili, un filo che li unisce.

02

Serializza e deserializza

La soluzione: entrambe le parti concordano su un formato unico, comune e standard per i dati in rete. Ogni macchina converte in quel formato prima dell'invio e fuori dopo averlo ricevuto.

Serializzazione

Conversione dati nativi (un oggetto JavaScript, una struttura Rust, una struttura Go, un oggetto Python) nel formato standard comune prima di inviarlo in rete (o memorizzarlo).

Deserializzazione

L'esatto contrario: prendere dati dentro il formato comune e analizzandolo nuovamente nel tipo di dati nativo della macchina, in modo che possa eseguire la propria logica applicativa.

Indipendente dalla lingua e indipendente dal dominio

Poiché il formato è neutro, qualsiasi macchina può parlare con qualsiasi altra macchina indipendentemente dai linguaggi o dalle tecnologie sottostanti. "Indipendente dalla lingua" = non importa se sei JS o Rust. "Indipendente dal dominio" = non importa quale ambiente o stack tecnologico esegui.

Non solo per la rete

La stessa idea di conversione in e da un formato comune si applica anche a stoccaggio: scrivere i dati su disco o in un file di configurazione/log e rileggerli successivamente. La trasmissione è il focus qui, ma il fenomeno è lo stesso.

Parte II, Gli standardQuale formato concordare
03

Concordare uno standard comune

Se ti trovassi di fronte a questo problema a freddo, due macchine in luoghi diversi, connesse tramite Internet, che devono scambiarsi dati in un modo che sia indipendente dalla lingua, la soluzione ovvia è definire a norma comune.

Un "standard" / "formato"

Solo una parola di fantasia per un accordo insieme di regole descrivere come devono essere scritti i dati. Sia il client che il server promettono: "invieremo e riceveremo dati a forma di questo."

Con tale accordo in atto, il client converte la sua logica nativa (ad esempio, da JavaScript) nello standard prima dell'invio; il server legge lo standard e lo converte in suo tipo nativo (ad esempio, una struttura Rust); fa il suo lavoro, riconverte la risposta nello standard e la invia; e il client lo analizza nuovamente in JavaScript. Quel viaggio di andata e ritorno è serializzazione e deserializzazione. In una riga: convertire i dati da e verso un formato comune durante la trasmissione (o l'archiviazione), in modo che siano comprensibili attraverso lingue e domini.

04

Formati basati su testo e formati binari

Esistono molti standard di serializzazione, ma rientrano in due famiglie.

  • Formati basati su testo: leggibile dall'uomo. JSON, YAML, e XML. Puoi aprire il payload e leggerlo.
  • Formati binari: compilato in binario grezzo per una trasmissione compatta e altamente efficiente. Protobuf (Buffer di protocollo) e Avro sono quelli popolari. Non pensato per essere letto a occhio.

YAML e XML vengono ancora utilizzati per la serializzazione, ma non così spesso per la comunicazione HTTP. Per le API REST HTTP tradizionali, la scelta predefinita è JSON.

05

JSON: lo standard del settore

Per la tradizionale comunicazione API REST HTTP, JSON è lo standard di serializzazione più popolare, utilizzato in qualcosa di simile L'80% delle volte.

JSON

JavaScripta Ooggetto Notazione. Chiamato così perché assomiglia e si comporta in modo molto simile a un oggetto JavaScript, ma nonostante il nome lo è non limitato a JavaScript ed è usato ovunque, in ogni lingua.

Perché ha vinto

  • Leggibile dall'uomo. JSON è stato progettato per essere letto dalle persone; puoi dare un'occhiata a un carico utile e capirlo. Questo è uno dei suoi punti di forza più forti.
  • Tipi di dati fondamentali. I suoi tipi di valore si adattano perfettamente ai concetti che ogni programmatore già conosce.

Dove lo incontrerai

  • Trasmissione HTTP: i corpi di richiesta/risposta delle API REST (il focus qui).
  • Registrazione: una scelta molto popolare per i log di applicazioni e server in fase di runtime.
  • File di configurazione: configurazione dell'app e dello strumento.
06

Regole di sintassi JSON

JSON ha pochissime regole, questo è il punto. Ecco un oggetto tipico, annotato con ogni regola richiamata dalla fonte:

Le regole, spiegate

  • Un oggetto JSON inizia con { e termina con }.
  • Le chiavi devono essere stringhe racchiuse tra virgolette doppie: e.g. "name":. Nessun altro tipo di dati può essere una chiave. (Virgolette doppie, sempre, non singole.)
  • Valori sono limitati alle tipologie fondamentali: a stringa, a numero, a booleano, un matrice, o altro oggetto nidificato.
  • A oggetto nidificato segue le stesse identiche regole in modo ricorsivo: parentesi graffe, chiavi di stringa tra virgolette e valori di quegli stessi tipi fondamentali. JSON può annidarsi quanto vuoi.
Queste sono le specifiche complete, in pratica

Non c'è molto altro da memorizzare. Parentesi graffe attorno all'oggetto, chiavi di stringa tra virgolette doppie e valori che sono stringhe, numeri, valori booleani, matrici o oggetti nidificati, ciascun oggetto nidificato obbedisce alle stesse caratteristiche. Questo è tutto quello che c'è da sapere su JSON.

Parte III, Sotto il cofanoCosa ignorare e cosa non ignorare
07

Il modello mentale OSI

Quando i dati attraversano Internet passano attraverso molti livelli di rete, il Modello OSI. Lo fai no necessità di padroneggiare pacchetti IP e frame di dati per essere un ingegnere backend; è sufficiente una foto di alto livello. Le due estremità della pila sono livello di applicazione (in alto) e il strato fisico (in basso); ci sono diversi livelli intermedi e lo stesso stack esiste sia sul client che sul server.

Il modello mentale dell'ingegnere backend

Ti concentri solo su livello di applicazione. Supponiamo che il tuo client serializzi i dati in JSON e li invii. Sotto il cofano la rete trasforma quel JSON in frame di dati -> pacchetti IP -> bit fisici (0s e 1s) inviati come segnali elettrici o ottici. Prima che il tuo server tocchi i dati, la rete riassembla quei bit nel file esattamente lo stesso JSON inviato dal cliente. Non ti occupi mai delle conversioni intermedie, solo del JSON.

08

Il flusso di lavoro end-to-end

Mettendo insieme ogni tassello, ecco il giro completo di una domanda reale, del fenomeno che, nel suo insieme, è serializzazione e deserializzazione.

In parole: il cliente raccoglie input, serializza lo invia a una stringa JSON nel corpo della richiesta e lo invia; i bit attraversano Internet; il server deserializza il JSON nel suo tipo nativo, esegue la logica applicativa (ad esempio salva in un database), serializza la sua risposta a JSON e la invia; il cliente deserializza quel JSON in un oggetto JavaScript e aggiorna l'interfaccia utente. L'intero flusso è ciò che chiamiamo serializzazione e deserializzazione, un fenomeno che per lo più devi solo conoscere esiste; ha pochissimi concetti propri.

09

Serializzazione in Go

Go serializza da/verso JSON con lo standard encoding/json pacchetto: Marshal = serializzare, Unmarshal = deserializzare. I pilastri si presentano attraverso interfacce (astrazione + polimorfismo), campi non esportati + tag struct (incapsulamento) e incorporamento (composizione, eredità di Go). I pilastri sono contrassegnati Ops.

Vai 1.22+serialize.go
package main

import ("encoding/json"; "fmt"; "time")

// ABSTRACTION: Serializer names a capability, "turn data into
// bytes and back", without binding to a concrete format. Code
// depends on this contract, so JSON could be swapped for another
// format with zero changes to callers.
type Serializer interface {
    Serialize(v any) ([]byte, error)   // native -> common format
    Deserialize(data []byte, v any) error // common format -> native
}

// POLYMORPHISM: JSONSerializer implements Serializer. Any other
// format (YAML, Protobuf) could implement the same interface and
// be used interchangeably through a Serializer variable.
type JSONSerializer struct{}

func (JSONSerializer) Serialize(v any) ([]byte, error) {
    return json.Marshal(v)   // SERIALIZE: struct -> JSON bytes
}
func (JSONSerializer) Deserialize(data []byte, v any) error {
    return json.Unmarshal(data, v) // DESERIALIZE: JSON bytes -> struct
}

// "INHERITANCE" via COMPOSITION: BaseModel holds shared fields;
// embedding it into User reuses them (and their json tags).
type BaseModel struct {
    ID        int       `json:"id"`         // tag = the JSON key name
    CreatedAt time.Time `json:"created_at"`
}

// ENCAPSULATION: an exported struct whose JSON shape is controlled
// by tags. "password" is unexported (lowercase) -> private AND
// invisible to the JSON encoder, so it never leaks over the wire.
type User struct {
    BaseModel            // embedded -> inherits ID, CreatedAt
    Name    string      `json:"name"`
    Active  bool        `json:"active"`
    Address Address     `json:"address"` // nested object
    password string     // unexported: hidden from JSON output
}

type Address struct {
    Country string `json:"country"`
    Phone   int    `json:"phone"`
}

func main() {
    var codec Serializer = JSONSerializer{} // program to the interface

    u := User{
        BaseModel: BaseModel{ID: 1, CreatedAt: time.Now()},
        Name:      "Ada", Active: true,
        Address:   Address{Country: "India", Phone: 123456},
    }

    // SERIALIZE, native Go struct into the common JSON format
    out, _ := codec.Serialize(u)
    fmt.Println(string(out))
    // {"id":1,"created_at":"...","name":"Ada","active":true,
    //  "address":{"country":"India","phone":123456}}

    // DESERIALIZE, JSON received over HTTP back into a Go struct
    incoming := []byte(`{"name":"Lin","address":{"country":"IN","phone":42}}`)
    var back User
    codec.Deserialize(incoming, &back)
    fmt.Println(back.Name, back.Address.Country) // Lin IN
}
10

Serializzazione in Python

Python usa il built-in json modulo: json.dumps = serializza (scarica su stringa), json.loads = deserializza (carica da stringa). La stessa architettura OOP: contratto ABC, ereditarietà, polimorfismo e un attributo privato.

Python 3.11+serialize.py
import json
from abc import ABC, abstractmethod
from dataclasses import dataclass, asdict, field

# ABSTRACTION: Serializer is an Abstract Base Class. The
# @abstractmethod forces subclasses to implement both directions.
# You cannot instantiate Serializer itself, it is a pure contract.
class Serializer(ABC):
    @abstractmethod
    def serialize(self, obj) -> str: ...      # native -> common
    @abstractmethod
    def deserialize(self, data: str): ...      # common -> native

# INHERITANCE + POLYMORPHISM: JSONSerializer IS-A Serializer and
# overrides both methods. A YamlSerializer could subclass the same
# ABC and be dropped in wherever a Serializer is expected.
class JSONSerializer(Serializer):
    def serialize(self, obj) -> str:
        return json.dumps(obj)               # SERIALIZE: dict -> JSON text
    def deserialize(self, data: str):
        return json.loads(data)              # DESERIALIZE: JSON text -> dict

# INHERITANCE: BaseModel is a shared parent (id, timestamps).
@dataclass
class BaseModel:
    id: int = 0

@dataclass
class Address:
    country: str
    phone: int                              # nested object

# ENCAPSULATION: __password is name-mangled (-> _User__password),
# effectively private, and to_dict() chooses what leaves the
# object, the secret never appears in the serialized output.
@dataclass
class User(BaseModel):                     # IS-A BaseModel
    name: str = ""
    active: bool = True
    address: Address | None = None
    __password: str = ""                  # private; excluded below

    def to_dict(self) -> dict:
        d = asdict(self)
        d.pop("_User__password", None)        # keep the secret out
        return d

if __name__ == "__main__":
    codec: Serializer = JSONSerializer()    # program to the contract

    user = User(id=1, name="Ada",
                address=Address("India", 123456))

    # SERIALIZE, native object into the common JSON format
    payload = codec.serialize(user.to_dict())
    print(payload)
    # {"id": 1, "name": "Ada", "active": true,
    #  "address": {"country": "India", "phone": 123456}}

    # DESERIALIZE, JSON received over HTTP back into native data
    incoming = '{"name": "Lin", "address": {"country": "IN", "phone": 42}}'
    data = codec.deserialize(incoming)
    print(data["name"], data["address"]["country"])  # Lin IN
Stessa forma, due lingue

Entrambi definiscono a Serializzatore contrarre (astrazione), implementarlo per JSON (polimorfismo), condividere i campi attraverso un modello base (ereditarietà/composizione) e mantenere i segreti fuori dal formato wire (incapsulamento). I verbi sono universali: serializzare = nativo -> JSON (Vai Marshal, Pitone dumps); deserializzare = JSON -> nativo (Vai Unmarshal, Pitone loads).

L'intera idea in un fiato

Due macchine con tipi di dati nativi incompatibili concordano su a formato comune (di solito JSON). Ciascuno serializza i suoi dati in quel formato prima dell'invio e deserializza restituirlo dopo aver ricevuto, quindi la comunicazione è indipendente dalla lingua e dal dominio. La rete trasforma JSON in bit e viceversa; al livello di applicazione hai sempre e solo a che fare con JSON.
