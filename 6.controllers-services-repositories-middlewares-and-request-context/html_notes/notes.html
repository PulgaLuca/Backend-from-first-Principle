01Cliente e server

Tutto inizia con una conversazione tra due partecipanti HTTP: a cliente (un browser, un'app mobile, un altro servizio) e a servitore. Il client invia una richiesta; il server alla fine invia una risposta.

Abbiamo già studiato il ciclo di vita esterno al server, come la richiesta viene impacchettata, inviata attraverso la rete e come ritorna la risposta. Quello che abbiamo no ancora tracciato è ciò che accade dentro il server: la lunga sequenza di eventi tra l'istante in cui arriva una richiesta e l'istante in cui parte una risposta. Tale sequenza interna è l'oggetto del presente manuale.

Parte I / Il viaggio della richiesta02 / 15

02Il ciclo di vita della richiesta all'interno del server

Dal momento in cui una richiesta raggiunge il server fino al momento in cui viene restituita una risposta, accadono molte cose. Lo chiamiamo il richiedere il ciclo di vita. Per comprendere l'architettura, è utile tracciare la richiesta da dall'alto verso il basso, seguendolo nell'ordine esatto in cui viene elaborato: arrivo, instradamento, gestore, servizio, repository e infine la risposta in uscita.

Questo ordinamento dall'alto verso il basso è intenzionale. Ogni argomento si basa sull'ultimo, rispecchiando il percorso che i dati seguono fisicamente attraverso il codice.

Parte I / Il viaggio della richiesta03 / 15

03Punto di ingresso e percorso

Quando arriva una richiesta, il sistema operativo inoltra la richiesta HTTP a qualunque porto il tuo server è in ascolto, :3000, :4000o qualsiasi porta configurata. Il punto in cui il tuo server riceve per la prima volta quella richiesta è il suo punto di ingresso. Il tuo server è sempre ascolto su quella porta e l'ascolto è il modo in cui raccoglie le richieste in arrivo.

Instradamento

Subito dopo arriva il punto di ingresso instradamento. Un server espone molti percorsi, /users, /users/123, percorsi dinamici come /users/:id, e così via. Il algoritmo di instradamento controlla il metodo e il percorso della richiesta in entrata e lo associa a un particolare gestore: una funzione predefinita responsabile di quel percorso.

Definizione/Gestore

A gestore (chiamato anche a controllore) è qualsiasi funzione predefinita per gestire le richieste per un determinato percorso. L'intero compito del routing è decidere quale il conduttore corre per quale richiesta in arrivo.

Parte I / Il viaggio della richiesta04 / 15

04Perché tre strati?

Una volta che il routing sceglie un gestore, incontriamo la struttura in tre parti al centro di un backend ben organizzato: gestori (controllori), servizi, e repository. Una domanda naturale: perché dividere le cose in tre componenti invece di concentrare tutta la logica in un unico gestore?

La risposta onesta: esiste nessun requisito difficile per separarli. Tu può fare tutto in un unico gestore. La separazione è a modello di progettazione: una scelta che ti regala vantaggi reali:

  • La tua base di codice diventa scalabile man mano che cresce.
  • È di più mantenibile nel tempo.
  • Lo è più facile aggiungere funzionalità senza rompere parti non correlate.
  • Lo è più facile da eseguire il debug perché ogni livello ha una chiara responsabilità.

Questo è il principio di separazione delle preoccupazioni. Il resto della Parte II percorre ogni livello nell'ordine in cui la richiesta li soddisfa.

Parte II / I tre strati05 / 15

05Il livello controller/gestore

Il gestore è il punto di ingresso di un percorso una volta che il routing lo ha abbinato. Il suo compito principale è quello di controllare il flusso di dati: dal client al server e dal server nuovamente al client. Fondamentalmente, in quasi ogni framework e linguaggio, il tuo gestore lo è dato due cose dal runtime stesso.

Fornito dal runtimeL'oggetto della richiesta

Trasporta tutto ciò che il client ha inviato: metodo, percorso, intestazioni, parametri di query, corpo. Lo fai no crealo, Go, Express, Flask, ecc. te lo consegnamo ad ogni richiesta.

Fornito dal runtimeL'oggetto risposta

L'handle attraverso il quale imposti i codici di stato, modifichi le intestazioni di risposta e invii il corpo. Anche fornito automaticamente, lo ricevi, non lo costruisci.

Con questi due oggetti in mano, il gestore esegue un flusso di lavoro preciso e ordinato.

  1. Estrazione dati
    Estrarre i dati rilevanti dall'oggetto della richiesta. Cosa tiri dipende dal metodo: GET → parametri di interrogazione; POST / PUT / PATCH → l'ente richiedente; DELETE → di solito niente, a volte un corpo.
  2. Associazione (Deserializzazione)
    Il corpo è arrivato come a JSON string perché JSON è un formato serializzabile che viaggia bene oltre il confine front-end/back-end. Il conduttore deserializza nel tipo nativo del linguaggio, una struttura Go, un dict/classe Python, una struttura Rust. I framework lo chiamano così vincolante. Se fallisce, fermati immediatamente e ritorna 400 Richiesta errata.
  3. Validazione
    Conferma che i dati corrispondano alla forma prevista: campi obbligatori presenti, tipi corretti, nessun payload dannoso. Convalidare tutto da un client esterno, parametri di percorso, parametri di query e corpo ed essere il più specifico possibile.
  4. Trasformazione
    Facoltativamente, rimodellare i dati convalidati per comodità dei livelli downstream, ad esempio inserendo valori predefiniti.
  5. Delegazione
    Passare i dati puliti, convalidati e trasformati (più il contesto come l'ID utente autenticato) fino al livello di servizio.
  6. Invio della risposta
    Quando il servizio ritorna, scegli il codice di stato corretto e invia la risposta finale al cliente.

Una nota su Node.js vs Go e Python

In un'app Node.js/Express avviene spesso la fase di deserializzazione a monte in un middleware (il json() body parser), quindi JSON è già un oggetto JavaScript nel momento in cui viene eseguito il gestore. Dentro Vai e Pitone in genere deserializzi esplicitamente all'interno del gestore, in una struttura, un dizionario o una classe.

06Il livello di servizio

Il livello di servizio è dove elaborazione vera e propria: la logica applicativa, accade. La regola più importante lo governa:

La regola d'oro dei servizi

Il livello di servizio dovrebbe saperlo assolutamente nulla su HTTP. Nessun oggetto di richiesta/risposta, nessun codice di stato, nessun problema di convalida. Se dai un'occhiata a un metodo di servizio, dovresti no essere in grado di dire che è utilizzato in un'API. È solo una funzione: ingresso dati, elaborazione, uscita dati.

Questo isolamento è ciò che mantiene il sistema disaccoppiato. Decide il servizio cosa fare; decide il conduttore come segnalarlo tramite HTTP. È qui che tracciamo la linea di responsabilità.

Orchestrazione

Un unico metodo di servizio può fare molto. Può chiamare uno o più metodi di repository e unire i risultati, effettuare chiamate API esterne, inviare e-mail, attivare notifiche e tutto ciò che l'operazione aziendale richiede. Questo ruolo di coordinamento si chiama orchestrazione: il servizio unisce dati provenienti da più fonti e restituisce un unico risultato pulito al gestore. Un servizio che invia solo un'e-mail potrebbe non toccare mai il repository.

book_service / pura logica applicativa 
// Notice: no http.Request, no ResponseWriter, no status codes.
// You cannot tell from this signature that it serves an API.
func (s *BookService) ListBooks(ctx context.Context, sort string) ([]Book, error) {
    // Orchestration: call the repository for the data it needs.
    books, err := s.repo.FindAllBooks(ctx, sort)
    if err != nil {
        return nil, err // bubble the error up; the handler decides the code
    }
    // Could also: enrich, merge other repo calls, send notifications...
    return books, nil
}

// A service that needs no database at all is perfectly valid:
func (s *BookService) NotifyOwner(email string) error {
    return s.mailer.Send(email, "Your book was added")
}
class BookService:
    def __init__(self, repo, mailer):
        self.repo = repo
        self.mailer = mailer

    # No request, no response, no status codes, just logic.
    def list_books(self, sort: str) -> list:
        # Orchestration: ask the repository for what it needs.
        books = self.repo.find_all_books(sort)
        # Could merge other repo calls, enrich, notify, etc.
        return books

    # A purely-logic service that never touches the DB:
    def notify_owner(self, email: str) -> None:
        self.mailer.send(email, "Your book was added")

07Il livello del deposito

Il deposito (o banca dati) layer ha un unico problema: parlando con il database. Riceve i dati dal servizio, costruisce la query del database: per l'inserimento, il filtraggio o l'ordinamento, lo esegue e restituisce il risultato non elaborato al servizio.

Responsabilità unica

Un metodo di repository dovrebbe andare bene una cosa e ritorno un tipo di dati. Fallo no scrivere un singolo metodo che, a seconda di un parametro opzionale, restituisca un libro o tutti i libri. Scrivi invece due metodi distinti: FindAllBooks() e FindBookByID(id).

book_repository / un lavoro per metodo 
// ONE method, ONE shape of result: all books, sorted.
func (r *BookRepo) FindAllBooks(ctx context.Context, sort string) ([]Book, error) {
    // Build the query from the data the service handed down.
    query := fmt.Sprintf("SELECT id, title, author FROM books ORDER BY %s", sort)
    rows, err := r.db.QueryContext(ctx, query)
    if err != nil { return nil, err }
    defer rows.Close()

    var books []Book
    for rows.Next() {
        var b Book
        rows.Scan(&b.ID, &b.Title, &b.Author)
        books = append(books, b)
    }
    return books, nil
}

// A SEPARATE method for the single-book case. No optional toggles.
func (r *BookRepo) FindBookByID(ctx context.Context, id int) (Book, error) {
    var b Book
    err := r.db.QueryRowContext(ctx,
        "SELECT id, title, author FROM books WHERE id = $1", id).
        Scan(&b.ID, &b.Title, &b.Author)
    return b, err
}
class BookRepo:
    def __init__(self, db):
        self.db = db

    # ONE method, ONE result shape: all books, sorted.
    def find_all_books(self, sort: str) -> list:
        # Build the query from data passed down by the service.
        query = f"SELECT id, title, author FROM books ORDER BY {sort}"
        cur = self.db.execute(query)
        return [dict(row) for row in cur.fetchall()]

    # SEPARATE method for one book. No optional toggle parameter.
    def find_book_by_id(self, book_id: int) -> dict:
        cur = self.db.execute(
            "SELECT id, title, author FROM books WHERE id = ?", (book_id,))
        return dict(cur.fetchone())

08L'intero ciclo di vita, dall'inizio alla fine

Mettendo insieme i livelli, ecco il percorso completo di andata e ritorno per una singola chiamata API, ad esempio GET /books:

  1. Vincolante
    Il gestore estrae i dati dall'oggetto della richiesta e li deserializza nel formato nativo.
  2. Validazione e trasformazione
    Il gestore convalida i dati e inserisce valori predefiniti/rimodella secondo necessità.
  3. Chiamata di servizio
    L'handler delega al servizio, che esegue l'elaborazione vera e propria, chiamando il repository per qualsiasi lavoro sul database.
  4. Ritorna il risultato
    Il repository restituisce le righe al servizio; il servizio restituisce un risultato pulito al gestore.
  5. Risposta
    Il gestore sceglie il codice di stato e invia la risposta. 200 / 201 / 204 sul successo; 400 per errore del cliente; 500 per errore del server.
200 OK 201 Creato 204 Nessun contenuto 400 Richiesta errata 500 Errore interno del server

09Cos'è il middleware

Ora riproduci il ciclo di vita, ma osserva il lacune. Tra il punto di ingresso e l'instradamento, tra l'instradamento e l'handler e tra l'handler e la risposta, ci sono confini: punti in cui possono essere eseguite funzioni extra. Le funzioni che vengono eseguite in queste lacune sono middleware. Il nome è letterale: eseguono nel mezzo degli altri contesti esecutivi.

I middleware lo sono facoltativo. Potrebbero essercene molti, o nessuno; una richiesta può fluire direttamente dal routing al gestore. Li aggiungi solo quando un requisito ne richiede uno.

Un middleware è essenzialmente un tipo speciale di gestore. Come un normale gestore riceve il file oggetto richiesta e il oggetto di risposta dal runtime, quindi anch'esso può leggere valori dalla richiesta, modificare le intestazioni di risposta e persino inviare una risposta direttamente al client. Ma riceve anche una terza cosa, come spiega la Parte 10.

Parte III/Middleware10 / 15

10La funzione next()

La terza cosa che riceve un middleware è next, una funzione. Chiamando next() passa l'esecuzione al contesto successivo: se si tratta del middleware successivo, della fase di routing o del gestore finale. È il modo in cui la richiesta passa da un confine a quello successivo.

Due modi in cui finisce un middleware

(1) Fa il suo lavoro, poi chiama next() per continuare la catena. (2) No chiamare next() e invece inviare una risposta immediatamente: cortocircuitare la richiesta prima che raggiunga il gestore. Questa uscita anticipata è esattamente il motivo per cui un controllo di autenticazione fallito o un limite di velocità superato possono interrompere una richiesta in modo economico.

Poiché un middleware ha sia gli oggetti richiesta che risposta, può leggere e modificare la richiesta e può terminarla esattamente dove si trova restituendo una risposta. Questa è l'intera portata del potere di un middleware.

forma del middleware / req, res, next 
// In Go, middleware wraps the "next" handler. Calling next.ServeHTTP
// is the equivalent of next(): pass execution along the chain.
func LoggingMiddleware(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        log.Printf("%s %s", r.Method, r.URL.Path) // do work

        // EARLY EXIT example (short-circuit, never calls next):
        if r.Header.Get("X-Blocked") == "yes" {
            http.Error(w, "forbidden", http.StatusForbidden)
            return // request stops here
        }

        next.ServeHTTP(w, r) // === next(): continue the chain ===
    })
}
# A WSGI/Flask-style middleware receives the request and a `next`
# callable that invokes the rest of the chain.
def logging_middleware(next):
    def wrapper(request):
        print(f"{request.method} {request.path}")  # do work

        # EARLY EXIT example (short-circuit, never calls next):
        if request.headers.get("X-Blocked") == "yes":
            return Response("forbidden", status=403)  # stops here

        return next(request)  # === next(): continue the chain ===
    return wrapper

Perché il middleware?

Lo stesso motivo per cui usiamo le funzioni: per evitare di ripetere le stesse righe ovunque. Un backend può servire migliaia o milioni di richieste ed esporre centinaia di endpoint. È necessario eseguire operazioni comuni, sicurezza, registrazione, autenticazione, analisi, compressione ogni richiesta. Senza middleware duplicheresti quel codice in ogni gestore. Anche l'estrazione di una funzione di supporto ti costringe comunque a farlo chiamare in ogni gestore. Middleware centralizza la logica comune e la applica automaticamente lungo tutta la catena.

Parte III/Middleware11 / 15

11Perché l'ordine è importante

Ogni middleware utilizza next() per passare l'esecuzione a quello successivo, in modo che la richiesta li attraversi in sequenza, nell'ordine in cui li registri. Quell'ordine non è cosmetico, cambia il comportamento.

L'esempio più vivido è gestione globale degli errori, che in genere viene posizionato ultimo. Perché la richiesta arriva una direzione, un middleware può rilevare solo gli errori che hanno origine a monte di esso. Se si posiziona il gestore degli errori al centro, verrà generato un errore successivamente nel gestore passato e non essere mai catturato. Posizionalo per ultimo e potrà acquisire errori da qualsiasi punto precedente della catena.

Un ordinamento predefinito sensato

CORSO prima (rifiutare le origini straniere il prima possibile) → registrazione &#8594; autenticazione → controlli specifici dell'applicazione → gestore &#8594; gestione degli errori globali per ultima. Dedica tempo reale alla decisione di questo ordine per la tua app.

12Middleware comuni

Ciascuno dei seguenti si qualifica come middleware per gli stessi due motivi: deve essere eseguito ogni richiesta e deve leggere la richiesta e/o modificare la risposta.

SicurezzaCORSO

I browser applicano una politica della stessa origine: un'app Web su example.com può accedere solo alle risorse da example.com a meno che il server remoto non invii le intestazioni corrette. Il middleware CORS legge la richiesta origine (fornito automaticamente dal runtime); se corrisponde a un'origine front-end consentita, aggiunge le intestazioni di risposta appropriate in modo che il browser non blocchi la risposta, quindi chiama next(). In caso contrario, omette le intestazioni e il browser lo blocca per impostazione predefinita. Posizionato presto.

SicurezzaIntestazioni di sicurezza

Imposta le intestazioni come Content-Security-Policy su ogni risposta, quindi inoltra al middleware successivo.

SicurezzaAutenticazione

Estrae un token (JWT, ID sessione, ecc.) dalle intestazioni o dal payload e lo verifica. Su fallimento, ritorna 401 Non autorizzato immediatamente e termina la richiesta, senza gestore, senza ulteriore middleware. Su successo, estrae i dettagli dell'utente (ID utente, ruolo, permessi) e li memorizza nel file contesto della richiesta prima di chiamare next().

SicurezzaLimitazione della velocità

Tiene traccia del numero di richieste effettuate da un IP all'interno di una finestra da te definita (ad esempio 30 chiamate in 2 secondi). Oltrepassata la soglia, ritorna 429 Troppe richieste proteggere le risorse del server; sotto di esso, chiama next().

OsservabilitàRegistrazione e monitoraggio

Registra i dettagli della richiesta, il percorso, il metodo, i parametri della query, il corpo, nel terminale o in un file di registro per il debug, il reporting e il controllo.

AffidabilitàGestione globale degli errori

Rileva qualsiasi errore non strutturato da qualsiasi punto a monte, decide se si tratta di un client (4xx) o server (5xx) errore e restituisce un messaggio pulito e strutturato (spesso con a message e un errore code il front-end può mappare un messaggio amichevole). Posizionato ultimo.

PrestazioniCompressione

Comprime risposte di grandi dimensioni (ad esempio gzip) in modo che viaggino in modo efficiente; i browser moderni li decomprimono in modo trasparente nuovamente in un formato utilizzabile.

ConvenienzaAnalisi dei dati

La serializzazione/deserializzazione e persino la convalida/trasformazione possono essere delegate a un middleware (ad esempio un parser del corpo) in modo che i gestori non lo ripetano. Questo è esattamente il motivo per cui Node's json() parser del corpo significa che JSON è già un oggetto JS nel momento in cui viene eseguito un gestore.

I middleware CORS e di autenticazione nel codice

cors + middleware di autenticazione 
var allowedOrigin = "https://app.example.com"

func CORSMiddleware(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        origin := r.Header.Get("Origin") // runtime gives us this
        if origin == allowedOrigin {
            w.Header().Set("Access-Control-Allow-Origin", origin)
        }
        next.ServeHTTP(w, r) // pass along; browser blocks if header absent
    })
}

func AuthMiddleware(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        token := r.Header.Get("Authorization")
        userID, role, err := verifyToken(token)
        if err != nil {
            http.Error(w, "unauthorized", http.StatusUnauthorized) // 401, stop
            return
        }
        // SUCCESS: stash identity in the request context, then continue.
        ctx := context.WithValue(r.Context(), "userID", userID)
        ctx = context.WithValue(ctx, "role", role)
        next.ServeHTTP(w, r.WithContext(ctx))
    })
}
ALLOWED_ORIGIN = "https://app.example.com"

def cors_middleware(next):
    def wrapper(request):
        resp = next(request)
        origin = request.headers.get("Origin")  # runtime gives us this
        if origin == ALLOWED_ORIGIN:
            resp.headers["Access-Control-Allow-Origin"] = origin
        return resp
    return wrapper

def auth_middleware(next):
    def wrapper(request):
        token = request.headers.get("Authorization")
        try:
            user_id, role = verify_token(token)
        except Exception:
            return Response("unauthorized", status=401)  # stop
        # SUCCESS: stash identity in the request context, then continue.
        request.context["user_id"] = user_id
        request.context["role"] = role
        return next(request)
    return wrapper

13Qual è il contesto della richiesta

Il middleware di autenticazione ha semplicemente fatto qualcosa di sottile: ha memorizzato l'ID utente e il ruolo da qualche parte in modo che un gestore successivo potesse leggerli. Quel "da qualche parte" è il contesto della richiesta.

Definizione/Contesto della richiesta

Un pezzo di conservazione o stato: di solito, si intende un semplice archivio di valori-chiave limitato a una singola richiesta HTTP. Ogni richiesta ha il proprio contesto; non si perde in altre richieste. Ogni framework in ogni linguaggio (Node, Go, Python) fornisce un'implementazione di questo concetto; la meccanica è diversa, l'idea è la stessa.

Perché esiste? Perché una richiesta passa da tanti confini di funzioni isolate: CORS, registrazione, routing, autenticazione, controlli dei permessi, gestore, gestore degli errori. Il contesto offre a tutti loro un luogo condiviso in cui leggere e scrivere lo stato senza accoppiamento stretto senza che un middleware debba passare manualmente i valori al successivo.

14Caso d'uso/Trasmissione dei dati di autenticazione

L'uso canonico. Il middleware di autenticazione verifica le credenziali, estrae il file user_id e rolee li scrive nel contesto. Molto più a valle, a POST /books il conduttore deve timbrare il nuovo libro con il suo proprietario. Invece di fidarsi di a user_id inviato nel payload JSON del client, legge l'ID dal contesto.

Sicurezza, perché è importante

Se hai preso il user_id dal payload del client, un client dannoso potrebbe inviare quello di qualcun altro Identificati e agisci come loro. Leggere l'identità dal contesto, popolato solo dal middleware di autenticazione verificata, chiude quel buco. Lo stesso ruolo memorizzato nel contesto guida i controlli delle autorizzazioni (questo utente è un amministratore? Ha accesso in scrittura?).

func CreateBookHandler(w http.ResponseWriter, r *http.Request) {
    var req CreateBookRequest
    json.NewDecoder(r.Body).Decode(&req)

    // Read the trusted user ID FROM THE CONTEXT, not from req.
    // The auth middleware put it there after verifying the token.
    userID := r.Context().Value("userID").(int)
    role := r.Context().Value("role").(string)

    if role != "admin" && role != "user" {
        http.Error(w, "forbidden", http.StatusForbidden)
        return
    }

    // Persist with the SERVER-VERIFIED owner id, never the client's.
    book, _ := bookService.Create(r.Context(), req, userID)
    w.WriteHeader(http.StatusCreated) // 201
    json.NewEncoder(w).Encode(book)
}

15Casi d'uso/Tracciamento e cancellazione

Richiedi il tracciamento

Un primo middleware può generare un ID univoco (un UUID) e salvarlo nel contesto. Per l'intero ciclo di vita di tale richiesta, ogni riga di registro può includere questo ID e qualsiasi chiamata in uscita ad altri microservizi può inoltrarlo in un'intestazione come X-Request-ID. Quando successivamente controlli i tuoi log per eseguire il debug di un problema, quel singolo ID te lo consente tracciare una richiesta per ogni servizio toccato: dove è iniziato e ovunque è andato.

middleware ID richiesta 
func RequestIDMiddleware(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        id := uuid.NewString() // one unique id for this request
        ctx := context.WithValue(r.Context(), "requestID", id)
        w.Header().Set("X-Request-ID", id) // echo it back / forward it
        log.Printf("[%s] %s %s", id, r.Method, r.URL.Path)
        next.ServeHTTP(w, r.WithContext(ctx))
    })
}
import uuid

def request_id_middleware(next):
    def wrapper(request):
        rid = str(uuid.uuid4())  # one unique id for this request
        request.context["request_id"] = rid
        print(f"[{rid}] {request.method} {request.path}")
        resp = next(request)
        resp.headers["X-Request-ID"] = rid  # echo it back / forward it
        return resp
    return wrapper

Cancellazione, segnali di interruzione e scadenze

Il contesto della richiesta è anche il luogo standard da trasportare segnali di cancellazione e scadenze. Se un client si disconnette o scade una scadenza, tali segnali si propagano alle chiamate esterne downstream, quindi un servizio mai pende perennemente aspettando un lavoro che non conta più. In Go questo è il built-in context.Context con WithTimeout; in Python emerge come timeout/token di cancellazione passati lungo la catena di chiamate.

L'intero quadro

Una richiesta entra nel punto di ingresso, scorre attraverso una catena ordinata di middleware e routing, arriva a un gestore che convalida e trasforma i dati, delega a un servizio che orchestra la logica applicativa, che chiama repository per il lavoro sul database, il tutto mentre una richiesta contesto porta con sé identità, un ID di traccia e scadenze. Il risultato risale e il gestore sceglie un codice di stato e invia la risposta. Questo è l'intero ciclo di vita della richiesta.
