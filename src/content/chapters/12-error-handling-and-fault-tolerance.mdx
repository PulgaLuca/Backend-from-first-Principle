Un riferimento dettagliato al backend

Gli errori non sono eccezionali, sono _inevitabili_. Le query del database falliscono, le API esterne scadono, gli utenti inviano dati errati e la logica applicativa colpisce casi limite che nessuno aveva previsto. Questo capitolo definisce la mentalità e gli strumenti concreti per rilevare, gestire e recuperare ogni tipo di errore di backend, prima che ti costi silenziosamente denaro o fiducia.

01

## La mentalità tollerante agli errori

> "La domanda non è se gli errori si verificheranno, ma come li gestirai quando si verificheranno."

Ogni ingegnere di backend deve interiorizzare una semplice verità: **il tuo sistema fallirà**. Non potrebbe. Volere. Le fonti sono ovunque:

- Le query del database occasionalmente falliscono o scadono.
- Le API esterne (pagamenti, email, autenticazione) verranno disattivate.
- Gli utenti invieranno dati non corretti, mancanti o dannosi.
- La logica applicativa colpirà casi limite a cui nessuno aveva pensato durante la progettazione.

Un sistema tollerante ai guasti non è un sistema che non si rompe mai. È uno che **si rompe in modo prevedibile, si riprende con grazia e ti dice esattamente cosa è successo**. Per raggiungere questo obiettivo è necessario un deliberato cambiamento di mentalità da "gestirò gli errori in seguito" a "progetterò per il fallimento fin dal primo giorno".

<Callout type="info">
La migliore gestione degli errori inizia _prima_ che si verifichi l'errore. Il rilevamento proattivo, i controlli dello stato e la convalida prevengono la maggior parte delle sorprese in fase di runtime.
</Callout>

02

## Le cinque classi di errori di backend

Gli errori di backend possono essere raggruppati in cinque grandi categorie. Ognuno ha un'origine, una strategia di rilevamento e una correzione diversa.

(1) Errori logici

L'app viene eseguita ma produce risultati errati. Più difficile da rilevare. Può drenare silenziosamente denaro per settimane.

(2) Errori del database

Errori di connessione, deadlock, violazioni di vincoli, SQL non valido. Può disattivare l'intera app.

(3) Errori di servizio esterni

Le API di terze parti (pagamento, e-mail, autenticazione) scadono, limitano la velocità o vanno offline. Non hai alcun controllo.

(4) Errori di convalida dell'input

Gli utenti inviano dati errati, mancanti o fuori portata. Più facile da gestire, se il livello di convalida è robusto.

(5) Errori di configurazione

Variabili di ambiente mancanti, credenziali errate durante la distribuzione. Surface all'avvio, non in fase di esecuzione, se lo fai bene.

03

## Errori logici: i killer silenziosi

Gli errori logici sono la classe più **pericolosa** perché la tua applicazione continua a funzionare, semplicemente fa la cosa sbagliata. Nessun arresto anomalo, nessuna traccia dello stack, nessuna risposta 500. Solo risultati silenziosamente sbagliati che si accumulano nel tempo.

### Esempio classico

Una piattaforma di e-commerce applica uno sconto due volte a causa di un bug nel motore delle promozioni. Il risultato: **costi di spedizione negativi**. L'app funziona perfettamente. Ogni ordine viene spedito. L'azienda perde denaro su ogni transazione. Ciò passa inosservato per settimane perché nessun avviso di monitoraggio si attiva sul "costo di spedizione negativo".

### Cause principali comuni

- **Requisiti fraintesi**: gli appunti di uno sprint meeting erano ambigui; hai implementato ciò che _pensavi_ fosse stato chiesto, non ciò che era previsto.
- **Algoritmi errati**: una formula di sconto o di determinazione del prezzo complessa presenta un errore sfalsato o un operatore sbagliato (`*` invece di `+`).
- **Casi limite non gestiti**: un utente che non ha mai effettuato acquisti prima attiva un percorso di sconti "basato sugli acquisti precedenti" che non è stato progettato per gli utenti che non effettuano acquisti.

<Callout type="info">
Errori logici che coinvolgono denaro, autorizzazioni o sicurezza possono corrompere i dati e produrre risultati aziendali errati per mesi senza una singola voce nel registro degli errori. Vengono rilevati solo attraverso test accurati, monitoraggio delle metriche aziendali e revisione del codice.
</Callout>

### Strategie di prevenzione

- Scrivi **test unitari per ogni regola aziendale**, in particolare la logica di sconti, prezzi e autorizzazioni.
- Aggiungi il **monitoraggio delle metriche aziendali** (ad esempio, avvisa se il valore medio dell'ordine scende di &gt;20% in un'ora).
- Utilizza **test basati sulle proprietà** (vai: `gopter`, Pitone: `hypothesis`) per generare automaticamente input di casi limite.
- Richiedi una **revisione tra pari** per tutte le modifiche al codice relative al pagamento e all'autenticazione.

## Errori del database

La maggior parte delle applicazioni backend non hanno senso senza il loro database. Un errore del database di qualsiasi tipo significa che la tua app non può fornire dati reali, il che di solito significa un'interfaccia utente interrotta o errori a catena tra i servizi.

### (1) Errori di connessione

Il tuo backend non può raggiungere il server del database. Possibili cause:

- Partizione di rete o errore DNS tra il server app e il server DB.
- Il server del database è sovraccarico o inattivo.
- **Pool di connessioni esaurito**: tutte le connessioni TCP del pool sono in uso; le nuove richieste si mettono in coda o falliscono immediatamente.

<Callout type="info">
**Il pool di connessioni** mantiene un numero fisso di connessioni TCP aperte al database, evitando il sovraccarico di un handshake TCP completo + negoziazione TLS su ogni query. Strumenti: `pgxpool` (Vai), `psycopg2` piscina o `SQLAlchemy` (Pitone), `pg` Piscina (nodo). Dimensiona attentamente la tua piscina: troppo piccola -&gt; collo di bottiglia; troppo grande -&gt; sovraccarico DB.
</Callout>

### (2) Errori di violazione dei vincoli

Stai tentando di eseguire un'operazione che viola una regola a livello di database:

| Tipo di vincolo | Trigger | Risposta appropriata |
| --------------- | ------------------------------------------ | ------------------------------------------------ |
| **Unico** | Inserisci un'e-mail / nome utente duplicato | HTTP 409 Conflitto o 400, "E-mail già in uso" |
| **Chiave esterna** | Fare riferimento a una riga che non esiste | HTTP 404, "ID autore non trovato" / 400 |
| **Non nullo** | Valore della colonna obbligatorio mancante | HTTP 400, "Il campo X è obbligatorio" |
| **Controlla** | Il valore non soddisfa una regola personalizzata (ad esempio prezzo &gt; 0) | HTTP 400, messaggio specifico del dominio |

### (3) Errori di query/sintassi

SQL non valido, errore di battitura nel nome della tabella, riferimento a una colonna rinominata o condizione di unione mancante. Questi di solito vengono catturati durante lo sviluppo ma possono sfuggire se le stringhe SQL grezze vengono create dinamicamente.

<Callout type="info">
Non costruire mai SQL mediante concatenazione di stringhe con l'input dell'utente. Utilizzare sempre query con parametri/istruzioni preparate. Ciò previene sia gli errori di query che gli attacchi SQL injection.
</Callout>

### (1) Guasti di rete

La connessione Internet tra il tuo server e l'API esterna non è affidabile. Incontrerai: timeout della connessione, errori di risoluzione DNS, partizioni di rete ed errori di handshake TLS. Imposta **timeout espliciti** su ogni chiamata HTTP in uscita, non lasciare mai che un'API lenta di terze parti blocchi la tua goroutine/thread a tempo indeterminato.

### (2) Limitazione della velocità: HTTP 429

Ogni API esterna seria applica limiti di velocità per prevenire abusi. Se la tua app blocca un'API (a causa di un bug, un picco di traffico o un errore di loop), riceverai `HTTP 429 Too Many Requests`.

### (3) Interruzione del servizio/Tempi di inattività

I principali fornitori di servizi cloud (AWS, GCP) e i più diffusi servizi SaaS si interrompono occasionalmente. La tua app necessita di una strategia per quando una dipendenza critica non è completamente disponibile:

- **Fallback**: se la cache Redis è inattiva, esegui il fallback alle letture DB dirette per i dati non critici.
- **Degradamento graduale**: disattiva la funzionalità interessata (ad esempio "Suggerimenti AI temporaneamente non disponibili") anziché bloccare l'intera app.
- **Modello interruttore automatico**: dopo N errori consecutivi, interrompe l'invio di richieste al servizio interrotto e restituisce immediatamente una risposta memorizzata nella cache/predefinita. Riprovare il servizio dopo un periodo di raffreddamento.

## Errori di convalida dell'input

Questi sono gli **errori più facili da gestire** perché _sei tu a definire le regole_. Il livello di convalida è la prima linea di difesa: rileva i dati errati nel punto di ingresso, prima che raggiungano il database o la logica applicativa.

### Tipi di convalida

| Digitare | Cosa controlla | Esempio |
| ----------------- | ----------------------------------------- | --------------------------------------- |
| **Formato** | Forma/modello del valore | Regex email, data ISO, telefono E.164 |
| **Gamma** | Limiti numerici, lunghezza della stringa, dimensione dell'array | Prezzo: 0-99999, nome: 2-100 caratteri |
| **Obbligatorio** | Campo obbligatorio presente | user\_id non deve essere null |
| **Regola aziendale** | Vincolo specifico del dominio | Fine\_data prenotazione &gt; inizio\_data |
| **Referenziale** | L'entità correlata esiste effettivamente | categoria\_id esiste nella tabella delle categorie |

Convalida sempre a **entrambi i livelli**: frontend (UX) _e_ backend (sicurezza). Non fidarti mai solo della convalida lato client. Il backend è il cancello autorevole.

<Callout type="info">
Restituisce HTTP `400 Bad Request` con un corpo dell'errore strutturato che elenca tutti i campi non riusciti e il motivo. Non restituire un singolo messaggio generico, aiuta l'utente a correggere tutti i propri errori in un unico viaggio di andata e ritorno.
</Callout>

## Errori di configurazione

Gli errori di configurazione si verificano al confine tra ambienti, sviluppo -&gt; staging -&gt; produzione. Una scomparsa `OPENAI_API_KEY`, un URL di database errato o un segreto dimenticato possono interrompere silenziosamente funzionalità specifiche mentre il resto dell'app appare integro.

### Errore rapido all'avvio: non in fase di runtime

La regola d'oro: **convalidare tutte le variabili di ambiente richieste prima che il server inizi ad accettare il traffico**. Se qualcuno manca o è danneggiato, si blocca immediatamente con un messaggio di errore chiaro.

#### Difetto: errore di runtime

- L'app si avvia correttamente
- Il primo utente raggiunge l'endpoint dell'immagine AI
- La chiamata OpenAI fallisce, manca la chiave
- L'utente riceve un misterioso errore 500
- La vecchia distribuzione è già stata interrotta
- Il sito è inattivo finché non viene risolto manualmente

#### Buono: errore di avvio

- Inizia la nuova distribuzione
- La convalida della configurazione viene eseguita immediatamente
- Rilevata chiave mancante -&gt; il processo esce con un messaggio chiaro
- Blu-verde: vecchia distribuzione ancora in esecuzione
- Zero tempi di inattività, correzioni e ridistribuzioni da parte del team operativo

<Callout type="info">
Le implementazioni blu-verdi rendono sicuri i crash all'avvio: la nuova versione deve superare i controlli di integrità prima che la vecchia versione venga terminata. Se la nuova versione si blocca all'avvio, la vecchia versione continua a servire il traffico.
</Callout>

### Convalida della configurazione all'avvio

controlla ogni variabile richiesta prima che la porta venga associata

```go title="config.go / Go"
package config

import (
    "fmt"
    "os"
    "strings"
)

type Config struct {
    DatabaseURL    string
    OpenAIKey      string
    JWTSecret      string
    ResendAPIKey   string
}

// MustLoad panics if any required variable is missing.
// Call this once in main() before http.ListenAndServe.
func MustLoad() Config {
    required := []string{
        "DATABASE_URL",
        "OPENAI_API_KEY",
        "JWT_SECRET",
        "RESEND_API_KEY",
    }

    var missing []string
    for _, key := range required {
        if os.Getenv(key) == "" {
            missing = append(missing, key)
        }
```

```go title="health.go / Go"
func healthHandler(db *pgxpool.Pool, rdb *redis.Client) http.HandlerFunc {
    return func(w http.ResponseWriter, r *http.Request) {
        checks := map[string]string{}
        overall := "ok"

        // DB check
        ctx, cancel := context.WithTimeout(r.Context(), 2*time.Second)
        defer cancel()
        if err := db.Ping(ctx); err != nil {
            checks["database"] = "unhealthy: " + err.Error()
            overall = "degraded"

        }

        if err := rdb.Ping(r.Context()).Err(); err != nil {
            checks["cache"] = "unhealthy: " + err.Error()
            overall = "degraded"
        } else {
            checks["cache"] = "ok"
        }

        status := http.StatusOK
        if overall != "ok" { status = http.StatusServiceUnavailable }

        w.Header().Set("Content-Type", "application/json")
        w.WriteHeader(status)
        json.NewEncoder(w).Encode(HealthStatus{Status: overall, Checks: checks})
    }
```

```ts title="health.ts / TypeScript 5+ + Express"
import type { Request, Response } from 'express'

interface HealthStatus {
  status: 'ok' | 'degraded'
  checks: Record<string, string>
}

// Describing a check as DATA rather than as another try/catch block is
// what keeps this endpoint honest as dependencies are added: one entry
// per dependency, all of them run concurrently, and nobody can add a
// fifth check that forgets its timeout.
const CHECKS: Array<{ name: string; probe: () => Promise<unknown> }> = [
  { name: 'database', probe: () => pool.query('SELECT 1') },
  { name: 'cache', probe: () => redis.ping() },
]

export async function health(_req: Request, res: Response): Promise<void> {
  const results = await Promise.all(
    CHECKS.map(async ({ name, probe }) => {
      try {
        await withTimeout(probe(), 2000)
        return [name, 'ok'] as const
      } catch (err) {
        return [name, `unhealthy: ${(err as Error).message}`] as const
      }
    }),
  )

  const checks = Object.fromEntries(results)
  const overall: HealthStatus['status'] =
    results.every(([, v]) => v === 'ok') ? 'ok' : 'degraded'

  res.status(overall === 'ok' ? 200 : 503).json({ status: overall, checks })
}
```

## Monitoraggio e osservabilità

I controlli sanitari ti dicono che qualcosa non funziona _proprio ora_. Il monitoraggio ti dice che qualcosa sta per rompersi e ti fornisce il contesto per capire perché qualcosa si è rotto dopo il fatto.

### Cosa monitorare

| Categoria | Metriche da monitorare | Perché |
| --------------------- | ---------------------------------------------------------- | ------------------------------------------- |
| **Livello HTTP** | Velocità 4xx/5xx, latenza p50/p95/p99 | Rivela immediatamente i problemi rivolti agli utenti |
| **Banca dati** | Durata della query, utilizzo del pool di connessioni, conteggio dei deadlock | Rileva query lente prima del timeout |
| **Servizi Esterni** | Tasso di successo delle chiamate, latenza, conteggio 429 | Sapere quando una dipendenza sta peggiorando |
| **Metriche aziendali** | Transazioni riuscite/min, pagamenti falliti, tasso di iscrizione | Rileva gli errori logici invisibili ai tassi di errore |
| **Infrastrutture** | CPU, memoria, I/O del disco, throughput di rete | L'esaurimento delle risorse precede gli arresti anomali |

<Callout type="info">
**Non tenere traccia solo dei tassi di errore.** Un calo delle transazioni riuscite da 1.000/min a 200/min è un problema critico, anche se il tasso di errore è pari allo 0%. Monitora sempre i risultati aziendali positivi, non solo i segnali di fallimento.
</Callout>

## Strategie di recupero

### Recuperabile e non recuperabile

#### Errori recuperabili

- Problema tecnico transitorio della rete all'API e-mail
- Pool di connessioni al database temporaneamente esaurito
- Limite di tariffa 429 dal servizio esterno

**Strategia:** Riprova con backoff esponenziale. Metti in coda il lavoro. Non arrenderti immediatamente.

#### Errori irreversibili

- Cluster Redis completamente inattivo
- Processore di pagamento offline per ore
- Dati corrotti nel DB

**Strategia:** Degradazione aggraziata. Ricaderci. Disabilita la funzione. Proteggi le funzionalità principali.

### Backoff esponenziale

Vai a Python JavaScript TypeScript Java

raddoppia l'attesa per ogni tentativo, aggiungi jitter e non ritentare mai un errore permanente

```go title="retry.go / Go"
func sendEmailWithRetry(to, subject, body string) error {
    maxRetries := 5
    baseDelay  := 1 * time.Second

    for attempt := 0; attempt < maxRetries; attempt++ {
        err := emailClient.Send(to, subject, body)
        if err == nil {
            return nil  // success
        }

        if !isRetryable(err) {
            return fmt.Errorf("permanent failure: %w", err)
        }

        // Exponential backoff: 1s, 2s, 4s, 8s, 16s
        wait := baseDelay * time.Duration(1<<attempt)
        // Add jitter (+/-20%) to prevent thundering herd
        jitter := time.Duration(rand.Int63n(int64(wait / 5)))
        time.Sleep(wait + jitter)

        log.Warn("email send failed, retrying",
            "attempt", attempt+1,
            "wait_ms", wait.Milliseconds(),
            "error", err)
    }
    return fmt.Errorf("all %d retries exhausted", maxRetries)
}

func isRetryable(err error) bool {
    // Retry on 429, 503, network errors; not on 400, 401, 422
    var httpErr *HTTPError
    if errors.As(err, &httpErr) {
        return httpErr.StatusCode == 429 || httpErr.StatusCode >= 500
    }
    return true  // network errors are always retryable
}
```

```ts title="retry.ts / TypeScript 5+"
// Generic, because "retry with backoff" is never needed exactly once.
// The type parameter keeps the wrapped call's return value intact, so
// adding retries to a call site changes nothing about how it is used.
export async function withRetry<T>(
  work: () => Promise<T>,
  opts: { maxRetries?: number; baseDelayMs?: number; signal?: AbortSignal } = {},
): Promise<T> {
  const { maxRetries = 5, baseDelayMs = 1000, signal } = opts

  for (let attempt = 0; attempt < maxRetries; attempt++) {
    // The AbortSignal matters more than it looks. Without it, a client
    // that hung up three seconds ago still costs you thirty-one seconds
    // of retries against an API you are paying per call for.
    signal?.throwIfAborted()

    try {
      return await work()
    } catch (err) {
      if (!isRetryable(err)) {
        throw new Error('permanent failure', { cause: err })
      }

      const wait = baseDelayMs * 2 ** attempt   // 1s, 2s, 4s, 8s, 16s
      const jitter = Math.random() * (wait / 5) // +/-20%, no thundering herd
      await sleep(wait + jitter, signal)

      log.warn({ attempt: attempt + 1, wait_ms: wait, err }, 'retrying')
    }
  }
  throw new Error(`all ${maxRetries} retries exhausted`)
}

function isRetryable(err: unknown): boolean {
  // Retry on 429, 503, network errors; not on 400, 401, 422
  if (err instanceof HTTPError) {
    return err.statusCode === 429 || err.statusCode >= 500
  }
  return true // network errors are always retryable
}

// Usage: the result is still a Message, cache or no retries.
```

```java title="EmailService.java / Java 17+ + Spring Retry"
        backoff = @Backoff(delay = 1000, multiplier = 2, random = true))
    public void sendEmail(String to, String subject, String body) {
        emailClient.send(to, subject, body); // 1s, 2s, 4s, 8s, 16s (+jitter)
    }

    // Called once every attempt is exhausted. Without a @Recover method
    // the final exception simply propagates, which is often right, but
    // that should be a decision rather than something you discover.
    @Recover
    void recover(RetryableException e, String to, String subject, String body) {
        log.error("all retries exhausted to={}", to, e);
        deadLetter.park(to, subject, body);
    }
}

// Resilience4j is the other standard choice, and its advantage is that
// the retry composes with a circuit breaker: a provider that is fully
// down stops being called at all, instead of being retried five times
// by every single request that arrives.
```

### Ripristino automatico o manuale

- **Automatico**: riavvia i processi bloccati (systemd, policy di riavvio Kubernetes), pulisci le cache danneggiate, passa ai sistemi di backup. Progetta attentamente, il ripristino automatico a volte può _amplificare_ un problema.
- **Manuale**: danneggiamento dei dati, discrepanze nei pagamenti, incidenti di sicurezza. Questi _richiedono il giudizio umano_. Documentare il runbook. Provalo. Scopri chi è di guardia.

<Callout type="info">
L'integrità dei dati è la tua priorità numero 1 durante qualsiasi incidente. Non eliminare o migrare mai automaticamente i dati come parte di una procedura di ripristino degli errori. Prima fai un backup, sempre.
</Callout>

## Implementazione del gestore errori globale

La forma è la stessa in ogni lingua e si divide in due: un **errore di applicazione digitato** che riporta il codice di stato e un messaggio sicuro rivolto all'utente, e un **posto unico** sul bordo che gira qualsiasi cosa gettata o restituita nella busta. Go non ha eccezioni, quindi i suoi errori viaggiano come valori restituiti; gli altri lasciano volare un'eccezione e la catturano al confine. In ogni caso, è esattamente un luogo a decidere cosa vede il cliente.

```go title="errors/types.go / Go"
// AppError is the canonical error type for this application.
type AppError struct {
    Code    int      // HTTP status code
    Message string   // Safe, user-facing message
    Details any      // Optional: field-level errors for 400s
    Err     error    // Original error, for logging only, NEVER sent to client
}

func (e *AppError) Error() string { return e.Message }
```

```java title="AppException.java / Java 17+"
    private final int code;              // HTTP status code
    private final Object details;        // Optional: field-level errors for 400s

        super(message, cause);           // cause is for logging only
        this.code = code;
        this.details = details;
    }

    public int code() { return code; }
    public Object details() { return details; }

    // Factories, so a status code is never typed as a bare int at a call site
    public static AppException notFound(String resource) {
        return new AppException(404, resource + " not found", null, null);
    }

    public static AppException conflict(String msg) {
        return new AppException(409, msg, null, null);
    }

    public static AppException badRequest(String msg, Object details) {
        return new AppException(400, msg, details, null);
    }

    public static AppException internal(Throwable cause) {
        // NEVER cause.getMessage() as the message: it reaches the client
        return new AppException(500, "something went wrong", null, cause);
```

```go title="middleware/error_handler.go / Go"
package middleware
import (
    "encoding/json"
    "errors"
    "log/slog"
    "net/http"

    "github.com/jackc/pgx/v5/pgconn"
    apperr "yourapp/errors"
)

type ErrorResponse struct {
    Code    int    `json:"code"`
    Message string `json:"message"`
    Details any    `json:"details,omitempty"`
}

// GlobalErrorHandler wraps a handler that returns an error.
func GlobalErrorHandler(next func(http.ResponseWriter, *http.Request) error) http.HandlerFunc {
    return func(w http.ResponseWriter, r *http.Request) {
        err := next(w, r)
        if err == nil { return }

        var appErr *apperr.AppError

        switch {
        // Already wrapped as AppError
        case errors.As(err, &appErr):
            if appErr.Err != nil {
                slog.Error("app error", "err", appErr.Err)
            }

        // Postgres unique constraint violation -> 409
        case isPgError(err, "23505"):
            appErr = apperr.Conflict("resource already exists")

        // Postgres foreign key violation -> 404
        case isPgError(err, "23503"):
            appErr = apperr.NotFound("referenced resource")

        // pgx no-rows -> 404
        case errors.Is(err, pgx.ErrNoRows):
            appErr = apperr.NotFound("resource")

        // Everything else -> 500 (never leak internal error)
        default:
            slog.Error("unhandled error", "err", err)
            appErr = apperr.Internal(err)
        }

        w.Header().Set("Content-Type", "application/json")
        w.WriteHeader(appErr.Code)
        json.NewEncoder(w).Encode(ErrorResponse{
            Code:    appErr.Code,
            Message: appErr.Message,
            Details: appErr.Details,
        })
    }
}

func isPgError(err error, code string) bool {
    var pgErr *pgconn.PgError
    return errors.As(err, &pgErr) && pgErr.Code == code
}
```

```js title="middleware/errorHandler.js / Node 20+ + Express"
import { AppError, conflict, notFound, internal } from '../errors.js'

// Express identifies an error handler by its FOUR parameters. Drop `next`
// and it silently becomes an ordinary middleware that is never called on
// an error, which is the classic way this safety net stops working.
export function globalErrorHandler(err, req, res, next) {
  let appErr

  if (err instanceof AppError) {
    // Already wrapped
    if (err.cause) log.error({ err: err.cause }, 'app error')
    appErr = err
  } else if (err.code === '23505') {
    // Postgres unique constraint violation -> 409
    appErr = conflict('resource already exists')
  } else if (err.code === '23503') {
    // Postgres foreign key violation -> 404
    appErr = notFound('referenced resource')
  } else {
    // Everything else -> 500 (never leak internal error)
    log.error({ err, path: req.path }, 'unhandled error')
    appErr = internal(err)
  }

  res.status(appErr.code).json({
    code: appErr.code,
    message: appErr.message,
    ...(appErr.details && { details: appErr.details }),
  })
}

// Registered LAST, after every route, because Express runs the chain in
// order and an error handler can only catch what is upstream of it.
```

```ts title="middleware/errorHandler.ts / TypeScript 5+ + Express"
import type { NextFunction, Request, Response } from 'express'
import { AppError, conflict, notFound, internal } from '../errors'

// Postgres surfaces its errors as a `code` string on an untyped object,
// so narrowing it is the honest first step rather than a cast.
function pgCode(err: unknown): string | undefined {
  return typeof err === 'object' && err !== null && 'code' in err
    ? String((err as { code: unknown }).code)
    : undefined
}

export function globalErrorHandler(
  err: unknown, // `unknown`, not `Error`: anything at all can be thrown
  req: Request,
  res: Response,
  _next: NextFunction,
): void {
  let appErr: AppError

  if (err instanceof AppError) {
    if (err.cause) log.error({ err: err.cause }, 'app error')
    appErr = err
  } else {
    switch (pgCode(err)) {
      case '23505': appErr = conflict('resource already exists'); break  // unique violation
      case '23503': appErr = notFound('referenced resource'); break      // FK violation
      default:
        log.error({ err, path: req.path }, 'unhandled error')
        appErr = internal(err) // never leak the original message
    }
  }

  res.status(appErr.code).json({
    code: appErr.code,
    message: appErr.message,
    ...(appErr.details && { details: appErr.details }),
  })
}
```

```java title="GlobalExceptionHandler.java / Java 17+ + Spring Boot"
// @RestControllerAdvice IS the global handler: one class, applied to
// every controller, with a method per exception type. Spring picks the
// most specific match, so the Exception method is the final net.
@RestControllerAdvice
public class GlobalExceptionHandler {
    private static final Logger log = LoggerFactory.getLogger(GlobalExceptionHandler.class);

    record ErrorResponse(int code, String message, Object details) {}

    // Already wrapped as AppException
    @ExceptionHandler(AppException.class)
    ResponseEntity<ErrorResponse> onApp(AppException e) {
        if (e.getCause() != null) {
            log.error("app error", e.getCause()); // the real error, internally
        }
        return ResponseEntity.status(e.code())
            .body(new ErrorResponse(e.code(), e.getMessage(), e.details()));
    }

    // Postgres unique constraint violation -> 409
    @ExceptionHandler(DuplicateKeyException.class)
    ResponseEntity<ErrorResponse> onDuplicate() {
        return ResponseEntity.status(409)
            .body(new ErrorResponse(409, "resource already exists", null));
    }

    // Foreign key / referenced row missing -> 404
    @ExceptionHandler(DataIntegrityViolationException.class)
    ResponseEntity<ErrorResponse> onIntegrity() {
        return ResponseEntity.status(404)
            .body(new ErrorResponse(404, "referenced resource not found", null));
    }

    // Everything else -> 500, and the real error goes to the log ONLY.
    @ExceptionHandler(Exception.class)
    ResponseEntity<ErrorResponse> onUnhandled(Exception e, HttpServletRequest req) {
        log.error("unhandled error path={}", req.getRequestURI(), e);
        return ResponseEntity.status(500)
            .body(new ErrorResponse(500, "something went wrong", null));
    }
}
```

## Sicurezza: cosa esporre, cosa nascondere

<Callout type="info">
Ogni messaggio di errore che lascia il tuo backend è una potenziale perdita di informazioni. Tratta le tue risposte agli errori con la stessa cura delle risposte API.
</Callout>

### (1) Non divulgare mai i dettagli interni

I messaggi di errore del database provenienti da Postgres contengono nomi di tabelle, nomi di colonne, nomi di indici e nomi di vincoli. Se inoltri un file raw `pgconn.PgError` messaggio direttamente al client, un utente malintenzionato apprende il tuo schema e può creare tentativi di SQL injection più mirati.

| Cosa hai | Cosa inviare al cliente |
| ------------------------------------------------------------------ | -------------------------------------- |
| `duplicate key value violates unique constraint "users_email_key"` | `"Email already in use"`               |
| `relation "usres" does not exist` (errore di battitura) | `"Something went wrong"`               |
| `deadlock detected on relation 42816`                              | `"Something went wrong, please retry"` |
| `stack trace: panic at server.go:142`                              | `"Internal server error"`              |

### (2) Errori di autenticazione vaghi (di proposito)

Gli endpoint di accesso sono la superficie più attaccata in qualsiasi applicazione. ### (3) Pratiche di registrazione sicure

I log vengono spesso inviati a servizi di aggregazione di terze parti (Datadog, Grafana Cloud, ELK). Nelle principali violazioni dei dati, i file di registro trapelati hanno esposto milioni di record, perché gli ingegneri avevano registrato incautamente campi sensibili.

- **Non accedere mai**: password, chiavi API, numeri di carta di credito, SSN, indirizzi email completi, token di sessione.
- **Registra invece**: ID utente (non email), ID correlazione/richiesta, nome operazione, codice errore.
- Utilizza una **libreria di pulizia dei log** (vai: `slog` con un gestore personalizzato; Pitone: `structlog` processori; Nodo: di pino `redact`; Java: un logback `RegexReplacement`) per oscurare automaticamente i campi sensibili noti.

Vai a Python JavaScript TypeScript Java

log l'identificatore, mai l'identità

```python title="safe_logging.py / Python + structlog"
# UNSAFE, never do this
log.error("login_failed",
    email=user.email,           # PII leak
    password=req.password,      # catastrophic
    api_key=cfg.openai_key,     # secret leak
)

# SAFE, IDs and correlation only
log.error("login_failed",
    user_id=user.id,
    correlation_id=request.headers.get("X-Request-ID"),
    reason="invalid_credentials",  # generic code, not DB message
)

# Better still: make the leak impossible rather than remembering not to
# do it. A structlog processor scrubs known-sensitive keys on every
# event, including the ones a future call site adds carelessly.
SENSITIVE = {"password", "api_key", "token", "card", "email"}

def scrub(logger, method_name, event_dict):
    for key in event_dict:
        if key.lower() in SENSITIVE:
            event_dict[key] = "[REDACTED]"
    return event_dict

structlog.configure(processors=[scrub, ...])
```

```js title="safeLogging.js / Node 20+ + pino"
// UNSAFE, never do this
log.error({
  email: user.email,          // PII leak
  password: req.body.password, // catastrophic
  api_key: config.openaiKey,   // secret leak
}, 'login_failed')

// SAFE, IDs and correlation only

  user_id: user.id,
  correlation_id: req.get('X-Request-ID'),
  reason: 'invalid_credentials', // generic code, not DB message
}, 'login_failed')

// Best: configure redaction ONCE, so the unsafe version above is
// neutralised even when somebody writes it by accident.
const log = pino({
  redact: {
    paths: ['*.password', '*.api_key', '*.token', '*.card', 'req.headers.authorization'],
    censor: '[REDACTED]',
  },
})

// Note what redaction does NOT cover: `log.error(user)` where the whole
// object is logged, or an error whose MESSAGE contains the token. The
// list is a safety net, not a substitute for choosing the fields.
```

```ts title="safeLogging.ts / TypeScript 5+ + pino"
// Redaction is a runtime safety net. TypeScript can add a compile-time
// one on top, which catches the mistake before it ever ships.
type Sensitive = 'password' | 'email' | 'api_key' | 'token' | 'card'

// A log payload that simply cannot carry a sensitive key: the mapped
// type sets each of them to `never`, so supplying one fails to compile.
type SafeLog = Record<string, unknown> & { [K in Sensitive]?: never }

export function logSafely(event: string, fields: SafeLog): void {
  log.error(fields, event)
}

// SAFE, IDs and correlation only
logSafely('login_failed', {
  user_id: user.id,
  correlation_id: req.get('X-Request-ID'),
  reason: 'invalid_credentials', // generic code, not DB message
})

// UNSAFE, and this one is now a BUILD failure rather than a breach:
// logSafely('login_failed', { email: user.email, password: req.body.password })
```

```java title="SafeLogging.java / Java 17+ + SLF4J"
// UNSAFE, never do this
log.error("login_failed email={} password={} api_key={}",
    user.email(), req.password(), config.openAiKey());

// SAFE, IDs and correlation only
log.atError()
   .setMessage("login_failed")
   .addKeyValue("user_id", user.id())
   .addKeyValue("correlation_id", req.getHeader("X-Request-ID"))
   .addKeyValue("reason", "invalid_credentials") // generic code, not DB message
   .log();

// Java's structural guard is `toString()`: a record prints ALL of its
// components, so logging a User record logs the password field with it.
// Override it once, at the type, and every log site is safe by default.
public record User(String id, String email, String passwordHash) {
    @Override
    public String toString() {
        return "User[id=" + id + "]"; // no email, no hash, ever
    }
}

// Logback can also mask at the appender with a RegexReplacement rule,
// which catches secrets embedded in exception messages, the case no
// field-level approach can reach.
```
