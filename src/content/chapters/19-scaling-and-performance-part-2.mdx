## assenza di stato: il fattore chiave

Il ridimensionamento orizzontale funziona solo se _qualsiasi_ istanza del server può gestire _qualsiasi_ richiesta. Nel momento in cui un server conserva dati esclusivi, un oggetto di sessione in memoria, un file caricato sul suo disco locale, una cache in-process, quel server diventa speciale. Perderlo e perderai quei dati. Indirizza un utente altrove e riceverà errori. Questa è statalità e interrompe il ridimensionamento orizzontale.

L’assenza di stato è il principio secondo cui nessuna singola istanza del server conserva informazioni a cui altre istanze non possono accedere. Ogni parte di stato persistente, sessioni, file, voci della cache, record di database deve vivere in un archivio _esterno_ condiviso che tutte le istanze possono raggiungere.

### Cosa deve essere esternalizzato

| Tipo di stato | Sbagliato (in corso) | Destra (esterna) |
| ------------------- | --------------------------- | ----------------------------------------- |
| **Sessioni** | Dizionario in memoria | Redis/database/token JWT |
| **Caricamenti di file** | File system locale | S3, Cloudflare R2, MinIO |
| **Cache** | Mappa in memoria | Redis, Memcached, Valkey |
| **Banca dati** | File SQLite su disco | Postgres (RDS), MySQL, SQLite centralizzato |
| **Lavori in background** | Goroutine/thread in corso | Coda Redis, RabbitMQ, Kafka |

la sessione risiede in Redis, quindi qualsiasi istanza può soddisfare qualsiasi richiesta

```go
import (
    "context"
    "github.com/redis/go-redis/v9"
    "time"
)

var rdb = redis.NewClient(&redis.Options{Addr: "redis:6379"})

// StoreSession saves session data in Redis so ANY server can read it.
func StoreSession(ctx context.Context, sessionID string, userID string) error {
    return rdb.Set(ctx, "session:"+sessionID, userID, 24*time.Hour).Err()
}

// GetSession retrieves session data, works regardless of which server
// the request lands on, because Redis is shared across all instances.
func GetSession(ctx context.Context, sessionID string) (string, error) {
    return rdb.Get(ctx, "session:"+sessionID).Result()
}
```

```ts
import session from 'express-session'
import { RedisStore } from 'connect-redis'

// Typing the session payload once is what stops it drifting into an
// untyped bag that each handler guesses at. Declaration merging widens
// the library's own type, so `req.session.userId` is checked everywhere.
declare module 'express-session' {
  interface SessionData {
    userId: string
    role: 'admin' | 'user'
  }
}

app.use(session({
  // The store is the ONLY line that matters for horizontal scaling:
  // omit it and express-session silently uses an in-process MemoryStore,
  // which is exactly the state that makes instances non-interchangeable.
  store: new RedisStore({ client: redis, prefix: 'session:' }),
  secret: process.env.SESSION_SECRET!,
  resave: false,
  saveUninitialized: false,
  cookie: { httpOnly: true, secure: true, maxAge: 86_400_000 },
}))

app.post('/login', async (req, res) => {
  const user = await authenticate(req.body.email, req.body.password)
  req.session.userId = user.id // written straight through to Redis
  res.json({ status: 'ok' })
})
```

```java
// ordinary servlet HttpSession is then backed by Redis, so every

// across instances with no code change at all.

@Configuration
@EnableRedisHttpSession(maxInactiveIntervalInSeconds = 86400) // 24h
public class SessionConfig { }

class AuthController {

    @PostMapping("/login")
    Map<String, String> login(@RequestBody LoginRequest body, HttpSession session) {
        User user = authenticate(body.email(), body.password());

        // Stored in Redis, accessible by ALL server instances
        session.setAttribute("userId", user.id());

        return Map.of("status", "ok");
    }
}
```

## Algoritmi del bilanciamento del carico

Con più istanze del server, è necessario un meccanismo per decidere quale istanza gestisce ciascuna richiesta in entrata. Il bilanciatore del carico si trova tra Internet e i tuoi server, riceve tutto il traffico e inoltra ogni richiesta in base a un algoritmo scelto.

### Girotondo

L'algoritmo più semplice: le richieste sono distribuite in ordine rotatorio, server A, B, C, A, B, C. Funziona bene quando tutti i server hanno la stessa capacità e tutte le richieste hanno più o meno lo stesso costo. Fallisce quando i costi delle richieste variano notevolmente: richieste costose (chiamate API esterne, scritture DB pesanti) possono accumularsi per caso su un server.

### Round Robin ponderato

Una variazione in cui i server con maggiore capacità ricevono proporzionalmente più richieste. Se il server A ha 8 GB di RAM e i server B/C hanno 4 GB ciascuno, A riceve il doppio del traffico. Ancora cieco nel richiedere il costo.

### Meno connessioni

Un algoritmo più intelligente: il bilanciatore del carico tiene traccia del numero di connessioni _attive_ su ciascun server e instrada ogni nuova richiesta al server con il minor numero di connessioni. Poiché le operazioni costose mantengono le connessioni aperte più a lungo, i server che gestiscono richieste pesanti ne ricevono naturalmente meno di nuove. Ciò si autobilancia tra carichi di lavoro eterogenei.

### Altri algoritmi

Il **Tempo di risposta minimo** favorisce i server che restituiscono le risposte più velocemente, mentre i server già in difficoltà ricevono meno richieste. **Basato sulle risorse** monitora l'utilizzo effettivo di CPU/RAM su ciascun server e instrada di conseguenza. **IP Hash** mappa deterministicamente ogni IP client su un server specifico (utile per l'affinità di sessione, sebbene l'assenza di stato sia la soluzione migliore).

## Controlli sanitari

Cosa succede quando un server si blocca? Senza controlli di integrità, un bilanciatore del carico round-robin continua a inviare richieste al server morto, ogni terzo utente riceve un errore 502. I controlli di integrità risolvono questo problema con un meccanismo semplice: il sistema di bilanciamento del carico invia periodicamente una richiesta di test leggero (tipicamente `GET /health`) a ogni backend. I server che restituiscono 200 rimangono nella rotazione; i server che falliscono vengono inseriti nella lista nera finché non vengono ripristinati.

```go
// A production health check verifies downstream dependencies, not just "I'm alive."
http.HandleFunc("/health", func(w http.ResponseWriter, r *http.Request) {
    checks := map[string]string{}

    if err := db.PingContext(r.Context()); err != nil {
        checks["database"] = "unreachable"
    } else {
        checks["database"] = "ok"
    }

    if err := rdb.Ping(r.Context()).Err(); err != nil {
        checks["redis"] = "unreachable"
    } else {
        checks["redis"] = "ok"
    }

    for _, v := range checks {
        if v != "ok" {
            w.WriteHeader(http.StatusServiceUnavailable)
            json.NewEncoder(w).Encode(checks)
            return
        }
    }
    json.NewEncoder(w).Encode(checks)
})
```

```python
# A production health check verifies downstream dependencies,
# not just "I'm alive."
@app.get("/health")
async def health(response: Response):
    checks = {}

    try:
        await db.execute(text("SELECT 1"))
        checks["database"] = "ok"
    except Exception:
        checks["database"] = "unreachable"

    try:
        await redis.ping()
        checks["redis"] = "ok"
    except Exception:
        checks["redis"] = "unreachable"

    if any(v != "ok" for v in checks.values()):
        response.status_code = 503

    return checks
```

```js
app.get('/health', async (req, res) => {
  const checks = {}

  // Run the probes CONCURRENTLY. Done in sequence, a health check with
  // four dependencies that each take a second is a four-second probe,
  // and the load balancer's timeout is usually shorter than that.
  const [db, cache] = await Promise.allSettled([
    pool.query('SELECT 1'),
    redis.ping(),
  ])

  checks.database = db.status === 'fulfilled' ? 'ok' : 'unreachable'
  checks.redis = cache.status === 'fulfilled' ? 'ok' : 'unreachable'

  const healthy = Object.values(checks).every((v) => v === 'ok')
  res.status(healthy ? 200 : 503).json(checks)
})
```

```ts
import type { Request, Response } from 'express'

type CheckResult = 'ok' | 'unreachable'

// Declaring the dependencies as data rather than as another pair of
// try/catch blocks is what keeps this endpoint correct as the service
// grows: adding a fifth dependency is one line, and it automatically
// inherits the concurrency and the timeout.
const DEPENDENCIES: Array<{ name: string; probe: () => Promise<unknown> }> = [
  { name: 'database', probe: () => pool.query('SELECT 1') },
  { name: 'redis', probe: () => redis.ping() },
]

export async function health(_req: Request, res: Response): Promise<void> {
  const results = await Promise.all(
    DEPENDENCIES.map(async ({ name, probe }): Promise<[string, CheckResult]> => {
      try {
        await Promise.race([
          probe(),
          new Promise((_, rej) => setTimeout(() => rej(new Error('timeout')), 2000)),
        ])
        return [name, 'ok']
      } catch {
        return [name, 'unreachable']
      }
    }),
  )

  const checks = Object.fromEntries(results)
  const healthy = results.every(([, v]) => v === 'ok')

  res.status(healthy ? 200 : 503).json(checks)
}
```

## Leggi le repliche

La scalabilità dei server delle applicazioni è semplice una volta esternalizzato lo stato. Scalare il _database_, il cuore con stato della tua architettura, è più difficile. Il primo e più comune approccio sono le repliche di lettura.

Poiché il 70-90% del tipico traffico SaaS viene letto, le repliche assorbono la maggior parte del carico.

### Il problema del ritardo di replica

I dati scritti sul primario devono propagarsi alle repliche e la propagazione richiede tempo, il ritardo di replica. Se un utente aggiorna il proprio nome sul primario e lo aggiorna immediatamente (una lettura che colpisce una replica), potrebbe vedere il vecchio nome perché la replica non ha ancora raggiunto il livello.

Le soluzioni includono: **routing lettura dopo scrittura**: instrada le letture che seguono una scrittura recente al primario invece che a una replica; **Ritardi in grado di riconoscere il ritardo**: ritarda la lettura fino alla conferma della replica; o **aggiornamenti ottimistici lato client**: mostra il nuovo valore localmente prima che il server confermi.

## Sharding e partizionamento

Lo sharding (chiamato anche partizionamento) significa suddividere un'unica tabella di grandi dimensioni su più istanze fisiche del database in base a una **chiave di shard**. Invece di una tabella degli ordini con 10 miliardi di righe, hai 12 frammenti, uno al mese, ciascuno contenente una frazione dei dati.

Lo sharding risolve due problemi contemporaneamente: la **latenza delle query** diminuisce perché ogni frammento contiene meno righe da scansionare e la **velocità effettiva** aumenta perché più istanze del database possono servire richieste in parallelo.

## CDN e la velocità della luce

La luce viaggia attraverso i cavi in fibra ottica a una velocità di circa 200.000 km/s. Un viaggio di andata e ritorno da Tokyo alla Virginia (US-East-1), circa 20.000 km, richiede un minimo di **100 ms**. Questo è un livello fisico che nessuna quantità di ottimizzazione del codice può ridurre. E 100 ms sono solo il transito in rete, l'aggiunta dell'elaborazione del server, le query del database e la serializzazione e il totale raggiunge facilmente 500-800 ms.

Le reti per la distribuzione di contenuti (CDN) risolvono questo problema posizionando i contenuti memorizzati nella cache sui **nodi periferici** (chiamati anche punti di presenza o PoP) fisicamente vicini agli utenti. Invece di 20.000 km andata e ritorno, la richiesta percorre 100-200 km, riducendo la latenza di rete da 100ms a 2-3ms.

Tokyo -&gt; Virginia: \~100ms   |   Tokyo -&gt; CDN locale: \~2ms

### Cosa memorizzare nella cache su una CDN

Il **contenuto statico** è l'ovvio punto di partenza: bundle JavaScript, CSS, file HTML, immagini, caratteri e video. Questi cambiano solo al momento della distribuzione, rendendoli perfetti per la memorizzazione nella cache di lunga durata. Le **risposte API** possono anche essere memorizzate nella cache quando i dati sono relativamente stabili, cataloghi di prodotti, post di blog, configurazione pubblica. I provider CDN come Cloudflare supportano l'eliminazione della cache basata su tag: quando i dati cambiano, invalidi solo le voci interessate.

### CDN come livello di sicurezza

I CDN assorbono anche gli **attacchi DDoS**. Un utente malintenzionato che inonda il tuo server di origine con il traffico proveniente da migliaia di bot può mandare in crash il tuo server o accumulare fatture ingenti per la scalabilità automatica. Con una CDN come Cloudflare di fronte, il traffico viene distribuito sulla loro rete globale, che è abbastanza grande da assorbire anche attacchi da terabyte al secondo, mentre il rilevamento automatico attiva i CAPTCHA e blocca gli IP sospetti prima che il traffico raggiunga la tua origine.

## Informatica perimetrale

I CDN tradizionali forniscono file statici, nessuna elaborazione, solo "trova file, invia file". L'edge computing aggiunge un livello di elaborazione al nodo CDN: il tuo codice viene eseguito all'edge, vicino all'utente, prima (o invece di) raggiungere il server di origine.

### Casi d'uso

**Autenticazione all'edge:** invece di un viaggio di andata e ritorno di 100 ms verso l'origine solo per verificare una sessione e restituire 401, il nodo edge convalida la sessione in 2-3 ms. La tua origine riceve solo richieste legittime e autenticate, riducendo sia la latenza che il carico. **Localizzazione:** i nodi edge rilevano la regione e la lingua dell'utente, offrendo una versione giapponese del tuo sito senza un viaggio di andata e ritorno verso l'origine. **Instradamento delle richieste:** Instradamento intelligente al backend più vicino in base alla geografia.

### Vincoli

Gli ambienti di edge computing hanno risorse limitate, in genere 1 GB di RAM, 1 core della CPU, nessun accesso al file system, nessun socket TCP grezzo. I Cloudflare Worker utilizzano gli isolati V8 (motore JavaScript di Chrome) che si avviano in meno di 1 ms ma possono eseguire solo JavaScript/TypeScript. Questi vincoli fanno sì che l'edge computing sia complementare ai tuoi server di origine, non può sostituirli per logiche aziendali complesse, operazioni con uso intensivo di database o attività a lunga esecuzione.

## Elaborazione asincrona e code

Non tutte le operazioni richiedono che l'utente ne attenda il completamento. L'elaborazione asincrona identifica le attività che possono verificarsi in background e le scarica su una coda di messaggi, riducendo drasticamente la latenza percepita dall'utente.

### Il modello

Prendi in considerazione l'idea di invitare un membro del team: convalidi la richiesta, salvi l'invito nel database (100 ms) e quindi devi inviare un'e-mail tramite un provider esterno (300 ms). L'utente non deve attendere l'invio dell'e-mail, ha solo bisogno della conferma che l'invito è stato registrato. Quindi restituisci 200 dopo la scrittura del database e inserisci "invia email" come lavoro in una coda. Un processo di lavoro separato preleva il lavoro e gestisce l'e-mail in modo asincrono.

Sincrono: 100ms (DB) + 300ms (email) = 400ms percepiti\
Asincrono: 100 ms (DB) + push to tail = 100 ms percepiti

### Cosa scaricare

**E-mail e notifiche**: gli utenti non si aspettano una consegna immediata. **Elaborazione immagini/video**: codifica, ridimensionamento, generazione di miniature. **Eliminazione dell'account**: eliminazioni a cascata su più tabelle. **Generazione di report**: aggregazione di dati su milioni di righe. **Consegna webhook**: nuovo tentativo in caso di errore senza bloccare la richiesta principale. La regola: se l'utente non ha bisogno del risultato nella stessa risposta HTTP, è un candidato per l'elaborazione asincrona.

```ts
// This is the cheapest possible fix for the most common queue bug: a
// producer that starts sending a renamed field while the worker still
// reads the old one, which fails silently, in a different process,

  subject: string
```

```java
        // calling thread, which slows the API down but never loses work.
        executor.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());
        return executor;
    }
}

// The limitation is the one that matters: @Async runs IN your API
// process, so a restart loses every queued job and the work does not
// scale independently of the web tier. For anything that must survive a
// deploy, put it in a real broker, Redis Streams, RabbitMQ or SQS, and
// run the worker separately. See chapter 10.
```

## Monoliti vs microservizi

Un monolite è una singola unità distribuibile: autenticazione, elaborazione degli ordini, notifiche, pagamenti, tutto in un'unica base di codice, un processo, una distribuzione. I monoliti sono semplici da sviluppare, testare, distribuire e rifattorizzare. Puoi ridimensionare orizzontalmente un monolite eseguendo più istanze dietro un bilanciatore del carico.

I microservizi suddividono l'applicazione in servizi indipendenti, ciascuno con la propria base di codice, distribuzione e spesso il proprio database. Riguardano principalmente il ridimensionamento dei _team_, non delle macchine.

### Quando i monoliti si rompono

**Accoppiamento della distribuzione:** con 200 sviluppatori su una base di codice, il lavoro incompiuto di un team può bloccare la distribuzione di un altro team. **Granularità della scalabilità:** non puoi scalare solo il modulo di pagamento, ma l'intero monolite, sprecando risorse su moduli che non ne hanno bisogno. **Blocco tecnologico:** ogni modulo deve utilizzare lo stesso linguaggio e lo stesso runtime, anche quando un linguaggio diverso sarebbe notevolmente migliore per un'attività specifica (ad esempio, Rust per l'elaborazione delle immagini rispetto a Node.js per il rendering markdown).

### Quanto costano i microservizi

**Latenza di rete:** quella che era una chiamata di funzione ora è una chiamata HTTP/gRPC sulla rete, più lenta e può non riuscire. **Complessità del debug:** una richiesta di un singolo utente può passare attraverso più di 4 servizi; il debug richiede la traccia distribuita su tutti loro. **Coerenza dei dati:** ogni servizio può possedere il proprio database, introducendo ritardi di replica ed eventuali problemi di coerenza. **Carico operativo:** ogni servizio necessita della propria pipeline CI/CD, monitoraggio, avvisi e rotazione su chiamata.

##### Monolite: scegli quando

- Squadra &lt; 50-100 ingegneri
- È sufficiente un unico stack tecnologico
- Le esigenze di ridimensionamento sono uniformi
- Desideri una velocità di iterazione elevata
- Stai iniziando un nuovo prodotto

##### Microservizi: scegli quando

- Team &gt; Oltre 100 ingegneri con confini chiari
- Moduli diversi necessitano di stack tecnologici diversi
- I singoli moduli necessitano di un ridimensionamento indipendente
- La velocità di distribuzione è bloccata dall'accoppiamento
- Hai una profonda esperienza nei sistemi distribuiti

<Callout type="info" title="La regola cardinale">
I microservizi **non** rappresentano un'ottimizzazione delle prestazioni. Sono un'architettura organizzativa per team di grandi dimensioni. Se il tuo team è piccolo, i microservizi aggiungono enorme complessità senza alcun vantaggio. Un monolite in scala orizzontale gestisce milioni di utenti e la maggior parte delle aziende non ne supera mai uno.
</Callout>

## Informatica senza server

I server tradizionali sono **sempre attivi**: fornisci una macchina (ad esempio, 4 GB di RAM, 2 core) e la paghi 24 ore su 24, 7 giorni su 7, indipendentemente dal fatto che gestisca 500 RPS o zero. È necessario prevedere la capacità: il provisioning è insufficiente e gli utenti ricevono errori durante i picchi di traffico; fornitura eccessiva e sprechi soldi.

Il serverless ribalta questo modello: tu fornisci il codice (funzioni) e la piattaforma fornisce una macchina _solo quando arriva una richiesta_. Dopo l'invio della risposta, la macchina può essere riciclata. Paghi solo per i millisecondi di esecuzione effettiva della CPU, non per i tempi di inattività.

### Come funziona

Un **API Gateway** riceve richieste HTTP e le instrada ciascuna a una funzione serverless. Alla prima richiesta, la piattaforma avvia un runtime, carica il codice, elabora la richiesta e restituisce una risposta. L'istanza potrebbe rimanere attiva per alcuni secondi (gestendo le richieste successive senza avvio a freddo) o essere distrutta. Lo scaling è automatico e teoricamente illimitato, la piattaforma crea tutte le istanze necessarie.

### Il problema dell'avviamento a freddo

L'avvio di un nuovo ambiente di esecuzione, l'avvio del sistema operativo/VM, il caricamento del runtime del linguaggio e il caricamento del codice richiedono tempo. Questo è l'avvio a freddo ed è lo svantaggio principale del serverless. Gli avviamenti a freddo variano notevolmente in base alla tecnologia:

| Piattaforma | Tecnologia | Inizio a freddo |
| -------------------- | ------------------------ | ------------- |
| Lavoratori di Cloudflare | Isolati V8 (JavaScript) | \~0-5ms |
| AWS Lambda (Node.js) | MicroVM petardo | \~100-300ms |
| AWS Lambda (Java) | Petardo + JVM | \~1-3 secondi |
| AWS Lambda (Python) | Petardo + CPython | \~200-500ms |

### Quando utilizzare il serverless

##### Buona vestibilità

- Attività guidate dagli eventi (elaborazione del caricamento di file, consumatori di code)
- Traffico sporadico e imprevedibile
- Pipeline di elaborazione immagini/video
- Lavori pianificati (attività simili a cron)
- Autenticazione e routing Edge

##### Cattiva vestibilità

- API sensibili alla latenza (servizi bancari, pagamenti)
- Processi di lunga durata (&gt;15 minuti su Lambda)
- Applicazioni con uso intensivo di WebSocket
- App che richiedono molte connessioni DB persistenti
- Traffico ad alto volume costante e prevedibile

<Callout type="info" title="La presa onesta">
Serverless è potente per casi d'uso specifici ma **non è un sostituto universale dei server**. Il settore è un po’ sopravvalutato. I server tradizionali con scalabilità automatica rimangono la scelta giusta per la maggior parte delle applicazioni SaaS con traffico costante. Serverless eccelle per carichi di lavoro sporadici e basati su eventi per i quali altrimenti pagheresti per l'elaborazione inattiva.
</Callout>

## Modelli mentali in scala

Dopo aver coperto l'intero panorama, dai percentili di latenza allo sharding del database, ai CDN, all'elaborazione asincrona, ai microservizi e al serverless, ecco i modelli mentali che collegano tutto insieme:

### 1. Inizia sempre dal problema

Ogni tecnica in queste note è una _soluzione_. Prima di cercare soluzioni, misura il tuo sistema utilizzando l'osservabilità (log, metriche, tracce). Scopri _specificamente_ quale componente è lento, perché è lento e quanto è lento. Risolvere il problema sbagliato è peggio che non fare nulla: ti dà falsa fiducia mentre il vero collo di bottiglia si aggrava.

### 2. Preferisci soluzioni semplici

Un monolite scalato verticalmente è più semplice di una mesh di microservizi scalata orizzontalmente. L'indicizzazione corretta del database è più semplice dell'aggiunta di una cache Redis. Le soluzioni semplici sono più facili da comprendere, eseguire il debug e utilizzare. La complessità è un costo, ogni componente che aggiungi è un altro componente che può guastarsi, che va monitorato, che va compreso. Accettare la complessità solo quando la semplicità è veramente insufficiente.

### 3. Adattati ai problemi che hai

Non è necessario creare per un milione di utenti fin dal primo giorno, la maggior parte delle piattaforme non raggiunge mai un milione di utenti. Costruisci per la tua scala attuale con un margine ragionevole e lascia che l'osservabilità ti dica quando e dove investire nella scalabilità. La tua applicazione ha caratteristiche uniche a cui i consigli generici dei blog tecnici di Netflix potrebbero non essere applicabili. Impara dal comportamento del _tuo_ sistema.

### 4. Misura dal primo giorno

L'osservabilità è l'unica eccezione all'"inizio semplice". La registrazione, la metrica e la tracciabilità a livello di produzione dovrebbero essere presenti fin dalla prima distribuzione. Si ripagano immediatamente, non devi mai indovinare dove si trova un bug, non vieni mai sorpreso da un picco di traffico e hai sempre i dati per prendere decisioni informate sulla scalabilità.

```go
// A minimal but real observability setup: Prometheus metrics + structured logging
import (
    "github.com/prometheus/client_golang/prometheus"
    "github.com/prometheus/client_golang/prometheus/promhttp"
    "log/slog"
)

var requestDuration = prometheus.NewHistogramVec(
    prometheus.HistogramOpts{
        Name:    "http_request_duration_seconds",
        Help:    "Duration of HTTP requests",
        Buckets: prometheus.DefBuckets,
    },
    []string{"method", "path", "status"},
)

func init() {
    prometheus.MustRegister(requestDuration)
}

// Expose /metrics for Prometheus to scrape
// Visualize in Grafana: p50, p90, p99 latency per endpoint
http.Handle("/metrics", promhttp.Handler())
```

### 5. La performance è una mentalità

Il ridimensionamento non è un progetto una tantum. È una pratica continua: costruisci sistemi, li guardi lottare nel traffico reale, ottimizzi ciò che conta e impari cosa no. Nel corso del tempo, attraverso prove ed errori, si sviluppa un'intuizione su dove si nascondono i colli di bottiglia e quali soluzioni effettivamente muovono l'ago. Il tuo compito non è prevedere ogni guasto, ma costruire sistemi che gestiscano i guasti con garbo e sviluppare le capacità diagnostiche per risolverli rapidamente quando si verificano.

<Callout type="info" title="Il manuale sulla scalabilità, in ordine">
**Passaggio 1:** Misura tutto (osservabilità dal primo giorno).\
**Passaggio 2:** Correggi il database (indici, N+1, pool di connessioni).\
**Passaggio 3:** aggiungi la memorizzazione nella cache (Redis per percorsi attivi).\
**Passaggio 4:** scarica il lavoro (elaborazione asincrona per email, caricamenti, eliminazioni).\
**Passaggio 5:** Utilizza CDN (contenuto statico + caching della risposta API).\
**Passaggio 6:** ridimensionamento verticale (macchina più grande, nessuna modifica al codice).\
**Passaggio 7:** Scalabilità orizzontale (server stateless + bilanciatore del carico).\
**Passaggio 8:** Ridimensionamento del database (lettura delle repliche, quindi partizionamento se necessario).\
**Passaggio 9:** solo allora prendi in considerazione i microservizi, il serverless o l'edge computing.
</Callout>
