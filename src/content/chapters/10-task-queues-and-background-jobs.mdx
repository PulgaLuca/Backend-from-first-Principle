Lavori in background\
e code di attività
=============

Qualsiasi codice eseguito al di fuori del ciclo di richiesta-risposta, differito, riprovabile e non bloccante, è un processo in background. Capire come progettarli e gestirli è ciò che distingue un backend giocattolo da uno di produzione.

01

## Cos'è un'attività in background?

Un'**attività in background** (chiamata anche lavoro in background) è qualsiasi parte di codice, logica o flusso di lavoro che viene eseguito _all'esterno_ del ciclo di vita richiesta-risposta. Pensa alla tua tipica interazione HTTP: un client invia una richiesta, il tuo server la elabora e invia una risposta. Tutto ciò che non è necessario che accada _entro_ quel breve lasso di tempo è candidato per un'attività in background.

La caratteristica chiave: **non è necessario che sia sincrono**. Non è mission-critical, nel senso che il cliente lo sta aspettando proprio adesso. Per questo motivo possiamo tranquillamente scaricarlo in un processo separato che termina a suo tempo, a seconda di come è stato programmato.

## Perché abbiamo bisogno di attività in background

Il classico esempio motivante è **registrazione utente + verifica email**. Ecco il quadro completo di ciò che accade:

- 1

  **L'utente compila il modulo di registrazione**

  Forniscono e-mail, nome utente, password. Il frontend convalida i vincoli di base ed effettua una chiamata API al tuo backend.

- 2

  **Il backend convalida e memorizza i dati**

  Sicurezza della password, unicità dell'e-mail, hashing, scrittura del record utente nel database, generazione di un token di verifica una tantum (OTP a 6 cifre o un URL firmato).

- 3

  **Invia un'email di verifica**

  Ciò richiede la chiamata a un _provider di posta elettronica di terze parti_ (Resend, Mailgun, Brevo). Il tuo backend sta ora effettuando una richiesta HTTP in uscita a un servizio esterno.

- 4

  **Il provider di posta elettronica elabora e consegna**

  Il provider controlla la tua chiave API, convalida l'e-mail, la instrada tramite SMTP e la consegna. Viene restituito il successo/fallimento.

### Il problema: l'invio sincrono di e-mail

Se i passaggi 3-4 si verificano in modo sincrono nel tuo gestore delle richieste, hai introdotto una **dipendenza rigida** su un servizio esterno all'interno del tuo percorso critico. Due scenari di fallimento:

Nessuna gestione degli errori

La chiamata API esterna non riesce -&gt; l'intera API di registrazione restituisce 500. L'utente visualizza un errore durante il tentativo di registrazione. Esperienza utente terribile.

Con gestione degli errori

Ingoi l'errore email e restituisci 200 "Controlla la tua email!", ma l'email non è mai stata inviata. L'utente attende per sempre un collegamento di verifica che non arriva mai. Anche UX terribile.

In entrambi i casi, il problema fondamentale è lo stesso: **stai associando l'affidabilità della tua API al tempo di attività di un servizio di terze parti**. Lo scaricamento dell'e-mail in un'attività in background li disaccoppia completamente.

## Come funzionano le code di attività

Una **coda di attività** è un sistema per la gestione e la distribuzione dei lavori in background. È il motore dietro le quinte che consente un'elaborazione in background affidabile e disaccoppiata. Consideralo come un _elenco di cose da fare per il tuo backend_, la tua applicazione aggiunge elementi all'elenco e i lavoratori li selezionano uno per uno.

Produttore

Il codice della tua applicazione (qualsiasi linguaggio/framework). Crea un'attività, la serializza (solitamente JSON) e la inserisce nella coda. Questo si chiama **accodamento** (ENQ).

Coda/Broker

Il middleware che archivia le attività finché un lavoratore non è pronto. Esempi: Redis, RabbitMQ, Amazon SQS. Fornisce garanzie di durata, ordinazione e consegna.

Consumatore/lavoratore

Un processo (o thread) separato che esegue costantemente il polling della coda, preleva le attività (questo è **dequeuing**: DEQ), le deserializza ed esegue la funzione del gestore registrata.

Gestore

La funzione/metodo effettivo registrato per un tipo di attività. Contiene la logica applicativa reale (ad esempio, la chiamata all'API di posta elettronica). Lo stesso codice che eseguiresti in modo sincrono, ma che ora vive all'interno di un lavoratore.

### Serializzazione e deserializzazione

Poiché le attività oltrepassano i confini del processo, tutti i dati devono essere serializzati. JSON è il formato più comune. Il lavoratore deserializza i tipi nativi:

```text
// Task payload (JSON in the queue)
{
  "type": "send_verification_email",
  "user_id": "usr_01J2K...",
  "email": "alice@example.com",
  "token": "eyJhbGci...",
  "created_at": "2024-01-15T10:30:00Z"
}
```

Pitone

Deserializza in a `dict`

JavaScript

Deserializza in un file `object`

TypeScript

Deserializza in un file `object`, digitato dall'interfaccia condivisa dal produttore e dal lavoratore

Vai

Deserializza in a `struct` (via `json.Unmarshal`)

Giava

Deserializza in a `record` o POJO (tramite Jackson's `readValue`)

## Approfondimento su produttori e consumatori

### Il lato del produttore

La responsabilità del produttore è minima e veloce, non dovrebbe mai svolgere lavori pesanti. Il suo unico lavoro:

1. Raccogli tutti i dati necessari al consumatore per eseguire l'attività.
2. Serializza i dati in un formato portatile (JSON).
3. Inserisci il payload serializzato nella coda.
4. Ritorna, immediatamente. Non aspettare.

### Il lato consumatore/lavoratore

Il consumatore viene eseguito come un **processo separato**: nella stessa base di codice (un punto di ingresso/binario diverso) o in un servizio completamente separato. Esso:

1. **Configura su quale coda ascoltare**: code diverse per diversi tipi di attività (coda di posta elettronica, coda di notifiche, coda di elaborazione immagini, ecc.).
2. **Registri gestori**: per ogni tipo di attività, viene registrata una funzione. Quando l'attività viene rimossa dalla coda, viene chiamata quella funzione.
3. **Sondaggi o attività inviate**: a seconda del broker (Redis/RabbitMQ utilizza il polling lungo; SQS utilizza gli intervalli di polling).
4. **Deserializza il payload**: JSON -&gt; struct/dict/object nativo.
5. **Esegue il gestore**: il lavoro vero e proprio: chiamata all'API di posta elettronica, ridimensionamento dell'immagine, ecc.
6. **Riconosce (ACK) il successo**: comunica alla coda che l'attività è stata completata e può essere rimossa.
7. **Segnala errore (NACK)**: in caso di errore, la coda sa di dover riprovare.

<Callout type="info" title="Più istanze del consumatore">
Puoi eseguire _N_ processi consumer in parallelo. Ognuno assume i compiti in modo indipendente. È così che si scala orizzontalmente, più utenti -&gt; più lavoratori, non server più grandi.
</Callout>

## Broker e tecnologie

La "coda" è supportata da una vera e propria infrastruttura, un **broker di messaggi**. Ecco le opzioni principali:

| Intermediario | Digitare | Ideale per | Note |
| --------------------------- | ------------------- | ------------------------------------------------- | ------------------------------------------------------------------ |
| **Redis** (Pub/Sub + Liste) | Archivio in memoria | Attività veloci e a bassa latenza. Sedano + BullMQ predefinito. | I dati possono andare persi in caso di arresto anomalo a meno che la persistenza non sia abilitata (AOF/RDB). |
| **ConiglioMQ** | Broker di messaggi AMQP | Routing complesso, fanout, scambi di argomenti.         | Regole di routing molto affidabili e ricche, richiedono un sovraccarico operativo.          |
| **Amazon SQS** | Coda cloud gestita | Scalabile, multiregione, serverless-friendly.      | Nativo AWS, nessuna gestione del server. Code standard + FIFO.          |
| **Stream Redis** | Registro persistente | Gruppi di consumatori, replay, auditing.                | Più durevole degli elenchi Redis di base. Buono per Asynq (Vai).          |

<Callout type="info" title="Framework &lt;-&gt; Accoppiamenti broker">
**Celery (Python)** -&gt; Redis o RabbitMQ  |  **BullMQ (Node.js)** -&gt; Redis  |  **Asynq (Vai)** -&gt; Flussi Redis  |  **Sidekiq (Rubino)** -&gt; Redis
</Callout>

### Componenti interni di Redis: come archivia le attività

Redis offre **due diverse strutture dati** utilizzate dalle librerie delle code delle attività dietro le quinte. Capire quale utilizza il tuo framework e perché ti aiuta a utilizzarlo correttamente in produzione.

#### Elenchi Redis (utilizzati da: Celery, BullMQ, Sidekiq)

Un elenco Redis è un elenco di stringhe doppiamente collegato. Le code di attività utilizzano due comandi: `LPUSH` (il produttore spinge a sinistra/testa) e `BRPOP` (blocchi lavoratore in attesa di apparire da destra/coda). Questo ti dà il classico comportamento FIFO.

```text
# What Celery does under the hood in Redis:

# Producer (your API), pushes serialized task to left of list
LPUSH celery '{"task":"send_email","args":["alice@example.com","token123"]}'

# Worker, blocks waiting for item, pops from right (FIFO)
# BRPOP blocks for up to 5 seconds, then re-polls
BRPOP celery 5

# To see queue depth at any time:
LLEN celery   # -> 42 (42 pending tasks)
Redis CLI
```

Problema con le liste

Una volta che un lavoratore apre l'attività (`BRPOP`), è **scomparso dall'elenco**. Se il lavoratore si arresta in modo anomalo prima di effettuare l'ACK, l'attività viene persa definitivamente. BullMQ risolve questo problema spostando le attività in un set ordinato "attivo" separato ed eliminandole solo su ACK.

Nessuna riproduzione

Le liste sono distruttive. Non è possibile rileggere le vecchie attività per il debug o il controllo.

Nessun gruppo di consumatori

Un singolo messaggio può arrivare solo a un consumatore. Non è possibile avere più gruppi di consumatori indipendenti che leggono la stessa coda (come Kafka).

#### Redis Streams (utilizzato da: Asynq, architetture più recenti)

Redis Streams (aggiunto in Redis 5.0) è un log di sola aggiunta, concettualmente simile ad Apache Kafka ma in Redis. È stato progettato appositamente per risolvere i problemi degli elenchi Redis per l'accodamento dei messaggi.

```text
# Producer adds entry to stream
# * means auto-generate ID (timestamp-sequence: 1705312200000-0)
XADD myapp:email_queue * user_id usr_01J2K email alice@example.com token eyJ...

# Create a consumer group (workers belong to a group)
XGROUP CREATE myapp:email_queue email_workers $ MKSTREAM

# Worker reads next undelivered message (> means "new")
XREADGROUP GROUP email_workers worker-1 COUNT 1 BLOCK 5000 STREAMS myapp:email_queue >

# After successful processing, ACK the message by ID
XACK myapp:email_queue email_workers 1705312200000-0

# Check pending (delivered but not ACKed), these are in-flight tasks
XPENDING myapp:email_queue email_workers - + 10
Redis CLI
```

## Amazon SQS: code standard e code FIFO

Amazon SQS è il servizio di accodamento dei messaggi completamente gestito di AWS. Nessun server da gestire, scalabilità automatica e replica su più zone di disponibilità. Ha due modalità con garanzie fondamentalmente diverse.

| Immobile | Coda standard | Coda FIFO |
| ----------------- | --------------------------------------------------------------- | -------------------------------------------------------------------------- |
| **Produttività** | Quasi illimitato (migliaia di TPS) | 300 TPS (3.000 con dosaggio) |
| **Ordinazione** | Miglior sforzo, NON garantito | FIFO rigoroso, garantito all'interno di un gruppo di messaggi |
| **Consegna** | Almeno una volta, un messaggio può essere consegnato _più di una volta_ | Esattamente una volta, l'ID di deduplicazione previene i duplicati |
| **Deduplicazione** | Nessuno integrato | Finestra di deduplicazione integrata di 5 minuti utilizzando l'hash del contenuto o l'ID esplicito |
| **Caso d'uso** | Attività ad alto volume, in cui l'ordine non ha importanza (e-mail, notifiche) | Transazioni finanziarie, aggiornamenti dell'inventario, qualsiasi cosa richieda un ordine rigoroso |
| **Nominazione** | `my-queue`                                                      | Deve finire in `.fifo` -&gt; `my-queue.fifo`                                     |
| **Costo** | $ 0,40 per milione di richieste | $ 0,50 per milione di richieste |

### Come funziona il timeout della visibilità SQS (specifico per AWS)

SQS implementa il timeout di visibilità in modo nativo. Quando un lavoratore chiama `ReceiveMessage`, il messaggio diventa invisibile a tutti gli altri consumatori per il timeout configurato (30 secondi predefiniti, massimo 12 ore). Il lavoratore deve chiamare `DeleteMessage` in caso di successo o non fare nulla per renderlo nuovamente visibile per riprovare.

```go title="sqs.go / Go + AWS SDK v2"
// Go, SQS producer + consumer using AWS SDK v2
package main

import (
    "context"
    "encoding/json"
    "github.com/aws/aws-sdk-go-v2/aws"
    "github.com/aws/aws-sdk-go-v2/service/sqs"
)

// -- PRODUCER ------------------------------------------
func EnqueueEmailTask(ctx context.Context, client *sqs.Client, queueURL string, payload EmailPayload) error {
    body, _ := json.Marshal(payload)
    _, err := client.SendMessage(ctx, &sqs.SendMessageInput{
        QueueUrl:    aws.String(queueURL),
        MessageBody: aws.String(string(body)),
        // For FIFO queue: add MessageGroupId + MessageDeduplicationId
        // MessageGroupId:         aws.String("email-group"),
        // MessageDeduplicationId: aws.String(payload.UserID),
    })
    return err
}

// -- CONSUMER ------------------------------------------
func PollQueue(ctx context.Context, client *sqs.Client, queueURL string) {
    for {
        result, _ := client.ReceiveMessage(ctx, &sqs.ReceiveMessageInput{
            QueueUrl:            aws.String(queueURL),
            MaxNumberOfMessages: 10,          // batch up to 10
            WaitTimeSeconds:     20,          // long-polling reduces empty receives
            VisibilityTimeout:   60,          // 60s to process before redelivery
        })

        for _, msg := range result.Messages {
            if err := processMessage(ctx, msg); err == nil {
                // ACK: delete from queue on success
                client.DeleteMessage(ctx, &sqs.DeleteMessageInput{
                    QueueUrl:      aws.String(queueURL),
                    ReceiptHandle: msg.ReceiptHandle, // unique handle per receive
                })
            }
            // On error: do nothing, visibility timeout expires, SQS redelivers
        }
    }
}
```

Poiché SQS standard esegue la consegna almeno una volta, i tuoi gestori **devono essere idempotenti**. In rari casi un messaggio può essere recapitato due volte (singhiozzo della rete, failover sulla zona di disponibilità). Progettare sempre i gestori in modo che siano sicuri da eseguire nuovamente. Vedere la Sezione 17 per i modelli di idempotenza.
</Callout>

## Nuovi tentativi e backoff esponenziale

Quando un'attività fallisce (il gestore genera un'eccezione, l'API esterna restituisce 5xx, timeout di rete), il framework **riaggiunge nuovamente l'attività** per riprovare. Riprovare ingenuamente immediatamente avrebbe martellato un servizio già in difficoltà. La soluzione: **backoff esponenziale**.

### Algoritmo di backoff esponenziale

Dopo ogni errore, il tempo di attesa prima del tentativo successivo raddoppia. Una formula comune:

```text
// Retry delay formula
delay = base_delay * (2 ^ attempt_number) + jitter

// Example with base_delay=1min, max_retries=5:
Attempt 1 -> wait 1 min   -> retry
Attempt 2 -> wait 2 min   -> retry
Attempt 3 -> wait 4 min   -> retry
Attempt 4 -> wait 8 min   -> retry
Attempt 5 -> wait 16 min  -> DEAD LETTER QUEUE
PSEUDOCODE
```

#### Perché il jitter è importante

Senza jitter (rumore casuale aggiunto al ritardo), tutti i consumatori riprovano esattamente nello stesso momento dopo un errore, creando un **gregge tonante** che colpisce il servizio esterno con un picco. L'aggiunta di un piccolo offset casuale distribuisce il carico.

#### Coda di lettere non recapitate (DLQ)

Dopo aver esaurito tutti i tentativi, l'attività viene spostata in una **Coda di lettere non consegnate**. Questa è una coda separata per le attività con errori persistenti. Gli ingegneri possono ispezionare i messaggi DLQ, diagnosticare la causa principale e riprodurli manualmente una volta risolto il problema.

<Callout type="info" title="Nota del mondo reale">
I principali provider di posta elettronica (Resend, Mailgun) hanno SLA del 99,9% + uptime. In pratica, il tempo di inattività si misura in secondi. Con il backoff esponenziale, un'attività che fallisce una volta avrà generalmente successo nel tentativo 2 o 3, ben entro la finestra di scadenza di 15-20 minuti dell'e-mail di verifica.
</Callout>

#### Perché esiste questo?

Senza il timeout di visibilità, se un consumatore si arresta in modo anomalo nel corso di un'attività, l'attività andrebbe persa in modo permanente, poiché era già rimossa dalla coda quando il consumatore l'ha presa. Il timeout della visibilità garantisce che se il lavoratore _non riconosce_ all'interno della finestra (si è bloccato, si è bloccato o il servizio esterno è scaduto), l'attività diventa nuovamente visibile e un altro lavoratore può riprenderla. **Le attività non vanno mai perse.**

ACK (successo)

Il consumatore invia la conferma -&gt; la coda elimina definitivamente l'attività.

NACK (fallimento)

Il consumatore segnala un errore -&gt; programma la coda di riprovare (con backoff).

Nessun segnale

Il consumer si è bloccato o si è bloccato -&gt; scade il timeout di visibilità -&gt; attività riaccodata per un altro lavoratore.

## Tipi di attività in background

Compiti una tantum

Attivato una volta da un evento specifico. Invia e-mail di verifica, e-mail di benvenuto, collegamento per la reimpostazione della password, notifica in-app. Tipo più comune.

Compiti ricorrenti

Programmato a intervalli fissi. Report settimanali, e-mail digest giornaliere, lavori di pulizia del database, eliminazione delle sessioni orfane. Implementato tramite scheduler simili a cron.

Compiti a catena

Dipendenze genitore-figlio. L'attività B può essere eseguita solo dopo che l'attività A ha avuto esito positivo. Le attività allo stesso livello possono essere eseguite in parallelo. Classico: pipeline di caricamento video.

Attività batch

Un trigger si espande in molte attività parallele. Elimina le attività secondarie che generano account per tipo di risorsa. Invia report da 10.000 a mezzanotte.

| Caso d'uso | Tipo di attività | Perché lo sfondo?                                                                   |
| -------------------------------- | ---------------- | --------------------------------------------------------------------------------- |
| **Verifica email/benvenuto** | Una tantum | Dipende dal provider di posta elettronica esterno. Il fallimento non deve interrompere la registrazione.                |
| **Ridimensionamento immagini/video** | Catena | Ad uso intensivo della CPU. Bloccherebbe il thread di richiesta per secondi.                        |

### Notifiche push: come funzionano realmente

Il tuo backend **non può** inviare una notifica push direttamente a un telefono. Ecco il flusso completo:

1. L'utente installa l'app -&gt; il sistema operativo genera un token del dispositivo univoco (token APN Apple/token FCM di Google).
2. L'app invia quel token al tuo backend al primo avvio, lo memorizzi per utente nel tuo DB.
3. Quando vuoi inviare una notifica all'utente: accoda un'attività "invia notifica push" con il token del dispositivo dell'utente + il payload del messaggio.
4. Il lavoratore rimuove le code -&gt; chiama gli APN Apple o l'API FCM di Google con il token e il payload.
5. Apple/Google inviano la notifica al dispositivo tramite il canale push a livello di sistema operativo.

<Callout type="info" title="Perché lo sfondo?">
Stesso motivo dell'e-mail, dipende dai servizi esterni Apple/Google. Tariffa limitata. Sono necessari nuovi tentativi. Potenzialmente milioni di gettoni per evento (app sportiva: goal segnato -&gt; avvisa tutti i tifosi).
</Callout>

### Il consumatore: definire e gestire il compito

Questo è il codice che viene eseguito nel processo **worker**, non nella tua API. Nota cosa fa ogni versione con gli errori, perché è l'intera storia dei nuovi tentativi: un payload che non verrà mai analizzato è un errore permanente e non deve essere riprovato, mentre un provider in timeout dovrebbe esserlo.

Vai a Python JavaScript TypeScript Java

il carico utile dell'attività e la funzione che lo elabora

```go title="tasks/email.go + handlers/email_handler.go / Go + Asynq"
// tasks/email.go, Task definitions (producer + payload)
package tasks

import (
    "context"
    "encoding/json"
    "fmt"
    "github.com/hibiken/asynq"
)

const TypeSendVerificationEmail = "email:send_verification"

// Payload struct, serialized to JSON in queue
type EmailPayload struct {
    UserID string `json:"user_id"`
    Email  string `json:"email"`
    Token  string `json:"token"`
}

// NewSendVerificationEmailTask creates the Asynq task
func NewSendVerificationEmailTask(userID, email, token string) (*asynq.Task, error) {
    payload, err := json.Marshal(EmailPayload{UserID: userID, Email: email, Token: token})
    if err != nil {
        return nil, fmt.Errorf("json.Marshal: %w", err)
    }
    // asynq.MaxRetry, after 5 failures, moves to dead letter
    return asynq.NewTask(TypeSendVerificationEmail, payload, asynq.MaxRetry(5)), nil
}

// handlers/email_handler.go, Consumer handler
package handlers

type EmailHandler struct {
    emailSvc EmailService // injected dependency
}

// HandleSendVerificationEmail, registered with the Asynq server
func (h *EmailHandler) HandleSendVerificationEmail(
    ctx context.Context,
    t *asynq.Task,
) error {
    // 1. Deserialize JSON -> Go struct
    var p tasks.EmailPayload
    if err := json.Unmarshal(t.Payload(), &p); err != nil {
        // Non-retryable error: mark as failed immediately
        return fmt.Errorf("json.Unmarshal: %w: %w", err, asynq.SkipRetry)
    }

    // 2. Execute: call email provider API
    slog.Info("sending verification email", "user_id", p.UserID, "email", p.Email)
    if err := h.emailSvc.SendVerification(ctx, p.Email, p.Token); err != nil {
        // Returning error triggers retry with exponential backoff
        return fmt.Errorf("emailSvc.SendVerification: %w", err)
    }

    // 3. Returning nil -> ACK to queue (task done)
    return nil
}
```

```python title="tasks.py / Python + Celery"
# tasks.py, Define the task (consumer side)
from celery import Celery
import resend

# Connect Celery to Redis broker
app = Celery('tasks', broker='redis://localhost:6379/0')

# Decorate the function as a Celery task
@app.task(bind=True, max_retries=5, default_retry_delay=60)
def send_verification_email(self, user_id: str, email: str, token: str):
    """
    Called by the worker process.
    self.retry() implements exponential backoff automatically.
    """
    try:
        params = {
            "from": "noreply@myapp.com",
            "to": [email],
            "subject": "Verify your email",
            "html": build_email_template(token),
        }
        resend.Emails.send(params)
    except Exception as exc:
        # Exponential backoff: 60s, 120s, 240s, 480s, 960s
        countdown = 60 * (2 ** self.request.retries)
        raise self.retry(exc=exc, countdown=countdown)
```

```js title="worker.js / Node 20+ + BullMQ"
// worker.js, Consumer, BullMQ calls this for each job
import { Worker } from 'bullmq'
import { Resend } from 'resend'

const connection = { host: 'localhost', port: 6379 }
const resend = new Resend(process.env.RESEND_API_KEY)

// The queue NAME is the contract between producer and consumer; both
// sides must spell it the same way. That is BullMQ's version of Asynq's
// task type constant.
export const worker = new Worker(
  'email',
  async (job) => {
    // 1. The payload is already a JS object; BullMQ serialized it for us
    const { userId, email, token } = job.data

    // 2. Execute: call email provider API
    console.log('sending verification email', userId, email)
    await resend.emails.send({
      from: 'noreply@myapp.com',
      to: [email],
      subject: 'Verify your email',
      html: buildEmailTemplate(token),
    })

    // 3. Returning normally ACKs the job (task done). THROWING is what
    //    triggers a retry, so never swallow an error in here: a caught
    //    exception looks exactly like success to the queue.
  },
  { connection, concurrency: 10 },
)

worker.on('failed', (job, err) => {
  console.error(`job ${job?.id} failed (attempt ${job?.attemptsMade})`, err)
})
```

```java title="EmailTaskHandler.java / Java 17+ + Spring Data Redis Streams"
// Java has no single dominant task queue, so this is the mechanism itself:
// a Redis Stream with a consumer group, which is exactly what Asynq builds
// on. Section 6 of this chapter describes the XADD/XREADGROUP/XACK cycle
// you are about to see in code.
public record EmailPayload(String userId, String email, String token) {}

@Component
public class EmailTaskHandler
        implements StreamListener<String, MapRecord<String, String, String>> {

    static final String STREAM = "tasks:email";
    static final String GROUP = "email-workers";
    static final String DLQ = "tasks:email:dead";

    private final StringRedisTemplate redis;
    private final ObjectMapper json;
    private final EmailService emailSvc; // injected dependency

    EmailTaskHandler(StringRedisTemplate redis, ObjectMapper json, EmailService emailSvc) {
        this.redis = redis;
        this.json = json;
        this.emailSvc = emailSvc;
    }

    @Override
    public void onMessage(MapRecord<String, String, String> record) {
        EmailPayload p;

        // 1. Deserialize JSON -> Java record
        try {
            p = json.readValue(record.getValue().get("payload"), EmailPayload.class);
        } catch (JsonProcessingException e) {
            // Non-retryable: this payload will never parse. ACK it so it
            // stops being redelivered, and park it in the dead letter stream.
            redis.opsForStream().add(DLQ, record.getValue());
            redis.opsForStream().acknowledge(STREAM, GROUP, record.getId());
            return;
        }

        // 2. Execute: call email provider API
        try {
            log.info("sending verification email user_id={} email={}", p.userId(), p.email());
            emailSvc.sendVerification(p.email(), p.token());
        } catch (RuntimeException e) {
            // Retryable: deliberately do NOT acknowledge. The message stays
            // in the group's pending list and another worker reclaims it
            // via XAUTOCLAIM once the idle timeout passes.
            log.warn("send failed; leaving unacked for redelivery", e);
            return;
        }

        // 3. XACK -> the task is done and leaves the pending list
        redis.opsForStream().acknowledge(STREAM, GROUP, record.getId());
    }
}
```

```ts title="scheduler.ts / TypeScript 5+ + BullMQ repeatable jobs"
  jobId: string
```

## Considerazioni sulla progettazione su larga scala

Quando la tua piattaforma cresce fino a raggiungere migliaia di utenti simultanei, l'ingenua configurazione della coda delle attività che ha funzionato durante lo sviluppo inizia a incrinarsi. Queste sono le aree che devi progettare attentamente prima di raggiungere la scala di produzione.

Ridimensionamento orizzontale

Progettare i consumatori affinché siano **senza stato**: tutti gli stati condivisi risiedono nel database o nella cache, non nel processo. Ciò ti consente di avviare N repliche senza modifiche alla configurazione. Più traffico -&gt; aggiungi lavoratori, non server più grandi.

Consegna ordinata

I consumatori paralleli interrompono l'ordinamento FIFO. Se l'ordine rigoroso è importante (ad esempio addebito -&gt; rimborso deve avvenire in sequenza), utilizzare SQS FIFO con a `MessageGroupId` o una coda a singolo consumatore per quel tipo di attività.

Categorie di errori

Distinguere gli errori _transitori_ (timeout di rete, 503 -&gt; nuovo tentativo) dagli errori _permanenti_ (payload non valido, 400 -&gt; salta il nuovo tentativo immediatamente, invia a DLQ). Riprovare con errori permanenti spreca risorse e riempie la coda.

Contropressione

Se la coda cresce più velocemente di quanto consumano i lavoratori, si ha una contropressione. Soluzioni: scalare i consumatori orizzontalmente, implementare code prioritarie o ridurre il carico con interruttori automatici sul lato produttore.

## Modelli di idempotenza in profondità

**Idempotenza** significa che l'esecuzione di un'attività una o 100 volte produce effetti collaterali identici. Questo non è negoziabile in qualsiasi sistema che ritenta le attività e lo fanno tutte le code delle attività di produzione. Esistono diversi modelli concreti per raggiungerlo.

### Modello 1: chiavi di idepotenza

Assegna una chiave univoca a ciascuna attività al momento della creazione (solitamente un UUID o un hash dell'input). Prima di eseguire qualsiasi lavoro, il gestore controlla se la chiave è già stata elaborata con successo. Se sì, ritorna prima senza rifare il lavoro.

Vai a Python JavaScript TypeScript Java

richiedi prima la chiave; solo il vincitore fa il lavoro

```go title="email_handler.go / Go + go-redis + Asynq"
// Go, Idempotency key pattern with Redis
func (h *EmailHandler) HandleSendVerificationEmail(
    ctx context.Context, t *asynq.Task,
) error {
    var p tasks.EmailPayload
    if err := json.Unmarshal(t.Payload(), &p); err != nil {
        return fmt.Errorf("json.Unmarshal: %w: %w", err, asynq.SkipRetry)
    }

    // Build idempotency key from task inputs
    key := fmt.Sprintf("idem:verify_email:%s:%s", p.UserID, p.Token)

    // SetNX = SET only if Not eXists, with a 1-hour expiry.
    // acquired is true only for the FIRST execution.
    acquired, err := h.rdb.SetNX(ctx, key, "done", time.Hour).Result()
    if err != nil {
        // Redis is unreachable, so we cannot tell a duplicate from a
        // first run. Retry rather than risk a second email.
        return fmt.Errorf("idempotency check: %w", err)
    }
    if !acquired {
        return nil // Already processed, ACK cleanly (idempotent return)
    }

    // First time, actually send the email
    if err := h.emailSvc.SendVerification(ctx, p.Email, p.Token); err != nil {
        h.rdb.Del(ctx, key) // release the key so the next retry can try again
        return fmt.Errorf("emailSvc.SendVerification: %w", err)
    }
    return nil
}
```

```python title="tasks.py / Python + redis-py + Celery"
import hashlib

r = redis.Redis(host='localhost', port=6379)

@app.task(bind=True, max_retries=5)
def send_verification_email(self, user_id: str, email: str, token: str):

    # SET NX = set only if Not eXists; EX = expire after 1 hour
    # Returns True if we are the FIRST execution, False if already done

        _send_email_via_provider(email, token)
```

```ts title="worker.ts / TypeScript 5+ + node-redis + BullMQ"
// Worth naming the gap in this shape before you rely on it: if the process
// dies AFTER the SET NX but BEFORE the send lands, the key is held and the
// retry skips the email entirely. The one-hour TTL is what bounds the
// damage. The stronger fix is the one chapter 07 uses for payments, store
// the RESULT under the key instead of a bare "done" marker, so a duplicate
// can return the original outcome rather than guessing.
async function handler(job: Job<EmailJob>): Promise<{ status: string }> {
  const { userId, email, token } = job.data
  const key = `idem:verify_email:${userId}:${token}`

  const acquired: string | null = await redis.set(key, 'pending', { NX: true, EX: 3600 })
  if (acquired === null) {
    return { status: 'already_sent' } // skip silently (idempotent return)
  }

  try {
    const messageId = await sendEmailViaProvider(email, token)
    // Overwrite the claim with the real result, still under the same TTL.
    await redis.set(key, JSON.stringify({ messageId }), { EX: 3600 })
    return { status: 'sent' }
  } catch (err) {
    await redis.del(key) // let the next retry attempt again
    throw err
  }
}
```

```java title="EmailTaskHandler.java / Java 17+ + Spring Data Redis"
// Java, Idempotency key pattern with Redis
@Override
public void onMessage(MapRecord<String, String, String> record) {
    EmailPayload p = parse(record); // as in the consumer example above

    // Build idempotency key from task inputs
    String key = "idem:verify_email:%s:%s".formatted(p.userId(), p.token());

    // setIfAbsent IS SET NX, and the Duration is the EX. It returns TRUE
    // only for the FIRST execution, FALSE if an earlier attempt got there.
    Boolean acquired = redis.opsForValue()
        .setIfAbsent(key, "done", Duration.ofHours(1));

    if (!Boolean.TRUE.equals(acquired)) {
        // Already processed, ACK cleanly (idempotent return). Note the
        // Boolean.TRUE.equals: `acquired` is a nullable Boolean, and
        // unboxing a null here would throw instead of skipping.
        redis.opsForStream().acknowledge(STREAM, GROUP, record.getId());
        return;
    }

    // First time, actually send the email
    try {
        emailSvc.sendVerification(p.email(), p.token());
        redis.opsForStream().acknowledge(STREAM, GROUP, record.getId());
    } catch (RuntimeException e) {
        redis.delete(key); // release the key so the redelivery can try again
        log.warn("send failed; leaving unacked for redelivery", e);
    }
}
```

### Modello 2: Transazione database + Upsert

Per le attività che scrivono in un database, utilizzare **upserts** (INSERT ... ON CONFLICT DO NOTHING / DO UPDATE) invece dei semplici INSERT. In questo modo, riprovando l'attività prova semplicemente a inserirla di nuovo e salta silenziosamente il duplicato.

```sql
-- PostgreSQL, Idempotent email log via upsert
-- If the verification_emails row already exists for this token, do nothing
INSERT INTO verification_emails (token, user_id, sent_at, provider_msg_id)
VALUES ($1, $2, NOW(), $3)
ON CONFLICT (token) DO NOTHING;

-- For updates: ON CONFLICT DO UPDATE
INSERT INTO user_status (user_id, email_verified, updated_at)
VALUES ($1, true, NOW())
ON CONFLICT (user_id) DO UPDATE
  SET email_verified = EXCLUDED.email_verified,
      updated_at = EXCLUDED.updated_at;
```

### Modello 3: rollback completo della transazione (per attività complesse)

Per le attività in più passaggi (come l'eliminazione di account) che riguardano molte tabelle, racchiudi l'intera attività in una transazione del database. Se un passaggio fallisce, la transazione viene ripristinata completamente, lasciando il database in uno stato pulito per il successivo tentativo di nuovo tentativo.

Vai a Python JavaScript TypeScript Java

ogni scrittura si impegna insieme, oppure nessuna di esse lo fa

```go title="account_handler.go / Go + Asynq"
// Go, Idempotent multi-step task with full transaction rollback
func (h *AccountHandler) HandleDeleteAccount(ctx context.Context, t *asynq.Task) error {
    var p DeleteAccountPayload
    json.Unmarshal(t.Payload(), &p)

    // Check if already deleted (idempotency guard)
    exists, _ := h.db.UserExists(ctx, p.UserID)
    if !exists {
        return nil // already deleted on a previous attempt, ACK cleanly
    }

    // Wrap all DB writes in a single transaction
    return h.db.WithTransaction(ctx, func(tx DB) error {
        steps := []func() error{
            func() error { return tx.DeleteUserProjects(ctx, p.UserID) },
            func() error { return tx.DeleteUserSessions(ctx, p.UserID) },
            func() error { return tx.DeleteUserAssets(ctx, p.UserID) },
            func() error { return tx.DeleteUserAccount(ctx, p.UserID) },
        }
        for _, step := range steps {
            if err := step(); err != nil {
                return err // triggers full rollback; task retried from scratch
            }
        }
        return nil // all steps succeeded -> commit -> ACK
    })
}
```

## Limitazione della velocità nei lavoratori

Le API esterne impongono limiti di velocità. Se i tuoi dipendenti inviano 500 e-mail al secondo e il limite di Reinvia è 100 al secondo, verrai inondato da errori 429, tentativi inutili e consegna ridotta. Devi **limitare i tuoi lavoratori** per rimanere entro i limiti.

### Due algoritmi principali

Secchio di gettoni

Un "secchio" si riempie di gettoni a una velocità fissa (ad esempio 100 gettoni/secondo). Ogni chiamata API consuma un token. Se il bucket è vuoto, la chiamata attende. Consente esplosioni fino alla capacità del secchio. Implementazione di Redis: `INCR` + `EXPIRE`.

Finestra scorrevole

Conta le richieste negli ultimi N secondi utilizzando una finestra temporale scorrevole. Più accurato del token bucket per una rigorosa conformità alle tariffe. Implementazione Redis: set ordinati con timestamp come punteggi.

### Bucket di token (supportato da Redis)

Lo script Lua riportato di seguito è identico in tutte e cinque le schede, e questo è il trucco: Redis esegue uno script in modo atomico, quindi il ciclo di lettura-riempimento-scrittura non può intercalarsi con quello di un altro lavoratore. Esegui invece i calcoli nella tua lingua e avrai ricostruito la corsa agli aggiornamenti perduti del capitolo 08, a cento lavoratori al secondo.

```go title="rate/token_bucket.go / Go + go-redis"
// rate/token_bucket.go, Redis token bucket implementation
package rate

// Loaded once; go-redis sends EVALSHA and only falls back to the full
// body if Redis has not seen the script before.
var tokenBucketScript = redis.NewScript(`
local key = KEYS[1]
local capacity = tonumber(ARGV[1])
local refill_rate = tonumber(ARGV[2])
local now = tonumber(ARGV[3])

local bucket = redis.call('HMGET', key, 'tokens', 'last_refill')
local tokens = tonumber(bucket[1]) or capacity
local last_refill = tonumber(bucket[2]) or now

-- Refill tokens based on time elapsed
local elapsed = now - last_refill
tokens = math.min(capacity, tokens + elapsed * refill_rate)

if tokens >= 1 then
    tokens = tokens - 1
    redis.call('HMSET', key, 'tokens', tokens, 'last_refill', now)
    redis.call('EXPIRE', key, 3600)
    return 1
end
return 0
`)

type TokenBucketLimiter struct {
    rdb        *redis.Client
    key        string  // e.g. "ratelimit:resend_emails"
    capacity   int     // max burst (e.g. 100)
    refillRate float64 // tokens per second (e.g. 10)
}

// Acquire reports whether a token was taken; false means rate limited.
func (l *TokenBucketLimiter) Acquire(ctx context.Context) (bool, error) {
    now := float64(time.Now().UnixMicro()) / 1e6
    got, err := tokenBucketScript.Run(ctx, l.rdb,
        []string{l.key}, l.capacity, l.refillRate, now).Int()
    if err != nil {
        return false, err
    }
    return got == 1, nil
}
```

```python title="rate_limiter.py / Python + redis-py + Celery"
        now = time.time()

        # Lua script ensures atomic read-modify-write (no race conditions)

        local key = KEYS[1]
        local capacity = tonumber(ARGV[1])
        local refill_rate = tonumber(ARGV[2])
```

```go title="rate/sliding_window.go / Go + go-redis"
// rate/sliding_window.go, Redis sorted-set sliding window
package rate

import (
    "context"
    "fmt"
    "time"
    "github.com/redis/go-redis/v9"
)

type SlidingWindowLimiter struct {
    client  *redis.Client
    key     string
    limit   int           // max requests
    window  time.Duration // time window
}

func (l *SlidingWindowLimiter) Allow(ctx context.Context) (bool, error) {
    now := time.Now()
    windowStart := now.Add(-l.window).UnixMicro()
    nowMicro := now.UnixMicro()

    pipe := l.client.Pipeline()
    // Remove entries older than the window
    pipe.ZRemRangeByScore(ctx, l.key, "0", fmt.Sprintf("%d", windowStart))
    // Count entries in current window
    countCmd := pipe.ZCard(ctx, l.key)
    // Add current request timestamp as a member
    pipe.ZAdd(ctx, l.key, redis.Z{Score: float64(nowMicro), Member: nowMicro})
    pipe.Expire(ctx, l.key, l.window*2)
    pipe.Exec(ctx)

    count := countCmd.Val()
    return count < int64(l.limit), nil
}

// Usage in Asynq handler
func (h *EmailHandler) HandleSendEmail(ctx context.Context, t *asynq.Task) error {
    allowed, _ := h.limiter.Allow(ctx)
    if !allowed {
        // Return a retryable error, asynq will retry with backoff
        return fmt.Errorf("rate limit exceeded: %w", asynq.ErrRetry)
    }
    return h.doSendEmail(ctx, t)
}
```

```python title="sliding_window.py / Python + redis-py + Celery"
# sliding_window.py, Redis sorted-set sliding window
import time


class SlidingWindowLimiter:
    def __init__(self, redis_client, key: str, limit: int, window_seconds: float):
        self.r = redis_client
        self.key = key
        self.limit = limit            # max requests
        self.window = window_seconds  # time window

    def allow(self) -> bool:
        now_us = int(time.time() * 1_000_000)
        window_start = now_us - int(self.window * 1_000_000)

        pipe = self.r.pipeline()
        # Remove entries older than the window
        pipe.zremrangebyscore(self.key, 0, window_start)
        # Count entries in current window
        pipe.zcard(self.key)
        # Add current request timestamp as a member
        pipe.zadd(self.key, {str(now_us): now_us})
        pipe.expire(self.key, int(self.window * 2))
        _, count, _, _ = pipe.execute()

        return count < self.limit
```

```js title="slidingWindow.js / Node 20+ + node-redis + BullMQ"
// slidingWindow.js, Redis sorted-set sliding window
export class SlidingWindowLimiter {
  constructor(redis, key, limit, windowMs) {
    this.redis = redis
    this.key = key
    this.limit = limit        // max requests
    this.windowMs = windowMs  // time window
  }

  async allow() {
    const now = Date.now() * 1000 // microseconds, used as the score
    const windowStart = now - this.windowMs * 1000

    const [, count] = await this.redis
      .multi()
      // Remove entries older than the window
      .zRemRangeByScore(this.key, 0, windowStart)
      // Count entries in current window
      .zCard(this.key)
      // Add current request timestamp as a member
      .zAdd(this.key, { score: now, value: String(now) })
      .expire(this.key, Math.ceil((this.windowMs * 2) / 1000))
      .exec()

    return count < this.limit
  }
}
```

```ts title="slidingWindow.ts / TypeScript 5+ + node-redis"
// Two behaviours of this algorithm that are easy to miss, and both are in
// the Go version above too:
//
//  1. The count is read BEFORE this request's own entry is added, so the
//     effective ceiling is limit + 1 in flight. Either compare against
//     `limit - 1`, or move the ZADD ahead of the ZCARD. Choose one on
//     purpose, because drifting between the two across services is how a
//     documented "100/s" quietly becomes 101/s at the provider.
//  2. An entry is added even when the request is REJECTED. A caller that
//     keeps hammering a limited endpoint therefore keeps its own window
//     permanently full and never recovers. If that is not what you want,
//     only ZADD on the allowed path.
export class SlidingWindowLimiter {
  constructor(
    private readonly redis: RedisClientType,
    private readonly key: string,
    private readonly limit: number,    // max requests
    private readonly windowMs: number, // time window
  ) {}

  async allow(): Promise<boolean> {
    const now = Date.now() * 1000
    const windowStart = now - this.windowMs * 1000

    const results = await this.redis
      .multi()
      .zRemRangeByScore(this.key, 0, windowStart)
      .zCard(this.key)
      .expire(this.key, Math.ceil((this.windowMs * 2) / 1000))
      .exec()

    const count = results[1] as number
    if (count >= this.limit) {
      return false // rejected, and deliberately NOT recorded
    }

    await this.redis.zAdd(this.key, { score: now, value: String(now) })
    return true
  }
}
```

```java title="SlidingWindowLimiter.java / Java 17+ + Spring Data Redis"
@Component
public class SlidingWindowLimiter {
    private final StringRedisTemplate redis;

    SlidingWindowLimiter(StringRedisTemplate redis) {
        this.redis = redis;
    }

    public boolean allow(String key, int limit, Duration window) {
        long nowMicros = Instant.now().toEpochMilli() * 1_000L;
        long windowStart = nowMicros - window.toMillis() * 1_000L;

        // Remove entries older than the window
        redis.opsForZSet().removeRangeByScore(key, 0, windowStart);
        // Count entries in current window
        Long count = redis.opsForZSet().zCard(key);
        // Add current request timestamp as a member
        redis.opsForZSet().add(key, String.valueOf(nowMicros), nowMicros);
        redis.expire(key, window.multipliedBy(2));

        return count != null && count < limit;
    }
}

// Written plainly like this it is four round trips AND four separate
// moments: another worker can slip an entry in between the ZCARD and the
// ZADD. Pipeline it with executePipelined, or move the whole sequence
// into a Lua script the way the token bucket does. At low rates you will
// never notice; at the rates that make you reach for a limiter, you will.
```

```go title="metrics/metrics.go / Go + client_golang"
// -- Middleware to wrap any handler with metrics -----------------
// asynq.MiddlewareFunc is the same shape as the Python decorator: it
// wraps the handler instead of being called from inside it, so no task
// body has to remember to record anything.
func Track(taskName string) asynq.MiddlewareFunc {
    return func(next asynq.Handler) asynq.Handler {
        return asynq.HandlerFunc(func(ctx context.Context, t *asynq.Task) error {
            start := time.Now()
            // deferred, so the duration is recorded on BOTH paths
            defer func() {
                TaskDuration.WithLabelValues(taskName).
                    Observe(time.Since(start).Seconds())
            }()

            if n, _ := asynq.GetRetryCount(ctx); n > 0 {
                RetryCount.WithLabelValues(taskName).Inc()
            }

            if err := next.ProcessTask(ctx, t); err != nil {
                TaskTotal.WithLabelValues(taskName, "failure").Inc()
                return err
            }
            TaskTotal.WithLabelValues(taskName, "success").Inc()
            return nil
        })
    }
}

// Start /metrics server on port 9090 (Prometheus scrapes this)
func Serve() {
    http.Handle("/metrics", promhttp.Handler())
    go http.ListenAndServe(":9090", nil)
}
```

```python title="metrics.py / Python + prometheus_client + Celery"
    ['task_name'],

    'worker_queue_depth',

    ['queue_name']

RETRY_COUNT = Counter(
    'worker_task_retries_total',
    'Number of task retries',
    ['task_name']
)

# -- Decorator to wrap any task with metrics --------------------
def track_metrics(task_name: str):
    def decorator(func):
        def wrapper(*args, **kwargs):
            start = time.time()
            try:
                result = func(*args, **kwargs)
                TASK_TOTAL.labels(task_name=task_name, status="success").inc()
                return result
            except Exception as e:
                TASK_TOTAL.labels(task_name=task_name, status="failure").inc()
                raise
            finally:
                TASK_DURATION.labels(task_name=task_name).observe(time.time() - start)
        return wrapper
    return decorator
```

```ts title="metrics.ts / TypeScript 5+ + prom-client + BullMQ"
import type { Job } from 'bullmq'

// The Prometheus rule worth burning in before you add a single label:
// labels must be LOW cardinality. `task_name` has maybe twenty values,
// which is fine. A user id or a job id creates a new time series per
// user, and that is how people take their own Prometheus down. Pinning
// the label type instead of accepting an open Record is a cheap guard.
type TaskLabels = { task_name: string; status?: 'success' | 'failure' }

// The generics keep the wrapper invisible at the call site: what goes in
// is a processor, what comes out is the SAME processor type.
export function trackMetrics<T, R>(
  taskName: string,
  processor: (job: Job<T>) => Promise<R>,
): (job: Job<T>) => Promise<R> {
  return async (job: Job<T>): Promise<R> => {
    const labels: TaskLabels = { task_name: taskName }
    const end = TASK_DURATION.startTimer(labels)

    if (job.attemptsMade > 0) {
      RETRY_COUNT.inc(labels)
    }

    try {
      const result = await processor(job)
      TASK_TOTAL.inc({ ...labels, status: 'success' })
      return result
    } catch (err) {
      TASK_TOTAL.inc({ ...labels, status: 'failure' })
      throw err
    } finally {
      end() // records the duration on both paths
    }
  }
}
```

## Migliori pratiche

### 1. Mantieni le attività piccole e mirate

Una singola attività dovrebbe fare **una cosa**. Non raggruppare l'invio di e-mail + la pulizia del DB + i report analitici in un'unica attività. Se un passaggio fallisce, riprovi tutto. Piccole attività = tentativi precisi, debug più semplice, migliore scalabilità.

Se più cose dipendono l'una dall'altra, utilizza **attività a catena** (genitore-figlio). Se sono indipendenti, eseguili in parallelo.

### 2. Evitare attività a lunga esecuzione

Se l'esecuzione di un'attività richiede minuti, suddividila in parti più piccole. Le attività lunghe consumano thread di lavoro, sono più difficili da riprovare correttamente e sono soggette alla scadenza del timeout di visibilità. Un'attività che richiede 10 minuti -&gt; 10 attività che richiedono 1 minuto ciascuna.

### 3. Robusta gestione e registrazione degli errori

A differenza di una richiesta web in cui puoi restituire un 500 e il client lo vede, **le attività in background falliscono silenziosamente** a meno che tu non abbia integrato l'osservabilità. Ogni gestore deve:

- Cattura tutte le eccezioni, non lasciare che il panico/le eccezioni non gestite uccidano silenziosamente il lavoratore.
- Registra l'ID attività, l'ID utente, il tipo di errore e l'analisi dello stack completo in caso di errore.
- Distinguere gli errori temporanei da quelli permanenti, utilizzare `SkipRetry` (Asynq) o `raises=(SkipRetry,)` (Sedano) per errori irreversibili.
- Invia errori critici a un canale di avviso (Slack, PagerDuty).

### 4. Monitorare la lunghezza della coda e la salute dei lavoratori

Imposta **soglie di avviso**: se la profondità della coda &gt; 10.000 -&gt; attiva la scalabilità automatica o avvisa i tecnici. Se un pod di lavoro si riavvia più di 3 volte in 5 minuti -&gt; avviso. Utilizza i dashboard Grafana supportati da Prometheus (o CloudWatch per SQS).

### 5. Utilizzare le code di messaggi non recapitabili

Non lasciare mai che le attività scompaiano silenziosamente. Configura un DLQ in modo che le attività che esauriscono tutti i tentativi arrivino in un posto ispezionabile. Controlla regolarmente il DLQ, gli errori ricorrenti indicano un bug sistemico.

<Callout type="info" title="Lista di controllo riepilogativa">
L'attività è idempotente   Il gestore ha try/catch   Gli errori vengono registrati con il contesto   Metriche Prometheus emesse   DLQ configurato   Backoff esponenziale abilitato   Timeout visibilità impostato in modo appropriato   I lavoratori sono stateless (scalabili orizzontalmente)

| **Temporale** | Poliglotta | Proprio server | Flussi di lavoro durevoli | Integrato | Pesante ma di livello aziendale. Orchestrazione completa del flusso di lavoro, non solo attività. |

## Orchestrazione temporale e del flusso di lavoro

Le code di attività standard (Celery, BullMQ, Asynq) sono ottime per _attività indipendenti_, attiva e dimentica, riprova in caso di errore. Ma quando hai **flussi di lavoro a più fasi e di lunga durata** con dipendenze complesse, ramificazioni condizionali, passaggi di approvazione umana o logica di compensazione (modello saga), hai bisogno di qualcosa di più potente: un **motore di orchestrazione del flusso di lavoro**.

<Callout type="info" title="Le soluzioni temporali del problema fondamentale">
Immagina un flusso di lavoro di pagamento: addebito su carta -&gt; prenotazione inventario -&gt; invio e-mail di conferma -&gt; notifica magazzino -&gt; aggiornamento punti fedeltà. Ogni passaggio può fallire in modo indipendente. Se il passaggio 4 fallisce, rimborsi il passaggio 1? Come si riprende dal passaggio 4 dopo un arresto anomalo del server? Come aspetti che un essere umano approvi il passaggio 3 prima di continuare? È qui che le code delle attività si interrompono e i motori del flusso di lavoro brillano.
</Callout>

### Coda di attività e motore del flusso di lavoro

| Capacità | Coda attività (Celery/Asynq/BullMQ) | Temporale |
| ------------------------------ | -------------------------------------------- | --------------------------------------------- |
| **Nuovi tentativi di attività individuali** | Integrato | Integrato |
| **Flussi di lavoro in più fasi** | Manuale, concatena tu stesso le attività | Nativi, i flussi di lavoro sono di prima classe |
| **Persistenza dello stato del flusso di lavoro** | Lo gestisci tu (record DB, flag) | Automatico, l'intera cronologia di esecuzione è persistente |
| **Recupero dopo un incidente** | Riprova dall'inizio dell'attività | Riprendi dal passaggio esatto in cui si è verificato l'arresto anomalo |
| **Compensazione / rollback** | Codice manuale | Supporto del modello saga nativo |
| **Di lunga durata (giorni/mesi)** | Difficile, timeout di visibilità, limiti di connessione | Nativo, i timer possono attivarsi dopo mesi |
| **Umano nel circuito** | Molto difficile | Segnali e query nativi |
| **Complessità operativa** | Basso | Alta, richiede cluster di server temporali |
| **Lingue** | Specifico della lingua | Vai, Python, Java, TypeScript, .NET |

### Concetti temporali fondamentali

Flusso di lavoro

Una funzione duratura che orchestra l'intero processo aziendale. Scritto come codice normale ma Temporal serializza ogni passaggio. Se il server si blocca, l'esecuzione riprende esattamente da dove era stata interrotta.

Attività

Un'unità di lavoro individuale, equivalente a un compito di Sedano. Dispone di criteri di ripetizione, timeout e heartbeat propri. Le attività interagiscono con il mondo esterno (DB, API esterne).

Lavoratore

Un processo che interroga il server temporale per le attività del flusso di lavoro/attività e le esegue. Stesso concetto dei lavoratori di Sedano.

Segnale

Un evento esterno inviato a un flusso di lavoro in esecuzione. Per esempio. "pagamento approvato dall'uomo" -&gt; il flusso di lavoro riprende. Abilita modelli human-in-the-loop.

Domanda

Leggi lo stato corrente di un flusso di lavoro in esecuzione senza influenzarlo. Per esempio. "a che punto si trova quest'ordine?"

Storia degli eventi

Temporale persiste ogni singolo evento nella durata di un flusso di lavoro. In questo modo si ottiene il ripristino da crash, al riavvio riproduce la cronologia per ripristinare lo stato.

### Esempio: flusso di lavoro di elaborazione video

La stessa attività della catena di caricamento video che abbiamo visto nella Sezione 9, ora implementata con Temporal. Temporal fornisce SDK di prima parte per Go, Java, Python e TypeScript e la forma seguente è deliberatamente la stessa in tutti essi: ogni passaggio si legge come una normale chiamata di funzione e ognuno viene registrato nella cronologia del flusso di lavoro, quindi un arresto anomalo riprende dal primo passaggio che non era terminato.

Vai a Python JavaScript TypeScript Java

cinque passaggi, due dei quali in parallelo, ripetibili in qualsiasi momento

```go title="workflows/video_processing.go / Go + Temporal SDK"
// workflows/video_processing.go
package workflows

import (
    "time"
    "go.temporal.io/sdk/workflow"
    "go.temporal.io/sdk/activity"
    "myapp/activities"
)

// VideoProcessingWorkflow, orchestrates the entire pipeline
// Temporal persists every step, crash at any point = resume here
func VideoProcessingWorkflow(ctx workflow.Context, videoID string) error {
    // Activity options, each step has its own retry policy
    actOpts := workflow.ActivityOptions{
        StartToCloseTimeout: 10 * time.Minute,
        RetryPolicy: &temporal.RetryPolicy{
            MaxAttempts:        3,
            InitialInterval:    time.Minute,
            BackoffCoefficient: 2.0,
        },
    }
    ctx = workflow.WithActivityOptions(ctx, actOpts)

    // Step 1: Encode video to multiple resolutions
    // If server crashes here, workflow resumes from step 1 on restart
    var encodedPath string
    if err := workflow.ExecuteActivity(ctx, activities.EncodeVideo, videoID).Get(ctx, &encodedPath); err != nil {
        return err // step 1 failed all retries, workflow fails
    }

    // Step 2 + 3: Thumbnail generation AND transcription in parallel
    thumbFuture := workflow.ExecuteActivity(ctx, activities.GenerateThumbnails, encodedPath)
    transcriptFuture := workflow.ExecuteActivity(ctx, activities.GenerateTranscription, encodedPath)

    // Wait for both, if either fails, the workflow fails (with its own retries first)
    if err := thumbFuture.Get(ctx, nil); err != nil { return err }
    if err := transcriptFuture.Get(ctx, nil); err != nil { return err }

    // Step 4: Process thumbnails (depends on step 2 completing)
    if err := workflow.ExecuteActivity(ctx, activities.ProcessThumbnailImages, videoID).Get(ctx, nil); err != nil {
        return err
    }

    // Step 5: Notify user their video is ready
    return workflow.ExecuteActivity(ctx, activities.NotifyUserVideoReady, videoID).Get(ctx, nil)
}
```

```python title="workflows/video_processing.py / Python + temporalio"
from datetime import timedelta

from temporalio import workflow
from temporalio.common import RetryPolicy

with workflow.unsafe.imports_passed_through():
    from activities import (
        encode_video, generate_thumbnails, generate_transcription,
        process_thumbnail_images, notify_user_video_ready,
    )


@workflow.defn
class VideoProcessingWorkflow:
    """Orchestrates the entire pipeline.

    Temporal persists every step, crash at any point = resume here.
    """

    @workflow.run
    async def run(self, video_id: str) -> None:
        # Activity options, each step has its own retry policy
        opts = dict(
            start_to_close_timeout=timedelta(minutes=10),
            retry_policy=RetryPolicy(
                maximum_attempts=3,
                initial_interval=timedelta(minutes=1),
                backoff_coefficient=2.0,
            ),
        )

        # Step 1: Encode video to multiple resolutions.
        # If the worker crashes here, the workflow resumes from step 1.
        encoded_path = await workflow.execute_activity(encode_video, video_id, **opts)

        # Step 2 + 3: Thumbnail generation AND transcription in parallel.
        # gather() is what makes them concurrent; awaiting each in turn
        # would quietly serialise them and double the wall-clock time.
        await asyncio.gather(

            workflow.execute_activity(generate_transcription, encoded_path, **opts),
        )

        # Step 4: Process thumbnails (depends on step 2 completing)
        await workflow.execute_activity(process_thumbnail_images, video_id, **opts)

        # Step 5: Notify user their video is ready
        await workflow.execute_activity(notify_user_video_ready, video_id, **opts)
```

```java title="VideoProcessingWorkflow.java / Java 17+ + Temporal SDK"
        activities.processThumbnailImages(videoId);

        // Step 5: Notify user their video is ready
        activities.notifyUserVideoReady(videoId);
    }
```

### Esempio: Human-in-the-Loop con segnali

Un **segnale** è un evento esterno inviato in un flusso di lavoro in esecuzione. È ciò che consente a un flusso di lavoro di restare in attesa di una persona, per un giorno o per un mese, senza trattenere un thread, una connessione o un blocco di riga da nessuna parte.

Vai a Python JavaScript TypeScript Java

attendere 24 ore per un essere umano e compensare se nessuno risponde

```go title="workflows/payment_approval.go / Go + Temporal SDK"
// workflows/payment_approval.go, Wait for human signal
func PaymentApprovalWorkflow(ctx workflow.Context, orderID string) error {
    // Register a signal channel, external events can wake this workflow
    approvalCh := workflow.GetSignalChannel(ctx, "approval-signal")

    // Step 1: Process payment details
    workflow.ExecuteActivity(ctx, activities.PreparePayment, orderID).Get(ctx, nil)

    // Step 2: Wait up to 24 hours for human approval
    // Temporal pauses here, no CPU/memory consumed while waiting
    var approved bool
    selector := workflow.NewSelector(ctx)
    selector.AddReceive(approvalCh, func(ch workflow.ReceiveChannel, more bool) {
        ch.Receive(ctx, &approved)
    })
    selector.AddFuture(workflow.NewTimer(ctx, 24*time.Hour), func(f workflow.Future) {
        approved = false // timeout, auto-reject
    })
    selector.Select(ctx)

    if !approved {
        // Saga: compensate previous steps
        workflow.ExecuteActivity(ctx, activities.RefundPayment, orderID).Get(ctx, nil)
        return nil
    }
    return workflow.ExecuteActivity(ctx, activities.FinalizePayment, orderID).Get(ctx, nil)
}
```

```python title="workflows/payment_approval.py / Python + temporalio"
@workflow.defn
class PaymentApprovalWorkflow:
    def __init__(self) -> None:
        self._approved: bool | None = None

    # A signal is just a method: external events can wake this workflow
    @workflow.signal
    def approve(self, approved: bool) -> None:
        self._approved = approved

    @workflow.run
    async def run(self, order_id: str) -> None:
        # Step 1: Process payment details
        await workflow.execute_activity(prepare_payment, order_id, **opts)

        # Step 2: Wait up to 24 hours for human approval.
        # Temporal pauses here, no CPU/memory consumed while waiting.
        try:
            await workflow.wait_condition(
                lambda: self._approved is not None,
                timeout=timedelta(hours=24),
            )
        except asyncio.TimeoutError:
            self._approved = False  # timeout, auto-reject

        if not self._approved:
            # Saga: compensate previous steps
            await workflow.execute_activity(refund_payment, order_id, **opts)
            return

        await workflow.execute_activity(finalize_payment, order_id, **opts)
```

<Callout type="info" title="Quando utilizzare Temporal rispetto a una normale coda di attività">
Utilizza una normale coda di attività (Celery/Asynq/BullMQ/Redis Streams) per **attività semplici e indipendenti**: e-mail, notifiche, elaborazione di immagini. Rivolgiti a Temporal quando disponi di **flussi di lavoro aziendali in più fasi** con logica di compensazione, lunghi periodi di attesa, approvazioni umane o quando hai bisogno di una cronologia completa di esecuzione per conformità/debug. Temporal ha un sovraccarico operativo più elevato (esegui un cluster di server Temporal), quindi non utilizzarlo a meno che non sia necessario.
</Callout>
