Parte I / Perché e cosa

## Perché esistono i test

La ragione onesta per scrivere test automatizzati non è la "correttezza" in astratto, è la **sicurezza di modificare il codice senza paura.** Un sistema senza test calcifica: ogni modifica rischia di rompere qualcosa di invisibile, quindi le persone smettono di refactoring, smettono di aggiornare le dipendenze e aggirano le parti spaventose. Un sistema ben testato rimane morbido, puoi ristrutturarlo in modo aggressivo perché una suite di test verde ti dice, in pochi secondi, che il comportamento è ancora valido. I test sono ciò che consente a una base di codice di continuare ad evolversi invece di marcire.

Un test è anche una **specifica eseguibile**. I documenti in prosa si allontanano dalla realtà (lo stesso problema notato nel capitolo gRPC sui contratti REST); un test che afferma `Divide(10, 2) == 5` non può mentire, o va contro il codice attuale oppure no. Leggi una buona suite di test e imparerai esattamente cosa promette il codice, con esempi. E i test sono una **rete di regressione**: una volta scritto un test per un bug, quel bug non potrà mai più ripresentarsi silenziosamente, la rete lo rileva ad ogni esecuzione futura.

Il test manuale consiste nel controllare il tuo lavoro rileggendolo una volta. I test automatizzati stanno assumendo un instancabile correttore di bozze che ricontrolla l'_intero_ documento, istantaneamente, ogni volta che cambi una singola parola, e non si annoia mai né perde una riga.

Quali test ti comprano davvero

**Fiducia nel cambiamento** (refactoring senza timore), **specifiche eseguibili** (documenti che non possono andare alla deriva), **protezione dalla regressione** (i bug risolti rimangono fissi) e **feedback più rapido** (secondi, non un clic manuale). La correttezza è un effetto collaterale; la mutevolezza è il premio.

## La Piramide dei Test

Non tutti i test sono uguali e la decisione strategica più importante è il _mix_. La **piramide dei test** è l'euristica guida: avere **molti unit test rapidi ed economici** alla base, **meno test di integrazione** nel mezzo e **pochissimi test end-to-end lenti e costosi** in alto. La forma deriva da un compromesso che attraversa l'intero manuale: man mano che si sale, i test diventano più _realistici_ (utilizzano maggiormente il sistema reale) ma anche più lenti, più fragili e più difficili da eseguire il debug.

L’anti-pattern del cono gelato

Invertire la piramide, molti test E2E lenti, pochi test unitari e ottieni il "cono gelato": una suite che impiega anni per essere eseguita, fallisce in modo intermittente (sec 14) e fornisce segnali vaghi (un errore potrebbe essere _ovunque_ nello stack). I team in questa trappola smettono di fidarsi della suite e smettono di eseguirla. Spingi i dettagli verso test unitari rapidi; utilizzare E2E con parsimonia per avere la certezza che i pezzi si colleghino.

## Anatomia di un test

Ogni buon test, ad ogni livello, ha la stessa struttura a tre battute, **Arrange, Act, Assert** (AAA; il mondo BDD lo chiama Dato-Quando-Allora). _Arrange_ imposta il mondo e gli input; _Act_ esegue l'operazione sotto test; _Assert_ verifica che il risultato sia quello previsto. Mantenere distinte queste fasi e testare _un_ comportamento per test è ciò che rende immediatamente leggibile un fallimento: sai esattamente quale comportamento ha rotto.

● Vai ● Python

```go
// File naming convention: foo.go is tested by foo_test.go in the same package.
// Test functions are func TestXxx(t *testing.T), the `go test` tool finds them.
func TestDiscount_AppliesPercentage(t *testing.T) {
    // Arrange, set up inputs (and any doubles)
    cart := Cart{Subtotal: 200}
    coupon := Coupon{Percent: 10}

    // Act, the ONE operation under test
    total := ApplyDiscount(cart, coupon)

    // Assert, state the expectation; a good message explains the failure
    if total != 180 {
        t.Errorf("ApplyDiscount(200, 10%%) = %d; want 180", total)
    }
}
```

```python
# pytest discovers files named test_*.py and functions named test_*.
# A bare `assert` is enough, pytest rewrites it to show a rich failure diff.
def test_discount_applies_percentage():
    # Arrange, set up inputs (and any doubles)
    cart = Cart(subtotal=200)
    coupon = Coupon(percent=10)

    # Act, the ONE operation under test
    total = apply_discount(cart, coupon)

    # Assert, pytest prints actual vs expected automatically on failure
    assert total == 180
```

#### Ciò che rende buona un'affermazione

- **Testare il comportamento, non l'implementazione.** Affermare il risultato osservabile (_viene applicato lo sconto_), non la meccanica interna (_è stato chiamato questo aiutante privato_). I test accoppiati all'implementazione si interrompono su ogni refactoring e vanificano l'intero scopo (sez 1, sec 20).
- **Un motivo per fallire.** Un test che asseri cinque cose non correlate ti dice poco quando diventa rosso. Preferisci test mirati con nomi descrittivi, il nome dovrebbe leggere come una frase sul comportamento.
- **Deterministico.** Stessi input, stesso risultato, ogni esecuzione, in qualsiasi ordine, la proprietà sec 14 riguarda la protezione.

<Callout type="info" title="Gli strumenti standard">
Questo manuale utilizza lo stack principale di ogni lingua: quello integrato di Go `testing` pacchetto con `go test` (non è necessario alcun framework; la libreria standard è il framework) e **pytest** di Python, lo standard de facto con dispositivi, parametrizzazione e plain-`assert` riscrittura. Entrambi sono ciò che troverai nei repository backend reali.

Parte II / Test unitari

## Test unitari

Un **test unitario** verifica un piccolo pezzo di logica, una funzione o un metodo, _in isolamento_ dal resto del sistema. Nessun database, nessuna rete, nessun filesystem, nessun orologio: solo input, output controllato. Questo isolamento è ciò che li rende veloci (migliaia di operazioni in pochi secondi) e precisi (un guasto punta esattamente a un'unità). Costituiscono l'ampia base della piramide (sezione 2) e dove dovrebbe risiedere la maggior parte del caso limite e della copertura dei rami.

L'obiettivo naturale per i test unitari è la tua **logica di dominio/aziendale**: i calcoli e le decisioni puri che non necessitano intrinsecamente di I/O: regole di prezzo, convalida, transizioni di stato, analisi. (Questo si mappa direttamente sul livello _service_ dal capitolo controller-servizi-repository; spingendo la logica in funzioni pure c'è esattamente ciò che lo rende testabile dall'unità qui.)

// The unit: pure logic, no I/O, trivially testable.
func IsStrongPassword(p string) bool {
    if len(p) < 8 { return false }
    var hasDigit, hasUpper bool
    for _, r := range p {
        if r >= '0' && r <= '9' { hasDigit = true }
        if r >= 'A' && r <= 'Z' { hasUpper = true }
    }
    return hasDigit && hasUpper
}

func TestIsStrongPassword(t *testing.T) {
    if IsStrongPassword("short1A") {            // 7 chars -> too short
        t.Error("expected short password to be rejected")
    }
    if !IsStrongPassword("longEnough9") {        // meets all rules
        t.Error("expected valid password to be accepted")
    }
}

// Run:  go test ./...        (-v for verbose, -run TestIsStrong to filter)
```

```python
# The unit: pure logic, no I/O, trivially testable.
def is_strong_password(p: str) -> bool:
    if len(p) < 8:
        return False
    return any(c.isdigit() for c in p) and any(c.isupper() for c in p)

def test_rejects_short_password():
    assert is_strong_password("short1A") is False    # 7 chars -> too short

def test_accepts_valid_password():
    assert is_strong_password("longEnough9") is True  # meets all rules

# Run:  pytest            (-v verbose, -k strong to filter by name)
```

Se un'unità è difficile da testare, il design ne è l'odore

Quando una funzione è difficile da testare unitariamente, raggiunge un globale, apre una connessione, legge l'orologio o fa dieci cose, il test ti sta dicendo che il _codice_ è mal fattorizzato, non che il test sia difficile. La soluzione consiste quasi sempre nel separare la logica pura dall'I/O e nell'inserire le dipendenze (sez. 6). Testabilità e buona progettazione sono la stessa proprietà vista da due angolazioni.

## Prova del doppio

Le unità reali dipendono da altre cose, un repository, un gateway di pagamento, un mittente di posta elettronica. Per testare un'unità in isolamento, sostituisci quei collaboratori con **test doppi**: controfigure che controlli. "Mock" è usato vagamente nelle conversazioni, ma il vocabolario preciso (di Gerard Meszaros / Martin Fowler) distingue cinque tipi e conoscere la differenza migliora il modo in cui esegui i test.

| Doppio | Cos'è | Lo usi per... |
| --------- | -------------------------------------------- | ------------------------------------------------------------- |
| **Manichino** | Un segnaposto passato ma mai utilizzato | soddisfare un parametro richiesto |
| **Stub** | Restituisce risposte predefinite alle chiamate | alimentare l'unità con input fissi (ad esempio "il DB restituisce questo utente") |
| **Spia** | Uno stub che registra anche come è stato chiamato | affermare in seguito che qualcosa _è stato_ chiamato e come |
| **Fintura** | Preprogrammato con aspettative verifica | affermare che è avvenuta un'_interazione_ (ad esempio "l'e-mail è stata inviata una volta") |
| **Falso** | Un'implementazione funzionante ma leggera | sostituire una dipendenza reale a buon mercato (ad esempio un DB in memoria) |

#### Verifica dello stato e verifica dell'interazione

La distinzione più profonda: **stub/falsi** supportano la verifica dello _stato_ (affermi il _risultato_), mentre i **mock/spies** supportano la verifica dell'_interazione_ (affermi che è avvenuta una _chiamata_). Preferisci la verifica dello stato, è robusto per il refactoring. Richiedi la verifica dell'interazione solo quando l'interazione _è_ il comportamento (un'e-mail deve essere effettivamente inviata, un addebito deve essere emesso esattamente una volta). Le interazioni eccessivamente beffarde sono una delle principali cause di test fragili (sez. 20).

```go
// The unit depends on an interface, the seam that lets us substitute a double (sec 6).
type UserRepo interface{ FindByID(id string) (*User, error) }

type Notifier interface{ Send(to, msg string) error }

func Greet(repo UserRepo, n Notifier, id string) error {
    u, err := repo.FindByID(id)        // collaborator 1
    if err != nil { return err }
    return n.Send(u.Email, "Hi "+u.Name) // collaborator 2 (interaction we care about)
}

// STUB: returns a canned user. SPY: also records what Send received.
type stubRepo struct{ user *User }
func (s stubRepo) FindByID(string) (*User, error) { return s.user, nil }

type spyNotifier struct{ calls int; lastTo string }
func (s *spyNotifier) Send(to, msg string) error { s.calls++; s.lastTo = to; return nil }

func TestGreet_SendsEmail(t *testing.T) {
    repo := stubRepo{user: &User{Email: "a@x.com", Name: "Ada"}} // arrange (stub)
    spy := &spyNotifier{}

    _ = Greet(repo, spy, "u1")                                   // act

    if spy.calls != 1 || spy.lastTo != "a@x.com" {               // assert the interaction
        t.Errorf("expected one email to a@x.com, got %d to %q", spy.calls, spy.lastTo)
    }
}
```

```python
from unittest.mock import Mock

# The unit depends on injected collaborators (sec 6).
def greet(repo, notifier, user_id):
    user = repo.find_by_id(user_id)          # collaborator 1
    notifier.send(user.email, f"Hi {user.name}")  # collaborator 2 (the interaction)

def test_greet_sends_email():
    # STUB: a Mock configured to return a canned user
    repo = Mock()
    repo.find_by_id.return_value = User(email="a@x.com", name="Ada")
    notifier = Mock()                        # will record calls (acts as spy/mock)

    greet(repo, notifier, "u1")              # act

    # assert the INTERACTION happened exactly as expected
    notifier.send.assert_called_once_with("a@x.com", "Hi Ada")
```

Go tende a scrivere a mano piccoli doppi su un'interfaccia (esplicito, senza magia); Di Pitone `unittest.mock` genera doppi flessibili che restituiscono sia stub che chiamate registrate. Stesso concetto, diversa ergonomia.

Non deridere ciò che non possiedi

Evita di prendere in giro direttamente librerie di terze parti o API HTTP esterne, il tuo mock codifica _la tua ipotesi_ su come si comportano, il che può essere sbagliato, quindi il test passa mentre la produzione si interrompe. Avvolgi invece la dipendenza dietro la tua stessa interfaccia e deridi _quello_, oppure usa un test falso/contratto (sez 11, sec 17). Deridi le tue cuciture, non le parti interne di qualcun altro.

## Iniezione di dipendenze per testabilità

L'unica tecnica che rende possibile il testing unitario è la **dependency injection (DI)**: invece di un'unità che _crea_ o _raggiunge_ i suoi collaboratori, li _riceve_ dall'esterno. Quel punto di passaggio è una **cucitura**: il luogo in cui un test può scivolare in un doppio (sez. 5). Nessuna cucitura, nessun isolamento. Questo è il motivo per cui l'architettura controller-servizi-repository insiste nel trasmettere le dipendenze: non è una cerimonia, è ciò che mantiene il codice testabile.

Progettare per la testabilità = buon design

DI, piccole interfacce e separazione della logica pura dall'I/O non sono "trucchi di prova", sono gli stessi principi che rendono il codice modulare e manutenibile. Una base di codice facile da testare è, quasi per definizione, ben strutturata. La suite di test è un segnale continuo di qualità del design.

## Test guidati da tabelle e parametrizzati

La maggior parte della logica deve essere verificata rispetto a _molte_ coppie input/output, percorso felice, casi limite, confini, casi di errore. Copiare e incollare un test per caso è rumore. Entrambi i linguaggi hanno un idioma per "stesso corpo di test, molti casi": **test guidati da tabelle** di Go e **parametrizza** di pytest. È qui che si ottiene una copertura economica e densa di rami e bordi, il vero cavallo di battaglia dello strato unitario.

func TestApplyDiscount(t *testing.T) {
    // The TABLE: each row is one case with a name.
    cases := []struct {
        name     string
        subtotal int
        percent  int
        want     int
    }{
        {"ten percent off 200", 200, 10, 180},
        {"zero discount",       100, 0,  100},
        {"full discount",       100, 100, 0},
        {"rounds down",          99, 10,  90}, // boundary/edge case
    }
    for _, c := range cases {
        // t.Run makes each row a named subtest, failures report the case name.
        t.Run(c.name, func(t *testing.T) {
            got := ApplyDiscount(Cart{Subtotal: c.subtotal}, Coupon{Percent: c.percent})
            if got != c.want {
                t.Errorf("got %d, want %d", got, c.want)
            }
        })
    }
}
// `go test -run TestApplyDiscount/rounds_down` runs just one case.
```

import pytest

        (100, 100, 0),

<Callout type="info" title="Dai un nome a ogni caso">
Il vantaggio di questi idiomi non è solo meno codice, ma è che ogni caso diventa un test _con nome indipendente ed eseguibile_ in modo indipendente. Quando uno si interrompe, il rapporto nomina il caso esatto ("arrotondamento per difetto non riuscito") ed è possibile eseguirlo nuovamente. Assegnare sempre nomi descrittivi ai casi; una riga anonima che fallisce dice semplicemente "caso 3", il che non aiuta nessuno.
</Callout>

Parte III/Test di integrazione

## Test di integrazione

I test unitari dimostrano che ogni pezzo funziona da solo; I **test di integrazione** dimostrano che i pezzi funzionano _insieme_ e, soprattutto, che si integrano correttamente con i sistemi esterni _reali_ che hai deriso a livello di unità: il database, la cache, il broker di messaggi, un altro servizio. Si trovano al centro della piramide (sec 2): sono più lenti degli unit test perché è coinvolto l'I/O reale, ma rilevano un'intera categoria di bug che gli unit test strutturalmente non possono.

Ciò che rilevano solo i test di integrazione

Una query SQL con una colonna digitata, una mappatura ORM che non corrisponde allo schema, una mancata corrispondenza della serializzazione tra i servizi, una migrazione non eseguita, una stringa di connessione errata, una transazione senza commit. Ognuno di questi vive nella _giunzione_ tra il tuo codice e un sistema reale, esattamente la cucitura che un test unitario traccia. Deridere il DB non può rivelare che la tua query non è un SQL valido; solo eseguirlo su un database reale può farlo.

Mantienili isolati e ripetibili

I test di integrazione toccano lo stato condiviso, quindi sono inclini a instabilità (sez. 14) se si confondono l'uno con l'altro. Ogni test deve iniziare da uno stato noto e ripulire se stesso, un nuovo schema, una transazione ripristinata o una tabella troncata (sez. 9). I test che dipendono da un database condiviso manualmente o dall'esecuzione in un ordine particolare prima o poi ti tradiranno.

## Test con un database reale

La domanda ricorrente: come si ottiene un database "reale" in un test senza dipendere da un server condiviso gestito manualmente? La risposta moderna è **Testcontainers**: una libreria che crea un vero database in un contenitore Docker usa e getta (i contenitori del capitolo 21) al momento del test, fornisce la sua stringa di connessione e lo smonta dopo. Esegui il test rispetto al motore _attuale_ (la stessa versione Postgres del prodotto), completamente isolato, senza nulla da installare. Per mantenere i test indipendenti l'uno dall'altro, le due tattiche standard sono il **rollback della transazione** (racchiudere ogni test in una transazione, eseguire il rollback alla fine) o il **troncare** le tabelle tra i test.

```go
// Build tag keeps slow integration tests out of the fast unit run:
//   //go:build integration      -> run with:  go test -tags=integration ./...
func TestUserRepo_SaveAndFind(t *testing.T) {
    ctx := context.Background()

    // Arrange: start a REAL Postgres in a throwaway container (testcontainers-go)
    pg, err := postgres.Run(ctx, "postgres:16",
        postgres.WithDatabase("app"), postgres.WithUsername("u"), postgres.WithPassword("p"))
    if err != nil { t.Fatal(err) }
    t.Cleanup(func() { pg.Terminate(ctx) }) // torn down automatically after the test

    dsn, _ := pg.ConnectionString(ctx, "sslmode=disable")
    db, _ := sql.Open("postgres", dsn)
    runMigrations(t, db)                    // apply the same schema as production

    repo := NewUserRepo(db)

    // Act: exercise the REAL query path
    _ = repo.Save(User{ID: "u1", Email: "a@x.com"})
    got, err := repo.FindByID("u1")

    // Assert: round-trips correctly through actual SQL
    if err != nil || got.Email != "a@x.com" {
        t.Fatalf("round-trip failed: %v / %+v", err, got)
    }
}
```

```python
import pytest
from testcontainers.postgres import PostgresContainer

# A fixture spins up a REAL Postgres once per module, then tears it down.
@pytest.fixture(scope="module")
def db_url():
    with PostgresContainer("postgres:16") as pg:   # throwaway container
        url = pg.get_connection_url()
        run_migrations(url)                         # same schema as production
        yield url
        # container stopped automatically on exit

@pytest.fixture
def repo(db_url):
    # function-scoped: clean state per test (truncate / rollback)
    r = UserRepo(db_url)
    yield r
    r.truncate_all()                                # keep tests independent (sec 8)

@pytest.mark.integration            # marker: pytest -m integration
def test_save_and_find(repo):
    repo.save(User(id="u1", email="a@x.com"))       # act through REAL SQL
    got = repo.find_by_id("u1")
    assert got.email == "a@x.com"                   # round-trips correctly
```

Entrambi isolano i test lenti dietro un flag/marker (tag Go build, marcatori pytest) in modo che la suite di unità di millisecondi rimanga veloce e i test DB più pesanti vengano eseguiti su richiesta o in CI (sec 19).

Prova con il motore reale, non con un sostituto

Scambiare in SQLite "perché è veloce" quando la produzione esegue Postgres è una trappola classica: i dialetti differiscono (tipi, vincoli, JSON, upsert, blocchi), quindi un test può passare su SQLite e la stessa query fallisce su Postgres. Testcontainers esiste proprio per consentirti di utilizzare il motore di produzione _attuale_ a buon mercato e testare ciò che spedisci.

## Test di gestori e API HTTP

I tuoi gestori (i capitoli HTTP e REST) sono un obiettivo di integrazione primario: vuoi inviare una richiesta reale al tuo routing + gestore + stack di serializzazione e affermare sulla risposta reale, codice di stato, intestazioni, corpo, _senza_ associare un socket o eseguire un server sulla rete. Entrambi gli ecosistemi forniscono un client di test in-process che guida direttamente il gestore: Go's `net/http/httptest` e il `TestClient` fornito con FastAPI/Starlette (e l'equivalente di Flask).

func TestCreateUser_Returns201(t *testing.T) {
    handler := NewRouter(deps)  // the REAL router + handlers (deps may use a fake repo sec 6)

    // Arrange: build a request and an in-memory response recorder (no network)
    body := strings.NewReader(`{"email":"a@x.com","name":"Ada"}`)
    req := httptest.NewRequest(http.MethodPost, "/api/v1/users", body)
    req.Header.Set("Content-Type", "application/json")
    rec := httptest.NewRecorder()

    // Act: drive the handler directly
    handler.ServeHTTP(rec, req)

    // Assert: on the real response, status, then body
    if rec.Code != http.StatusCreated {
        t.Fatalf("status = %d; want 201; body=%s", rec.Code, rec.Body.String())
    }
    if ct := rec.Header().Get("Content-Type"); !strings.Contains(ct, "application/json") {
        t.Errorf("content-type = %q", ct)
    }
}

Scegli deliberatamente il mirino per test, più stretto è più veloce e più preciso; più ampio è più realistico.

## Test del contratto

Nel mondo dei microservizi (i capitoli gRPC e API-design), un servizio raramente vive da solo, ne _consuma_ altri e viene _consumato_ da altri. Il pericolo: un fornitore cambia la sua forma di risposta, tutti i suoi test passano, ma distrugge silenziosamente ogni consumatore. Il test end-to-end di ogni combinazione è proibitivamente lento. Il **test del contratto** risolve questo problema verificando che entrambe le parti siano d'accordo sull'_interfaccia_, senza eseguirle insieme.

<Callout type="info" title="Dove si adattano i test contrattuali">
Sono la via di mezzo pragmatica tra "deridere l'altro servizio e sperare che la tua simulazione sia accurata" (veloce ma può allontanarsi dalla realtà, l'avvertimento del sec 5) e "far girare tutto e testare end-to-end" (realistico ma lento e fragile). ## Test end-to-end

Un **test end-to-end (E2E)** esercita il sistema completamente assemblato attraverso la sua vera interfaccia esterna, esattamente come farebbe un utente o un cliente, senza stub interni, tutto in esecuzione: l'API, il database, la cache, i servizi dipendenti. Risponde all'unica domanda che nessun livello inferiore può: _tutti i pezzi, collegati insieme per davvero, forniscono effettivamente il risultato rivolto all'utente?_ È la punta della piramide (sezione 2): massimo realismo, massimo costo.

I test E2E sono lenti, costosi da mantenere e i più soggetti a problemi (sez. 14): un singhiozzo ovunque, rete, tempistica, dipendenza, li fallisce e un fallimento non ti dice _dove_ è il problema. ## Copertura di prova

La **Copertura** misura la quantità di codice eseguita dai test, in genere come percentuale di linee o rami eseguiti durante la suite. È utile come _torcia_ per trovare codice che non esegue alcun test, ma è pericolosamente facile da interpretare erroneamente come misura della _qualità_ del test. Non lo è. La copertura ti dice cosa è stato _eseguito_, mai cosa è stato _affermato_ in modo significativo.

______

● Vai ● Python

```bash
# Built into the toolchain, no extra dependency.
go test -cover ./...                       # prints % per package

go test -coverprofile=cover.out ./...      # write a detailed profile
go tool cover -func=cover.out              # per-function breakdown
go tool cover -html=cover.out              # open an annotated, line-by-line HTML view
```

pip install pytest-cov

pytest --cov=app                           # coverage for the `app` package
pytest --cov=app --cov-report=term-missing # show exactly which lines are UNcovered
pytest --cov=app --cov-report=html         # browsable htmlcov/ report
pytest --cov=app --cov-branch              # branch coverage, not just line
```

#### Copertura linea vs filiale

**Copertura della linea** chiede "questa linea funzionava?" **Copertura delle filiali** pone la domanda più difficile: "è stata presa ciascuna _direzione_ di ciascuna decisione?" Un singolo test può colpire il 100% delle linee in un file `if` prendendo sempre e solo il ramo vero, il `else` il percorso non è eseguito e non è stato testato sebbene la copertura della linea sembri completa. La copertura delle filiali è il numero più onesto; lo preferisco.

La copertura è un limite, non un obiettivo, e Goodhart morde

Puoi raggiungere una copertura del 100% con test che non asseriscono _niente_, basta chiamare ogni funzione e non controllare alcuna eccezione. Completamente coperto, totalmente inutile. Nel momento in cui una _percentuale_ di copertura diventa un obiettivo, le persone la giocano con test privi di asserzioni (legge di Goodhart: una misura che diventa un obiettivo smette di essere una buona misura). Usa la copertura per trovare aree non testate che meritano attenzione; giudicare la qualità in base al fatto che i test affermino un comportamento significativo (sez. 3, sez. 20). Una copertura elevata con asserzioni deboli è una falsa fiducia.

## Test traballanti

Un **test instabile** a volte riesce e altre volte fallisce _senza alcuna modifica al codice_. La fragilità è corrosiva: addestra il team a ignorare le build rosse ("basta rieseguirlo"), e una volta che le persone smettono di fidarsi della suite, la suite è morta, una corsa verde non significa più nulla. I test inadeguati sono probabilmente peggiori dell’assenza di test, perché costano tempo ed erodono la fiducia che dà ai test il loro valore (sez. 1).

| Causa di desquamazione | Correzione |
| ----------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| **Ora/orologio**: "adesso", timeout, ore di sonno, limiti di data | Iniettare l'orologio; affermare intervalli non istanti esatti (sez. 17). Mai `sleep` "aspettare"; interrogare una condizione.  |
| **Dipendenza dall'ordine dei test**: un test si basa sugli avanzi di un altro | Imposta e smonta ogni test nel proprio stato (sez. 9, sez. 15). Esegui in ordine casuale per stanarli. |
| **Stato mutabile condiviso**: una riga DB globale, condivisa, un singleton | Isolare per test; evitare lo stato globale; utilizzare infissi nuovi.                                                |
| **Concorrenza/gare**: goroutine, thread, timing asincrono | Sincronizza su segnali non sincronizzati; correre con il rilevatore di gare (`go test -race`).                         |
| **Rete reale/API esterna**: latenza, limiti di velocità, tempi di inattività | Deridere il confine (sec 17); mantieni le chiamate reali a un set E2E piccolo e tollerante.                                 |
| **Dati non ordinati**: iterazione della mappa, righe DB senza `ORDER BY`     | Ordina prima del confronto o asserisci l'appartenenza a un insieme e non una sequenza.                                            |

La cura è il determinismo

Ogni test instabile è un non determinismo nascosto, tempo, ordinamento, concorrenza o stato condiviso che trapelano. La soluzione è sempre quella di rimuovere la fonte della casualità: controllare l'orologio, isolare lo stato, sincronizzarsi sugli eventi invece che sulle sospensioni e interrompere la rete. **Messa in quarantena** un test instabile (contrassegna e salta dall'esecuzione del gating) solo come misura temporanea mentre trovi la vera causa, non coprirlo mai con una coperta "riprova fino al verde", che nasconde semplicemente il bug.

## Infissi e fabbriche

I test necessitano di dati e di uno stato iniziale noto, e il modo in cui li costruisci decide se la tua suite rimane leggibile o marcisce in una zuppa di configurazione. Due strumenti correlati: **fixtures** gestiscono _setup e smontare_ (il mondo in cui viene eseguito un test, una connessione DB, una directory temporanea, un client registrato) e **fabbriche** costruiscono _oggetti di test_ con valori predefiniti sensati in modo che ogni test indichi solo i campi che gli interessano effettivamente.

______

● Vai ● Python

```go
// Go favors explicit helpers over magic. t.Helper() keeps failure line numbers useful.
// A "factory" with functional options: specify only the fields that matter to the test.
func newUser(t *testing.T, opts ...func(*User)) User {
    t.Helper()
    u := User{ID: "u1", Email: "default@x.com", Active: true} // sensible defaults
    for _, o := range opts { o(&u) }
    return u
}
func withEmail(e string) func(*User) { return func(u *User) { u.Email = e } }

// A "fixture" via t.Cleanup: setup returns the thing + auto-teardown.
func newTempStore(t *testing.T) *Store {
    t.Helper()
    dir := t.TempDir()                 // auto-removed after the test
    s := OpenStore(dir)
    t.Cleanup(func() { s.Close() })    // teardown runs even if the test fails
    return s
}

func TestSignup(t *testing.T) {
    store := newTempStore(t)
    u := newUser(t, withEmail("ada@x.com")) // only the relevant field is stated
    _ = store.Save(u)
    // ...assert...
}
```

```python
import pytest

# pytest FIXTURES: setup before `yield`, teardown after. Injected by parameter name.
@pytest.fixture
def temp_store(tmp_path):           # tmp_path is a built-in fixture (auto-cleaned dir)
    store = Store(tmp_path)
    yield store                     # the test runs here
    store.close()                   # teardown, runs even if the test fails

# A FACTORY: defaults + overrides, so tests state only what they care about.
def make_user(**overrides):
    return User(**{"id": "u1", "email": "default@x.com", "active": True, **overrides})

def test_signup(temp_store):
    user = make_user(email="ada@x.com")   # only the relevant field is stated
    temp_store.save(user)
    # ...assert...

# Libraries like factory_boy / model_bakery scale this up for complex object graphs.
```

Mantieni visibili i dati rilevanti

Lo scopo delle fabbriche è nascondere la configurazione _irrilevante_, non nascondere i dati da cui dipende un test. Se un test afferma qualcosa su un utente premium, la parola "premium" dovrebbe apparire _in quel test_ (`make_user(tier="premium")`), non essere sepolto in un dispositivo condiviso a tre file di distanza. Un lettore dovrebbe comprendere la premessa di un test senza fare speleologia. Dispositivi eccessivamente condivisi e opachi (l '"ospite misterioso") rendono difficile diagnosticare i guasti e difficile fidarsi dei test.

## TDD: Rosso/Verde/Refactoring

**Sviluppo basato sui test** inverte il solito ordine: scrivi prima un test _fallito_, poi il codice minimo per superarlo, quindi pulisci, ripetendo in piccoli cicli. La disciplina è il famoso ciclo di tre battute: **Rosso** (scrivere un test, guardarlo fallire), **Verde** (farlo passare nel modo più semplice possibile), **Refactoring** (migliorare la progettazione mentre il test rimane verde). Scrivere il test prima ti costringe a definire il comportamento desiderato e un'interfaccia pulita _prima_ di essere coinvolto nell'implementazione.

## Tempo di simulazione, casualità e API esterne

Tre fonti di test di naufragio del non determinismo se lasciate reali, l'orologio, il generatore casuale e la rete, e sono i soliti sospettati dietro l'instabilità (sezione 14). La cura per tutti e tre è la stessa: trasformare la dipendenza nascosta in una dipendenza _iniettata_ (sez. 6) in modo che il test la controlli.

#### Tempo e casualità: iniettateli

Codice che chiama `time.Now()` o `random()` direttamente non è testabile e instabile, il suo output cambia ad ogni esecuzione. Crea l'orologio e le dipendenze RNG che l'unità riceve, quindi passa un orologio fisso (restituisce sempre lo stesso istante) o un RNG seminato nei test. Ora "il token scade tra 1 ora" o "scegli un frammento casuale" è completamente deterministico e asseribile.

#### HTTP esterno: stub il confine

Non utilizzare mai una vera API di terze parti in un test di unità/integrazione, è lenta, instabile, con velocità limitata e potrebbe avere effetti collaterali. Entrambi gli ecosistemi ti consentono di intercettare HTTP localmente: Go's `httptest.Server` attiva un server falso a cui indichi il tuo cliente; Di Pitone `responses`/`respx` applicare una patch al livello HTTP per restituire risposte predefinite. (E ricorda la sezione 5: preferisci racchiudere l'API dietro la tua interfaccia in modo che la maggior parte dei test si burli di _quello_, riservando stub a livello HTTP per testare l'adattatore client stesso.)

Il determinismo non è negoziabile

Un test deve produrre lo stesso risultato su ogni esecuzione, su ogni macchina, in qualsiasi ordine. Nell'istante in cui si insinua il tempo reale, la reale casualità o una vera rete, hai piantato un futuro traballante fallimento. Inietta e controlla tutti e tre, è la stessa cucitura DI del sec 6 applicata alle tre cose che cambiano da sole.

## Test di prestazioni e carico

I test funzionali dimostrano che il codice è _corretto_; i test sulle prestazioni dimostrano che è _abbastanza veloce_, un asse completamente diverso e che conta molto per le preoccupazioni di ridimensionamento dei capitoli 18-19. Due versioni distinte: **benchmark** (micro: quanto è veloce questa funzione/endpoint?) e **test di carico** (macro: come si comporta l'intero sistema con N utenti simultanei?).

| Gentile | Domanda | Strumento |
| --------------- | -------------------------------------------------------- | ----------------------------------------- |
| **Parametro di riferimento** | Quanto velocemente/quante allocazioni per questo percorso di codice?      | Vai `testing.B`; Pitone `pytest-benchmark` |
| **Test di carico** | Throughput e latenza in caso di traffico simultaneo sostenuto? | k6, Locusta, Gatling, vegeta |
| **Test di stress** | Dove si rompe e come fallisce?               | stessi strumenti, hanno superato la capacità |
| **Soak test** | Si degrada nel corso delle ore (perdite, frammentazione)?       | stessi strumenti, lunga durata |

  stages: [

    { duration: '30s', target: 0 },    // ramp down
  ],

    http_req_duration: ['p(95)<300'],  // 95th-percentile latency must stay < 300ms
    http_req_failed:   ['rate<0.01'],  // error rate must stay under 1%
  },

Un benchmark o un test di carico senza un numero target è solo banalità.

## Test in CI/CD

Una suite di test ha valore solo se viene eseguita _automaticamente_, ad ogni modifica, come un cancello. È qui che i test incontrano la pipeline del capitolo 21 (sez. 19 lì): a ogni push, CI esegue i test e un errore **blocca l'unione o la distribuzione**. Lo scopo centrale del gradiente di velocità della piramide (sec 2) è fornire un feedback rapido qui, eseguire i test unitari in millisecondi su ogni commit, i test di integrazione/E2E più pesanti nella fase giusta.

```yaml title=".github/workflows/test.yaml / the test gate"
name: tests
on: [push, pull_request]
jobs:
  unit:                          # fast, runs on every push
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: go test -race -cover ./...          # Go: race detector + coverage
      # - run: pytest -m "not integration" --cov  # Python: skip slow tests here

  integration:                   # heavier, real DB via services / testcontainers
    runs-on: ubuntu-latest
    needs: unit                  # only if unit tests passed
    services:
      postgres:
        image: postgres:16
        env: { POSTGRES_PASSWORD: p }
        ports: ["5432:5432"]
    steps:
      - uses: actions/checkout@v4
      - run: go test -tags=integration ./...     # or: pytest -m integration
# A failed job fails the check -> branch protection blocks the merge.
```

<Callout type="info" title="Rendi la suite veloce e parallela">
Se i test sono lenti, le persone li saltano, quindi la velocità è una caratteristica. Esegui test in parallelo (Go lo fa tra i pacchetti per impostazione predefinita e all'interno di un test tramite `t.Parallel()`; pytest via `pytest-xdist`), dividere il fast unit gate dalle fasi di integrazione lenta/E2E e dalle dipendenze della cache. Una suite che ritorna in meno di pochi minuti viene eseguita; uno che ne richiede trenta viene ignorato e un test non eseguito non protegge nulla.
</Callout>

## Una strategia di test

I test hanno un costo da scrivere, eseguire e mantenere man mano che il codice cambia, quindi l'obiettivo non è mai "testare tutto" ma **massima sicurezza per unità di sforzo**. Una strategia coerente è principalmente un insieme di giudizi su _cosa_ testare, a quale livello e cosa lasciare stare.

#### Cosa testare pesantemente

- **Logica e regole di business**: prezzi, convalida, macchine a stati, qualsiasi cosa con filiali e casi limite. Unit test economici e veloci; il profitto più alto (sez. 4, sez. 7).
- **Bug che hai corretto**: ogni correzione riceve un test di regressione quindi non può restituire (sec 1).
- **Percorsi critici e denaro**: autenticazione, pagamenti e integrità dei dati ottengono copertura a più livelli, incluso un sottile E2E (sez. 12).
- **Concimi di integrazione**: le tue query, la serializzazione e i contratti tra servizi (sez. 8-11), dove si nascondono i bug sottili.

#### Cosa testare leggermente o per niente

- **Codice banale**: getter semplici, colla per framework, codice generato. Metterli alla prova è uno sforzo senza intuizione.
- **Librerie di terze parti**: presumono che funzionino; testa il _tuo_ utilizzo di essi, non i loro componenti interni (sez. 5).
- **Dettagli di implementazione**: aiutanti privati e sequenze esatte delle chiamate. Testare il comportamento osservabile in modo che i refactoring non causino errori spuri.

La regola d'oro: testare il comportamento, non l'implementazione

L'unico principio che separa una suite che _aiuta_ da una che _fa male_: affermare _cosa fa il codice_ (i suoi input osservabili-&gt;output ed effetti collaterali), mai _come lo fa_ internamente. I test incentrati sul comportamento sopravvivono al refactoring, diventano verdi finché vale il contratto, che è esattamente la fiducia nel cambiamento che ha giustificato i test in primo luogo (sez. 1). I test accoppiati all'implementazione si interrompono a ogni ristrutturazione, penalizzano i miglioramenti e vengono lentamente eliminati. Scrivi test per i quali il tuo sé futuro ti ringrazierà, non imprecare.

## Cheat-Sheet

L'intero manuale compresso in ciò che raggiungi sotto pressione.

| Concetto | Una riga |
| ------------------ | ------------------------------------------------------------------------------------- |
| Perché testare | Fiducia nel cambiamento, specifiche eseguibili, rete di regressione, feedback rapido.                 |
| Piramide | Molte unità (veloci) / qualche integrazione / pochi E2E (lenti). Non invertirlo.                |
| AAA | Organizza, Agisci, Asserisci, un comportamento per test, nome descrittivo.                        |
| Prova unitaria | Un'unità isolata, nessun I/O, millisecondi, precisa.                                 |
| Prova raddoppia | Falso / Stub / Spia / Finto / Falso. Preferisci la verifica dello stato rispetto alla verifica dell'interazione.         |
| Non prendere in giro | Ciò che non possiedi, avvolgilo dietro la tua interfaccia e deridilo.                  |
| DI | Iniettare collaboratori -&gt; la cucitura in cui si inserisce un doppio. Non testabile = odore di design.  |
| Tabella/parametrizzare | Un corpo di prova, molti casi nominati, una fitta copertura di casi limite.                            |
| Integrazione | DB/dip reali collegati insieme, rileva bug SQL, mappatura e serializzazione.                |
| DB reale | Testcontainer: motore vero, usa e getta, isolato. Non SQLite per Postgres.            |
| Test HTTP | `httptest` / `TestClient`, gestori di unità in corso, nessun socket.                      |
| Prova contrattuale | Verificare l'accordo fornitore/consumatore sull'interfaccia, senza eseguire entrambi (Pact, buf).    |
| E2E | Intero sistema tramite interfaccia reale, solo viaggi critici; prova del fumo dopo la distribuzione.     |
| Copertura | Trova codice non testato; non una misura di qualità. Preferisci il ramo; mai un bersaglio (Goodhart). |
| Traballante | Non determinismo: tempo, ordine, stato condiviso, concorrenza, rete. Cura = determinismo. |
| Impianti/stabilimenti | Gestisci configurazione/smontaggio e crea dati con le impostazioni predefinite; mantenere visibili i dati rilevanti.         |
| TDD | Rosso -&gt; Verde -&gt; Refactoring. Uno strumento di progettazione; utilizzare dove si adatta, non dogmaticamente.         |
| Determinismo | Iniettare l'orologio, seminare l'RNG, interrompere la rete, controllarli tutti e tre.                  |
| Perf | Benchmark (micro) + test di carico (macro). Traccia p95/p99 rispetto a uno SLO, non le medie.       |
| Porta CI | I test vengono eseguiti su ogni push e blocco di unione/distribuzione. Mantienili veloci e paralleli.            |
| Strategia | Fiducia per sforzo. Prova logica, bug, denaro, cuciture; salta curiosità e dettagli interni.       |
| Regola d'oro | **Comportamento del test, non implementazione**: sopravvive al refactoring.                          |

**L'intero argomento in un fiato:** i test automatizzati esistono per darti la sicurezza necessaria per modificare il codice (sec 1) e la forma strategica è una piramide, molti test unitari veloci, meno integrazione, un sottile strato E2E (sec 2). Ogni test è Arrange-Act-Assert su un comportamento (sez. 3). I test unitari isolano un'unità (sez 4) utilizzando test doppi (sez 5) resi possibili dall'iniezione di dipendenza (sez 6), con casi guidati da tabelle e parametrizzati per una copertura densa (sez 7). I test di integrazione collegano insieme le dipendenze reali (sez. 8), un database reale tramite testcontainer (sez. 9), gestori tramite client in-process (sez. 10) e un accordo tra servizi tramite test contrattuali (sez. 11). E2E copre solo i viaggi critici (sez. 12); la copertura è una torcia e non un obiettivo (sez. 13); la desquamazione è il non determinismo da eliminare (sez 14); e gli impianti e le fabbriche mantengono l'allestimento pulito (sez. 15). TDD guida la progettazione in cicli rosso/verde/refactoring (sec 16), il determinismo deriva dall'iniezione di tempo, casualità e rete (sec 17), le prestazioni sono il proprio asse di benchmark e test di carico rispetto a uno SLO (sec 18) e la suite si guadagna da vivere solo eseguendo come un gate veloce in CI/CD (sec 19). Soprattutto: comportamento del test, non implementazione (sez. 20).
