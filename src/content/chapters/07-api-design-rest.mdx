## Cos'è realmente il REST

Nel 1990 **Tim Berners-Lee** ha avviato un progetto per condividere la conoscenza in tutto il mondo, il World Wide Web. Nel giro di circa un anno ha inventato essenzialmente tutto ciò che usiamo ancora: l'**URI** (uniform Resource Identifier), il protocollo **HTTP**, **HTML**, il primo server web, il primo browser e il primo editor HTML WYSIWYG integrato in quel browser. Notevole per una persona in dodici mesi.

Poi è arrivato il problema: **scala**. Il web è cresciuto in modo esponenziale, ben oltre ciò che Berners-Lee aveva pianificato. Il design originale semplicemente non poteva assorbire la base di utenti che acquisiva ogni giorno. Intorno al 1993, **Roy Fielding**: co-fondatore del progetto del server HTTP Apache, si preoccupò proprio di questo. Per rendere il web scalabile ha proposto una serie di _vincoli_ architettonici. Lui e Berners-Lee hanno poi scritto insieme le specifiche per **HTTP/1.1**, la prima versione standardizzata del protocollo. Infine, nel **2000**, Fielding ha nominato e descritto l'intero stile architettonico nella sua tesi di dottorato: **REST, REpresentational State Transfer**.

<Callout type="info" title="Vale la pena leggerlo">
La tesi di Fielding è il documento originale di REST. Cerca "Dissertazione REST di Roy Fielding", è una lettura davvero utile per qualsiasi ingegnere di backend, perché spiega _perché_ esistono questi modelli, non solo cosa sono.
</Callout>

Il nome si scompone in tre idee e ognuna rappresenta un concetto reale che usi ogni giorno:

### Rappresentativo

Una risorsa (un dato, un utente, un libro, un carrello) può essere _rappresentata_ in formati diversi a seconda di chi lo richiede. Lo stesso `user` il record potrebbe essere inviato come **JSON** a un client API (da server a server) o come **HTML** a un browser o come **XML** ad alcuni consumer legacy. La risorsa sottostante è una cosa; le sue rappresentazioni sono molteplici.

### Trasferimento

Poiché abbiamo un client e un server, il punto è spostare queste rappresentazioni tra di loro. Il _trasferimento_ avviene tramite lo standard comune, HTTP, utilizzando i suoi metodi (`GET`, `POST`, `PUT`, `PATCH`, `DELETE`, ...). Quando il tuo browser richiede una pagina con `GET`, sta trasferendo una rappresentazione dal server al client.

<Callout type="info" title="Modello mentale">
REST = risorse che hanno più **rappresentazioni**, il cui **stato** può essere **trasferito** tra client e server tramite HTTP, il tutto entro una serie di vincoli che mantengono il sistema scalabile. Non è necessario memorizzare la teoria, ma conoscere le tre parole ti dice cosa sta realmente facendo ogni chiamata API: spostare una rappresentazione dello stato attuale di alcune risorse.
</Callout>

## I sei vincoli

Per essere veramente "RESTful" e ottenere la scalabilità ricercata da Fielding, un sistema segue sei vincoli. Ne sono richiesti cinque; il sesto è facoltativo. Questa non è burocrazia; ognuno acquista una proprietà di ridimensionamento concreta.

I sei vincoli e ciò che ciascuno acquista

| Vincolo | Cosa dice | Cosa compra |
| --------------------------------- | ------------------------------------------------------------------------------------ | ------------------------------------------------------------- |
| **1 / Client-Server** | Rigorosa separazione delle preoccupazioni: il client possiede UI/UX, il server possiede dati e logica applicativa. | Ciascun lato si evolve in modo indipendente.                              |
| **2 / Interfaccia uniforme** | Un modo standardizzato per far comunicare tutti i componenti. (Quattro sottovincoli di seguito.) | Coerenza in ogni servizio.                             |
| **3 / Sistema a strati** | Strati gerarchici; un livello vede solo quello immediatamente sottostante.                 | Inserisci bilanciatori di carico/proxy senza toccare la logica principale. |
| **4 / Cache** | Le risposte devono etichettarsi come memorizzabili nella cache o meno.                                    | Meno carico sul server, risposte più veloci.                           |
| **5 / senza stato** | Il server non conserva memoria delle richieste passate; ogni richiesta porta con sé tutto ciò di cui ha bisogno.   | Qualsiasi server può gestire qualsiasi richiesta -&gt; ridimensionamento orizzontale.      |
| **6 / Codice su richiesta** (facoltativo) | Il server può fornire codice eseguibile (ad esempio JavaScript) per estendere il client.              | Comportamento flessibile del cliente quando necessario.                         |

### I due che contano di più nella pratica

**senza stato** è il pezzo forte. Il server non ricorda la tua richiesta precedente, ogni richiesta deve contenere tutte le informazioni necessarie per comprenderla ed elaborarla. Questo è ciò che rende possibile la scalabilità: metti un bilanciatore del carico davanti a tre server identici e poiché nessun server mantiene la tua sessione in memoria, _qualsiasi_ di essi può gestire _qualsiasi_ richiesta tramite round robin. L'assenza di stato è la ragione per cui puoi aggiungere server e "funzionano e basta".

Il **Sistema a strati** è ciò che consente l’assenza di stato. Poiché il client comunica sempre e solo con il livello immediatamente precedente, puoi inserire CDN, proxy inversi, bilanciatori del carico e gateway API tra il client e l'origine, e il client non lo sa né se ne preoccupa. Questa è la base fondamentale per cui una piccola app diventa una che serve milioni di persone.

#### I quattro sottovincoli di Uniform Interface

- **Identificazione della risorsa**: ogni risorsa è indirizzabile tramite un URI.
- **Manipolazione attraverso rappresentazioni**: agisci su una risorsa inviando/ricevendo la sua rappresentazione (il JSON che metti _è_ il modo in cui lo modifichi).
- **Messaggi auto-descrittivi**: ogni messaggio contiene metadati sufficienti (intestazioni, tipo di contenuto, metodo) per essere compreso da solo.
- **HATEOAS**: _Hypermedia come motore dello stato dell'applicazione_: le risposte possono includere collegamenti che indicano al client cosa può fare dopo. (Il vincolo secondario più ambizioso; poche API lo implementano completamente.)

## Perché REST ci confonde adesso

Ecco l'onesto retroscena su cui si basa la trascrizione: le persone continuano a inciampare nel REST, nel percorso _plurale o singolare? PUT o PATCH? quale codice di stato per un'azione personalizzata?_ e il motivo è storico. Quando questi standard si stavano formando, il web funzionava su **MPA (applicazioni multipagina)**: ogni interazione era una richiesta di pagina intera al server, che eseguiva il rendering dell'HTML e lo rimandava indietro.

Oggi creiamo principalmente **SPA (applicazioni a pagina singola)**: la prima richiesta scarica un grosso pacchetto di JavaScript e da quel momento in poi il browser esegue il proprio routing sul lato client, recuperando _data_ (JSON) dalle API anziché da intere pagine. Il cliente è diventato pesante; il server è diventato una pura API di dati. I vecchi standard non hanno mai previsto questo cambiamento, motivo per cui alcune delle loro regole sembrano ambigue rispetto all’uso moderno.

<Callout type="info" title="Lo scopo di questo capitolo">
Non per inventare nuove regole, gli standard già esistono, ma per _estrarne_ linee guida chiare e pratiche e impegnarsi per uno stile coerente. Una volta interiorizzate le convenzioni, smetti di ribattere "è RESTful?" su ogni endpoint e puoi invece dedicare le tue energie alla logica applicativa.
</Callout>

## Anatomia di un percorso

Inizia con un normale URL del sito Web e le sue parti:

Un URL tipico, scomposto

https\://api.example.com/v1/books/harry-potter?sort=name#reviews

**Schema**: `https`, il trasporto crittografato.

**Autorità**: dominio + facoltativo `api.` sottodominio.

**Versione**: `v1`, controllo delle versioni dell'API tramite path.

**Percorso/risorsa**: l'oggetto a cui stai accedendo; `/` significa gerarchia.

**Parametri query**: coppie chiave/valore per filtri e opzioni.

**Frammento**: scorre il browser fino a una sezione.

La forma **standard di settore** di un percorso API (una convenzione, non una regola rigida) li mette insieme: `https://` + un `api.` sottodominio + una versione simile `/v1` + il percorso della risorsa.

### Regola 1: nomi sempre plurali

La risorsa nel percorso è **sempre plurale**, anche quando si recupera un singolo elemento. Elenca tutti i libri -&gt; `/books`. Prendi un libro -&gt; `/books/123`, _non_ `/book/123`. La risorsa _type_ ("libri") è una raccolta; l'ID si restringe semplicemente ad esso. Questo è l’errore più comune tra i principianti.

### Regola 2: niente spazi o trattini bassi; utilizzare le lumache

Gli URL viaggiano in molti ambienti server/client/sistema operativo, quindi mantienili puliti. Non inserire mai spazi o caratteri di sottolineatura in un percorso. Per inserire un nome leggibile dall'utente in un URL, crea uno **slug**:

1

Prendi il nome: `Harry Potter`

2

Tutto in minuscolo (evita bug di mancata corrispondenza tra maiuscole e minuscole tra gli ambienti): `harry potter`

3

Sostituisci gli spazi con i trattini: `harry-potter` -&gt; `/books/harry-potter`

### Regola 3: la barra significa gerarchia

Una barra esprime una **relazione gerarchica** tra le risorse. `/organizations/123/projects` si legge come "i progetti che appartengono specificamente all'organizzazione 123". Primo livello: la collezione. Livello successivo: un membro specifico. Successivamente: la sottoraccolta di quel membro. Progetta i tuoi percorsi in modo che il nido racconti la storia.

## Metodi e idempotenza

**Idempotenza** è il concetto che sblocca "quale metodo dovrei usare?" Un'operazione è idempotente se eseguita più volte ha sul server lo stesso effetto di eseguirla una volta. La sottigliezza chiave: l'idempotenza riguarda l'**effetto collaterale che provochi sul server**, non il fatto che i byte di risposta siano identici.

I cinque metodi in sintesi

| Metodo | Scopo | Idempotente? | Ha un corpo?     |
| -------- | --------------------------------- | ----------- | ------------- |
| `GET`    | Leggi/recupera una rappresentazione | sì + sicuro | No |
| `POST`   | Crea una risorsa/azione personalizzata | no | Sì |
| `PUT`    | Sostituisci interamente una risorsa | sì | Sì (completo) |
| `PATCH`  | Aggiorna parte di una risorsa | solitamente | Sì (parziale) |
| `DELETE` | Rimuovere una risorsa | sì | No |

`HEAD` (recupera solo le intestazioni) e `OPTIONS` (utilizzato nel pre-volo CORS per chiedere "questa origine è consentita?"), ma questi cinque portano il vero lavoro sui dati.

### GET: idempotente e sicuro

Recupera i dati; non cambia nulla sul server. Chiamalo una o mille volte, lo stato del server è identico. "Ma cosa succede se qualcun altro crea un libro tra le mie chiamate e la risposta cambia?" Ciò non rompe l'idempotenza: l'idempotenza chiede quale effetto collaterale provoca la _tua_ chiamata, e a `GET` non ne causa nessuno. Poiché è sicuro, è possibile riprovare liberamente e memorizzare nella cache.

In trasmissione, un GET è semplicemente una riga di richiesta, intestazioni e una riga vuota, **nessun corpo**. Tutti gli input passano nell'URL (percorso + stringa di query), motivo per cui non inserisci mai segreti in un GET: l'intero URL finisce nella cronologia del browser, nei log del server e nei log CDN.

GET /v1/books/123 HTTP/1.1 Host: api.example.com Autorizzazione: Bearer eyJhbGci... Accetta: application/json &lt;- riga vuota = "intestazione completata, nessun corpo" HTTP/1.1 200 OK Tipo di contenuto: application/json Cache-Control: max-age=300 ETag: "9a3f-1f" \{ "id": 123, "title": "The Hobbit" \}

| Codice | Su un GET, questo significa |
| ----------------------- | ------------------------------------------------------------------------------------------------ |
| `200 OK`                | Trovato; il corpo è la rappresentazione.                                                        |
| `304 Not Modified`      | La tua copia cache è ancora aggiornata (hai inviato `If-None-Match`); nessun corpo restituito, salva il carico utile. |
| `301` / `302`           | Mosso; seguire il `Location` intestazione.                                                             |
| `400 Bad Request`       | La stringa della tua query non è valida.                                                                  |
| `401` / `403`           | Non autenticato/autenticato ma non consentito.                                               |
| `404 Not Found`         | Nessuna risorsa unica del genere.                                                                         |
| `429 Too Many Requests` | Tariffa limitata; controllare `Retry-After`.                                                               |

### PUT & PATCH: aggiornamenti idempotenti

Entrambi si aggiornano. La differenza è la portata:

- **PATCH**: aggiornamento parziale. Invia solo i campi che desideri modificare (ad esempio just `status`). La soluzione migliore per le app JSON dell'era SPA, in cui si aggiornano quasi sempre alcuni campi, non l'intero record.
- **PUT**: sostituzione completa. È necessario inviare la rappresentazione _intera_; il server sostituisce ciò che ha con il tuo carico utile. Ometti un campo e lo hai cancellato.

Perché idempotente? Supponiamo che il nome di un utente sia `A` e lo PATCH a `B`. Prima chiamata: `A -> B`. Seconda chiamata identica: `B -> B`. Millesima chiamata: ancora `B`. Lo stato finale non cambia mai dopo la prima chiamata, quindi ripetere lo stesso payload di aggiornamento è idempotente.

<Callout type="info" title="PUT vs PATCH nel mondo reale">
Gli sviluppatori spesso li usano in modo intercambiabile e internamente va per lo più bene. Ma per un'**API pubblica**, attenersi alla semantica: PATCH per parziale, PUT per sostituzione completa. I consumatori presumono che tu segua lo standard, se usi PUT dove intendi PATCH, fornisci loro un presupposto confuso e sbagliato. In pratica le API più moderne (guidate da SPA) si appoggiano a PATCH, perché raramente si desidera sostituire un'intera entità.
</Callout>

#### Sul filo: il corpo fa la differenza

\# PATCH, invia SOLO ciò che cambia PATCH /v1/users/divyansh HTTP/1.1 Content-Type: application/json \{ "city": "Bangalore" \} &lt;- nome ed email intatti # PUT, invia l'INTERA rappresentazione PUT /v1/users/divyansh HTTP/1.1 Content-Type: application/json \{ "name": "Divyansh", "email": "d\@x.com", "city": "Bangalore" \}

<Callout type="info" title="La trappola PUT/cancellazione silenziosa del campo">
PUT _sostituisce_. Se l'utente memorizzato ha `name`, `email`, e `city`, ma hai MESSO solo `{"city":"Bangalore"}`, hai appena cancellato il nome e l'e-mail. I campi che dimentichi di inviare sono spariti. Se hai solo _parte_ del record in mano, usa PATCH, mai PUT. Questo è il modo n. 1 con cui le persone distruggono accidentalmente i dati tramite un'API.
</Callout>

#### Modifiche simultanee: il problema degli aggiornamenti persi

Due client OTTIENE lo stesso record. A modifica l'e-mail e salva. B (che non ha mai visto il cambiamento di A) salva la città utilizzando la copia obsoleta di B e la scrittura di B sovrascrive silenziosamente l'e-mail di A. La soluzione è la **concorrenza ottimistica** con `ETag` + `If-Match`: il server fornisce un'impronta digitale della versione e applica la tua scrittura solo se quella versione è ancora aggiornata.

\# GET prima, il server restituisce un tag di versione ETag: "v7" # più tardi, quando riscrivi, echo la versione che hai visto PATCH /v1/users/divyansh HTTP/1.1 If-Match: "v7" # se qualcun altro lo ha già eseguito il bumping a "v8": HTTP/1.1 412 Precondition Failed &lt;- recuperare, unire nuovamente, riprovare

### DELETE: idempotente

Elimina utente `1`. Prima chiamata: l'utente viene allontanato (un vero effetto collaterale). Seconda chiamata: il server controlla, non trova tale utente e restituisce `404`, ma _non è cambiato nulla sul server_. Non si è verificato alcun nuovo effetto collaterale. Hai cambiato stato solo alla prima chiamata; ogni chiamata successiva è una no-op che riporta semplicemente "non trovato". Quindi DELETE è idempotente.

### POST: l'unico non idempotente

POST crea. Invia un payload "crea libro" una volta -&gt; un libro con ID `1`. Invia di nuovo lo stesso identico carico -&gt; un _secondo_ libro con ID `2` (Gli ID vengono generati lato server/DB e i nomi in genere non devono essere univoci). Dieci POST identici -&gt; dieci libri distinti. L'effetto collaterale cambia ogni volta, quindi il POST non è idempotente.

Sul cavo, POST porta un **corpo** (dichiarato da `Content-Type`) e viene restituita una creazione riuscita `201` con a `Location` intestazione che punta alla nuova risorsa:

POST /v1/orders HTTP/1.1 Autorizzazione: Bearer eyJhbGci... Tipo di contenuto: application/json \{ "productId": "sku\_42", "quantity": 2 \} Percorso di creazione HTTP/1.1 201: /v1/orders/ord\_9f2a &lt;- dove vive la nuova risorsa \{ "id": "ord\_9f2a", "status": "pending" \}

<Callout type="info" title="Il pericolo della non-idempotenza/e la soluzione">
Dillo tu `POST /payments {amount: 5000}` e la rete si interrompe _dopo_ che il server ha addebitato la carta ma _prima_ che la risposta ti arrivasse. Non sai se ha funzionato, quindi riprovi e ora ti sono stati addebitati 10.000 INR. La soluzione standard è una **chiave di idempotenza**: il client invia un ID univoco, il server lo registra con il risultato e qualsiasi tentativo con la stessa chiave restituisce il risultato _originale_ invece di addebitare nuovamente. Questo è il modo in cui Stripe e tutte le API di pagamento serie rendono POST sicuro per riprovare.
</Callout>

interface StoredResult {
  status: number
  body: Payment
}

export async function createPayment(req: Request, res: Response): Promise<void> {
  const key = req.get('Idempotency-Key') // client-generated UUID
  if (key === undefined) {
    res.status(400).json(errBody('Idempotency-Key header is required'))
    return
  }

  // already processed this exact request? return the SAME result, don't re-charge
  const prior: StoredResult | null = await idemStore.get(key)
  if (prior !== null) {
    res.status(prior.status).json(prior.body)
    return
  }

  // Worth knowing: this read-then-write is itself racy if two retries land
  // at once. In production the key is claimed with a single atomic insert
  // (a unique index on the key), and a duplicate insert means "someone else
  // is already charging this, wait for their result".
  const payment = await charge(req.body.amount as number) // the non-idempotent side effect
  await idemStore.save(key, 201, payment) // remember it, keyed by the idempotency key
  res.status(201).json(payment)
}

## Azioni personalizzate: oltre il CRUD

A volte un'azione non è adatta a Crea/Leggi/Aggiorna/Elimina. "Clonare un progetto", "archiviare un'organizzazione", "inviare un'e-mail" attivano una rete di lavoro in background che va oltre la semplice scrittura di un database. Le specifiche REST rendono `POST` il **metodo aperto** proprio per questi casi.

### La regola e la forma del percorso

Quando un'azione non corrisponde a un metodo standard, impostala come a `POST` e aggiungi l'azione come **verbo alla fine** di un percorso di risorsa specifico:

POST /organizations/5/archivio POST /projects/123/clone

Ciò mantiene la gerarchia onesta: tutte le organizzazioni -&gt; un'organizzazione specifica -&gt; l'azione da eseguire su di essa.

<Callout type="info" title="Perché l'archivio non è solo una PATCH">
In superficie, l'archiviazione sembra un'impostazione `status = "archived"`, quindi perché non PATCH? Perché l'archiviazione di un'organizzazione può innescare molto più di una semplice scrittura sul campo: eliminare tutti i suoi progetti e le relative attività, inviare un'e-mail al proprietario, revocare l'accesso, mettere in coda lavori di pulizia. L'inversione di stato è un _effetto collaterale_ dell'azione, non l'azione stessa. Quando l'operazione reale è più grande della modifica dei dati, si tratta di un'azione personalizzata -&gt; POST.
</Callout>

### L'esempio "invia e-mail".

Considera `POST /emails` con il corpo `{"target": "someone@example.com"}`. L'invio di un'e-mail è un recupero? No. Una creazione? Non proprio. Un aggiornamento o un'eliminazione? No. È un'azione personalizzata, quindi vive sotto POST. E nota: spesso ritorna un POST di azione personalizzata `200 OK` (l'azione si è svolta), no `201 Created`, perché non è stato necessariamente creato nulla di nuovo. Non dare mai per scontato "POST =&gt; 201".

Una risposta impaginata include quattro campi:

- `data`, l'array di elementi per questa pagina.
- `total`, il conteggio assoluto degli elementi nel database (in modo che l'interfaccia utente possa indicare "mostra 10 su 50").
- `page`, quale pagina rappresenta questa risposta.
- `totalPages`, il numero massimo di pagine (il frontend lo usa per sapere quando interrompere il recupero in caso di scorrimento infinito: quando `page === totalPages`, fermare).

Il client lo controlla con due parametri: `limit` (quanti per pagina) e `page` (quale pezzo). E, un momento sano di default, se il client non invia nessuno dei due, il server dovrebbe andare in default `page` a `1` e `limit` a qualcosa di simile `10` o `20`, non schiantarsi mai.

### Ordinamento

Due parametri: `sortBy` (quale campo) e `sortOrder` (`ascending` / `descending`). Impostazione predefinita cruciale: anche senza parametri di ordinamento, il server deve ordinare per _qualcosa_, altrimenti il ​​DB restituisce le righe in ordine arbitrario e la stessa chiamata produce ogni volta ordinamenti diversi. Il valore predefinito naturale è `sortBy=createdAt`, `sortOrder=descending` (prima il più recente).

### Filtraggio

Passa i campi delle risorse come parametri di query per restringere l'elenco: `?status=active`oppure combinali: `?status=archived&name=org`. Il server applica ciascuno di essi come filtro sul set di risultati.

## Codici di stato: fatto bene

| Codice | Significato | Usalo quando |
| ---------------- | ------------------- | ---------------------------------------------------------------------------- |
| `200 OK`         | Successo | Recupera, aggiorna (PATCH/PUT) o un'azione personalizzata eseguita.                      |
| `201 Created`    | Creato | Un POST ha creato con successo una nuova entità. Restituisce la nuova entità nel corpo. |
| `204 No Content` | Successo, corpo vuoto | Un DELETE riuscito, niente da rispedire.                                   |
| `404 Not Found`  | Risorsa mancante | Il cliente ha richiesto un ID specifico che non esiste.                         |

### La regola 404: quella che le persone sbagliano

Ritorno `404` solo quando un client richiede una **risorsa singola specifica** che non esiste (ad es. `GET /users/999`). Se un client seleziona un **API di elenco** e non c'è nulla che corrisponda (ad esempio "tutti gli utenti chiamati Zack" o un filtro che non corrisponde a nulla), _non_ restituisce 404. Restituisci `200 OK` con un array vuoto `[]`. Un elenco che non ha trovato nulla ha comunque avuto successo, semplicemente non ha trovato nulla.

### Le cinque famiglie: leggi la prima cifra

La **prima cifra** di ogni codice di stato ti dice quasi tutto. Questo è l'istinto di debug più veloce che puoi costruire.

| Famiglia | Classe | Di chi è il problema |
| ------ | ------------- | -------------------------------------------------------- |
| `1xx`  | Informativo | Raro; praticamente non li gestirai mai direttamente.      |
| `2xx`  | Successo | Ha funzionato.                                               |
| `3xx`  | Reindirizzamento | Vai a cercare altrove / usa la cache.                      |
| `4xx`  | Errore cliente | **Hai** inviato qualcosa di sbagliato, correggi la richiesta.           |
| `5xx`  | Errore del server | **Il server** si è rotto, non per colpa tua; riprova/avvisa op. |

<Callout type="info" title="Il riflesso della prima cifra">
Quando una chiamata fallisce: **4xx -&gt; correggi la tua richiesta** (controlla corpo, autenticazione, URL). **5xx -&gt; non è colpa tua**; riprovare con il backoff o chiamare il team del server. Quando riesce: **20x -&gt; fatto**, **30x -&gt; segui il reindirizzamento**. Quella singola divisione risolve la maggior parte di "cosa devo fare con questa risposta?" domande all'istante.
</Callout>

### I codici 4xx che le persone confondono

#### 401 vs 403

**401 Non autorizzato** significa "Non so chi sei", nessuna credenziale oppure non sono valide/scadute. La soluzione consiste nell'accedere o aggiornare il token. **403 Proibito** significa "So esattamente chi sei e non ti è consentito", credenziali valide, autorizzazione insufficiente. Effettuare nuovamente l'accesso non aiuterà. (I nomi sono storicamente invertiti, 401 riguarda in realtà l'autenticazione, 403 l'autorizzazione.)

#### 409 Conflitto

La richiesta entra in conflitto con lo stato corrente della risorsa: creazione di qualcosa che già esiste, un conflitto di campi univoci o eliminazione di qualcosa da cui dipendono ancora altri record ("impossibile eliminare un utente con ordini attivi").

#### 422 vs 400

**400 Bad Request** = la richiesta non è valida a livello di _sintassi_ (JSON non funzionante, una stringa in cui era richiesto un numero). **422 Entità non elaborabile** = la sintassi è perfetta, ma non rispetta una regola _semantica_/aziendale (un'età negativa, un'e-mail che non è un'e-mail, una data di fine prima della data di inizio). Usa 422 quando hai analizzato bene il corpo ma i valori non hanno senso.

#### 429 Troppe richieste

Tariffa limitata. Rispetta il `Retry-After` header (secondi di attesa) invece di martellare, altrimenti rimarrai semplicemente strozzato.

### I codici che incontrerai il 90% delle volte

| Codice | Significato semplice |
| ----------- | ----------------------------------- |
| `200`       | lavorato |
| `201`       | creato (successo POST) |
| `204`       | ha funzionato, nessun corpo (DELETE successo) |
| `301 / 302` | reindirizzamento |
| `304`       | la tua cache è ancora buona |
| `400`       | la tua richiesta non è valida (sintassi) |

| `409`       | conflitto con lo stato attuale |
| `422`       | i dati non superano la convalida (semantica) |
| `429`       | rallenta |
| `500`       | si sono schiantati |
| `503`       | sono sovraccarichi / in manutenzione |

## Esempio lavorato: una piattaforma PM

Di seguito la creazione della trascrizione: un prodotto di gestione del progetto (si pensi a Jira / Linear). Dai wireframe estraiamo i **nomi** -&gt; risorse: `organizations`, `projects`, `tasks` (anche utenti, tag). Quelli diventano tabelle, quindi endpoint. Ecco l'endpoint completo impostato per una risorsa, lo stesso modello si ripete per ogni altra risorsa.

| Azione | Metodo + Percorso | Successo |
| ------------------- | ------------------------------------ | --------------------- |
| Elenco organizzazioni | `GET /v1/organizations`              | 200 / impaginato |
| Crea organizzazione | `POST /v1/organizations`             | 201/nuovo ente |
| Prendine uno | `GET /v1/organizations/:id`          | 200 / 404             |
| Aggiornamento (parziale) | `PATCH /v1/organizations/:id`        | 200/ente aggiornato |
| Elimina | `DELETE /v1/organizations/:id`       | 204 / vuoto |
| Archivio (personalizzato) | `POST /v1/organizations/:id/archive` | 200/ente archiviato |

Notare la simmetria: **list** e **crea** condividono l'URL della raccolta (`/organizations`) e differiscono solo per il metodo, i percorsi del server `GET` al gestore della lista e `POST` al gestore di creazione. Allo stesso modo **prendine uno / aggiorna / elimina** condividi `/organizations/:id` e differiscono solo per il metodo. L'azione personalizzata aggiunge un verbo. `projects` rispecchierebbe esattamente questo, con `clone` come azione personalizzata.

## Regole d'oro

### Estrai prima i nomi dall'interfaccia utente

Prima di scrivere una linea di logica applicativa, guarda i wireframe (Figma) o parla con gli addetti al prodotto. I **nomi** con cui gli utenti interagiscono, progetti, utenti, attività, tag, sono le tue risorse. Osservare il modo in cui l'utente finale tocca i dati ti dice come il livello più basso (il DB) è correlato al livello superiore (lo schermo) e questo è il posto giusto per iniziare a progettare l'interfaccia.

### Progettare l'interfaccia prima della codifica

Un'API REST è _progettata_, non programmata prima. Disponi percorsi, carichi utili e risposte in uno strumento come **Insomnia** o **Postman** prima di toccare Go, Python, Node, Spring o qualsiasi altro framework. Il punto centrale è un'interfaccia deliziosa, intuitiva e inequivocabile, in modo che il consumatore non debba mai leggere il codice sorgente o indovinare il tuo comportamento per tentativi ed errori.

### Fornire impostazioni predefinite sensate

Non bloccarsi mai perché il client ha omesso qualcosa di ovvio. No `page` -&gt; predefinito `1`. No `limit` -&gt; predefinito `10`. No `sortBy` -&gt; `createdAt` discendente. No `status` su crea -&gt; `active`. Richiedi solo le informazioni che veramente non puoi dedurre.

### Sii spietatamente coerente

- **JSON nel `camelCase`, sempre**: sia payload che risposte.
- **Nessuna abbreviazione**: se un campo lo è `description`, non chiamarlo mai `desc` in un altro punto finale. Hai un contesto che il consumatore non ha; un'abbreviazione che non riescono a decodificare costa loro una chiamata fallita e una ricerca di documenti.
- **Stesse forme per tutte le risorse**: if `organizations` sono plurali e impaginati con `{data,total,page,totalPages}`, quindi `projects` e `tasks` lo sono anche loro. I consumatori integrano un endpoint, quindi _presumono_ che il resto segua lo stesso stile. Premia questa ipotesi.

<Callout type="info" title="Perché la coerenza è l'intero gioco">
Seguire uno standard condiviso elimina congetture, supposizioni ed errori umani dall'integrazione. Se un consumatore può presumere che la tua API sia conforme allo standard per circa l'80%, il tempo di integrazione diminuirà drasticamente, meno bug, meno "come si comporta questo endpoint?" chiamate. La coerenza dello stile è uno dei segni più chiari di un buon ingegnere di backend.
</Callout>

### Spedisci documenti interattivi

Genera un parco giochi interattivo con **Swagger / OpenAPI** fin dall'inizio. Funge anche da documentazione per gli ingegneri frontend che ti integrano e da banco di prova per te. La costanza con cui mantieni le specifiche OpenAPI ti distingue davvero.

<Callout type="info" title="Il capitolo in un fiato">
Estrai risorse (sostantivi plurali) dalla tua interfaccia utente, assegna a ciascuna il set CRUD su un URL gerarchico pulito, scegli il metodo in base all'intento (GET leggi / POST crea/azione / PUT sostituisci / PATCH parziale / DELETE rimuovi), lascia che l'idempotenza decida la possibilità di riprovare, restituisce il codice di stato onesto (201 creato / 204 eliminato / 404 solo per una singola risorsa mancante), crea pagine/ordina/filtra elenchi con valori predefiniti sensati e rimani spietatamente coerente, così puoi smettere di discutere su REST e tornare alla tua logica applicativa.
</Callout>

## Versioning: non danneggiare i tuoi consumatori

Nel momento in cui un altro team o un'altra azienda integra la tua API, non puoi più modificarla liberamente, un campo che rinomini o una risposta che rimodella interrompe il _loro_ codice in produzione. Il controllo delle versioni è il modo in cui evolvi senza interrompere ciò che è già stato distribuito. Tre strategie comuni:

| Strategia | Sembra | Scambio |
| -------------------------- | ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Percorso URL** (più comune) | `/v1/books` -&gt; `/v2/books`                | Evidente, banale da eseguire il debug, facile da instradare. REST leggermente "impuro" (la versione non fa parte dell'identità della risorsa). Il default pragmatico. |
| **Intestazione** | `Accept: application/vnd.example.v2+json` | Mantiene gli URL puliti e "puri", ma invisibili in un browser e più difficili da testare/debug. Utilizzato da GitHub per anni.                                       |
| **Parametri query** | `/books?version=2`                        | Semplice ma ingombra ogni URL e confonde la memorizzazione nella cache. Meno consigliato.                                                                             |

### Quando eseguire il bumping della versione

Solo con un **cambiamento decisivo**: qualcosa che distruggerebbe un consumatore esistente:

- Rimuovere o rinominare un campo; cambiandone il tipo o il significato.
- Rimozione di un endpoint o modifica del suo metodo/percorso.
- Rendere obbligatorio un campo precedentemente facoltativo o modificare il comportamento predefinito.

**Le modifiche aggiuntive NON sono interrotte**: e non necessitano di una nuova versione. L'aggiunta di un nuovo campo facoltativo, un nuovo endpoint o un nuovo parametro di query facoltativo lascia i vecchi client intatti (ignorano semplicemente ciò di cui non sono a conoscenza). Aumentare la versione per modifiche aggiuntive è inutile.

<Callout type="info" title="Deprecazione, fatta gentilmente">
Quando devi ritirare una versione, non strattonarla. Annuncia una sequenza temporale, corri `v1` e `v2` in parallelo durante una finestra di migrazione e inviare un file `Deprecation` / `Sunset` intestazione di risposta sulla vecchia versione in modo che gli integratori ricevano un avviso programmatico. Spezzare le persone in silenzio è il modo in cui perdi la loro fiducia.
</Callout>

## Risposte agli errori: l'altra metà del contratto

Le persone progettano attentamente il percorso felice e quindi restituiscono tracce di stack grezze o stringhe nude in caso di fallimento. Ma anche la forma dell'errore fa parte del contratto API, il codice di gestione degli errori del consumatore dipende dal fatto che sia **coerente e leggibile dalla macchina**. Il solo codice di stato non è sufficiente; il corpo dovrebbe spiegare cosa è andato storto in una struttura prevedibile.

### Una busta di errore coerente

Scegli una forma di errore e utilizzala su _ogni_ errore, su ogni endpoint. Una busta solida e minimale:

HTTP/1.1 422 Tipo di contenuto entità non elaborabile: application/json \{ "error": \{ "code": "validation\_failed", &lt;- stable, machine-readable "message": "Some fields are invalid.", &lt;- human-readable "details": \[ &lt;- per-field, for forms \{ "field": "email", "issue": "must be a valid email" \}, \{ "field": "age", "issue": "must be >= 0" \} ], "requestId": "req\_9f2a3c" &lt;- traccialo nei tuoi log \&#125; \&#125;

Perché ogni pezzo guadagna il suo posto:

- **`code`**: una stringa stabile che il client può `switch` su. Non costringerli mai ad analizzare il messaggio umano; i messaggi vengono riformulati, i codici no.
- **`message`**: per esseri umani/tronchi. Sicuro da mostrare o in superficie.
- **`details`**: errori per campo in modo che un modulo possa evidenziare esattamente quali input non sono riusciti (si abbina naturalmente a `422`).
- **`requestId`**: il singolo campo più utile in produzione: il consumatore lo cita in una segnalazione di bug e tu trovi la richiesta esatta nei tuoi log in pochi secondi.

<Callout type="info" title="Non perdere mai parti interne">
Non restituire tracce di stack, errori SQL, percorsi di file o dump di eccezioni del framework ai client, sono inutili per il consumatore e un regalo per gli aggressori (rivelano lo stack, lo schema e la struttura). Registra i dettagli cruenti lato server contro il file `requestId`; restituire la busta pulita al cliente. A `500` body dovrebbe dire "qualcosa è andato storto, ecco l'ID della tua richiesta", niente di più.
</Callout>

public record ApiFieldError(String field, String issue) {}

public record ErrorEnvelope(String code, String message,
                            List<ApiFieldError> details, String requestId) {}

@RestControllerAdvice
class ApiErrors {

    static ResponseEntity<Map<String, ErrorEnvelope>> writeError(
            HttpStatus status, String code, String message, List<ApiFieldError> details) {
        var envelope = new ErrorEnvelope(code, message, details, MDC.get("requestId"));
        // SAME shape for every error in the whole API
        return ResponseEntity.status(status).body(Map.of("error", envelope));
    }

    // The framework's OWN validation failures get funnelled through the same
    // helper, so a bean-validation error and a hand-written one are
    // indistinguishable to the client. That is what "consistent" has to mean.
    @ExceptionHandler(MethodArgumentNotValidException.class)
    ResponseEntity<?> onInvalid(MethodArgumentNotValidException e) {
        List<ApiFieldError> details = e.getBindingResult().getFieldErrors().stream()
            .map(f -> new ApiFieldError(f.getField(), f.getDefaultMessage()))
            .toList();
        return writeError(HttpStatus.UNPROCESSABLE_ENTITY,
            "validation_failed", "Some fields are invalid.", details);
    }
}

## Vincoli vs Convenzioni

Rimpicciolisci. Plurale o singolare e `PUT`-o-`PATCH` non sono le uniche cose che fanno inciampare le persone riguardo a REST, lo stesso vale per _count_ stesso. Chiedi a un tecnico "i principi del REST" e ne sentirai **sei**; chiedi a un altro e otterrai una lista di controllo di **otto** o dieci. Entrambi hanno ragione perché rispondono a due domande diverse. Questa sezione di chiusura è una scheda di riferimento per distinguerli.

### Due elenchi, due domande

I **sei** sono i _vincoli architettonici_ formali di Roy Fielding, definiscono ciò che rende un sistema RESTful _del tutto_. Questa è la risposta accademica, ed è l'intero [sec 02](#s2). Le **otto** sono _convenzioni_ pratiche, ovvero il modo in cui progetti un'API pulita e prevedibile una volta accettati tali vincoli. Questo è ciò che in realtà insegna la maggior parte di questo manuale, distribuito nei suoi capitoli. I vincoli sono la teoria; le convenzioni sono il mestiere.

#### I sei vincoli: la definizione di REST

1. **Client-Server**: dividi l'interfaccia utente da dati e logica in modo che ogni lato si evolva in modo autonomo.
2. **Interfaccia uniforme**: un modo standard per indirizzare e manipolare ogni risorsa.
3. **Sistema a più livelli**: lascia che proxy, cache e gateway si trovino tra il client e l'origine, in modo invisibile.
4. **Cacheable**: ogni risposta dichiara se può essere memorizzata nella cache.
5. **senza stato**: ogni richiesta porta con sé tutto ciò di cui ha bisogno; il server non ricorda nulla tra le chiamate.
6. **Codice su richiesta** (facoltativo), il server può fornire codice eseguibile per estendere il client.

Tutti e sei, più i quattro sottovincoli dell'interfaccia uniforme, tra cui HATEOAS, sono scompattati in [sec 02](#s2).

#### Le otto convenzioni: come costruirne una bene

Le otto convenzioni e dove le tratta questo manuale

| Convenzione | In una riga | Coperto in |
| ----------------------------- | -------------------------------------------------------------------------------------- | --------------------------- |
| **Risorse come sostantivi plurali** | Modella _cose_, non azioni; il metodo è il verbo. `/orders/123`, mai `/getOrder`. | [sez. 04 Percorsi](#s4)        |
| **Metodi per intento** | `GET` leggi / `POST` creare/azione/ `PUT` sostituire / `PATCH` parziale / `DELETE` rimuovere. | [sez. 05 Metodi](#s5)       |
| **Codici di stato onesti** | Lascia che sia il codice a portare il risultato, non seppellire un errore all'interno di a `200`.                    | [sec 08 Stato](#s8)        |
| **assenza di stato** \* | Ogni richiesta è autonoma -&gt; qualsiasi server può rispondere -&gt; ridimensionamento orizzontale.        | [sec 02 Vincoli](#s2)   |
| **Coerenza spietata** | Un involucro, un formato della data, una forma di impaginazione, ovunque.                         | [Sez. 10 Regole d'Oro](#s10) |
| **Versione** | Bump solo in caso di modifiche importanti; le modifiche aggiuntive non richiedono una nuova versione.                   | [sez. 11 Versionamento](#s11)   |
| **Pagina/ordinamento/filtro** | Non scaricare mai un'intera tabella; impaginare elenchi e fornire valori predefiniti sensati.                       | [sec 07 Elenco API](#s7)     |

<Callout type="info" title="Dove i due elenchi si toccano">
Non sono rivali, le convenzioni rappresentano il modo in cui onori i vincoli giorno per giorno. La sovrapposizione più evidente è l’**assenza di stato**, che è sia il vincolo n. 5 di Fielding sia una regola da seguire su ogni endpoint. Anche gli altri fanno eco: la **cacheability** emerge come your `Cache-Control` / `ETag` intestazioni e l'**interfaccia uniforme** è esattamente ciò che "URL con nomi plurali + metodi per intento + forme coerenti" offrono nella pratica. **HATEOAS**: il vincolo secondario più ambizioso, è l'unico pezzo della teoria che la maggior parte delle API del mondo reale ignora silenziosamente.
</Callout>

<Callout type="info" title="Quale lista vuole qualcuno?">
Se la domanda è accademica, un colloquio, "definisci REST", un esame di sistema, vogliono **i sei vincoli**. Se si tratta di "come posso progettare un'API pulita?", una revisione del codice, un nuovo servizio, vogliono **le otto convenzioni**. Stesso standard, due altitudini: i sei dicono cosa _è_ il RIPOSO; gli otto dicono come _farlo bene_.
</Callout>

## Gli Otto Principi

[sez. 13](#s13) li mise in fila con i sei di Fielding a colpo d'occhio; questi sono gli stessi otto scritti per intero, la lista di controllo in inglese semplice. Ciascuna è una convenzione di lavoro che trasforma la teoria in un'API che altri sviluppatori apprezzano effettivamente utilizzare e ciascuna rimanda al capitolo che la spiega in modo approfondito.

### 1. Modellare le risorse come sostantivi, non come azioni

Gli URL dovrebbero rappresentare _cose_, non operazioni. Utilizzare `/users/123/orders` piuttosto che `/getUserOrders?id=123`. Il metodo HTTP fornisce il verbo, quindi il nome e il metodo insieme descrivono l'azione. Le collezioni sono plurali, `/orders`, no `/order`. (Trattamento completo in [sez 04](#s4).)

### 2. Utilizzare i metodi HTTP per la semantica prevista

`GET` legge (e non cambia mai stato), `POST` crea, `PUT` sostituisce un commercio all'ingrosso di risorse, `PATCH` ne aggiorna una parte e `DELETE` lo rimuove. Il rispetto di ciò consente a client, cache e proxy di ragionare correttamente sulla tua API, a `GET` è sicuro riprovare, a `PUT` è idempotente (chiamarlo due volte ha lo stesso effetto di una volta), ma a `POST` generalmente non lo è. (Vedi [sez. 05](#s5).)

### 3. Restituisce codici di stato significativi

Appoggiati a quelli standard invece di tornare sempre `200` con un errore sepolto nel corpo: `200`/`201`/`204` per il successo, `400` per input errati, `401`/`403` per problemi di autenticazione, `404` quando manca qualcosa, `409` per i conflitti, `422` per errori di convalida, `500` per errori del server. Ciò consente ai client di gestire i risultati a livello di codice. (Vedi [sez. 08](#s8).)

### 4. Rimani senza stato

Ogni richiesta dovrebbe contenere tutto ciò di cui il server ha bisogno per elaborarla, token di autenticazione, parametri, senza fare affidamento sulla memoria della sessione lato server delle chiamate precedenti. Questo è ciò che ti consente di scalare orizzontalmente: qualsiasi server può gestire qualsiasi richiesta. È anche uno dei vincoli fondamentali di Fielding ([sec 02](#s2)).

### 5. Sii coerente

Scegli le convenzioni e applicale ovunque: stile di denominazione (`snake_case` contro `camelCase` in JSON), formati di data (ISO 8601), come vengono formati gli errori, come funziona l'impaginazione. La prevedibilità vale più dell'intelligenza, uno sviluppatore che apprende un endpoint dovrebbe essere in grado di indovinare gli altri. (Vedi [sez. 10](#s10).)

### 6. Versione della tua API

Le modifiche sostanziali sono inevitabili, quindi pianificale fin dall'inizio, in genere tramite il percorso URL (`/v1/users`) o un'intestazione. Ciò ti consente di evolvere senza interrompere i clienti esistenti. ([sez. 11](#s11) approfondisce quando eseguire il bumping della versione.)

### 7. Gestisci le raccolte con garbo

Gli elenchi di grandi dimensioni richiedono l'impaginazione (`?page=2&limit=50` o basato sul cursore), oltre al filtraggio (`?status=active`), ordinamento (`?sort=-created_at`) e spesso la selezione del campo. Restituire diecimila record in una risposta non serve a nessuno. ([sez.07](#s7) ha lo schema completo.)

### 8. Progettare errori chiari e strutturati

Una buona risposta all'errore indica al client cosa è andato storto e, idealmente, come risolverlo, un codice leggibile dalla macchina, un messaggio leggibile dall'uomo e spesso quale campo ha fallito. La coerenza qui conta tanto quanto la coerenza nelle risposte di successo. ([sez. 12](#s12) mostra un involucro di cemento.)

<Callout type="info" title="La linea passante">
Un'API è un contratto pensato per essere utilizzato da altri sviluppatori, quindi prevedibilità, conformità agli standard e comunicazione chiara superano ogni volta la novità. Definisci questi otto e un consumatore può integrare un endpoint, quindi _indovinare_ correttamente il resto.
</Callout>

// A REST API in Go (standard library) for managing "tasks".
//
// This version applies three REST-design rules from the course notes:
//
//	sec 3  URL versioning         -> every route lives under /v1
//	sec 6  List query parameters  -> pagination + sorting + filtering
//	sec 8  Consistent naming      -> JSON fields use camelCase, with sane defaults
//
// Requires Go 1.22+ for the method-aware router.
//
//	Run:   go run ./RestAPI       (from the module root, where go.mod is)
//	Then:  curl "http://localhost:8080/v1/tasks?limit=5&sortBy=title&sortOrder=asc&done=false"

///- stateless HTTP server that exposes one resource (tasks) as a REST API:
package main

import (
	"encoding/json"
	"errors"
	"log"
	"math"
	"net/http"
	"sort"
	"strconv"
	"strings"
	"sync"
	"time"

// ---------- Model ----------

// Task is a single to-do item.
//
// sec 8 (consistent naming): every JSON field is camelCase, note `createdAt`,
// NOT `created_at`. The Go field names stay idiomatic PascalCase; only the
// json struct tags define the wire format the client sees.
type Task struct {
	ID        int       `json:"id"`
	Title     string    `json:"title"`
	Done      bool      `json:"done"`
	CreatedAt time.Time `json:"createdAt"`
}

// ---------- Store (unchanged: thread-safe in-memory map) ----------

var errNotFound = errors.New("task not found")

type store struct {
	mu     sync.RWMutex
	tasks  map[int]Task
	nextID int
}

func newStore() *store { return &store{tasks: make(map[int]Task), nextID: 1} }

func (s *store) list() []Task {
	s.mu.RLock()
	defer s.mu.RUnlock()
	out := make([]Task, 0, len(s.tasks)) // non-nil so an empty result encodes as [] not null
	for _, t := range s.tasks {
		out = append(out, t)
	}
	return out
}

func (s *store) get(id int) (Task, error) {
	s.mu.RLock()
	defer s.mu.RUnlock()
	t, ok := s.tasks[id]
	if !ok {
		return Task{}, errNotFound
	}
	return t, nil
}

func (s *store) create(title string, done bool) Task {
	s.mu.Lock()
	defer s.mu.Unlock()
	t := Task{ID: s.nextID, Title: title, Done: done, CreatedAt: time.Now()}
	s.tasks[t.ID] = t
	s.nextID++
	return t
}

func (s *store) update(id int, title string, done bool) (Task, error) {
	s.mu.Lock()
	defer s.mu.Unlock()
	t, ok := s.tasks[id]
	if !ok {
		return Task{}, errNotFound
	}
	t.Title, t.Done = title, done
	s.tasks[id] = t
	return t, nil
}

func (s *store) delete(id int) error {
	s.mu.Lock()
	defer s.mu.Unlock()
	if _, ok := s.tasks[id]; !ok {
		return errNotFound
	}
	delete(s.tasks, id)
	return nil
}

// ---------- HTTP helpers ----------

func writeJSON(w http.ResponseWriter, status int, v any) {
	w.Header().Set("Content-Type", "application/json")
	w.WriteHeader(status)
	if v != nil {
		_ = json.NewEncoder(w).Encode(v)
	}
}

func writeError(w http.ResponseWriter, status int, msg string) {
	writeJSON(w, status, map[string]string{"error": msg})
}

func idFromPath(r *http.Request) (int, error) { return strconv.Atoi(r.PathValue("id")) }

// ---------- List endpoint: pagination, sorting, filtering (sec 6) ----------

// listResponse is the envelope returned by GET /v1/tasks. Wrapping the array
// in an object gives us a place to attach pagination metadata beside the data.
// sec 8: these fields are camelCase too.
type listResponse struct {
	Data       []Task     `json:"data"`
	Pagination pagination `json:"pagination"`
}

type pagination struct {
	Page       int `json:"page"`
	Limit      int `json:"limit"`
	TotalItems int `json:"totalItems"`
	TotalPages int `json:"totalPages"`
}

// sortableFields is an allowlist, clients may only sort by these, never by an
// arbitrary field name they invent.
var sortableFields = map[string]bool{"id": true, "title": true, "createdAt": true}

func (s *server) handleList(w http.ResponseWriter, r *http.Request) {
	q := r.URL.Query()
	tasks := s.store.list()

	// --- Filtering (sec 6): narrow the set by matching query params. ---
	if raw := q.Get("done"); raw != "" {
		done, err := strconv.ParseBool(raw)
		if err != nil {
			writeError(w, http.StatusBadRequest, "query param 'done' must be true or false")
			return
		}
		filtered := make([]Task, 0)
		for _, t := range tasks {
			if t.Done == done {
				filtered = append(filtered, t)
			}
		}
		tasks = filtered
	}
	if title := strings.TrimSpace(q.Get("title")); title != "" {
		needle := strings.ToLower(title)
		filtered := make([]Task, 0)
		for _, t := range tasks {
			if strings.Contains(strings.ToLower(t.Title), needle) {
				filtered = append(filtered, t)
			}
		}
		tasks = filtered
	}

	// --- Sorting (sec 6) with sane defaults (sec 8: default = createdAt, descending). ---
	sortBy := q.Get("sortBy")
	if sortBy == "" {
		sortBy = "createdAt" // sane default
	}
	if !sortableFields[sortBy] {
		writeError(w, http.StatusBadRequest, "query param 'sortBy' must be one of: id, title, createdAt")
		return
	}
	sortOrder := q.Get("sortOrder")
	if sortOrder == "" {
		sortOrder = "desc" // sane default
	}
	if sortOrder != "asc" && sortOrder != "desc" {
		writeError(w, http.StatusBadRequest, "query param 'sortOrder' must be 'asc' or 'desc'")
		return
	}
	sort.Slice(tasks, func(i, j int) bool {
		var less bool
		switch sortBy {
		case "id":
			less = tasks[i].ID < tasks[j].ID
		case "title":
			less = strings.ToLower(tasks[i].Title) < strings.ToLower(tasks[j].Title)
		case "createdAt":
			less = tasks[i].CreatedAt.Before(tasks[j].CreatedAt)
		}
		if sortOrder == "desc" {
			return !less
		}
		return less
	})

	// --- Pagination (sec 6) with sane defaults (sec 8: default limit = 10). ---
	page, err := parsePositiveInt(q.Get("page"), 1)
	if err != nil {
		writeError(w, http.StatusBadRequest, "query param 'page' must be a positive integer")
		return
	}
	limit, err := parsePositiveInt(q.Get("limit"), 10)
	if err != nil {
		writeError(w, http.StatusBadRequest, "query param 'limit' must be a positive integer")
		return
	}
	if limit > 100 {
		limit = 100 // cap the page size so a client can't ask for everything at once
	}

	totalItems := len(tasks)
	totalPages := int(math.Ceil(float64(totalItems) / float64(limit)))

	// Slice out the requested page. A page past the end yields an EMPTY data
	// array, still 200 OK, never 404 (sec 7: an empty list is not "not found").
	start := (page - 1) * limit
	if start > totalItems {
		start = totalItems
	}
	end := start + limit
	if end > totalItems {
		end = totalItems
	}
	data := tasks[start:end]
	if data == nil {
		data = []Task{} // guarantee [] rather than null in the JSON
	}

	writeJSON(w, http.StatusOK, listResponse{
		Data: data,
		Pagination: pagination{
			Page:       page,
			Limit:      limit,
			TotalItems: totalItems,
			TotalPages: totalPages,
		},
	})
}

// parsePositiveInt returns def when raw is empty, otherwise the parsed value if
// it is a positive integer. Anything else (non-numeric, zero, negative) errors.
func parsePositiveInt(raw string, def int) (int, error) {
	if raw == "" {
		return def, nil
	}
	n, err := strconv.Atoi(raw)
	if err != nil || n < 1 {
		return 0, errors.New("invalid")
	}
	return n, nil
}

// ---------- Single-resource handlers (unchanged logic) ----------

type server struct{ store *store }

func (s *server) handleGet(w http.ResponseWriter, r *http.Request) {

		writeError(w, http.StatusBadRequest, "invalid id")

		writeError(w, http.StatusNotFound, "task not found")
		return
	}
	writeJSON(w, http.StatusOK, t)
}

func (s *server) handleCreate(w http.ResponseWriter, r *http.Request) {
	var body struct {
		Title string `json:"title"`
	}
	if err := json.NewDecoder(r.Body).Decode(&body); err != nil {
		writeError(w, http.StatusBadRequest, "invalid JSON body")
		return
	}
	if body.Title == "" {
		writeError(w, http.StatusBadRequest, "title is required")
		return
	}
	writeJSON(w, http.StatusCreated, s.store.create(body.Title, false))
}

func (s *server) handleUpdate(w http.ResponseWriter, r *http.Request) {
	id, err := idFromPath(r)
	if err != nil {
		writeError(w, http.StatusBadRequest, "invalid id")
		return
	}
	var body struct {
		Title string `json:"title"`
		Done  bool   `json:"done"`
	}
	if err := json.NewDecoder(r.Body).Decode(&body); err != nil {
		writeError(w, http.StatusBadRequest, "invalid JSON body")
		return
	}
	if body.Title == "" {
		writeError(w, http.StatusBadRequest, "title is required")
		return
	}
	t, err := s.store.update(id, body.Title, body.Done)
	if err != nil {
		writeError(w, http.StatusNotFound, "task not found")
		return
	}
	writeJSON(w, http.StatusOK, t)
}

func (s *server) handleDelete(w http.ResponseWriter, r *http.Request) {
	id, err := idFromPath(r)
	if err != nil {
		writeError(w, http.StatusBadRequest, "invalid id")
		return
	}
	if err := s.store.delete(id); err != nil {
		writeError(w, http.StatusNotFound, "task not found")
		return
	}
	w.WriteHeader(http.StatusNoContent)
}

### Cosa implementa il codice

Un file, tre livelli puliti, la stessa forma da cui nasce ogni vero servizio. Leggi dal basso verso l'alto, ogni strato conosce solo quello sottostante.

#### 1. Il modello

Una struttura unica, `Task`, con quattro campi. Il `json` I tag struct svolgono un lavoro discreto ma importante: i campi Go rimangono idiomatici PascalCase (`CreatedAt`) mentre il formato wire visualizzato dal client è camelCase (`createdAt`, mai `created_at`). I tag sono l'unico luogo in cui si trova la convenzione di denominazione ([sec 10](#s10)) viene applicato.

#### 2. Il negozio

Un in memoria `map[int]Task` custodito da a `sync.RWMutex`, il sostituto di un database. Legge (`list`, `get`) prendi una condivisione `RLock`; scrive (`create`, `update`, `delete`) prendi un'esclusiva `Lock`, quindi le richieste simultanee non possono danneggiare la mappa. Due dettagli contano per il contratto API: `list()` restituisce una porzione _diversa da zero_ quindi un risultato vuoto viene serializzato come `[]` piuttosto che `null`e una chiave mancante restituisce il file `errNotFound` sentinella che il livello HTTP si trasforma in un 404. Scambia questo livello con Postgres in seguito e non cambia un singolo gestore.

#### 3. Il livello HTTP

È qui che vive REST. Tre piccoli aiutanti mantengono ogni handler onesto: `writeJSON` imposta il tipo di contenuto, scrive lo stato e codifica il corpo in un unico posto; `writeError` avvolge un messaggio in modo coerente `{"error": ...}` busta; `idFromPath` tira `{id}` fuori dall'URL. I cinque gestori di risorse più il controllo dello stato eseguono ciascuno un lavoro e `routes()` li lega a `"METHOD /path"` modelli in movimento 1.22 `ServeMux`, il router stesso codifica quale verbo appartiene a quale URL, quindi i gestori non devono mai controllare manualmente il metodo.

### Una richiesta, dall'inizio alla fine

Prendi il comando esatto dalla parte superiore del file: `curl ".../v1/tasks?limit=5&sortBy=title&sortOrder=asc&done=false"`. Seguendo il diagramma C: il router corrisponde `GET /v1/tasks` e chiamate `handleList`. Crea un'istantanea di tutte e dodici le attività seminate, filtrandole fino alle dieci esistenti `done=false`, convalida `sortBy=title` e `sortOrder=asc` (passano entrambi), ordina A-&gt;Z, quindi prende la pagina 1 a 5 per pagina, le prime cinque righe. La risposta:

GET /v1/tasks?limit=5\&sortBy=titolo\&sortOrder=asc\&done=false 200 OK \{ "data": \[ \{ "id": 5, "title": "Add filtering", "done": false, "createdAt": "2026-07-02T..." \}, ... altri quattro, ordinati per titolo A-&gt;Z ... ], "impaginazione": \{ "page": 1, "limit": 5, "totalItems": 10, "totalPages": 2 \} \&#125;

Cambia una cosa e il ramo cambia con essa: `POST /v1/tasks` con un titolo restituisce **201** e la nuova riga; `GET /v1/tasks/999` restituisce **404**; `DELETE /v1/tasks/3` restituisce **204** senza corpo; e `?sortBy=colour` viene rifiutato immediatamente con **400** perché non è nell'elenco consentiti.

### Quali principi dimostra

Questo file tocca quasi tutte le regole del capitolo, ripetizione apposta, in modo da poter vedere la teoria approdare nel codice reale.

| Principio | Dove appare nel codice |
| ---------------------------------------- | ---------------------------------------------------------------------------------- |
| **Sostantivi risorsa, plurale** [sez 04](#s4) | `/v1/tasks` e `/v1/tasks/{id}`, una cosa, mai un verbo come `/getTask`            |
| **Metodi per intento** [sez 05](#s5)      | `GET` legge/ `POST` crea/ `PUT` sostituisce / `DELETE` rimuove, un gestore ciascuno |
| **Codici di stato onesto** [sez 08](#s8)    | `200` / `201` / `204` / `400` / `404`, vedere la tabella dei risultati |
| **assenza di stato** [sez 02](#s2)          | Nessuna sessione; il negozio è condiviso e ogni richiesta porta con sé tutto ciò di cui ha bisogno |
| **Coerenza** [sez 10](#s10)           | camelCase JSON, uno `{data, pagination}` busta, valori predefiniti sani ovunque |
| **Versionamento** [sez 11](#s11)            | Ogni risorsa viene instradata sotto `/v1`; `/healthz` lasciato deliberatamente senza versione |
| **Pagina/ordina/filtra** [sez 07](#s7)   | `?page ?limit ?sortBy ?sortOrder ?done ?title`, con `limit` limitato a 100 |
| **Errori strutturati** [sez 12](#s12)     | Un coerente `{"error": ...}` corpo su ogni fallimento |

<Callout type="info" title="Piccoli tocchi che vale la pena rubare">
La **lista consentita** è attiva `sortBy` significa che un cliente può ordinare solo in base ai campi approvati, mai a un nome di colonna arbitrario inventato. Tappatura `limit` a **100** impedisce a una richiesta di richiedere l'intera tabella. Ritorno `[]` invece di `null` salva ogni consumatore un controllo nullo. E `DELETE` risponde **204** senza corpo, perché non è rimasto nulla di significativo da inviare.
</Callout>

<Callout type="info" title="Ciò che è stato intenzionalmente tralasciato">
Questo è uno scheletro didattico, quindi alcuni problemi di produzione sono deliberatamente assenti: **persistenza** (scambia la mappa con un database reale dietro la stessa interfaccia del negozio), **autenticazione**, un percorso **PATCH** per aggiornamenti parziali (solo `PUT`/full-replace is here), and the richer **RFC 9457** error envelope from [sec 12](#s12). Ognuno di essi è un passo successivo naturale e nessuno di essi cambia la forma che vedi qui.
</Callout>
