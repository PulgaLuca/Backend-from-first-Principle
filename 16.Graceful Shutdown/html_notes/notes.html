Grazioso
Spegnimento

Insegnare le buone maniere al tuo backend, come finire il lavoro in corso, ripulirlo e chiudere educatamente la porta invece di sbatterla.

01 / MOTIVAZIONE

Lo scenario

Immaginiamo uno scenario molto realistico. Sei nel bel mezzo dell'elaborazione a transazione di pagamento critica e all'improvviso il tuo server deve essere riavviato per una distribuzione. Qualcuno ha inviato qualcosa all'ambiente di produzione e il tuo server deve distribuirsi.

La distribuzione senza tempi di inattività non elimina il problema

Naturalmente, abbiamo tecniche come distribuzione senza tempi di inattività ciò garantisce che il nostro server esistente non si interrompa prima che il nostro nuovo server (il server con il nostro nuovo codice) si attivi e sia pronto a ricevere traffico. Quei meccanismi ci sono.

Ma ecco il problema: a un certo punto, quando il nostro nuovo server sarà pronto per andare online e a ricevere traffico, il nostro vecchio server deve essere spento. Deve smettere di ricevere traffico e la transizione avverrà al nuovo server. Stiamo parlando di quel momento critico in cui ti trovi nel bel mezzo di una transazione.

La questione dei pagamenti nell’e-commerce

Supponiamo che tu stia effettuando una transazione di e-commerce, acquistando qualcosa da Amazon o Flipkart e che il server Amazon/Flipkart debba essere riavviato per una distribuzione. La domanda diventa:

1. Cosa succede esattamente a quel pagamento? Si perde nel mondo digitale?
2. Il cliente (tu) ottiene addebitato due volte a causa di una sorta di condizione di gara?

Questi sono scenari a cui devi pensare come ingegnere di backend.

Questo non è un problema nuovo. Esiste dall'inizio dei server e dei backend. E ovviamente abbiamo già una soluzione, si chiama quella soluzione spegnimento grazioso, ed è esattamente come suona il nome: vogliamo fermare il nostro server con grazia. Non vogliamo fermarci bruscamente o all'improvviso. Questa è l'idea.

Perché lo spegnimento graduale è importante

Preoccuparsi dell'arresto regolare offre alla tua applicazione un'esperienza utente molto positiva ed evita problemi come corruzione dei dati. Se sei nel mezzo di un'operazione di pagamento, ti consente di evitare:

- Doppio addebito al cliente
- La transazione viene persa
- Dovere elaborare i rimborsi per addebiti non riusciti/duplicati

02/DEFINIZIONE

Cos'è lo spegnimento grazioso?

Vogliamo insegnare al nostro backend le buone maniere, non possiamo semplicemente sbattere la porta quando è il momento di andarsene.

Se semplifichiamo eccessivamente cosa significa "arresto regolare" per il nostro server, possiamo sostanzialmente dire che vogliamo insegnare al nostro server, insegnare al nostro backend, buone maniere. Non può interrompersi bruscamente quando si trova nel mezzo di una transizione verso una nuova distribuzione. Deve eseguire alcuni tipi di passaggi.

L'analogia delle "buone maniere".

Pensalo come se avessi degli ospiti. Quando sono le 21:00 ed è ora di andare a dormire, non puoi semplicemente spingere i tuoi ospiti fuori dalla porta e sbattergli la porta in faccia. Ci sono dei passaggi che devi eseguire. Allo stesso modo, il tuo backend educatamente:

  • Termina le conversazioni in corso: completa qualunque cosa stia attualmente facendo
  • Saluta tutti gli ospiti: chiude correttamente le interazioni esistenti
  • Si pulisce da solo: riordina le risorse che stava utilizzando
  • Poi finalmente chiude la porta: solo allora esce effettivamente

Questa è l'arte e la scienza di rendere le tue applicazioni backend quanto più educate ed efficienti possibile. Il resto di questo capitolo getta le basi: perché lo facciamo, i concetti circostanti e come viene effettivamente implementato.

03 / FONDAZIONI

Gestione del ciclo di vita del processo

Il primo concetto da capire. Il tuo backend è un'applicazione che funziona come a processo in una specie di server, in una specie di computer. Questo è importante: tutto ciò che viene eseguito in un sistema operativo viene eseguito come un processo.

Se hai familiarità con i concetti del sistema operativo, questo avrà senso. In caso contrario, non è un grosso problema, impara semplicemente il termine: processo. Qualunque cosa esegui, viene eseguita all'interno di un processo.

Ogni processo ha un ciclo di vita

Come tutti gli esseri viventi, ogni processo ha un ciclo di vita, quando inizia, come inizia, quando finisce e come finisce. In un certo senso:

Fig 1.1: Le tre fasi del ciclo di vita di un processo: nato -> vissuto -> muore

Lo sono nato quando il processo inizia, loro vivere mentre il processo è in esecuzione, e loro morire quando il processo è terminato. Tutta questa faccenda è chiamata il ciclo di vita di un processo. Comprenderlo è essenziale perché è strettamente connesso al modo in cui viene implementato lo spegnimento graduale.

Il sistema operativo non si limita a staccare la spina

Quando il tuo sistema operativo decide che è ora che l'applicazione smetta di funzionare, lo fa no basta staccare la spina o interrompere il processo. Ne consegue un protocollo di comunicazione stabilito: come comunicare con il processo per dire "è ora che ti fermi, seguiremo questi passaggi e poi lo fermeremo".

Puoi immaginarlo come una conversazione tra il tuo sistema operativo e la tua applicazione (che è in esecuzione all'interno di un processo nel tuo sistema operativo):

La conversazione (semplificata)

Sistema operativo: "Ehi, è ora che ti fermi."
Applicazione: "Va bene, dammi qualche secondo (realisticamente), poi mi fermerò, oppure puoi fermarmi tu."

Naturalmente questa conversazione non avviene tramite testo, stiamo parlando di programmi che non capiscono il testo. L'intera comunicazione avviene attraverso un concetto chiamato segnali.

04 / SEGNALI

Segnali e comunicazione tra processi

I segnali sono un concetto importante in Sistemi operativi Unix. Quando diciamo Unix intendiamo tutti i sistemi operativi Linux (Arch, Ubuntu, ecc.) e anche i Mac, i Mac hanno avuto origine da un core Unix, un kernel Unix.

Perché Linux è importante per i server

Principalmente quando parliamo di server, intendiamo solo Linux, perché il 99% delle volte, ogni volta che distribuisci la tua applicazione a un provider cloud, seleziona un sistema operativo Linux e distribuisce lì la tua applicazione. Non vedrai mai Windows tranne che per alcuni casi d'uso specializzati come Windows Server. Per l'implementazione dei server utilizziamo prevalentemente sistemi operativi basati su Linux.

I segnali vengono utilizzati per IPC

I sistemi operativi Unix hanno questo concetto chiamato segnali, che viene utilizzato per IPC (comunicazione tra processi). In parole povere, IPC è una tecnica mediante la quale due processi possono comunicare tra loro utilizzando un protocollo stabilito (di cui non devi preoccuparti delle parti interne).

Come funzionano i gestori

La tua applicazione viene eseguita all'interno di un processo e it registra alcuni gestori. Cosa intendiamo per gestori?

I gestori sono fondamentalmente codice che:

  • Aspetta e corre continuamente dietro le quinte
  • Sta aspettando un qualche tipo di comunicazione, una specie di segnale: dal sistema operativo
  • Rileva ogni volta che arrivano questi segnali e poi fa qualcosa (pulizia, richieste di finitura, ecc.)

Questi gestori essenzialmente dicono al tuo sistema operativo: "Quando vuoi che mi fermi, mandami questo messaggio specifico e lo gestirò in modo appropriato. Mi fermerò utilizzando protocolli e passaggi predefiniti." Non puoi semplicemente dire "stop", è un testo leggibile dall'uomo. Deve essere un segnale specifico.

Fig 2.1: Il sistema operativo invia un segnale; il gestore registrato dell'applicazione lo rileva ed esegue i passaggi di arresto

I tre segnali

Il prefisso SIG in tutto ciò significa semplicemente segnale. La seconda parte è il comando vero e proprio. Ci sono tre segnali a cui teniamo:

4.1: SIGTERM (Terminare)

SIG significa segnale, TERM significa terminare. SIGTERM è un modo educato affinché il tuo sistema operativo chieda all'applicazione di spegnersi. Non è un modo estremo, è solo una spintarella.

L'analogia del colpo di spalla

Immagina di stare in piedi e qualcuno arriva da dietro e ti colpisce delicatamente la spalla, "ehi, scusami, potresti finire e andartene?" Questo è SIGTERM. È una richiesta molto gentile e, per questo motivo, il tuo backend ha un file opportunità di completare ciò che sta già facendo. Non è necessario che parta in quel momento esatto, ha una finestra di pochi secondi.

Cosa potrebbe fare il tuo backend quando riceve SIGTERM? Dato che stiamo parlando di un backend HTTP, potrebbe esserlo elaborazione delle richieste: questa è la cosa principale che fa il tuo backend. Il tuo client (front-end, app Web, estensione Chrome, qualunque cosa) invia richieste HTTP e il tuo back-end le elabora e restituisce risposte.

In un momento casuale, il tuo backend potrebbe elaborare 10-12 richieste o, se la tua applicazione è abbastanza grande, centinaia o addirittura 500-600 richieste contemporaneamente. Quando riceve un segnale SIGTERM, è il momento di eseguire questi tre passaggi:

Fig 2.2: I tre passaggi SIGTERM: completare le richieste -> ripulire -> esci

Chi utilizza SIGTERM?

SIGTERM è utilizzato principalmente da sistemi di distribuzione, gestori di processi o piattaforme di orchestrazione: praticamente qualsiasi sistema che hai stabilito per gestire il tuo processo:

  • Kubernetes: orchestrazione del contenitore
  • systemd: gestore dei servizi Linux
  • PM2: Gestore del processo Node.js

Questi sistemi e strumenti utilizzano SIGTERM per consentire alla tua applicazione di completare correttamente qualsiasi cosa stia facendo, ripulire e uscire con garbo.

4.2: SIGINT (interruzione)

SIG significa segnale, INT significa interrompere. Il caso d'uso più famoso di questo segnale, che quasi sicuramente hai utilizzato come sviluppatore, è CTRL+C.

Se hai lavorato con applicazioni da riga di comando o basate su terminale, hai utilizzato questo, alcuni processi o attività sono in esecuzione e se desideri chiuderli bruscamente, premi Ctrl + C e quel processo viene immediatamente interrotto.

Demo dal vivo dalla conferenza

Nella conferenza, un backend basato su Go era in esecuzione localmente, pronto ad accettare richieste. Premendo Ctrl + C sulla tastiera registrato: "è stato ricevuto un segnale e il tipo di segnale è un segnale di interruzione." Poiché è stato implementato lo spegnimento graduale, l'app ha registrato ogni passaggio mentre si spegneva, anziché morire all'istante.

SIGINT richiede a all'utente/sviluppatore di premere un tasto (Ctrl + C utilizzando una tastiera). Quindi viene utilizzato principalmente negli ambienti di sviluppo ed è anche chiamato a arresto avviato dall'utente. Nella comunicazione da processo a processo, SIGINT normalmente non viene utilizzato, poiché richiede la pressione di un tasto.

Gestire SIGINT allo stesso modo di SIGTERM

In quasi tutti i casi, vuoi gestire SIGINT the allo stesso modo ti occupi di SIGTERM. Se ci pensi, ha senso:

SegnaleTipicamente avviato daContesto di esempio
SIGINTUn essere umano (pressione di un tasto)Lo sviluppatore preme Ctrl+C localmente per arrestare il server di sviluppo
SIGTERMUn programmaPM2 su un'istanza AWS EC2 che segnala l'arresto del backend distribuito

Non importa se il tuo backend è in esecuzione in un ambiente di sviluppo e lo interrompi con Ctrl + C, anziché in esecuzione all'interno di un'istanza AWS EC2 gestita da PM2 (un gestore di processi) che invia un SIGTERM. In entrambi i casi, il l'intenzione è la stessa: vogliamo chiudere. E vogliamo chiudere in modo pulito e aggraziato. Ciò che conta è l’intenzione, non se un essere umano o un programma l’ha avviata.

4.3: SIGKILL (L'opzione nucleare)

SIG significa segnale, KILL è il comando vero e proprio, ed è esattamente come sembra. Lo vogliamo uccidi immediatamente l'applicazione.

SIGKILL non può essere catturato o ignorato

La cosa interessante (e pericolosa) di SIGKILL è che non può essere catturato e non può essere ignorato:

Non può essere catturato: l'applicazione non può registrare un gestore che esegue la pulizia quando riceve SIGKILL. All'applicazione semplicemente non viene concessa la capacità/autorizzazione per rilevarlo.

Non può essere ignorato: Non puoi dire "poiché non sono riuscito a rilevarlo, lo ignorerò e non mi fermerò". Nemmeno questo accade.

Se alla tua applicazione viene inviato un SIGKILL, non sarà in grado di rilevarlo e dovrà interrompersi in quell'esatto momento. Non succede nient'altro, tutto si ferma. Ecco perché si chiama segnale di uccisione.

L'analogia del staccare la spina

Immagina la differenza tra due modi per spegnere il computer:

Grazioso (SIGTERM/SIGINT): Facendo clic sull'icona del sistema -> facendo clic su "Arresto" -> il sistema operativo chiude correttamente le app.

SIGKILL: Andando direttamente alla presa di corrente e tirandolo. Il tuo computer semplicemente muore. Nessuna pulizia, nessun addio.

Perché questo rende importante lo spegnimento regolare

Ecco la catena critica di conseguenze. Il segnali educati sono SIGTERM e SIGINT, ti consentono di finire qualunque cosa tu stia facendo, ripulire e uscire con grazia. Se tu non rispettare i segnali educati, poi alla fine tu volontà ricevere un SIGKILL. Dovrai fermarti e non avrai nemmeno l'opportunità di ripulirti.

Fig 2.3: Ignora i segnali educati e il sistema operativo passa a SIGKILL, il che non ti dà alcuna possibilità di ripulire

Questo è il motivo principale per cui lo spegnimento graduale è un concetto importante: è la tua occasione per gestire lo spegnimento prima l’OS ricorre all’opzione nucleare.

05 / PASSO UNO

Connessione Drenante

Ora approfondiamo le due cose importanti che accadono durante uno spegnimento regolare: completare le richieste esistenti (questa sezione) e ripulire le risorse (sezione successiva). La prima parte importante è fermare le richieste al volo.

Cosa sono le richieste al volo?

Il tuo server HTTP elabora più richieste contemporaneamente. Quando è il momento di fermare il tuo server, è possibile che il tuo backend stia già elaborando un numero di richieste, 10, 12, centinaia o migliaia a seconda della scala. Quelle richieste già in elaborazione in quel momento sono le richieste al volo (in volo)..

L'analogia del ristorante

Immagina di essere andato in un ristorante con gli amici e che il ristorante debba chiudere (sono le 22:30-23 o per qualche altro motivo). Che succede? I proprietari non può spegni tutte le luci e buttati fuori. Invece:

Fig 3.1: Mappa di chiusura del ristorante direttamente sul collegamento di scarico
  • Smetti di consentire nuovi clienti: Qualcuno alla reception/al cancello smette di far entrare nuove persone. Non vuoi nuovi clienti a cui dovresti dire di no.
  • Annuncio ai clienti esistenti: Dite a tutti quelli che stanno già mangiando: "È ora di chiudere, avete 15-20 minuti per finire il pasto. Prendetevi il vostro tempo". 15-20 minuti sono più che sufficienti.
  • Paga le bollette e vattene: Finiscono, pagano i conti (e le mance!) e lasciano il ristorante.

La stessa idea per il tuo backend

Chiamiamo questo processo drenaggio del collegamento. Quando la tua applicazione riceve un segnale di arresto (SIGTERM da un processo o SIGINT da Ctrl+C di uno sviluppatore), la prima cosa che deve fare è smettere di accettare nuove connessioni: esattamente come impedire l'ingresso di nuovi clienti. Ciò impedisce che la situazione diventi più complicata e difficile da gestire. Quindi lascia che le connessioni esistenti finiscano il prima possibile.

Connessione Drenante Per Architettura

L'implementazione differisce a seconda dell'architettura dell'applicazione, ma l'idea di alto livello è sempre lo stesso processo in tre fasi: smetti di accettare nuovi -> termina esistente -> chiudi connessione.

ArchitetturaCosa significa "drenante".
Back-end HTTPSmettere di accettare nuove richieste HTTP da qualsiasi client; consentire il completamento delle richieste in volo
Database (anche un backend!)Completare tutte le query/transazioni esistenti; interrompere l'esecuzione di nuove query prima di chiudere la connessione
Connessioni WebSocketPer prima cosa avvisa i client che si sta chiudendo, quindi chiudi il socket, non chiuderlo mai bruscamente
Anche un database è un backend

Come discusso nei capitoli precedenti, un database è anche un backend, può essere immaginato come un backend. Non nel senso HTTP, ma è comunque un'applicazione che viene eseguita come un processo e segue gli stessi principi di chiusura graduale: terminare le transazioni esistenti, smettere di accettarne di nuove, quindi chiudere.

5.1: Il compromesso del timeout

La sfida con il drenaggio della connessione è la tempistica. Vuoi dare alle connessioni esistenti abbastanza tempo per completare il loro lavoro, ma non puoi aspettare tutto il tempo necessario. Ci deve essere un limite.

La maggior parte dei sistemi di produzione implementano a meccanismo di timeout: comunemente 30 secondi (a volte 60). Questa è la durata massima di attesa del sistema. Dopodiché, si ferma. Nella maggior parte dei casi, se non accetti nuove richieste, 30 secondi sono più che sufficienti per completare tutte le richieste esistenti. Ma se alcune operazioni di blocco non possono terminare all'interno della finestra, lo sarai fermato con forza: questo è il piano di riserva. Non puoi lasciare che il tuo backend impieghi tutto il tempo che vuole; il timeout è il limite rigido.

La considerazione del design / Quanto tempo dovresti aspettare?

Troppo corto -> rischi di interrompere le effettive operazioni legittime (un pagamento reale durante il volo viene interrotto).

Troppo lungo -> l'intero processo di arresto diventa lento, il che alla fine influisce sulla velocità di distribuzione e sulla reattività del sistema.

Non esiste una regola ferrea. Il timeout corretto dipende dall'applicazione durata tipica della richiesta e il tuo requisiti operativi. Per un backend tradizionale/normale, 30 secondi sono più che sufficienti. Per i WebSocket o le architetture più complicate, devi comprendere il tuo sistema e scegliere di conseguenza.

Coordinamento con bilanciatori di carico e rilevamento dei servizi

Lo svuotamento della connessione richiede anche il coordinamento tra i tuoi bilanciatori di carico e sistemi di rilevamento dei servizi. Deve funzionare con i tuoi sistemi di controllo dello stato e con la registrazione/annullamento della registrazione con il rilevamento del servizio.

Questo è leggermente avanzato: scoperta del servizio significa che se hai distribuito una serie di applicazioni (il tuo backend, il tuo database, la tua istanza Elasticsearch), l'individuazione dei servizi è il meccanismo responsabile del modo in cui si trovano, si connettono e comunicano tra loro dopo la distribuzione. Durante l'arresto, l'istanza deve annullare la registrazione in modo che il sistema di bilanciamento del carico interrompa l'instradamento di nuovo traffico verso di essa.

06 / FASE DUE

Pulizia delle risorse

Il secondo passo importante. Pensa a lavorare alla scrivania: quando è il momento di uscire di casa o di andare a dormire, fai prima un po' di pulizia. Se hai preso il caffè, porti la tazza nel lavandino; gestisci i tuoi cavi, ecc. Tutti noi abbiamo piccoli compiti di pulizia prima di lasciare le nostre scrivanie. Lo stesso vale per il tuo backend.

Cosa conta come "risorsa"?

Quando diciamo risorse, intendiamo cose che l'applicazione ha acquisito durante la sua esecuzione e che ora deve lasciare andare:

  • Maniglie dei file
  • Connessioni di rete
  • Connessioni al database
  • File temporanei
  • Cache
  • Eventuali altre risorse di sistema

Maniglie dei file

Quando il tuo backend era in esecuzione e tentava di accedere a una particolare posizione nel file system, il modo in cui funziona è: invii un segnale al tuo sistema operativo e questo ti fornisce un maniglia a quel file. Esiste un protocollo per il modo in cui un processo accede al file system sottostante, ma ad alto livello ottieni un handle che puoi deve lasciare andare/ripulire ad un certo punto.

Perché le maniglie non chiuse sono pericolose

Se non ripulisci l'handle di un file, quell'handle continua a funzionare e acquisirai sempre più memoria, il che significa che continuerai a consumare il tuo RAM (memoria ad accesso casuale), e ad un certo punto ne rimarrai senza. Anche i sistemi operativi limitare il numero di handle di file (e connessioni di rete) un singolo processo può essere aperto contemporaneamente, quindi la loro perdita alla fine interrompe la tua app.

Connessioni di rete (la pulizia più comune)

Il tipo più comune di pulizia delle risorse è la pulizia delle connessioni di rete. Il tuo sistema operativo è il mediatore: tutte le richieste provenienti da Internet passano attraverso il tuo sistema operativo prima di raggiungere la tua applicazione. Il sistema operativo è il vero driver che riceve tutte le richieste dalla tua scheda di rete e te le trasmette, quindi ha piena conoscenza di tutte le tue connessioni di rete.

Fig 4.1: Tutto il traffico di rete passa attraverso il sistema operativo prima di raggiungere l'applicazione

Proprio come gli handle di file, se non rinunci a una connessione di rete dopo averla gestita, alla fine rimarrai senza memoria o dovrai affrontare problemi di prestazioni, perché il sistema operativo limita il numero di connessioni che un processo può tenere aperte.

Connessioni al database: commit o rollback

Questa è la parte direttamente collegata al nostro scenario di pagamento fin dall'inizio. Prima che l'applicazione/il processo backend si spenga, le transazioni del database con cui aveva a che fare devono essere entrambe impegnato o rollback esplicito dalla tua candidatura.

Cosa succede se non lo fai

Se non esegui il commit o il rollback delle transazioni aperte, potrebbero entrare in un file stato incoerente, che può portare a:

- Deadlock
- Corruzione dei dati
- Tutti i tipi di altri problemi

Questo è esattamente il problema del doppio addebito/mancato pagamento dello scenario di apertura, risolto dalla gestione esplicita delle transazioni durante la chiusura.

Ripulire in ordine inverso di acquisizione

Una regola importante: quando si puliscono le risorse durante l'arresto regolare, è necessario pulirle nel file ordine inverso di come li hai acquisiti, Last In, First Out (LIFO), come una pila.

Fig 4.2: Acquisisci Redis -> DB -> HTTP, ma rilascia al contrario: HTTP -> DB -> Redis (LIFO)

Ad esempio, supponiamo di aver stabilito una connessione Redis, quindi una connessione DB, quindi avviato il server HTTP. Quando rinunci alle risorse, procedi al contrario. Perché? Per evitare situazioni in cui stai ripulendo una risorsa o un'operazione che dipende da un'operazione precedente. L'eliminazione al contrario garantisce che le dipendenze siano ancora vive quando le cose che ne hanno bisogno vengono chiuse.

07/CODICE

Esempi di codici

In genere evitiamo di esaminare il codice in questa serie, ma un esempio pratico aiuta a evitare una comprensione vuota. Non è necessario capire ogni riga, basta seguire la narrazione. In pratica, la maggior parte dei framework (Node.js, Go, Rust, Python) forniscono questo codice pronto per il copia-incolla; ciò che conta è capire cosa succede e perché.

7.1: Spegnimento regolare in Go

Ciò rispecchia la demo live della lezione: registrare un gestore in attesa di segnali, quindi, al ricevimento, eseguire la funzione di spegnimento che chiude il server HTTP, quindi il database, quindi il server dei processi in background supportato da Redis, in ordine inverso rispetto all'acquisizione.

main.go/Go/net/http + signal.NotifyContext 
package main

import (
    "context"
    "errors"
    "log"
    "net/http"
    "os"
    "os/signal"
    "syscall"
    "time"
)

func main() {
    // --- Startup phase: acquire resources in order ---
    db := connectDatabase()           // 1. acquire DB (TCP pool)
    jobs := startBackgroundJobs()     // 2. acquire Redis-backed worker

    srv := &http.Server{Addr: ":8080", Handler: router()}

    // Register a handler that waits for SIGINT (Ctrl+C) or SIGTERM (PM2/k8s).
    // We handle BOTH the same way, the intention is identical: shut down.
    ctx, stop := signal.NotifyContext(context.Background(),
        os.Interrupt, syscall.SIGTERM)
    defer stop()

    // Run the server in a goroutine so main can wait for the signal.
    go func() {
        log.Println("server started, ready to accept requests")
        if err := srv.ListenAndServe(); err != nil &&
            !errors.Is(err, http.ErrServerClosed) {
            log.Fatalf("listen error: %v", err)
        }
    }()

    // Block here until a signal arrives (the "living" phase).
    <-ctx.Done()
    log.Println("signal received, starting graceful shutdown")

    // Hard limit: give in-flight work up to 30 seconds, then force stop.
    shutdownCtx, cancel := context.WithTimeout(
        context.Background(), 30*time.Second)
    defer cancel()

    gracefulShutdown(shutdownCtx, srv, db, jobs)
    log.Println("server exited properly")
}

// gracefulShutdown releases resources in REVERSE order of acquisition.
// Acquired: DB -> jobs -> HTTP server. Released: HTTP -> jobs -> DB.
func gracefulShutdown(
    ctx context.Context,
    srv *http.Server,
    db *Database,
    jobs *JobServer,
) {
    // 1. CONNECTION DRAINING: srv.Shutdown stops accepting NEW
    //    connections and waits for in-flight requests to finish
    //    (or until the 30s ctx deadline forces it).
    log.Println("draining HTTP connections...")
    if err := srv.Shutdown(ctx); err != nil {
        log.Printf("forced HTTP shutdown: %v", err)
    }

    // 2. Stop the background job server (closes Redis connections,
    //    waits for workers to finish current jobs).
    log.Println("stopping background job server...")
    jobs.Shutdown()

    // 3. Close the database LAST, finish/commit open transactions,
    //    then close all pooled TCP connections one by one.
    log.Println("closing database connection...")
    if err := db.Close(); err != nil {
        log.Printf("db close error: %v", err)
    }
}

7.2: Spegnimento ordinato in Python

Gli stessi concetti in Python usando il file signal modulo: registra i gestori per SIGINT e SIGTERM, drena il lavoro in volo, quindi rilascia le risorse al contrario.

server.py/Python/segnale + asyncio 
import asyncio
import signal
import logging

logging.basicConfig(level=logging.INFO)
log = logging.getLogger("app")

SHUTDOWN_TIMEOUT = 30  # hard limit in seconds


class Application:
    def __init__(self):
        self._shutdown = asyncio.Event()

    async def startup(self):
        # Acquire resources IN ORDER
        self.redis = await connect_redis()       # 1
        self.db = await connect_database()      # 2
        self.server = await start_http_server()  # 3
        log.info("server started, ready to accept requests")

    def install_signal_handlers(self):
        # Handle SIGINT (Ctrl+C, dev) and SIGTERM (PM2/k8s, prod)
        # the SAME way, both mean "shut down gracefully".
        loop = asyncio.get_running_loop()
        for sig in (signal.SIGINT, signal.SIGTERM):
            loop.add_signal_handler(sig, self._on_signal, sig)

    def _on_signal(self, sig):
        # NOTE: SIGKILL can never reach here, it cannot be
        # caught or ignored. Only the polite signals arrive.
        log.info(f"signal received: {sig.name}, shutting down")
        self._shutdown.set()

    async def graceful_shutdown(self):
        # 1. CONNECTION DRAINING: stop accepting new requests,
        #    let in-flight requests finish within the timeout.
        log.info("draining HTTP connections...")
        self.server.stop_accepting_new()
        try:
            await asyncio.wait_for(
                self.server.wait_for_inflight(),
                timeout=SHUTDOWN_TIMEOUT,
            )
        except asyncio.TimeoutError:
            log.warning("timeout exceeded, forcing shutdown")

        # 2 & 3. Release resources in REVERSE order of acquisition.
        #    Acquired redis -> db -> server; release server -> db -> redis.
        log.info("committing/rolling back open transactions...")
        await self.db.close()     # commit or rollback, then close pool
        log.info("closing redis connection...")
        await self.redis.close()
        log.info("server exited properly")


async def main():
    app = Application()
    await app.startup()
    app.install_signal_handlers()
    await app._shutdown.wait()   # the "living" phase, block until signal
    await app.graceful_shutdown()


if __name__ == "__main__":
    asyncio.run(main())
