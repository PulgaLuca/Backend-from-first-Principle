Instradamento, il dove
di ogni richiesta.

I metodi HTTP descrivono il file cosa di una richiesta, il tuo intento. Il routing descrive il dove: a quale risorsa sul server è rivolto il tuo intento. Questo manuale tratta il routing end-to-end, i percorsi statici e dinamici, i parametri di percorso e di query, la nidificazione, il controllo delle versioni e tutti gli elementi generali, con router funzionanti in Go e Python.

Parte I, Il modelloL'idea centrale
01

Che cos'è il routing

Ogni richiesta porta con sé due cose raggruppate insieme. Il Metodo HTTP risposte "cosa voglio fare?", recuperare, aggiungere, aggiornare o eliminare dati. Questo è tuo intento, la tua azione. Il percorso risposte "dove voglio farlo?", su quale risorsa, a quale indirizzo sul server, desideri eseguire l'azione.

Devi dirlo al server dove andare. Invia un GET richiesta (intento: recuperare) alla rotta /users (l'indirizzo) e il server risponde con una serie di utenti. Il routing è il macchinario che prende il cosa e il dove, li associa a un particolare gestore e consente a tale gestore di eseguire la logica applicativa e restituire i dati.

Instradamento, definizione

Il percorso è mappatura dei percorsi URL (più il metodo HTTP) alla logica lato server: un gestore che esegue la logica applicativa, le operazioni del database e qualsiasi altra cosa necessaria, quindi restituisce una risposta. Questo è tutto.

Le parole usate in questo manuale

  • Intento/azione: cosa vuole fare la richiesta, espressa dal metodo HTTP (recupera, aggiungi, aggiorna, elimina).
  • Risorsa: la "cosa" su cui agisce la richiesta, solitamente un sostantivo nel percorso come books o users. (Le risorse vengono studiate correttamente nelle API REST; qui le trattiamo semplicemente come destinazione del percorso.)
  • Itinerario/percorso dell'instradamento/percorso URL: la parte dell'indirizzo che dice dove sul server che stai visitando, ad es. /api/books.
  • Gestore: l'insieme di istruzioni che il server esegue quando una richiesta corrisponde a un percorso; possiede la logica per quell'endpoint.
02

Metodo + Percorso -> Gestore

Questo è il cuore del routing. Il server prende il metodo e il percorso e tratta i due insieme come a chiave unica che corrisponde a un gestore. Controlla prima il metodo, poi il percorso, li concatena e forma un percorso di routing univoco.

Consideriamo due richieste allo stesso indirizzo. GET /api/books va a prendere i libri; POST /api/books ne crea uno. Il percorso è identico, ma il metodo è diverso, quindi le chiavi sono diverse e vengono indirizzate a gestori diversi. I metodi distinguono tra due percorsi altrimenti identici e le chiavi non entrano mai in conflitto.

Il metodo è il "cosa" (breve)

Il routing deve solo conoscere il metodo come l'altra metà della chiave. I verbi comuni e il loro intento: GET prendere / POST aggiungi/crea/ PUT / PATCH aggiornare / DELETE rimuovere. Lo studio approfondito dei metodi appartiene all'argomento HTTP; qui si accoppiano semplicemente con un percorso per formare la chiave.

03

Percorsi statici

A percorso statico è un percorso fisso con nessun parametro variabile al suo interno. /api/books è statico: la stringa rimane coerente, è una costante. Utilizzi sempre la stessa stringa quando effettui la richiesta, non cambia nulla e restituisce sempre lo stesso gentile di risposta. Questo è esattamente il motivo per cui si chiama "statico".

Percorso statico

Una stringa di percorso costante senza segmenti dinamici, ad es. /api/books. I primi due esempi dalla fonte, GET e POST su /api/books, sono entrambi percorsi statici.

La corrispondenza di una route statica è un confronto letterale di stringhe. La maggior parte delle API inizia qui: un endpoint che elenca una raccolta e uno che crea un elemento, entrambi sullo stesso percorso costante.

04

Percorsi dinamici e parametri di percorso

A percorso dinamico ha un parametro variabile all'interno del percorso, quindi un modello può servire molte risorse specifiche. GET /api/users/123 recupera i dettagli di uno utente, il 123 è l'ID dell'utente, che il server estrae dal percorso per svolgere il proprio lavoro (recuperare l'utente dal database e restituirlo).

Sul lato server, la definizione del percorso per questo appare come un metodo più un modello. Scritta, la parte corrispondente è qualcosa del tipo:

definizione del percorsomodello
r.get("/api/users/:id", handler)
        //          +--- ":id" = a dynamic parameter slot

La parte del metodo corrisponde GET; la parte del percorso corrisponde /api/users/ seguito da qualsiasi stringa. La convenzione del colon :id, afferma "questo segmento è dinamico; qui il cliente fornisce un valore". Troverai questo :name convenzione su Node, Python, Go, Rust e Java; è una pratica diffusa in tutto il settore.

Parametro del percorso (parametro del percorso)

Un valore dinamico che vive all'interno del percorso, subito dopo una barra. Poiché fa parte del percorso, si chiama a parametro del percorso o parametro del percorso, e trasporta significato semantico: identifica quale risorsa a cui si riferisce la richiesta.

  • Tutto in un percorso arriva come a stringa. 123 sembra un numero, ma nei percorsi di instradamento numeri e caratteri speciali sono tutti trattati come stringhe; il conduttore lo lancia se necessario.
  • Leggi ad alta voce, GET /api/users/123 dice "recupera i dati dell'utente il cui ID è 123." Quel costrutto leggibile dall'uomo è l'idea alla base del routing in stile REST e conferisce ai percorsi un chiaro significato semantico.
05

Parametri della query

A parametro di interrogazione è una coppia chiave/valore collegata alla fine del percorso dopo a punto interrogativo. Più coppie sono unite da una e commerciale. Ad esempio, /api/search?query=some+value, il percorso è /api/search, e dopo il ? arriva la chiave query con il valore some+value.

Perché esistono i parametri di query

POST e PUT le richieste hanno a corpo: un contenitore per l'invio di dati definiti dall'utente al server. Ma GET le richieste, per convenzione REST, non hanno corpo. Allora come fa un GET a inviare valori extra? I parametri di query sono la risposta: consentono a un GET di spedire un insieme di coppie chiave/valore che trasportano metadati sulla richiesta: non l'identità della risorsa, ma le istruzioni per modellare la risposta.

Parametro di query

Un facoltativo key=value coppia nella stringa di query, utilizzata per filtrare, ordinare, impaginare o cercare. Tipicamente utilizzato con le richieste GET perché non hanno corpo. Opzionale, ripetibile e indipendente dall'ordine.

L'esempio principale: l'impaginazione

Immagina un endpoint che restituisca un elenco di libri in formato paginato. La prima chiamata, /api/books, accetta le impostazioni predefinite del server e restituisce una parte di dati più alcuni metadati descrivendo l'intero set:

JSON/rispostaGET /api/books
{
  "data": [ /* ...the first 20 books (the default page)... */ ],
  "total":        100,   // how many books exist in total
  "currentPage":  1,     // which page this is (default = 1)
  "limit":        20,    // page size (default limit)
  "totalPages":   5      // 100 / 20 = 5 pages
}

Il client utilizza questi metadati di risposta per effettuare la richiesta successiva. L'impostazione predefinita non richiedeva parametri; per ottenere la pagina due inviata dal client /api/books?page=2. Lo stesso meccanismo prevede filtri (ad esempio filtro in base a un valore definito dall'utente) e ordinamento (ascendente o discendente), tutti come coppie chiave/valore nella query.

06

Percorso e parametri di query

Entrambi inseriscono i dati nell'URL ed è facile confonderli, quindi vale la pena essere precisi. Servono a scopi diversi.

I parametri di percorso hanno uno scopo particolare: un'espressione semantica di quale risorsa, "l'utente il cui ID è 123." Tu potrebbe tecnicamente inserisci un valore di ricerca nel percorso (/api/search/some+value), ma è difficile da mantenere e vanifica l'intero scopo di dare ai percorsi un chiaro significato semantico. I metadati come un termine di ricerca appartengono invece alla stringa di query: /api/search?query=some+value.

07

Percorsi nidificati

La nidificazione non è realmente una cosa separata tipo ovviamente, è una pratica che vedrai ovunque. Nelle API di stile REST, spesso si annidano risorse diverse per esprimere una relazione semantica. Ogni livello più profondo restringe il significato e lo associa al proprio gestore, restituendo una diversa granularità dei dati.

Camminando l'esempio più profondo, /api/users/123/posts/456:

  • /api/users, a statico parte; da solo restituisce l'elenco di tutti gli utenti.
  • 123, a parametro del percorso per l'ID utente; /api/users/123 restituisce quell'utente.
  • posts, a statico parte che nomina una sottoraccolta; /api/users/123/posts restituisce tutti i post di quell'utente.
  • 456, a parametro del percorso per un posto specifico; il percorso completo recupera "il post con ID 456 appartenente all'utente con ID 123."

Questo è il motivo per cui viene chiamato percorso annidato, annidi diversi tipi di informazioni a livelli diversi per esprimere significati semantici diversi e ciascuno produce una risposta diversa. Lo vedrai utilizzato praticamente ovunque una volta che un'API ha una complessità anche media.

09

Versioni e deprecazione

Versionamento del percorso è una pratica molto comune per la gestione delle modifiche negli endpoint API. Inserisci una parola chiave della versione nel percorso, /api/v1/products e /api/v2/products. Sembra un percorso normale con a v1 o v2 segmento aggiunto.

Perché preoccuparsi? Supponiamo che v1 restituisca ciascun prodotto come { id, name, price }. Successivamente arrivano nuovi requisiti, ad esempio che ora offri un'app mobile e devi modificare la forma della risposta, rinominandola name a title. Se modifichi il percorso live, interrompi tutti i client esistenti. Il controllo delle versioni consente a entrambe le forme di vivere contemporaneamente:

/api/v1/products/api/v2/products
{ id, name, price }{ id, title, price }

Questo fa due cose. Esprime chiaramente l'intento, v1 della risposta e v2 della risposta fianco a fianco. E significa che non dovevi cambiare l'intero percorso (non ti serviva un /api/new-products); hai appena aumentato la versione.

Deprecazione

Annuncio che un endpoint (ad esempio v1) scomparirà una volta rilasciata la v2. Gli ingegneri ottengono una definizione finestra di migrazione spostare le proprie richieste alla v2; solo dopo il team rimuove la v1. Il controllo delle versioni e la deprecazione offrono un flusso di lavoro stabile per la spedizione apportare modifiche senza interrompere i client in quel momento.

10

Percorsi "catch-all".

A percorso universale gestisce le richieste per percorsi che il server non serve effettivamente. Supponiamo che arrivi una richiesta /api/v3/products ma non esiste un gestore per questo. Il server inserisce un catch-all ultimo, dopo tutti i percorsi e i metodi specifici, tipicamente scritti con un carattere jolly, /*. Qualsiasi richiesta che passa attraverso ogni partita precedente arriva lì.

Senza una gestione generale, il comportamento predefinito è spesso una risposta nulla, che crea confusione. Con esso, il gestore restituisce un messaggio intuitivo, "questo percorso non esiste"/"percorso non trovato", quindi il client capisce chiaramente che il server non soddisfa quell'endpoint.

Caratteri jolly e ordinamento

Il * il carattere jolly corrisponde a qualsiasi cosa, motivo per cui il catch-all deve essere registrato ultimo. Posizionato in anticipo, intercetterebbe ogni richiesta prima che i percorsi reali prendano una svolta. La regola affidabile: prima i percorsi specifici, alla fine il tutto.

Un router in Go

Un router è, in fondo, un piccolo problema di invio orientato agli oggetti: una tabella da "metodo + percorso" a un gestore. Go esprime i quattro pilastri dell'OOP attraverso interfacce (astrazione + polimorfismo), campi non esportati (incapsulamento) e incorporamento di strutture (composizione, forma di ereditarietà di Go). I commenti taggati Ops sottolinearli ciascuno.

Vai 1.22+router.go
package main

import ("fmt"; "strings")

// ABSTRACTION: Handler is an interface, it names a capability
// ("be able to Handle a request") without saying how. Any type
// with a Handle method IS-A Handler. The router depends only on
// this contract, never on a concrete type.
type Handler interface {
    Handle(req Request) Response
}

type Request struct {
    Method string
    Path   string
    Params map[string]string // extracted path params (:id)
    Query  map[string]string // query params (?page=2)
}
type Response struct { Status int; Body string }

// ENCAPSULATION: "routes" is lowercase => unexported => private to
// the package. Outsiders cannot touch the table directly; they go
// through the methods we expose (Register / Dispatch).
type Router struct {
    routes map[string]Handler // key = "METHOD /route"
}

func NewRouter() *Router {
    return &Router{routes: make(map[string]Handler)}
}

// Register binds method + route -> handler (the dispatch table).
func (r *Router) Register(method, pattern string, h Handler) {
    r.routes[method+" "+pattern] = h // method + path = the unique key
}

// POLYMORPHISM: Dispatch calls h.Handle(req) without knowing which
// concrete type h is. Same call, different behaviour per handler.
func (r *Router) Dispatch(req Request) Response {
    for key, h := range r.routes {
        method, pattern, _ := strings.Cut(key, " ")
        if method == req.Method && match(pattern, req.Path, &req) {
            return h.Handle(req) // polymorphic dispatch
        }
    }
    return Response{404, "route not found"} // catch-all fallback
}

// match compares "/users/:id" against "/users/123", filling Params.
func match(pattern, path string, req *Request) bool {
    p, q := strings.Split(pattern, "/"), strings.Split(path, "/")
    if len(p) != len(q) { return false }
    for i := range p {
        if strings.HasPrefix(p[i], ":") { // dynamic segment
            req.Params[p[i][1:]] = q[i] // bind :id => "123"
        } else if p[i] != q[i] { // static segment must match exactly
            return false
        }
    }
    return true
}

// "INHERITANCE" via COMPOSITION: BaseHandler holds shared logic;
// concrete handlers EMBED it and reuse its methods.
type BaseHandler struct{ Name string }

func (b BaseHandler) log(req Request) {
    fmt.Printf("[%s] %s %s\n", b.Name, req.Method, req.Path)
}

// GetUser embeds BaseHandler (composition) and satisfies Handler.
type GetUser struct{ BaseHandler }
func (h GetUser) Handle(req Request) Response {
    h.log(req) // reused (inherited) behaviour
    return Response{200, "user id = " + req.Params["id"]}
}

type ListBooks struct{ BaseHandler }
func (h ListBooks) Handle(req Request) Response {
    h.log(req)
    page := req.Query["page"] // query param drives pagination
    if page == "" { page = "1" }
    return Response{200, "books page " + page}
}

func main() {
    r := NewRouter()
    r.Register("GET", "/api/users/:id", GetUser{BaseHandler{"users"}})
    r.Register("GET", "/api/books",     ListBooks{BaseHandler{"books"}})

    req := Request{Method: "GET", Path: "/api/users/123",
        Params: map[string]string{}, Query: map[string]string{}}
    fmt.Println(r.Dispatch(req).Body) // => user id = 123
}

Un router in Python

La stessa architettura nella sintassi delle classi classiche: una classe base astratta per il contratto (astrazione), sottoclassi reali (ereditarietà), metodi sovrascritti (polimorfismo) e un attributo privato con nome alterato (incapsulamento).

Python 3.11+router.py
from abc import ABC, abstractmethod
from dataclasses import dataclass, field
from urllib.parse import urlsplit, parse_qs

# ABSTRACTION: Handler is an Abstract Base Class. @abstractmethod
# forces every subclass to define handle(). You cannot create a
# Handler directly, it is a pure contract.
class Handler(ABC):
    @abstractmethod
    def handle(self, req: "Request") -> "Response": ...

@dataclass
class Request:
    method: str
    path: str
    params: dict = field(default_factory=dict)  # path params (:id)
    query: dict = field(default_factory=dict)   # query params (?page=2)

@dataclass
class Response:
    status: int
    body: str

# INHERITANCE: BaseHandler is a concrete parent holding shared
# behaviour (logging). Subclasses inherit and reuse _log().
class BaseHandler(Handler):
    def __init__(self, name): self._name = name   # protected by convention
    def _log(self, req): print(f"[{self._name}] {req.method} {req.path}")

# POLYMORPHISM: each subclass OVERRIDES handle() differently, yet
# the router calls them all identically, handler.handle(req).
class GetUser(BaseHandler):           # IS-A BaseHandler IS-A Handler
    def handle(self, req):
        self._log(req)              # inherited from parent
        return Response(200, f"user id = {req.params['id']}")

class ListBooks(BaseHandler):
    def handle(self, req):
        self._log(req)
        page = req.query.get("page", ["1"])[0]   # query param
        return Response(200, f"books page {page}")

# ENCAPSULATION: self.__routes is name-mangled to _Router__routes,
# so it is effectively private. The public surface is register()
# and dispatch(); the table stays hidden.
class Router:
    def __init__(self):
        self.__routes: dict[tuple[str, str], Handler] = {}

    def register(self, method, pattern, handler):
        self.__routes[(method, pattern)] = handler  # method + path key

    def dispatch(self, method, url):
        parts = urlsplit(url)
        query = parse_qs(parts.query)               # ?a=1&b=2 -> dict
        for (m, pattern), handler in self.__routes.items():
            params = self.__match(pattern, parts.path)
            if m == method and params is not None:
                return handler.handle(
                    Request(method, parts.path, params, query))  # polymorphic
        return Response(404, "route not found")       # catch-all

    @staticmethod
    def __match(pattern, path):
        p = pattern.strip("/").split("/")
        q = path.strip("/").split("/")
        if len(p) != len(q): return None
        params = {}
        for seg, val in zip(p, q):
            if seg.startswith(":"):       # dynamic segment
                params[seg[1:]] = val    # bind :id -> "123"
            elif seg != val:            # static must match exactly
                return None
        return params

if __name__ == "__main__":
    r = Router()
    r.register("GET", "/api/users/:id", GetUser("users"))
    r.register("GET", "/api/books",     ListBooks("books"))
    print(r.dispatch("GET", "/api/users/123").body)   # user id = 123
    print(r.dispatch("GET", "/api/books?page=2").body) # books page 2

L'intero modello in un fiato

Una richiesta raggruppa a metodo (il cosa) e a percorso (il dove). Il server li unisce in una chiave univoca, la confronta con la sua tabella, prima i percorsi statici, poi quelli dinamici, per ultimo catch-all, estrae qualsiasi parametri del percorso dal percorso e parametri di interrogazione dalla stringa di query, quindi chiama il file corrispondente gestore. Modifica il percorso per evolversi, deprecalo per andare in pensione e prendi tutto per fallire con grazia.
