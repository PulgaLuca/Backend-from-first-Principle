Un riferimento dettagliato al backend

Padroneggiare la concorrenza e il parallelismo

Ogni sistema backend che costruirai condivide un requisito non negoziabile: deve gestire più cose contemporaneamente. Un server Web che può elaborare solo una richiesta alla volta costringe tutti gli altri utenti ad attendere e ciò semplicemente non funziona in produzione. Questa guida costruisce il modello mentale completo da zero, dai cicli grezzi della CPU e dalle operazioni di I/O, attraverso i thread del sistema operativo e i cicli di eventi, fino alle moderne primitive di concorrenza come goroutine e async/await. Tutto è basato sul pratico utilizzo del codice backend Vai e Pitone.

01

Perché la concorrenza è importante

Quando parliamo di "applicazione backend" in questo contesto, intendiamo un server web basato su HTTP, un processo in esecuzione su una macchina, in ascolto su una porta, ricevendo richieste da browser e altri client e inviando risposte.

Se il tuo server può solo elaborare una richiesta alla volta, quindi ogni altro utente, potenzialmente migliaia, dovrà attendere in fila o ricevere un errore. Questa è una situazione impossibile per qualsiasi applicazione di produzione reale.

Intuizione chiave

Capire come il tuo server fa più cose contemporaneamente non è solo "bello da sapere", ma modella il modo in cui esegui il debug dei problemi, strutturi la tua applicazione e prendi decisioni sull'architettura.

La maggior parte di noi impara parole chiave come async, await, e threading dalla documentazione del nostro linguaggio di programmazione. Sappiamo che "rendono le cose concorrenti". Ma raramente capiamo cosa siano queste parole chiave farlo davvero dietro le quinte, a livello meccanico, cosa succede nella CPU e nel sistema operativo.

02

Il costo di restare inattivi

Cominciamo con uno scenario concreto. Hai un browser che effettua una richiesta al tuo backend. Il backend deve interrogare un database, attendere la risposta e restituire i dati al client. Questo è il ciclo di vita tipico di una chiamata API.

Quanto tempo richiede una query sul database?

Il tempo di attesa dipende da dove risiede il tuo database rispetto al tuo server:

Scenario Latenza Descrizione
Host locale 1-2 ms Server e database sulla stessa macchina
Stessa regione, diversa AZ 20-30 ms Configurazione di produzione tipica (ad esempio AWS us-east-1a -> us-east-1b)
Interregionale 90-100 ms Database in una regione geograficamente distante

Durante quel tempo di attesa, che sia 2 ms o 100 ms, se il tuo server elabora in modo sincrono (una richiesta alla volta, riga per riga), la tua CPU sta facendo assolutamente niente. È completamente inattivo.

Quantificare i rifiuti

Una CPU moderna funziona in modo approssimativo 3 miliardi di istruzioni al secondo, che riguarda 3 milioni di istruzioni al millisecondo. Se il tuo server rimane inattivo per 100 ms in attesa di una risposta del database, potrebbe essere stato eseguito 300 milioni di istruzioni: ma invece ha eseguito zero.

Fig 1: un server sincrono spreca la stragrande maggioranza dei cicli della CPU in attesa di IO

Una ripartizione realistica delle chiamate API

Una tipica chiamata API di medio-complessità prevede 3-5 query di database più 1-2 chiamate di servizio esterne (e-mail, cache come Redis, ecc.). Se ciascuna di queste cinque operazioni di rete richiede in media 50 ms, il tempo totale trascorso in attesa dell'IO è di circa 250 ms. Ma il calcolo effettivo della CPU, la convalida, l'analisi JSON e la serializzazione riguardano solo 10 ms. Ciò significa che l'hardware del tuo server è inattivo Il 95% delle volte. Questo è esattamente il problema che la concorrenza risolve.

03

Associato a IO e associato a CPU

Ogni operazione eseguita dal tuo backend rientra in una delle due categorie. Questa distinzione è il concetto più importante in tutta la guida guida ogni decisione su quale modello di concorrenza utilizzare.

Operazioni legate a IO

IO sta per Ingresso/Uscita: qualsiasi operazione in cui la CPU non può fare nulla di utile perché è in attesa di qualcosa di esterno. La "I" si riferisce ai dati in arrivo in il tuo processo; la "O" si riferisce ai dati in corso fuori. Secondo il Linux read(2) pagina man, una lettura su un descrittore di file (socket, file, pipe) bloccherà il thread chiamante fino all'arrivo dei dati.

Operazioni comuni legate all'IO nei sistemi backend:

  • Interrogazioni del database: invio di una query SQL su TCP, in attesa del ritorno delle righe
  • Chiamate API esterne: Richieste HTTP a servizi di terze parti (gateway di pagamento, provider di posta elettronica)
  • Operazioni sul file system: lettura di file di configurazione, scrittura di caricamenti, gestione di file temporanei
  • Interazioni nella cache: Redis GET/SET operazioni in rete
  • I/O standard: accesso a stdout, leggendo da stdin
  • Code di messaggi: pubblicazione o consumo da Kafka, RabbitMQ, ecc.

Operazioni legate alla CPU

Il lavoro legato alla CPU avviene quando il processore elabora attivamente i dati, esegue le istruzioni il più velocemente possibile e il collo di bottiglia è la CPU stessa, non una risorsa esterna. La maggior parte del lavoro legato alla CPU in un backend tipico è leggero (1-2 ms per l'analisi o la convalida JSON), ma alcune operazioni sono fortemente legate alla CPU:

  • Elaborazione immagini/video: moltiplicazioni di matrici, convoluzioni, trasformazioni dello spazio colore
  • Crittografia/hashing: verifica JWT, hashing della password bcrypt, handshake TLS
  • Compressione: codifica gzip, zstd, Brotli dei corpi delle risposte
  • Serializzazione: JSON/Protobuf marshal/unmarshal su larga scala
  • Inferenza ML: esecuzione di un passaggio in avanti del modello senza offload della GPU
La regola pratica

Più di 70% del tempo in una tipica applicazione backend viene dedicato all'IO. Per il lavoro legato a IO, concorrenza è obbligatorio. Per il lavoro legato alla CPU, parallelismo (più core) aumenta la velocità.

04

Concorrenza vs Parallelismo

Questi due termini vengono spesso confusi, e per una buona ragione, poiché entrambi implicano "fare più cose". Ma la distinzione è fondamentale.

Parallelismo: fare più cose contemporaneamente

Un programma è parallelo quando esegue più istruzioni nello stesso momento. Ciò richiede supporto hardware: almeno due core CPU, perché un singolo core può eseguire solo un'istruzione alla volta. Se hai 4 core, puoi eseguire 4 istruzioni veramente contemporaneamente.

Concorrenza: gestire più cose contemporaneamente

Concorrenza riguarda strutturazione il tuo programma in modo che più attività possano essere avviate, messe in pausa e riprese, anche su un singolo core. Dall'esterno sembra che tutto stia accadendo contemporaneamente. Ma se si esamina ogni singolo momento, si vedrà che solo una cosa è effettivamente in esecuzione su un dato core. La chiave è che quando un'attività viene bloccata (in attesa di IO), un'altra attività ottiene la CPU.

Il classico one-liner

Parallelismo riguarda facendo più cose contemporaneamente.
Concorrenza riguarda affrontare più cose contemporaneamente.

Attribuito a Rob Pike, co-creatore di Go

Fig 3: La concorrenza interlaccia le attività su un core; Il parallelismo li esegue simultaneamente su core separati
05

Thread del sistema operativo

Il primo meccanismo fondamentale per fare più cose contemporaneamente è il filo. Un thread è un'unità di esecuzione indipendente gestita dal sistema operativo. Non è una caratteristica del tuo linguaggio di programmazione, è una caratteristica del kernel del sistema operativo. Quando "crei un thread", stai creando un file chiamata di sistema (come clone() su Linux o pthread_create() tramite POSIX) per chiedere al kernel di impostare un nuovo contesto di esecuzione.

Ciò che il sistema operativo crea per ogni thread

Quando viene creato un nuovo thread, il kernel gli assegna diverse cose:

  • Una pila: utilizzato per tenere traccia delle chiamate di funzione (call frame), delle variabili locali e degli indirizzi di ritorno. Su Linux, la dimensione dello stack predefinita è 8 MB di memoria virtuale (sebbene le pagine fisiche vengano allocate solo su richiesta tramite page fault).
  • Un puntatore all'istruzione (IP): tiene traccia esattamente della posizione del thread nel suo codice, in modo che il kernel possa riprenderlo dopo un cambio di contesto.
  • Strutture dati del kernel: metadati per lo scheduler: stato del thread (in esecuzione/inattivo/bloccato), priorità, affinità della CPU, maschere di segnale, ecc.

Pianificazione preventiva

Il sistema operativo pianificatore decide quale thread ottiene il tempo della CPU e per quanto tempo. Assegna a ciascun thread a fetta di tempo (in genere pochi millisecondi). Dopo la scadenza della fetta, lo scheduler con la forza mette in pausa il thread, che sia finito o meno, salva il suo stato e passa a un altro thread. Questo si chiama programmazione preventiva perché i thread vengono anticipati (interrotti) senza la loro cooperazione.

Memoria condivisa tra thread

Una proprietà importante: i thread all'interno del file stesso processo condividere lo stesso spazio di memoria (heap, variabili globali, descrittori di file). Se il thread 1 alloca un oggetto nell'heap, il thread 2 può accedervi tramite un puntatore. Ciò rende veloce la comunicazione tra thread (nessuna copia, nessuna serializzazione), ma anche pericoloso, come vedremo nella sezione sulle condizioni di gara.

Discussioni diverse processi, tuttavia, sono completamente isolati, non possono vedere la memoria dell'altro. Questo isolamento viene applicato dal sistema di memoria virtuale del kernel per garantire sicurezza e stabilità.

Thread per richiesta in Python

# Python, threading model (simplified)
import threading

def handle_request(conn):
    # 1. Parse the HTTP request (CPU work)
    request = parse_http(conn)

    # 2. Database query, this BLOCKS the thread
    #    The OS scheduler will switch to another thread
    user = db.execute(
        "SELECT * FROM users WHERE id = %s",
        (request.user_id,)
    )

    # 3. Thread resumes here after DB responds
    response = json.dumps(user)
    conn.send(response)

# Create a new OS thread for each incoming connection
while True:
    conn = server_socket.accept()
    t = threading.Thread(target=handle_request, args=(conn,))
    t.start()Python

Nota che non c'è async o await ovunque. Il blocco avviene in modo trasparente, a livello del sistema operativo, quando db.execute() effettua una chiamata di rete. Il thread è contrassegnato come "bloccato", il sistema operativo passa a un altro thread e successivamente riattiva questo thread quando arriva la risposta del database sul socket.

06

Overhead del thread e cambio di contesto

I thread sono potenti, ma presentano tre categorie di sovraccarico che limitano il numero che puoi praticamente eseguire.

1. Sovraccarico di memoria

Ogni thread ottiene il proprio stack. Su Linux il valore predefinito è 8 MB di spazio di indirizzi virtuali (anche se solo le pagine toccate consumano RAM fisica). Anche con una memoria fisica effettiva di 500 KB-1 MB per thread, 10.000 connessioni simultanee consumerebbero 5-10 GB di RAM solo per gli stack di thread, prima ancora che l'applicazione allochi una singola struttura dati.

2. Sovraccarico della creazione

La creazione di un thread richiede una chiamata di sistema al kernel. Il kernel deve allocare lo stack, impostare strutture dati interne (descrittore del thread, stato del segnale, metadati dello scheduler) e registrare il thread con lo scheduler. Questo richiede da pochi microsecondi a pochi millisecondi: veloce per gli standard umani, ma significativo su larga scala quando crei e distruggi migliaia di thread.

3. Cambio di contesto in alto

Questa è la cosa più importante. Ogni volta che lo scheduler passa da un thread all'altro deve:

  1. Salva i registri della CPU del thread corrente (generico, a virgola mobile, SIMD)
  2. Aggiornare le strutture contabili (stato del thread, contabilità temporale)
  3. Seleziona il thread successivo da eseguire (coinvolge l'algoritmo dello scheduler)
  4. Ripristina i registri salvati del nuovo thread
  5. Potenzialmente svuotare le cache della CPU (le linee della cache L1/L2 diventano "fredde")

Ogni cambio di contesto costa 1-10 microsecondi su hardware moderno. Con 4 core e 1.000 thread, lo scheduler deve costantemente destreggiarsi tra di essi e questo sovraccarico può diventare una fonte misurabile di latenza. Il tempo di cambio di contesto è puramente improduttivo, è un lavoro di manutenzione, non un calcolo reale.

Fig 4: Il cambio di contesto è un puro sovraccarico: durante il cambio non avviene alcun lavoro utile
Perché il thread per richiesta è in difficoltà

Questo è esattamente il motivo per cui il modello "un thread per richiesta" non funziona in caso di concorrenza elevata. 10.000 connessioni simultanee = 10.000 thread = gigabyte di memoria dello stack + sovraccarico di cambio di contesto costante. Il Problema C10k è stata la consapevolezza del settore che questo modello semplicemente non è scalabile.

07

Il modello del ciclo degli eventi

Il ciclo degli eventi adotta un approccio radicalmente diverso alla concorrenza: invece di molti thread, utilizza un filo e un ciclo che controlla continuamente le operazioni di I/O completate, quindi esegue il callback appropriato. Questo è il modello che alimenta Node.js, L'asincio di Python, Nginxe molti altri sistemi ad alte prestazioni.

Il meccanismo centrale

Quando un'attività (come servire la Richiesta A) deve effettuare una query sul database, invece di bloccarsi e attendere,:

  1. Avvia l'IO: invia i byte della query sul socket TCP al database.
  2. Registra una richiamata: indica al ciclo di eventi: "Quando il database risponde su questo socket, esegui questa funzione."
  3. Controllo dei rendimenti: ritorna immediatamente, liberando il singolo thread per riprendere l'attività successiva.

Il ciclo degli eventi stesso è essenzialmente un ciclo infinito. Ad ogni iterazione, utilizza un meccanismo a livello di sistema operativo per verificare quali socket dispongono di dati pronti, quindi esegue i callback per le operazioni completate e torna al controllo.

Multiplexing IO a livello di sistema operativo

Il ciclo di eventi non implementa il monitoraggio IO stesso, si basa sul sistema operativo. Il sistema operativo fornisce chiamate di sistema speciali in grado di monitorare in modo efficiente migliaia di descrittori di file (socket, file, pipe) contemporaneamente:

sistema operativo Meccanismo Note
Linux epoll O(1) per evento pronto. Scala fino a milioni di connessioni. Vedi epoll(7)
macOS/BSD kqueue Simile a epoll ma con un'API diversa. Vedi kqueue(2)
Finestre IOCP Porte di completamento IO, equivalenti di Windows

Sotto il cofano, Node.js utilizza libuv che astrae questi meccanismi specifici della piattaforma. Di Pitone asyncio usi selectors modulo che avvolge epoll/kqueue.

Fig 5: il ciclo di eventi controlla lo stato di IO su ogni iterazione ed esegue callback per le operazioni completate

Perché i loop di eventi sono efficienti per l'IO

Dato che c'è un solo thread, c'è nessun sovraccarico di cambio di contesto, nessuna allocazione di stack multi-megabytee nessuna manipolazione dello scheduler. La CPU trascorre il suo tempo eseguendo il codice effettivo (callback) o aspettando in modo efficiente all'interno epoll_wait(). Questo è il motivo per cui Node.js può gestire decine di migliaia di connessioni simultanee su hardware modesto.

Il compromesso fondamentale: non bloccare mai il ciclo

Se esegui un'operazione ad uso intensivo della CPU, ad esempio un'attività di elaborazione di immagini da 100 ms, direttamente sul thread del ciclo di eventi, tutto si ferma. Non è possibile servire altre richieste, non possono essere attivati ​​callback, né è possibile elaborare completamenti I/O. L'intero server si blocca fino al termine del lavoro della CPU. Questo è il motivo per cui i linguaggi basati su loop di eventi come JavaScript insistono sul codice non bloccante e scaricano calcoli pesanti su thread di lavoro o processi separati.

Callback -> Promesse -> async/await: l'evoluzione

Il ciclo degli eventi funziona sui callback, ma i callback grezzi portano a codice profondamente annidato (il famigerato "inferno dei callback"). L'evoluzione in JavaScript è andata: 

// Stage 1: Raw callbacks (pre-ES6)
db.query("SELECT * FROM users WHERE id = ?", [userId],
  function(err, result) {
    if (err) return sendError(res, err);
    // Nested callback for second query
    db.query("SELECT * FROM orders WHERE user_id = ?", [userId],
      function(err, orders) {
        if (err) return sendError(res, err);
        // Another level of nesting...
        sendResponse(res, { user: result, orders: orders });
      }
    );
  }
);JavaScript / callback hell
// Stage 2: async/await (modern, syntactic sugar over callbacks)
async function handleRequest(req, res) {
  const user  = await db.query("SELECT * FROM users WHERE id = ?", [req.userId]);
  const orders = await db.query("SELECT * FROM orders WHERE user_id = ?", [req.userId]);
  sendResponse(res, { user, orders });
}JavaScript / async/await

Il await la parola chiave è zucchero sintattico. Quando il runtime incontra await, dice: "Sto cedendo il controllo della CPU al loop degli eventi. Tutto ciò che segue questa riga è effettivamente un callback che verrà eseguito al completamento di questa operazione di IO."

L'asincio di Python: la stessa idea

import asyncio
import aiohttp

async def handle_request(user_id: int) -> dict:
    # await = "yield control to the event loop until this IO completes"
    user = await db.fetchone(
        "SELECT * FROM users WHERE id = $1", user_id
    )
    orders = await db.fetch(
        "SELECT * FROM orders WHERE user_id = $1", user_id
    )
    return {"user": user, "orders": orders}

# Run with an event loop (uvloop for performance)
asyncio.run(handle_request(123))Python

08

Asincrono/Aspetta come macchina a stati

Per capire veramente async/await, è utile vedere in cosa il compilatore o il runtime trasforma effettivamente il tuo codice. An async la funzione viene essenzialmente convertita in a macchina statale che interagisce con il ciclo degli eventi. Ciascuno await è un punto di transizione tra gli stati.

La funzione asincrona originale

async def fetch_user_data(user_id):
    user   = await db.get_user(user_id)      # State 0 -> 1
    orders = await db.get_orders(user_id)    # State 1 -> 2
    return {"user": user, "orders": orders}  # State 2 -> donePython

Cosa vede il runtime (concettuale)

# Conceptual state machine representation
def fetch_user_data_machine(user_id):
    state = 0
    user = None
    orders = None

    def step():
        nonlocal state, user, orders

        if state == 0:
            state = 1
            # Start the IO, register callback for when it completes
            return db.get_user(user_id).then(
                lambda result: (user := result, step())
            )

        elif state == 1:
            state = 2
            return db.get_orders(user_id).then(
                lambda result: (orders := result, step())
            )

        elif state == 2:
            return {"user": user, "orders": orders}

    return stepPython / conceptual
Figura 6, ciascuno await è una transizione di stato; il ciclo degli eventi esegue altro lavoro nel mezzo

Questo spiega due cose

1. Perché await può apparire solo all'interno async funzioni. La funzione deve essere contrassegnata async perché deve essere trasformata in una macchina statale. Una funzione regolare non dispone di un'infrastruttura della macchina a stati per supportare la pausa e la ripresa.

2. Perché bloccare il ciclo degli eventi è catastrofico. Se si esegue un'operazione ad uso intensivo della CPU all'interno di uno stato (ad esempio un calcolo di 500 ms), la macchina a stati non potrà mai effettuare la transizione. Nessun'altra macchina a stati (altre richieste) può avanzare. L'intero server si blocca.

Vai a routine e thread virtuali

Go adotta un terzo approccio che non prevede né thread grezzi del sistema operativo né un loop di eventi a thread singolo. Utilizza goroutine: thread leggeri e in spazio utente gestiti dallo scheduler di runtime di Go. Il termine "thread virtuale" cattura l'idea: si comportano come thread (codice di blocco, logica sequenziale), ma sono molto più economici perché non sono costrutti a livello del sistema operativo.

Perché le goroutine costano poco

Proprietà Discussione del sistema operativo Goroutine
Dimensione della pila ~8 MB (virtuali), ~KB fisici ~2-8 KB iniziali (cresce dinamicamente)
Tempo di creazione ~us a ms (chiamata di sistema) ~ns a noi (allocazione dello spazio utente)
Cambio di contesto 1-10 noi (modalità kernel) ~200 ns (scambio puntatore nello spazio utente)
Limite pratico ~10.000 (collo di bottiglia della memoria) ~1.000.000+ (a seconda della RAM)
Programmato da kernel del sistema operativo Vai allo scheduler di runtime

Server HTTP di Go: una goroutine per richiesta

La libreria standard di Go net/http crea un nuova goroutine per ogni richiesta in arrivo. Sembra che il modello thread per richiesta che abbiamo appena detto non sia scalabile, ma le goroutine sono così leggere che funzionano magnificamente. Ecco il modello di codice sorgente effettivo di Go's net/http pacchetto: 

// From Go's standard library net/http/server.go (simplified)
func (srv *Server) Serve(l net.Listener) error {
    for {
        conn, err := l.Accept()   // Accept new TCP connection
        if err != nil {
            return err
        }
        // Create a NEW goroutine for each connection
        go srv.handleConn(conn)
    }
}Go

Il go la parola chiave genera una nuova goroutine. Ciò equivale a creare un thread, ma a una frazione del costo (nanosecondi contro microsecondi, kilobyte contro megabyte).

Un tipico gestore di Go

func handleGetUser(w http.ResponseWriter, r *http.Request) {
    userID := r.URL.Query().Get("id")

    // This BLOCKS the goroutine, but not the OS thread.
    // The Go scheduler parks this goroutine and runs another.
    user, err := db.QueryRow(
        "SELECT name, email FROM users WHERE id = $1",
        userID,
    )
    if err != nil {
        http.Error(w, "not found", http.StatusNotFound)
        return
    }

    // Goroutine resumes here after DB responds
    json.NewEncoder(w).Encode(user)
}Go

Avviso: no async, no await, nessuna richiamata. Il codice si legge come un codice sincrono e bloccante, perché il goroutine lo fa blocco. Ma lo scheduler di runtime Go lo parcheggia in modo trasparente e prende un'altra goroutine. Ottieni l'ergonomia del codice bloccante con l'efficienza dell'IO non bloccante.

10

Lo schedulatore M:N

Lo scheduler di Go utilizza un file Modello M:N: multipla le goroutine M sui thread N OS. Il numero di thread del sistema operativo è controllato da GOMAXPROCS variabile di ambiente (il valore predefinito è il numero di core della CPU). Ogni thread del sistema operativo esegue una coda locale di goroutine.

Fig 7: Go esegue il multiplexing di molte goroutine su un pool fisso di thread del sistema operativo

Quando una goroutine si blocca su IO (ad esempio, la lettura di un database), il runtime Go internal sondaggi di rete (costruito su epoll/kqueue dietro le quinte) rileva il completamento dell'I/O e rimette la goroutine in una coda di esecuzione. Questo è il meglio di entrambi i mondi: codice in stile blocco con efficienza a livello di ciclo di eventi.

Condizioni di gara e stato condiviso

La concorrenza introduce un'intera categoria di bug che non esistono nel codice sequenziale. Quasi tutti risalgono a una causa principale: stato mutevole condiviso. Quando due attività simultanee leggono e scrivono la stessa variabile e le loro operazioni si intersecano in modi inaspettati, ottieni un condizione di gara.

Il classico controesempio

Due thread tentano entrambi di incrementare un contatore condiviso da 0 a 1. L'incremento richiede tre passaggi della CPU: leggere il valore attuale, aggiungere uno, scrivere indietro. Se i thread si intercalano:

Fig 8: due thread leggono lo stesso valore obsoleto e un aggiornamento sovrascrive l'altro

Anche le condizioni di gara sono in asincrono/attendono

Potresti pensare: "Uso JavaScript/Python con async/await, c'è solo un thread, quindi nessuna condizione di competizione". Sbagliato. Possono ancora verificarsi condizioni di gara tra await punti. Considera questo esempio Python: 

balance = 100

async def withdraw(amount: int):
    global balance
    if balance >= amount:               # Check at time T1
        await process_withdrawal(amount)  # <- yields control here!
        balance -= amount                 # Deduct at time T2

# Both coroutines see balance=100, both pass the check,
# both deduct 100 -> balance = -100 (invalid!)
await asyncio.gather(
    withdraw(100),
    withdraw(100),
)Python

Il problema: il if l'assegno e la detrazione sono separati da un await. Tra questi due punti, il ciclo degli eventi esegue il secondo withdraw chiamata, che vede anche balance == 100 e supera il controllo. Entrambi detraggono e il saldo va a -100.

Chiave da asporto

Le condizioni di gara si verificano ogni volta che c'è un controlla e poi agisci modello separato da un punto di snervamento (await) o un cambio di contesto. Il codice asincrono a thread singolo è no immune alle condizioni di gara.

Blocchi, mutex e canali

Le soluzioni alle condizioni di gara sono state studiate per decenni. Ecco gli approcci principali.

Mutex (Mutua esclusione)

Un mutex garantisce solo questo un thread/goroutine può eseguire una sezione critica alla volta. Tutti gli altri devono attendere finché il blocco non viene rilasciato. Questa è la primitiva di sincronizzazione più comune in tutti i linguaggi.

Python: threading.Lock

import threading

counter = 0
lock = threading.Lock()

def increment():
    global counter
    with lock:          # Acquire lock, blocks other threads
        counter += 1   # Only one thread executes this at a time
                        # Lock is released automatically at end of `with`

# Create 1000 threads all incrementing the same counter
threads = [threading.Thread(target=increment) for _ in range(1000)]
for t in threads: t.start()
for t in threads: t.join()
print(counter)  # Always 1000, no lost updatesPython

Vai: sync.Mutex

package main

import (
    "fmt"
    "sync"
)

func main() {
    var counter int
    var mu sync.Mutex
    var wg sync.WaitGroup

    for i := 0; i < 1000; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            mu.Lock()         // Acquire, other goroutines wait here
            counter++
            mu.Unlock()       // Release, next goroutine can proceed
        }()
    }

    wg.Wait()
    fmt.Println(counter) // Always 1000
}Go

Canali: l'approccio preferito di Go

Go ha un famoso proverbio: "Non comunicare condividendo la memoria; condividi la memoria comunicando." Invece di più goroutine che scrivono su una variabile condivisa (che necessita di un mutex), puoi usare canali: pipe tipizzate attraverso le quali le goroutine inviano e ricevono valori. Solo la goroutine quella possiede i dati lo modificano; altri inviano messaggi per richiedere modifiche. 

package main

import "fmt"

func counterService(ch chan int, done chan bool) {
    counter := 0
    for {
        select {
        case delta := <-ch:
            counter += delta   // Only this goroutine modifies counter
        case done <- counter:
            return
        }
    }
}

func main() {
    ch := make(chan int, 100)     // Buffered channel
    done := make(chan bool)

    go counterService(ch, done)

    // 1000 goroutines send +1 through the channel
    for i := 0; i < 1000; i++ {
        ch <- 1
    }

    result := <-done
    fmt.Println(result) // 1000, no race condition, no mutex needed
}Go

Python asyncio.Lock per codice asincrono

import asyncio

balance = 100
lock = asyncio.Lock()

async def withdraw(amount: int):
    global balance
    async with lock:                     # Only one coroutine at a time
        if balance >= amount:
            await process_withdrawal(amount)
            balance -= amount

# Now safe, second withdraw waits for the lock
await asyncio.gather(
    withdraw(100),
    withdraw(100),
)
print(balance)  # 0, not -100Python

Scegliere il modello giusto

Ecco il riassunto pratico, quando usare cosa e perché.

Carico di lavoro Miglior modello Perché Esempi
IO-Bound, concorrenza elevata Ciclo di eventi/attesa asincrona/goroutine Overhead minimo, nessun cambio di contesto, gestisce oltre 100.000 connessioni Server Web, gateway API, proxy di microservizi, server di chat
Vincolato alla CPU, parallelizzabile Thread del sistema operativo con parallelismo (core multipli) Vera esecuzione simultanea; più core = proporzionalmente più veloce Elaborazione di immagini, codifica video, inferenza ML, crittografia

La linea di fondo

Concorrenza mantiene il tuo programma produttivo, impedisce alla CPU di rimanere inattiva mentre attende l'IO. Utilizzare async/await, goroutine o thread virtuali per questo.

Parallelismo ti consente di utilizzare più core della CPU per eseguire più calcoli nello stesso istante. Utilizzare thread del sistema operativo o pool di processi per questo.

La maggior parte delle applicazioni backend lo sono prevalentemente legato a IO: il collo di bottiglia è quasi sempre la rete, non la CPU. Ma quando si affronta il lavoro legato alla CPU, il parallelismo è lo strumento che sblocca più throughput.
