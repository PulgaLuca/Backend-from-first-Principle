Parte I / Il modello mentale
01

Cosa sono e perché esistono

Le convalide e le trasformazioni non sono una singola funzionalità da installare. Lo sono una serie di regole e linee guida da tenere a mente durante la progettazione delle API. Quasi tutto in loro si riconduce a due obiettivi, e quei due obiettivi sono la lente attraverso la quale viene presa ogni decisione successiva:

Obiettivo 01Integrità dei dati
Qualunque dato raggiunga finalmente la tua logica applicativa e il tuo database sia nel esatto modellare le aspettative della tua applicazione, campi corretti, tipi corretti, intervalli corretti, significato corretto.
Obiettivo 02Sicurezza
Non è mai consentito che input non attendibili provenienti dal mondo esterno portino il tuo sistema in uno stato inaspettato e non gestito. Il server rimane sulla difensiva riguardo a tutto ciò che oltrepassa i suoi confini.

Cosa conta come "dati cliente in entrata"

Il limite di convalida copre ogni tipo di dati che un client può inviare al server, non solo al corpo della richiesta. Tutti i seguenti elementi devono essere considerati non attendibili fino a prova contraria:

  • Payload JSON: il corpo di a POST / PUT / PATCH richiesta.
  • Parametri di query: e.g. ?page=2&limit=20.
  • Parametri del percorso: per esempio. il 5 dentro /users/5.
  • Intestazioni: tutto ciò che il client imposta sulla richiesta.
La definizione di una frase Risposte di convalida "questi dati sono nel formato esatto previsto dalla mia API?" Risposte di trasformazione "come posso rimodellare questi dati nel formato desiderato dal mio livello di servizio?" Corrono insieme, davanti alla porta, prima che succeda qualcosa di importante.
02

Dove vive: i tre strati

Per individuare dove la convalida avviene, è necessario prima il modello mentale standard di un backend: tre livelli impilati, ciascuno con un lavoro. Una richiesta viaggia lungo lo stack e la risposta risale.

In bassoLivello di deposito
Si occupa solo del database, delle connessioni, delle interrogazioni, degli inserimenti, degli aggiornamenti, delle eliminazioni. Non importa perché si sta scrivendo una riga, solo che lo è. Funziona con un DB relazionale (Postgres), Redis o qualsiasi altro archivio persistente.
MedioLivello di servizio
Il logica applicativa. Un singolo metodo di servizio può chiamare uno o più metodi di repository, inviare notifiche push, inviare e-mail a utenti, archiviare dati, attivare un webhook, tutto ciò che ci si aspetta che un'API faccia effettivamente fare.
In altoLivello di controllo
Il punto di ingresso rivolto a HTTP. Possiede tutto HTTP: quale codice di stato restituire, il formato della risposta e, soprattutto, le convalide. Riceve i dati del cliente, chiama il metodo del servizio corrispondente e restituisce tutto ciò che quel metodo restituisce.

Il motivo per cui il controller e il servizio sono deliberatamente separati è mantenere le preoccupazioni HTTP (codici di errore, codici di successo, forma della risposta, convalida) in un posto e la pura logica applicativa in un altro. Il titolare del trattamento chiama il servizio; il servizio può chiamare o meno il repository, a seconda di ciò di cui ha bisogno la richiesta.

03

Il ciclo di vita della richiesta

Una richiesta non appare magicamente all'interno del metodo del controller. Arriva, arriva percorso abbinatoe solo allora viene richiamato il metodo controller assegnato a quella route. Tale ordinamento è la chiave per posizionare correttamente la convalida.

  1. I dati arrivano. Un client apre una connessione HTTP e invia una richiesta, in genere un payload JSON, oltre a parametri e intestazioni di query e percorso.
  2. Esecuzioni di corrispondenza del percorso. Il router confronta il percorso in entrata con i suoi modelli e seleziona il metodo del controller registrato per il percorso corrispondente.
  3. Incendi di pipeline di convalida e trasformazione. Prima qualsiasi esecuzioni logiche significative, il controller abbinato passa i dati grezzi attraverso la pipeline.
  4. La logica applicativa funziona. Solo se i dati vengono trasmessi il titolare del trattamento chiama il metodo del servizio.
  5. Servizio -> archivio. Il servizio esegue la logica, richiamando facoltativamente metodi di repository che colpiscono il database.
  6. La risposta torna indietro. Qualunque cosa restituisca il servizio viene consegnata al controller, che la restituisce al chiamante tramite la connessione HTTP.
04

Il punto di esecuzione

La convalida e la trasformazione avvengono a esattamente un punto: all'interno del livello controller, immediatamente dopo il percorso è abbinato e prima viene chiamato qualsiasi metodo di servizio o viene eseguita qualsiasi logica applicativa. Concretamente è implementato come riutilizzabile middleware o funzione di utilità che hai in mano a schema: la descrizione di come dovrebbero apparire i dati e percorre ogni campo del payload in entrata rispetto a quello schema.

Perché la porta d'ingresso, in particolare La convalida al punto di ingresso garantisce che il sistema non porti mai un file stato inaspettato più profondo della porta d'ingresso. I dati errati vengono rifiutati quando è ancora economico rifiutarli, prima che si aprano le connessioni al database, prima che le e-mail vengano messe in coda, prima che si attivi qualsiasi effetto collaterale.
05

Perché è fondamentale: la storia 500 vs 400

Il modo più chiaro per sentire il bisogno di convalida è guardare cosa succede senza esso. Immagina un'API "crea libro" che prevede un corpo JSON con a name campo che dovrebbe essere una stringa. Un client invia invece il file numero 0:

POST /api/books
Corpo della richiesta (formato non valido)
{ "name": 0 }

Nel tuo schema Postgres la colonna è stata quasi certamente dichiarata in questo modo, una colonna stringa che non può essere nulla:

schema.sqlSQL
CREATE TABLE books (
  id    SERIAL PRIMARY KEY,
  name  TEXT NOT NULL   -- expects text, refuses an integer
);

Con nessuna convalida, quello 0 naviga attraverso il controller, attraverso il servizio, scende nel repository e diventa un file INSERT. Postgres controlla il tipo di colonna, vede un numero dove richiesto TEXT, e rifiuta l'operazione. La chiamata al database fallisce e il client riceve:

Risposta senza convalida 500 ERRORE SERVER INTERNO
"Qualcosa è andato storto sul server"
{ "error": "Internal Server Error" }

Questo è un scarsa esperienza utente. A 500 dice "qualcosa di inaspettato si è rotto dentro di noi" quando in realtà il cliente ha inviato input errati e non fornisce loro nulla da correggere. Con una pipeline di convalida nel punto di ingresso, il server rileva immediatamente l'errore, il database non viene mai toccato e il client ottiene un'azione utilizzabile 400 Richiesta errata:

Risposta con convalida 400 RICHIESTA ERRATA
Azionabile, restituito prima di qualsiasi chiamata DB
{ "errors": [ "name: expected a string, received a number" ] }
06

All'interno della pipeline: passo dopo passo

Una pipeline robusta elabora un campo strati, e l'ordine è importante: ogni controllo viene eseguito solo se quello precedente è stato superato. Prendi un singolo campo, name, che deve essere una stringa di lunghezza compresa tra 5 e 100:

  1. Verifica dell'esistenza. Lo fa name esistere nel payload? Altrimenti -> "name is required", fermare.
  2. Controllo del tipo. Esiste, è una stringa o il client ha inviato un array/booleano/numero? Se tipo sbagliato -> "expected a string", fermare.
  3. Controllo dei vincoli. È una stringa, soddisfa le restrizioni? Lunghezza 5-100. Una stringa di 2 caratteri o un intero paragrafo falliscono entrambi con un messaggio su misura.

Nel codice, le librerie lo esprimono come uno schema dichiarativo. Go utilizza comunemente i tag struct con go-playground/validator; Python utilizza Pydantic, dove lo stesso modello viene convalidato entrambi e trasforma. Ecco un completo, eseguibile versione della pipeline in ciascuno:

v Go (a sinistra) / Python (a destra), entrambi mostrati per intero, senza interruttore
pipeline.goVai
package books

import (
    "encoding/json"
    "fmt"
    "net/http"
    "strings"

    "github.com/go-playground/validator/v10"
)

// one shared, reusable validator (the pipeline engine)
var validate = validator.New()

// CreateBook is the SCHEMA. The tags declare every rule:
//   required      -> existence check
//   the Go type   -> type check (string)
//   min=5,max=100 -> constraint check
type CreateBook struct {
    Name string `json:"name" validate:"required,min=5,max=100"`
}

// runPipeline decodes then validates; returns 400-ready messages.
func runPipeline(r *http.Request) (*CreateBook, []string) {
    var body CreateBook

    // 1. TYPE CHECK during decode: a JSON number for `name`
    //    cannot unmarshal into a Go string -> caught here.
    if err := json.NewDecoder(r.Body).Decode(&body); err != nil {
        return nil, []string{"name: expected a string"}
    }
    // 2. EXISTENCE + CONSTRAINT checks in one pass.
    if err := validate.Struct(body); err != nil {
        return nil, formatErrors(err)
    }
    return &body, nil
}

// formatErrors turns validator output into human messages.
func formatErrors(err error) []string {
    var msgs []string
    for _, e := range err.(validator.ValidationErrors) {
        f := strings.ToLower(e.Field())
        switch e.Tag() {
        case "required":
            msgs = append(msgs, fmt.Sprintf("%s: is required", f))
        case "min":
            msgs = append(msgs, fmt.Sprintf("%s: min %s chars", f, e.Param()))
        case "max":
            msgs = append(msgs, fmt.Sprintf("%s: max %s chars", f, e.Param()))
        default:
            msgs = append(msgs, fmt.Sprintf("%s: failed %s", f, e.Tag()))
        }
    }
    return msgs
}
pipeline.pyPitone
from fastapi import HTTPException
from pydantic import BaseModel, Field, ValidationError


# CreateBook is the SCHEMA. Each annotation = one rule:
#   no default      -> existence check (required)
#   : str           -> type check
#   min/max_length  -> constraint check
class CreateBook(BaseModel):
    name: str = Field(min_length=5, max_length=100)


def run_pipeline(raw: dict) -> CreateBook:
    """Decode + validate in one call.
    Raises a 400-ready error on failure."""
    try:
        # constructing the model runs all three layers
        # in order: existence -> type -> constraint
        return CreateBook(**raw)
    except ValidationError as e:
        # reshape pydantic errors into clean strings
        messages = [
            f"{err['loc'][0]}: {err['msg']}"
            for err in e.errors()
        ]
        raise HTTPException(status_code=400, detail=messages)


# run_pipeline({})            -> 400 ["name: Field required"]
# run_pipeline({"name": 0})   -> 400 ["name: Input should be
#                                      a valid string"]
# run_pipeline({"name": "ab"})-> 400 ["name: String should
#                                      have at least 5 chars"]
# run_pipeline({"name": "Dune"}) ... still <5 -> 400
# run_pipeline({"name": "The Hobbit"}) -> OK

07

Convalida del tipo

Il sapore più elementare: il campo corrisponde a tipo di dati l'API si aspetta? È una stringa, un numero, un valore booleano, un array o un oggetto JSON nidificato e non qualcos'altro? Può anche applicarsi ricorsivamente: un campo array potrebbe richiederlo ogni elemento è una stringa, quindi elemento 0 essere un numero è di per sé un errore di tipo.

POST /api/valid/type
Tipi errati inviati
{ "stringField":"x", "numberField":"x", "arrayField":"x", "boolField":"x" }
Risposta 400
numberField: expected number, received string
arrayField:  expected array,  received string
boolField:   expected boolean, received string
Quindi una matrice di numeri in cui sono richieste le stringhe
{ "arrayField": [1, 2] }  ->  arrayField[0]: expected string, received number
Completamente corretto -> 200
{ "stringField":"something", "numberField":10, "arrayField":["one","two"], "boolField":false }
type_validation.goVai
package validate

import (
    "encoding/json"
    "errors"
    "net/http"
)

// *bool so we can tell "false" apart from "missing".
type TypePayload struct {
    StringField string   `json:"stringField" validate:"required"`
    NumberField float64  `json:"numberField" validate:"required"`
    // dive = recurse INTO the slice; each element required
    ArrayField  []string `json:"arrayField" validate:"required,dive,required"`
    BoolField   *bool    `json:"boolField" validate:"required"`
}

func parseTypes(r *http.Request) (*TypePayload, error) {
    var p TypePayload
    dec := json.NewDecoder(r.Body)
    dec.DisallowUnknownFields() // reject stray keys

    // json.Decode enforces the BASE types: a string for
    // numberField / arrayField / boolField fails to unmarshal.
    if err := dec.Decode(&p); err != nil {
        return nil, errors.New("a field has the wrong data type")
    }
    // existence + recursive element check
    if err := validate.Struct(p); err != nil {
        return nil, err
    }
    return &p, nil
}

// {"numberField":"x"} -> expected number, received string
// {"arrayField":[1,2]} -> arrayField[0]: expected string
type_validation.pyPitone
from pydantic import BaseModel
from typing import List


class TypePayload(BaseModel):
    stringField: str
    numberField: float
    arrayField:  List[str]   # recursive: EVERY element a string
    boolField:   bool


# Strict, explicit type errors:
#
# TypePayload(stringField="x", numberField="x",
#             arrayField="x", boolField="x")
#   -> numberField: Input should be a valid number
#   -> arrayField:  Input should be a valid list
#   -> boolField:   Input should be a valid boolean
#
# TypePayload(..., arrayField=[1, 2], ...)
#   -> arrayField.0: Input should be a valid string
#   -> arrayField.1: Input should be a valid string
#
# TypePayload(stringField="something", numberField=10,
#             arrayField=["one","two"], boolField=False) -> OK
08

Validazione sintattica

Qui il tipo è già corretto (una stringa) ma la stringa deve seguire a modello strutturale specifico. L'algoritmo di validazione controlla il forma del valore:

  • E-mail: una parte locale, quindi il @ carattere, quindi un dominio composto da un nome più un dominio di primo livello (.com, .co.in, .org, ...). Esistono migliaia di TLD validi; la struttura è ciò che viene controllato.
  • Numero di telefono: un codice paese seguito dal numero esatto di cifre per quel paese (ad esempio un codice paese seguito da un numero di 10 cifre).
  • Data: deve corrispondere alla struttura prevista, ad es. YYYY-MM-DD (anno, poi mese, poi giorno).
POST /api/valid/syntactic
Corpo vuoto
{ }
Risposta 400, gli errori raddoppiano come documentazione live
email: required   phone: required   date: required
Cattivi valori
{ "email":"randomstring", "phone":1234567, "date":"2025-11-05" }
Risposta 400
email: invalid email format
phone: expected a string, received a number
Corretto
{ "email":"test@test.com", "phone":"1234567", "date":"2025-11-05" }  ->  200
Un vantaggio gratuito Anche un client che accede all'API alla cieca, con un payload vuoto, recupera l'elenco dei campi obbligatori e le forme previste. Quando i documenti API mancano o non sono aggiornati, gli stessi messaggi di errore di convalida sono un ottimo modo per scoprire cosa richiede l'endpoint.
syntactic.goVai
package validate

import (
    "errors"
    "regexp"
)

// optional + then 7-15 digits (country code + national no.)
var phoneRe = regexp.MustCompile(`^\+?[0-9]{7,15}$`)

type Contact struct {
    Email string `validate:"required,email"`            // local @ domain.tld
    Phone string `validate:"required"`                  // checked below
    Date  string `validate:"required,datetime=2006-01-02"` // YYYY-MM-DD
}

// checkSyntax handles the phone pattern (validator's
// built-ins cover email + date structure already).
func (c Contact) checkSyntax() error {
    if !phoneRe.MatchString(c.Phone) {
        return errors.New("phone: invalid phone number format")
    }
    return nil
}

// "randomstring"            -> email: invalid email format
// phone sent as JSON number -> received a number, want string
// "2025-13-40"              -> date: does not match YYYY-MM-DD
syntactic.pyPitone
from datetime import date
from pydantic import BaseModel, EmailStr, Field


class Contact(BaseModel):
    email: EmailStr                       # local @ domain.tld
    # country code + 7-15 digits
    phone: str = Field(pattern=r"^\+?[0-9]{7,15}$")
    date:  date                           # only accepts YYYY-MM-DD


# Contact(email="randomstring", phone=1234567,
#         date="2025-11-05")
#   -> email: value is not a valid email address
#   -> phone: Input should be a valid string
#
# Contact(email="bad@", ...)
#   -> email: there must be something after the @-sign
#

#         date="2025-11-05")  -> OK
09

Convalida semantica

Il tipo è corretto e la sintassi è corretta, ma ha il valore ha senso nel mondo reale? I controlli semantici codificano la logica del dominio:

  • A data di nascita non può essere nel futuro, se lo è oggi 2025-01-11, un DOB di 2025-01-13 non ha senso anche se è una data perfettamente valida.
  • An età di 365 (o 430) non ha senso, almeno non ancora. Una fascia di età umana ragionevole è approssimativamente 1 a 120.
POST /api/valid/semantic
Futuro DOB
{ "dateOfBirth":"2026-06-12", "age":43 }
Risposta 400
dateOfBirth: date of birth cannot be in the future
Età impossibile
{ "dateOfBirth":"1995-06-12", "age":430 }
Risposta 400
age: number must be less than or equal to 120
Sensibile
{ "dateOfBirth":"1995-06-12", "age":43 }  ->  200
semantic.goVai
package validate

import (
    "errors"
    "time"
)

type Profile struct {
    DateOfBirth string `validate:"required,datetime=2006-01-02"`
    // gte/lte cover the "430 is impossible" semantic bound
    Age int `validate:"required,gte=1,lte=120"`
}

// Type & syntax can't express "not in the future"
// semantics need real logic against the real clock.
func (p Profile) checkSemantics() error {
    dob, err := time.Parse("2006-01-02", p.DateOfBirth)
    if err != nil {
        return errors.New("dateOfBirth: invalid date")
    }
    if dob.After(time.Now()) {
        return errors.New(
            "dateOfBirth: date of birth cannot be in the future")
    }
    return nil
}

// {"dateOfBirth":"2026-06-12"} -> cannot be in the future
// {"age":430}                  -> age: must be 120 or less
semantic.pyPitone
from datetime import date
from pydantic import BaseModel, Field, field_validator


class Profile(BaseModel):
    dateOfBirth: date
    age: int = Field(ge=1, le=120)   # 430 -> must be <= 120

    @field_validator("dateOfBirth")
    @classmethod
    def not_in_future(cls, v: date) -> date:
        if v > date.today():
            raise ValueError(
                "date of birth cannot be in the future")
        return v


# Profile(dateOfBirth="2026-06-12", age=43)
#   -> dateOfBirth: date of birth cannot be in the future
# Profile(dateOfBirth="1995-06-12", age=430)
#   -> age: Input should be less than or equal to 120
# Profile(dateOfBirth="1995-06-12", age=43) -> OK

Validazione complessa/dipendente

Il sapore più potente: da cui dipendono le regole di un campo altri campi. La pipeline può codificare una logica incrociata arbitraria:

  • Conferma della password: passwordConfirmation deve corrispondere esattamente password; e password deve contenere almeno 8 caratteri. Rendono due corde diverse "le password non corrispondono"; si ottiene una password di 6 caratteri "la stringa deve contenere almeno 8 caratteri".
  • Requisito condizionale: partner è facoltativo quando married è false, ma il momento married è true il partner il nome diventa obbligatorio: "Il nome del partner è obbligatorio in caso di matrimonio è vero".
POST /api/valid/complex
Password non corrispondente + breve
{ "password":"random", "passwordConfirmation":"another", "married":false }
Risposta 400
password: string must contain at least 8 characters
passwordConfirmation: passwords don't match
sposato=vero ma senza partner
{ "password":"random12", "passwordConfirmation":"random12", "married":true }
Risposta 400
partner: partner name is required when married is true
Completo
{ "password":"random12", "passwordConfirmation":"random12", "married":true, "partner":"Sam" }  ->  200
complesso.goVai
package validate

type Signup struct {
    Password string `json:"password" validate:"required,min=8"`
    // eqfield: must equal another field on the struct
    PasswordConf string `json:"passwordConfirmation" \
        validate:"required,eqfield=Password"`
    Married *bool `json:"married" validate:"required"`
    // required_if: partner required only if married == true
    Partner string `json:"partner" \
        validate:"required_if=Married true"`
}

// {password:"random", passwordConfirmation:"another",
//  married:false}
//   -> password: must be at least 8 characters
//   -> passwordConfirmation: passwords don't match
//
// {password:"random12", passwordConfirmation:"random12",
//  married:true}
//   -> partner: required when married is true
complesso.pyPitone
from pydantic import BaseModel, Field, model_validator


class Signup(BaseModel):
    password: str = Field(min_length=8)
    passwordConfirmation: str
    married: bool
    partner: str | None = None

    # mode="after": runs once all fields are parsed,
    # so it can compare them against each other.
    @model_validator(mode="after")
    def cross_field_rules(self):
        if self.password != self.passwordConfirmation:
            raise ValueError("passwords don't match")
        if self.married and not self.partner:
            raise ValueError(
                "partner name is required when married is true")
        return self


# Signup(password="random", passwordConfirmation="another",
#        married=False)
#   -> password: String should have at least 8 characters
#   -> Value error, passwords don't match
Parte III/Trasformazione
11

Trasformazione come fusione di tipo

Trasformazione significa eseguire operazioni sui dati in ingresso per convertirli in un formato desiderabile, prima della convalida (quindi può pass) o dopo di esso (per prepararlo per il livello di servizio). Il caso da manuale è parametri di query di impaginazione.

Considera GET /bookmarks?page=2&limit=20 con questi requisiti:

  • page, un numero maggiore di 0 e inferiore a 500.
  • limit, un numero maggiore di 0 e inferiore a 10.000 (al massimo 10.000 record restituiti alla volta).
La cattura I parametri di query sono sempre stringhe per impostazione predefinita. Ogni valore nella stringa di query arriva al tuo server come stringa, non hanno altro tipo nativo. Quindi page arriva come stringa "2", non il numero 2. Convalida che richiede a numero fallisce al primo controllo, anche se il client non ha fatto nulla di sbagliato, le stringhe sono semplicemente il modo in cui funzionano i parametri di query.

La soluzione non è l'errore. È il responsabilità del server a cast prima la stringa in un numero. Il "casting" forza un tipo di dati a diventare un altro. Cast "2" -> 2, quindi eseguire le convalide numeriche. La fase del casting è la trasformazione.

impaginazione.goVai
package validate

import (
    "errors"
    "net/url"
    "strconv"
)

type Pagination struct {
    Page  int
    Limit int
}

// Query params are ALWAYS strings, so we must CAST
// (transform) before we can VALIDATE the numbers.
func parsePagination(q url.Values) (*Pagination, error) {
    // TRANSFORM: force the string "2" into the int 2
    page, err := strconv.Atoi(q.Get("page"))
    if err != nil {
        return nil, errors.New("page: must be a number")
    }
    limit, err := strconv.Atoi(q.Get("limit"))
    if err != nil {
        return nil, errors.New("limit: must be a number")
    }

    // VALIDATE the now-numeric values
    if page <= 0 || page >= 500 {
        return nil, errors.New("page: must be 1..499")
    }
    if limit <= 0 || limit >= 10000 {
        return nil, errors.New("limit: must be 1..9999")
    }
    return &Pagination{Page: page, Limit: limit}, nil
}

Trasformazione come normalizzazione

Anche la trasformazione pulisce dati dopo la convalida, rimodellandoli in ciò che preferisce il livello di servizio. Il server normalizza silenziosamente il carico utile prima di fare qualsiasi cosa con esso:

  • An e-mail inviato con custodia mista, Test@TEST.com, ritorna memorizzato come tutto in minuscolo test@test.com.
  • A telefono la stringa ottiene a + prefisso iniettato prima di esso.
  • A data viene ricalcolato nel formato canonico previsto dal backend.

normalize.goVai
package validate

import "strings"

// normalize runs AFTER validation passes and BEFORE
// the data is handed to the service layer.
func (c *Contact) normalize() {
    // lowercase + trim the email
    c.Email = strings.ToLower(strings.TrimSpace(c.Email))

    // inject the leading + if it is missing
    c.Phone = strings.TrimSpace(c.Phone)
    if !strings.HasPrefix(c.Phone, "+") {
        c.Phone = "+" + c.Phone
    }
}

// "Test@TEST.com" -> "test@test.com"
// "1234567"       -> "+1234567"
normalize.pyPitone
from pydantic import BaseModel, EmailStr, field_validator


class Contact(BaseModel):
    email: EmailStr
    phone: str

    # field_validators double as transformers: whatever
    # they return REPLACES the incoming value.
    @field_validator("email")
    @classmethod
    def lower_email(cls, v: str) -> str:
        return v.strip().lower()       # normalize case

    @field_validator("phone")
    @classmethod
    def add_plus(cls, v: str) -> str:
        v = v.strip()
        return v if v.startswith("+") else "+" + v

Una pipeline combinata

In pratica lo sono validazioni e trasformazioni accoppiati in un'unica pipeline. Il motivo è la località: l'intero "livello dei dati di input", ogni requisito e ogni operazione eseguita sui dati in entrata prima dell'esecuzione di qualsiasi logica applicativa, vive un posto. Non è mai necessario cercare tra i file per scoprire cosa si aspetta un endpoint o cosa fa silenziosamente ai dati. La pipeline può trasformare -> convalidare o convalidare -> trasformare, in entrambi gli ordini, a seconda dei requisiti.

Convalida frontend e backend

Un errore comune e pericoloso è considerare la convalida del frontend come un file sostituzione per la convalida del backend. Non sono intercambiabili, servono a scopi diversi e sono necessari entrambi per ogni API.

FrontendPer l'esperienza utente
Un modulo Web viene convalidato mentre l'utente digita e invia, dando feedback immediato e amichevole ("non sembra un'e-mail") prima che venga effettuata qualsiasi chiamata API. Il suo intero lavoro è l'esperienza dell'utente. Lo è no sulla sicurezza o sull’integrità dei dati.
BackendPer la sicurezza
La convalida lato server è obbligatorio ed esiste per la sicurezza e l'integrità dei dati. Non importa quale sia il client o se sia stato validato, il server deve essere il più rigoroso e specifico possibile.

Perché il backend non può fidarsi del frontend? Perché un server può avere molti clienti diversi. Un'app Web raffinata potrebbe essere convalidata magnificamente, ma la stessa API può anche essere raggiunta direttamente tramite un client API come Il postino o l'insonnia, dove non esiste un frontend che funga da proxy e quindi nessuna convalida del frontend. Se il backend dipendesse mai dal frontend per la sicurezza o l'integrità, il server si romperebbe nel momento in cui il client cambiasse.

Quando i due sono collegati correttamente si completano a vicenda: in un modulo web, un'e-mail non valida blocca l'invio e mostra un errore in linea, non viene nemmeno effettuata alcuna chiamata API. Correggilo su un indirizzo reale e l'invio attiva una richiesta adeguata; il payload viene inviato, il server convalida nuovamente e restituisce 200. Il frontend ha fornito un feedback immediato; il backend ha fornito la garanzia.

La regola, detta chiaramente Progetta la convalida lato server in modo che sia il più rigorosa e specifica possibile senza mai pensarci come appare la convalida del client. La convalida del frontend riguarda l'esperienza dell'utente; la convalida del backend riguarda la sicurezza e l'integrità dei dati. Hai sempre bisogno di entrambi.

Controller completo con annotazioni

Mettendo insieme il quadro completo: un controller completo che corrisponde al percorso, esegue la pipeline combinata (trasforma -> convalida -> normalizza) prima qualsiasi logica applicativa, restituisce un risultato pulito 400 in caso di errore e solo allora chiama il livello di servizio, che chiama il repository. main.goVai
package main

import (
    "context"
    "encoding/json"
    "net/http"
    "strings"

    "github.com/go-playground/validator/v10"
)

var validate = validator.New()

// ---- schema (the gate) ----
type CreateBook struct {
    Name string `json:"name" validate:"required,min=5,max=100"`
}

type Book struct {
    ID   int    `json:"id"`
    Name string `json:"name"`
}

// ---- helper ----
func writeJSON(w http.ResponseWriter, status int, b any) {
    w.Header().Set("Content-Type", "application/json")
    w.WriteHeader(status)
    json.NewEncoder(w).Encode(b)
}

// ---- CONTROLLER: owns HTTP + the validation gate ----
func createBookHandler(w http.ResponseWriter, r *http.Request) {
    var body CreateBook

    // === GATE, runs before ANY business logic ===
    if err := json.NewDecoder(r.Body).Decode(&body); err != nil {
        writeJSON(w, 400, map[string]string{
            "error": "name: expected a string"})
        return // 400, the DB is never touched
    }
    body.Name = strings.TrimSpace(body.Name) // transform
    if err := validate.Struct(body); err != nil {
        writeJSON(w, 400, map[string]string{
            "error": err.Error()})
        return // 400 Bad Request, not a confusing 500
    }

    // === only now: business logic (service -> repo) ===
    book, err := createBook(r.Context(), body.Name)
    if err != nil {
        writeJSON(w, 500, map[string]string{
            "error": "could not create book"})
        return
    }
    writeJSON(w, 201, book)
}

// ---- service + repository (sketched) ----
func createBook(ctx context.Context, name string) (*Book, error) {
    // service logic ... repository INSERT ... then:
    return &Book{ID: 1, Name: name}, nil
}

func main() {
    http.HandleFunc("/api/books", createBookHandler)
    http.ListenAndServe(":8080", nil)
}
main.pyPitone
from fastapi import FastAPI, HTTPException
from pydantic import BaseModel, Field, field_validator

app = FastAPI()


# ---- schema (the gate) ----
class CreateBook(BaseModel):
    name: str = Field(min_length=5, max_length=100)

    @field_validator("name")
    @classmethod
    def trim(cls, v: str) -> str:
        return v.strip()          # transform / normalize


class Book(BaseModel):
    id: int
    name: str


# ---- service + repository (sketched) ----
def create_book(name: str) -> Book:
    # service logic ... repository INSERT ... then:
    return Book(id=1, name=name)


# ---- CONTROLLER ----
# FastAPI runs the CreateBook schema (the GATE) BEFORE
# this function body. A bad payload never enters the
# function, the client gets an automatic 422/400, so
# the DB is never touched and no client mistake leaks
# out as a confusing 500.
@app.post("/api/books", status_code=201)
def create_book_endpoint(body: CreateBook) -> Book:
    # validation already passed, straight to logic
    try:
        return create_book(body.name)  # service -> repo
    except Exception:
        raise HTTPException(
            status_code=500, detail="could not create book")
