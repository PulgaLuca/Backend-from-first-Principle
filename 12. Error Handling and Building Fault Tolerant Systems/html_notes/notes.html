Gestione degli errori e sistemi tolleranti ai guasti

Gli errori non sono eccezionali, lo sono inevitabile. Le query del database falliscono, le API esterne scadono, gli utenti inviano dati errati e la logica applicativa colpisce casi limite che nessuno aveva previsto. Questo capitolo definisce la mentalità e gli strumenti concreti per rilevare, gestire e recuperare ogni tipo di errore di backend, prima che ti costi silenziosamente denaro o fiducia.

01

La mentalità tollerante agli errori

"La domanda non è se gli errori si verificheranno, ma come li gestirai quando si verificheranno."

Ogni ingegnere di backend deve interiorizzare una semplice verità: il tuo sistema fallirà. Non potrebbe. Volere. Le fonti sono ovunque:

  • Le query del database occasionalmente falliscono o scadono.
  • Le API esterne (pagamenti, email, autenticazione) verranno disattivate.
  • Gli utenti invieranno dati non corretti, mancanti o dannosi.
  • La logica applicativa colpirà casi limite a cui nessuno aveva pensato durante la progettazione.

Un sistema tollerante ai guasti non è un sistema che non si rompe mai. È uno di quelli si rompe in modo prevedibile, si riprende con grazia e ti dice esattamente cosa è successo. Per raggiungere questo obiettivo è necessario un deliberato cambiamento di mentalità da "gestirò gli errori in seguito" a "progetterò per il fallimento fin dal primo giorno".

Inizia la migliore gestione degli errori prima si verifica l'errore. Il rilevamento proattivo, i controlli dello stato e la convalida prevengono la maggior parte delle sorprese in fase di runtime.
02

Le cinque classi di errori di backend

Gli errori di backend possono essere raggruppati in cinque grandi categorie. Ognuno ha un'origine, una strategia di rilevamento e una correzione diversa.

(1) Errori logici

L'app viene eseguita ma produce risultati errati. Più difficile da rilevare. Può drenare silenziosamente denaro per settimane.

(2) Errori del database

Errori di connessione, deadlock, violazioni di vincoli, SQL non valido. Può disattivare l'intera app.

(3) Errori di servizio esterni

Le API di terze parti (pagamento, e-mail, autenticazione) scadono, limitano la velocità o vanno offline. Non hai alcun controllo.

(4) Errori di convalida dell'input

Gli utenti inviano dati errati, mancanti o fuori portata. Più facile da gestire, se il livello di convalida è robusto.

(5) Errori di configurazione

Variabili di ambiente mancanti, credenziali errate durante la distribuzione. Surface all'avvio, non in fase di esecuzione, se lo fai bene.

03

Errori logici: i killer silenziosi

Gli errori logici sono i più frequenti pericoloso class perché la tua applicazione continua a funzionare, fa semplicemente la cosa sbagliata. Nessun arresto anomalo, nessuna traccia dello stack, nessuna risposta 500. Solo risultati silenziosamente sbagliati che si accumulano nel tempo.

Esempio classico

Una piattaforma di e-commerce applica uno sconto due volte a causa di un bug nel motore delle promozioni. Il risultato: spese di spedizione negative. L'app funziona perfettamente. Ogni ordine viene spedito. L'azienda perde denaro su ogni transazione. Ciò passa inosservato per settimane perché nessun avviso di monitoraggio si attiva sul "costo di spedizione negativo".

Cause principali comuni

  • Requisiti fraintesi: gli appunti di uno sprint meeting erano ambigui; hai implementato ciò che tu pensiero è stato chiesto, non cosa si intendesse.
  • Algoritmi errati: una formula di sconto o di determinazione del prezzo complessa presenta un errore sfasato o un operatore sbagliato (* invece di +).
  • Casi limite non gestiti: un utente che non ha mai acquistato prima attiva un percorso di sconti "basato sugli acquisti precedenti" che non è stato progettato per gli utenti con acquisto zero.
Errori logici che coinvolgono denaro, autorizzazioni o sicurezza possono corrompere i dati e produrre risultati aziendali errati per mesi senza una singola voce nel registro degli errori. Vengono rilevati solo attraverso test accurati, monitoraggio delle metriche aziendali e revisione del codice.

Strategie di prevenzione

  • Scrivi test unitari per ogni regola aziendale, in particolare la logica di sconti, prezzi e autorizzazioni.
  • Aggiungi monitoraggio delle metriche aziendali (ad esempio, avvisa se il valore medio dell'ordine scende di >20% in un'ora).
  • Utilizzare test basati sulle proprietà (Vai: gopter, Pitone: hypothesis) per generare automaticamente input di casi limite.
  • Richiedi revisione tra pari per tutte le modifiche al codice relative al pagamento e all'autenticazione.
04

Errori del database

La maggior parte delle applicazioni backend non hanno senso senza il loro database. Un errore del database di qualsiasi tipo significa che la tua app non può fornire dati reali, il che di solito significa un'interfaccia utente interrotta o errori a catena tra i servizi.

(1) Errori di connessione

Il tuo backend non può raggiungere il server del database. Possibili cause:

  • Partizione di rete o errore DNS tra il server app e il server DB.
  • Il server del database è sovraccarico o inattivo.
  • Pool di connessioni esaurito: tutte le connessioni TCP in pool sono in uso; le nuove richieste si mettono in coda o falliscono immediatamente.
Raggruppamento delle connessioni mantiene un numero fisso di connessioni TCP aperte al database, evitando il sovraccarico di un handshake TCP completo + negoziazione TLS su ogni query. Strumenti: pgxpool (Vai), psycopg2 piscina o SQLAlchemy (Pitone), pg Piscina (nodo). Dimensiona attentamente la tua piscina: troppo piccola -> collo di bottiglia; troppo grande -> sovraccarico DB.

(2) Errori di violazione dei vincoli

Stai tentando di eseguire un'operazione che viola una regola a livello di database:

Tipo di vincoloInnescoRisposta adeguata
UnicoInserisci un'e-mail/nome utente duplicatoConflitto HTTP 409 o 400, "E-mail già in uso"

ControllaIl valore non soddisfa una regola personalizzata (ad esempio prezzo > 0)HTTP 400, messaggio specifico del dominio

(3) Errori di query/sintassi

SQL non valido, errore di battitura nel nome della tabella, riferimento a una colonna rinominata o condizione di unione mancante. Questi di solito vengono catturati durante lo sviluppo ma possono sfuggire se le stringhe SQL grezze vengono create dinamicamente.

Non costruire mai SQL mediante concatenazione di stringhe con l'input dell'utente. Utilizzare sempre query con parametri/istruzioni preparate. Ciò impedisce entrambi gli errori di query e Attacchi SQL injection.

(4) Deadlock

Un deadlock si verifica quando due (o più) transazioni detengono ciascuna un blocco di cui l'altra ha bisogno:

Fig 1: Deadlock: due transazioni in attesa l'una sui blocchi dell'altra a tempo indeterminato. Il DB ne rileva e ne interrompe uno.

Postgres rileva automaticamente i deadlock e interrompe una transazione con un codice di errore 40P01. La tua domanda deve riprovare la transazione. Prevenzione: acquisire sempre i lucchetti in a ordine coerente attraverso tutti i percorsi del codice.

05

Errori di servizio esterni

I moderni backend SaaS dipendono da una costellazione di servizi di terze parti, processori di pagamento (Stripe), e-mail (Resend, SendGrid), archiviazione di oggetti (S3), autenticazione (Clerk, Auth0), AI (OpenAI). Ognuno di questi è a punto di fallimento fuori dal tuo controllo.

Fig 2: Ogni dipendenza esterna è un punto di errore indipendente che la tua app deve gestire con garbo.

(1) Guasti di rete

La connessione Internet tra il tuo server e l'API esterna non è affidabile. Incontrerai: timeout della connessione, errori di risoluzione DNS, partizioni di rete ed errori di handshake TLS. Impostato timeout espliciti su ogni chiamata HTTP in uscita, non lasciare mai che un'API lenta di terze parti blocchi la tua goroutine/thread a tempo indeterminato.

(2) Limitazione della velocità: HTTP 429

Ogni API esterna seria applica limiti di velocità per prevenire abusi. Se la tua app blocca un'API (a causa di un bug, un picco di traffico o un errore di loop), riceverai HTTP 429 Too Many Requests.

La mitigazione standard è Backoff esponenziale con jitter:

Fig 3: Backoff esponenziale: ogni tentativo attende 2 volte più a lungo. Il jitter diffonde i tentativi per evitare una mandria tuonante.

(3) Interruzione del servizio/Tempi di inattività

I principali fornitori di servizi cloud (AWS, GCP) e i più diffusi servizi SaaS si interrompono occasionalmente. La tua app necessita di una strategia per quando una dipendenza critica non è completamente disponibile:

  • Ripiego: se la cache Redis è inattiva, torna alle letture DB dirette per i dati non critici.
  • Degrado grazioso: disabilita la funzionalità interessata (ad esempio "Suggerimenti AI temporaneamente non disponibili") anziché bloccare l'intera app.
  • Schema dell'interruttore automatico: dopo N errori consecutivi, interrompe l'invio di richieste al servizio interrotto e restituisce immediatamente una risposta memorizzata nella cache/predefinita. Riprovare il servizio dopo un periodo di raffreddamento.
06

Errori di convalida dell'input

Questi sono i errori più facili da gestire perché sei tu a definire le regole. Il livello di convalida è la prima linea di difesa: rileva i dati errati nel punto di ingresso, prima che raggiungano il database o la logica applicativa.

Tipi di convalida

DigitareCosa controllaEsempio
FormatoForma/modello del valoreRegex email, data ISO, telefono E.164
GammaLimiti numerici, lunghezza della stringa, dimensione dell'arrayPrezzo: 0-99999, nome: 2-100 caratteri
ObbligatorioCampo obbligatorio presenteuser_id non deve essere nullo
Regola aziendaleVincolo specifico del dominioData_fine prenotazione > data_inizio
ReferenzialeL'entità correlata esiste effettivamenteCategory_id esiste nella tabella delle categorie

Convalidare sempre a entrambi gli strati: frontend (UX) e back-end (sicurezza). Non fidarti mai solo della convalida lato client. Il backend è il cancello autorevole.

Restituisce HTTP 400 Bad Request con un corpo dell'errore strutturato che elenca tutti i campi non riusciti e il motivo. Non restituire un singolo messaggio generico, aiuta l'utente a correggere tutti i propri errori in un unico viaggio di andata e ritorno.
07

Errori di configurazione

Gli errori di configurazione si verificano al confine tra ambienti, sviluppo -> staging -> produzione. Una scomparsa OPENAI_API_KEY, un URL di database errato o un segreto dimenticato possono interrompere silenziosamente funzionalità specifiche mentre il resto dell'app appare integro.

Errore rapido all'avvio: non in fase di runtime

La regola d'oro: convalidare tutte le variabili di ambiente richieste prima che il server inizi ad accettare il traffico. Se qualcuno manca o è danneggiato, si blocca immediatamente con un messaggio di errore chiaro.

Difetto: errore di runtime

  • L'app si avvia correttamente
  • Il primo utente raggiunge l'endpoint dell'immagine AI
  • La chiamata OpenAI fallisce, manca la chiave
  • L'utente riceve un misterioso errore 500
  • La vecchia distribuzione è già stata interrotta
  • Il sito è inattivo finché non viene risolto manualmente

Buono: errore di avvio

  • Inizia la nuova distribuzione
  • La convalida della configurazione viene eseguita immediatamente
  • Rilevata chiave mancante -> il processo esce con un messaggio chiaro
  • Blu-verde: vecchia distribuzione ancora in esecuzione
  • Zero tempi di inattività, correzioni e ridistribuzioni da parte del team operativo
Le implementazioni blu-verdi rendono sicuri i crash all'avvio: la nuova versione deve superare i controlli di integrità prima che la vecchia versione venga terminata. Se la nuova versione si blocca all'avvio, la vecchia versione continua a servire il traffico.

Gopackage config

import (
    "fmt"
    "os"
    "strings"
)

type Config struct {
    DatabaseURL    string
    OpenAIKey      string
    JWTSecret      string
    ResendAPIKey   string
}

// MustLoad panics if any required variable is missing.
// Call this once in main() before http.ListenAndServe.
func MustLoad() Config {
    required := []string{
        "DATABASE_URL",
        "OPENAI_API_KEY",
        "JWT_SECRET",
        "RESEND_API_KEY",
    }

    var missing []string
    for _, key := range required {
        if os.Getenv(key) == "" {
            missing = append(missing, key)
        }
    }
    if len(missing) > 0 {
        // Crash immediately, loud and clear
        panic(fmt.Sprintf("[FATAL] missing required env vars: %s",
            strings.Join(missing, ", ")))
    }

    return Config{
        DatabaseURL:  os.Getenv("DATABASE_URL"),
        OpenAIKey:    os.Getenv("OPENAI_API_KEY"),
        JWTSecret:    os.Getenv("JWT_SECRET"),
        ResendAPIKey: os.Getenv("RESEND_API_KEY"),
    }
}

// main.go
func main() {
    cfg := config.MustLoad()  // panics here if config invalid
    server := newServer(cfg)
    log.Fatal(server.ListenAndServe())
}

Rilevamento proattivo degli errori: controlli dello stato

"La migliore gestione degli errori inizia prima che si verifichi l'errore."

I controlli dello stato verificano continuamente che il tuo sistema funzioni, non solo che lo sia correre. C'è una differenza fondamentale:

Fig 4: Liveness vs Readiness: la suddivisione standard del settore (Kubernetes utilizza entrambi).

Cosa controllare

  • Banca dati: esegue una query rappresentativa leggera. Tieni traccia del tempo di query; se passa da 50ms a 4s, c'è qualcosa che non va prima che l'utente se ne accorga.
  • Servizi esterni: processori di pagamento: eseguono transazioni di prova periodiche; email: inviare ad un indirizzo interno; auth: genera e convalida un token di prova.
  • Configurazione: verifica che tutte le variabili di ambiente richieste siano caricate e non vuote all'avvio.
  • Riscaldamento della cache: garantisce che le cache critiche (archivio sessioni, catalogo prodotti) siano popolate prima di servire il traffico.

Vai: Endpoint di controllo approfondito dello stato

Gotype HealthStatus struct {
    Status   string            `json:"status"`
    Checks   map[string]string `json:"checks"`
}

func healthHandler(db *pgxpool.Pool, rdb *redis.Client) http.HandlerFunc {
    return func(w http.ResponseWriter, r *http.Request) {
        checks := map[string]string{}
        overall := "ok"

        // DB check
        ctx, cancel := context.WithTimeout(r.Context(), 2*time.Second)
        defer cancel()
        if err := db.Ping(ctx); err != nil {
            checks["database"] = "unhealthy: " + err.Error()
            overall = "degraded"
        } else {
            checks["database"] = "ok"
        }

        // Redis check
        if err := rdb.Ping(r.Context()).Err(); err != nil {
            checks["cache"] = "unhealthy: " + err.Error()
            overall = "degraded"
        } else {
            checks["cache"] = "ok"
        }

        status := http.StatusOK
        if overall != "ok" { status = http.StatusServiceUnavailable }

        w.Header().Set("Content-Type", "application/json")
        w.WriteHeader(status)
        json.NewEncoder(w).Encode(HealthStatus{Status: overall, Checks: checks})
    }
}

Monitoraggio e osservabilità

I controlli sanitari ti dicono che qualcosa è rotto proprio adesso. Il monitoraggio ti dice che qualcosa lo è sul punto di rompersie ti fornisce il contesto per capire perché qualcosa si è rotto dopo il fatto.

Cosa monitorare

CategoriaMetriche da monitorarePerché
Livello HTTPVelocità 4xx/5xx, latenza p50/p95/p99Fai emergere immediatamente i problemi rivolti agli utenti
Banca datiDurata della query, utilizzo del pool di connessioni, conteggio dei deadlockRileva query lente prima del timeout
Servizi EsterniTasso di successo delle chiamate, latenza, conteggio 429Scopri quando una dipendenza è degradante
Metriche aziendaliTransazioni riuscite/min, pagamenti falliti, tasso di iscrizioneRileva gli errori logici invisibili ai tassi di errore
InfrastrutturaCPU, memoria, I/O del disco, throughput di reteL'esaurimento delle risorse precede gli arresti anomali
Non monitorare solo i tassi di errore. Un calo delle transazioni riuscite da 1000/min a 200/min è un problema critico, anche se il tasso di errore è pari allo 0%. Monitora sempre i risultati aziendali positivi, non solo i segnali di fallimento.

Registrazione strutturata (JSON)

È difficile eseguire query sui log in testo semplice su larga scala. Utilizza log JSON strutturati in modo che gli strumenti di aggregazione dei log (Grafana Loki, Datadog, ELK) possano analizzarli, filtrarli e inviare avvisi in modo programmatico.

Strategie di recupero

Recuperabile e non recuperabile

Errori recuperabili

  • Problema tecnico transitorio della rete all'API e-mail
  • Pool di connessioni al database temporaneamente esaurito
  • Limite di tariffa 429 dal servizio esterno

Strategia: Riprovare con backoff esponenziale. Metti in coda il lavoro. Non arrenderti immediatamente.

Errori irreversibili

  • Cluster Redis completamente inattivo
  • Processore di pagamento offline per ore
  • Dati corrotti nel DB

Strategia: Degrado grazioso. Ricaderci. Disabilita la funzione. Proteggi le funzionalità principali.

Backoff esponenziale in Go

Gofunc sendEmailWithRetry(to, subject, body string) error {
    maxRetries := 5
    baseDelay  := 1 * time.Second

    for attempt := 0; attempt < maxRetries; attempt++ {
        err := emailClient.Send(to, subject, body)
        if err == nil {
            return nil  // success
        }

        if !isRetryable(err) {
            return fmt.Errorf("permanent failure: %w", err)
        }

        // Exponential backoff: 1s, 2s, 4s, 8s, 16s
        wait := baseDelay * time.Duration(1<<attempt)
        // Add jitter (+/-20%) to prevent thundering herd
        jitter := time.Duration(rand.Int63n(int64(wait / 5)))
        time.Sleep(wait + jitter)

        log.Warn("email send failed, retrying",
            "attempt", attempt+1,
            "wait_ms", wait.Milliseconds(),
            "error", err)
    }
    return fmt.Errorf("all %d retries exhausted", maxRetries)
}

func isRetryable(err error) bool {
    // Retry on 429, 503, network errors; not on 400, 401, 422
    var httpErr *HTTPError
    if errors.As(err, &httpErr) {
        return httpErr.StatusCode == 429 || httpErr.StatusCode >= 500
    }
    return true  // network errors are always retryable
}

Ripristino automatico o manuale

  • Automatico: riavviare i processi in crash (systemd, policy di riavvio Kubernetes), pulire le cache danneggiate, passare ai sistemi di backup. Progettare attentamente, a volte il ripristino automatico può amplificare un problema.
  • Manuale: corruzione dei dati, discrepanze nei pagamenti, incidenti di sicurezza. Questi richiedono il giudizio umano. Documentare il runbook. Provalo. Scopri chi è di guardia.
L'integrità dei dati è la tua priorità numero 1 durante qualsiasi incidente. Non eliminare o migrare mai automaticamente i dati come parte di una procedura di ripristino degli errori. Prima fai un backup, sempre.

Gestore globale degli errori: la rete di sicurezza finale

Il gestore degli errori globale è un singolo middleware che si trova nello strato più esterno dell'applicazione, rileva ogni errore che emerge da qualsiasi livello e lo converte in una risposta HTTP adeguatamente formattata.

Fig 5: Tutti gli errori riguardano un middleware. Un posto per definire ogni formato di risposta.

Due vantaggi principali

  • Nessuna condizione di errore dimenticata: ogni errore non gestito passa al caso predefinito del gestore globale (500 + "something went wrong"). Niente ingoiato silenziosamente.
  • Ridondanza zero: risiede la logica di gestione degli errori del database un file, non sparsi in 40 metodi di repository. Cambia il messaggio di violazione univoco una volta, si applica ovunque.

Vai: Implementazione del gestore errori globale

Go non ha eccezioni, gli errori sono valori restituiti. Lo schema consiste nel restituire gli errori nello stack di chiamate e gestirli nel middleware.

Go / errors/types.gopackage apperr

import "net/http"

// AppError is the canonical error type for this application.
type AppError struct {
    Code    int      // HTTP status code
    Message string   // Safe, user-facing message
    Details any      // Optional: field-level errors for 400s
    Err     error    // Original error, for logging only, NEVER sent to client
}

func (e *AppError) Error() string { return e.Message }

// Constructors
func NotFound(resource string) *AppError {
    return &AppError{Code: http.StatusNotFound, Message: resource + " not found"}
}
func Conflict(msg string) *AppError {
    return &AppError{Code: http.StatusConflict, Message: msg}
}
func BadRequest(msg string, details any) *AppError {
    return &AppError{Code: http.StatusBadRequest, Message: msg, Details: details}
}
func Internal(err error) *AppError {
    return &AppError{
        Code:    http.StatusInternalServerError,
        Message: "something went wrong",  // NEVER expose err.Error() here
        Err:     err,
    }
}
Go / middleware/error_handler.gopackage middleware

import (
    "encoding/json"
    "errors"
    "log/slog"
    "net/http"

    "github.com/jackc/pgx/v5/pgconn"
    apperr "yourapp/errors"
)

type ErrorResponse struct {
    Code    int    `json:"code"`
    Message string `json:"message"`
    Details any    `json:"details,omitempty"`
}

// GlobalErrorHandler wraps a handler that returns an error.
func GlobalErrorHandler(next func(http.ResponseWriter, *http.Request) error) http.HandlerFunc {
    return func(w http.ResponseWriter, r *http.Request) {
        err := next(w, r)
        if err == nil { return }

        var appErr *apperr.AppError

        switch {
        // Already wrapped as AppError
        case errors.As(err, &appErr):
            if appErr.Err != nil {
                slog.Error("app error", "err", appErr.Err)
            }

        // Postgres unique constraint violation -> 409
        case isPgError(err, "23505"):
            appErr = apperr.Conflict("resource already exists")

        // Postgres foreign key violation -> 404
        case isPgError(err, "23503"):
            appErr = apperr.NotFound("referenced resource")

        // pgx no-rows -> 404
        case errors.Is(err, pgx.ErrNoRows):
            appErr = apperr.NotFound("resource")

        // Everything else -> 500 (never leak internal error)
        default:
            slog.Error("unhandled error", "err", err)
            appErr = apperr.Internal(err)
        }

        w.Header().Set("Content-Type", "application/json")
        w.WriteHeader(appErr.Code)
        json.NewEncoder(w).Encode(ErrorResponse{
            Code:    appErr.Code,
            Message: appErr.Message,
            Details: appErr.Details,
        })
    }
}

func isPgError(err error, code string) bool {
    var pgErr *pgconn.PgError
    return errors.As(err, &pgErr) && pgErr.Code == code
}

    return JSONResponse(
        status_code=exc.status,
        content={"code": exc.status, "message": exc.message, "details": exc.details}
    )

@app.exception_handler(pg_errors.UniqueViolation)
async def unique_violation_handler(request: Request, exc):
    logger.warning("unique_violation", extra={"path": request.url.path})
    return JSONResponse(status_code=409,
        content={"code": 409, "message": "resource already exists"})

@app.exception_handler(pg_errors.ForeignKeyViolation)
async def fk_violation_handler(request: Request, exc):
    return JSONResponse(status_code=404,
        content={"code": 404, "message": "referenced resource not found"})

@app.exception_handler(Exception)
async def unhandled_error_handler(request: Request, exc: Exception):
    # Log the real error internally, never expose it
    logger.error("unhandled_exception", exc_info=exc,
        extra={"path": request.url.path})
    return JSONResponse(status_code=500,
        content={"code": 500, "message": "something went wrong"})

Sicurezza: cosa esporre, cosa nascondere

Ogni messaggio di errore che lascia il tuo backend è una potenziale perdita di informazioni. Tratta le tue risposte agli errori con la stessa cura delle risposte API.

(1) Non divulgare mai i dettagli interni

I messaggi di errore del database provenienti da Postgres contengono nomi di tabelle, nomi di colonne, nomi di indici e nomi di vincoli. Se inoltri un file raw pgconn.PgError messaggio direttamente al client, un utente malintenzionato apprende il tuo schema e può creare tentativi di SQL injection più mirati.

Quello che haiCosa inviare al cliente
duplicate key value violates unique constraint "users_email_key""Email already in use"
relation "usres" does not exist (errore di battitura)"Something went wrong"
deadlock detected on relation 42816"Something went wrong, please retry"
stack trace: panic at server.go:142"Internal server error"

(2) Errori di autenticazione vaghi (di proposito)

Gli endpoint di accesso sono la superficie più attaccata in qualsiasi applicazione. Se restituisci messaggi specifici come "non esiste alcun utente con questa email" contro "la password non è corretta", un utente malintenzionato può enumerare i messaggi di posta elettronica validi tramite un semplice ciclo.

Fig 6: Messaggi di errore di autenticazione specifici consentono attacchi di enumerazione della posta elettronica. Utilizza un singolo messaggio generico per tutti gli errori di autenticazione.

(3) Pratiche di registrazione sicure

I log vengono spesso inviati a servizi di aggregazione di terze parti (Datadog, Grafana Cloud, ELK). Nelle principali violazioni dei dati, i file di registro trapelati hanno esposto milioni di record, perché gli ingegneri avevano registrato incautamente campi sensibili.

  • Non accedere mai: password, chiavi API, numeri di carta di credito, SSN, indirizzi email completi, token di sessione.
  • Accedi invece: ID utente (non email), ID correlazione/richiesta, nome operazione, codice errore.
  • Utilizzare a libreria di pulizia dei log (ad es. Vai: slog con gestore personalizzato; Pitone: structlog processori) per oscurare automaticamente i campi sensibili noti.
Go / safe vs unsafe logging//UNSAFE, never do this
slog.Error("login_failed",
    "email", user.Email,          // PII leak
    "password", req.Password,     // catastrophic
    "api_key", cfg.OpenAIKey,      // secret leak
)

// SAFE, IDs and correlation only
slog.Error("login_failed",
    "user_id", user.ID,
    "correlation_id", r.Header.Get("X-Request-ID"),
    "reason", "invalid_credentials",  // generic code, not DB message
)
