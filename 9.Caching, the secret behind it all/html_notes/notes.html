Capitolo 09 / Memorizzazione nella cache

Memorizzazione nella cache

Comprendere il meccanismo che rende veloci i sistemi backend ad alte prestazioni, da Ricerca Google a Netflix a Redis.

01/DEFINIZIONE

Cos'è la memorizzazione nella cache?

La memorizzazione nella cache è un meccanismo mediante il quale riduciamo la quantità di tempo e impegno necessari per eseguire alcune operazioni.

Quella riga è l'intero concetto riassunto. Ma analizziamolo correttamente perché le implicazioni sono profonde in tutta l'ingegneria di backend.

La definizione in due parti

Esistono due modi per comprendere la memorizzazione nella cache, una versione in inglese semplice e una tecnica. Entrambi dicono esattamente la stessa cosa, solo a diversi livelli di precisione:

Definizione inglese semplice

La memorizzazione nella cache è un meccanismo mediante il quale riduciamo la quantità di tempo e impegno necessari per eseguire una certa quantità di lavoro. Questa è la spiegazione in linea di cosa sia esattamente la memorizzazione nella cache.

Definizione tecnica

La memorizzazione nella cache lo è mantenendo un sottoinsieme di alcuni dati: diciamo che abbiamo una fonte dati primaria, quando conserviamo a sottoinsieme (non tutti i dati, un sottoinsieme) di tali dati, a seconda degli usi dei dati, della frequenza degli usi, della probabilità del prossimo utilizzo, del tempo, ecc.: a seconda di molti parametri, manteniamo quel sottoinsieme in a posizione a cui è più veloce accedere, che richiede meno tempo e anche meno sforzo. Quindi, tecnicamente parlando, il caching è un meccanismo mediante il quale possiamo ridurre la quantità di tempo e lo sforzo necessari per recuperare o eseguire qualche tipo di operazione.

Perché "Sottoinsieme" è la parola più importante

La definizione dice sottoinsieme, non tutti i dati, non una copia di tutto, ma uno scelto con cura porzione dei dati primari. Questo è fondamentale per due ragioni:

  • La memorizzazione nella cache è più costosa dell'archiviazione su disco. L'archiviazione dei dati in una cache (in genere nella RAM) costa molto di più per gigabyte rispetto all'archiviazione dei dati su un disco rigido o SSD. Semplicemente non puoi permetterti di memorizzare tutto nella cache. Gli archivi su disco sono relativamente più economici e offrono anche molta capacità, questo è il motivo per cui non inseriamo tutto nella memoria cache.
  • La capacità della cache è limitata. La RAM è scarsa rispetto alla memoria secondaria. Un server tipico potrebbe avere 64 GB o 128 GB di RAM ma più terabyte di disco. Devi essere selettivo.
  • Memorizzare tutto nella cache vanifica lo scopo. Se memorizzassi tutto nella cache, duplicheresti semplicemente lo spazio di archiviazione a un costo molto più elevato. Il punto è memorizzare nella cache il file giusto cose, i dati a cui si potrà effettivamente accedere nuovamente presto.

Parametri che determinano cosa memorizzare nella cache

Quando si progetta un livello di caching, questi sono i parametri da valutare per decidere cosa merita di essere nella cache:

  • Frequenza d'uso: Con quale frequenza si accede a questi dati? I dati a cui si accede migliaia di volte al minuto sono un candidato di gran lunga migliore rispetto ai dati a cui si accede una volta al giorno.
  • Probabilità di prossimo utilizzo: Sulla base dei modelli di accesso, qual è la probabilità statistica che questi dati vengano richiesti nuovamente a breve? I modelli di apprendimento automatico vengono utilizzati su larga scala (Netflix, Twitter) per prevederlo.
  • Attualità: è stato effettuato l'accesso a questi dati di recente? È statisticamente più probabile che i dati consultati di recente vengano consultati di nuovo presto (il principio della località temporale).
  • Costo del ricalcolo: Quanto costa rigenerare questi dati se non sono nella cache? Una semplice ricerca nel DB è economica. Un calcolo ML di argomenti di tendenza su miliardi di tweet è estremamente costoso. Quanto più costoso è il calcolo, tanto più forte è la necessità di memorizzare nella cache.
  • Volatilità dei dati: Con quale frequenza cambiano questi dati? I dati altamente volatili (ad esempio i prezzi delle azioni in tempo reale) sono un cattivo candidato per la memorizzazione nella cache perché diventano immediatamente obsoleti. I dati statici (descrizioni dei prodotti, profili utente) sono un ottimo candidato.

Perché la memorizzazione nella cache è importante: il contesto ad alte prestazioni

Questo singolo meccanismo, il caching, è a fattore enorme in molte applicazioni ad alte prestazioni. Quando parliamo di prestazioni elevate, intendiamo applicazioni che tengono traccia della latenza in microsecondi o millisecondi a due cifre. Su questa scala, anche una differenza di 5 ms nel tempo di risposta è evidente e una differenza di 50 ms è inaccettabile.

Senza caching, i sistemi ad alto traffico si trovano ad affrontare due colli di bottiglia impossibili:

I due scenari principali in cui la memorizzazione nella cache è essenziale

1. Calcolo pesante: quando la generazione di un risultato richiede notevoli risorse di CPU, GPU o memoria (inferenza ML, join complessi su milioni di righe, pipeline di aggregazione). Non vuoi ripeterlo per ogni singola richiesta dell'utente.

2. Trasferimento dati intenso: Quando i dati inviati sono di grandi dimensioni (file video, librerie di immagini, payload JSON di grandi dimensioni) e inviarli in rete per ogni richiesta sarebbe lento e costoso. Vuoi che i dati siano già vicini all'utente.

Questi due scenari, evitare costosi ricalcoli ed evitare trasferimenti di dati pesanti e ridondanti, sono i modelli che riconoscerai in ogni singolo caso d'uso della memorizzazione nella cache che incontrerai nella tua carriera. Ogni volta che vedi una di queste due situazioni, il tuo primo istinto dovrebbe essere: "Possiamo nasconderlo?"

02 / ESEMPI DEL MONDO REALE

Esempi del mondo reale

Prima di approfondire i meccanismi, è utile capire perché la memorizzazione nella cache è importante su scala di produzione. Esaminiamo tre esempi che illustrano il concetto e i due scenari principali in cui la memorizzazione nella cache viene sempre visualizzata. Dopo questi esempi, inizierai a vedere lo schema ovunque.

Esempio 1: Ricerca Google

Praticamente tutti noi utilizziamo o abbiamo utilizzato Ricerca Google nei nostri browser. Cosa succede esattamente quando digiti qualcosa nella barra di ricerca di Google e premi Invio?

Tale query viene elaborata dal motore di ricerca di Google attraverso un algoritmo e un flusso di lavoro piuttosto complessi. Ogni query passa attraverso una pipeline che in genere comporta:

  • Strisciando: i bot di Google scansionano continuamente il Web, scoprendo e scaricando miliardi di pagine
  • Indicizzazione: il contenuto sottoposto a scansione viene analizzato e aggiunto a un vasto indice ricercabile
  • Classifica: quando arriva una query, centinaia di algoritmi di classificazione determinano quali risultati sono più pertinenti

L'intero processo lo è computazionalmente costoso: quando diciamo costoso intendiamo computazionalmente costoso. Richiede molta potenza di calcolo, molta CPU, molte risorse di memoria, ecc.

Consideriamo ora una query del tipo "che tempo fa oggi", vengono cercate query come questa milioni e milioni di volte ogni giorno. Senza la memorizzazione nella cache, senza implementare questo meccanismo chiamato memorizzazione nella cache, i server di Google avrebbero bisogno di farlo ricalcolare tutti i risultati per ogni singola query. Ogni singola query riguardante il meteo attuale di una località richiederebbe di esaminare tutto l’indice, eseguire tutti gli algoritmi di classificazione e recuperare i risultati, il che a sua volta rallenterebbe notevolmente i tempi di risposta e porterebbe a un carico molto elevato del server.

Cosa fa invece Google

Google utilizza a sistema di caching in memoria distribuito per memorizzare i risultati. La parola chiave qui è distribuito, i server del sistema di caching sono sparsi in tutto il mondo. Non sono concentrati solo in una singola posizione ma sparsi in tutto il mondo e quei server di cache memorizzano i risultati, qualunque siano i risultati restituiti da tutti quegli algoritmi di classificazione e dai diversi algoritmi coinvolti nell'intero flusso di lavoro di Ricerca Google. Vengono memorizzati nella cache o archiviati in questi server.

Quando un utente effettua una ricerca, il sistema controlla innanzitutto se i risultati di quella particolare query sono presenti nella cache oppure no:

Fig 1.1: Ricerca Google: flusso di cache hit e cache miss con ciclo di archiviazione dei risultati

Tracciamo precisamente entrambi i percorsi:

  • Hit della cache: Se la query è stata cercata in precedenza (ad esempio, "meteo a Delhi" è stata cercata 5 minuti fa da qualcun altro), il sistema la trova nella cache e restituisce i risultati istantaneamente. Il recupero dei dati da una cache è molto veloce, questo è uno dei motivi principali per cui utilizziamo una cache.
  • Signorina cache: Se la query non è mai stata cercata prima o la cache è scaduta, il sistema esegue il normale flusso di lavoro completo, tutta la classifica, tutto l'ordinamento, qualunque algoritmo sia coinvolto. Quindi ci vuole quel risultato, lo memorizza nella cachee lo restituisce all'utente. Pertanto, la prossima volta che lo stesso utente o un altro utente digita la stessa query, tali risultati possono essere recuperati direttamente dalla cache.
Vocabolario chiave introdotto

Hit della cache: Quando cerchi dati nella cache e trovalo. Percorso veloce. Non è necessario alcun ricalcolo.

Signorina cache: Quando cerchi i dati nella cache ed è non lì. È necessario accedere alla fonte primaria, calcolare il risultato e quindi archiviarlo per un uso futuro.

Esempio 2: Netflix e CDN

Netflix è un'enorme piattaforma di streaming globale che offre diversi tipi di contenuti, film, serie, anime, ecc. a milioni di utenti in tutto il mondo. Trasmette grandi volumi di dati e, quando diciamo grandi, possono essere diversi terabyte, a causa del modo in cui funzionano queste piattaforme di streaming.

Come Netflix archivia un singolo film

Per un singolo video, diciamo un singolo film chiamato Movie One, passa attraverso un processo chiamato codifica. Si prepara risoluzioni diverse per dispositivi diversi e velocità di rete diverse. Per una spiegazione di alto livello, diciamo che ha:

  • 1080p, per Internet veloce e dispositivi di fascia alta
  • 720p, per connessioni moderate
  • 480p, per connessioni lente o dati mobili
  • e più formati per diversi codec e dispositivi

A seconda della velocità della tua rete e del dispositivo che stai utilizzando, Netflix invia dinamicamente una versione ottimizzata di quei contenuti in modo da non sprecare la larghezza di banda e diminuire anche il carico sui server di Netflix. È tutta una questione di codifica. Ma la vera domanda è: come fa Netflix a fornire effettivamente centinaia e migliaia di terabyte di dati a milioni di utenti sparsi in tutto il mondo, con un buffering minimo?

La risposta: CDN (rete per la distribuzione di contenuti)

Netflix ha i propri server di origine, diciamo che sono da qualche parte negli Stati Uniti, in diversi data center e luoghi, con rack di server che archiviano i film veri e propri. Ma Netflix fa uno sforzo in più. In tutto il mondo, in luoghi diversi, Netflix colloca quelli che vengono chiamati Posizioni periferiche.

Questi sono chiamati Posizioni periferiche perché questi server lo sono posizionato strategicamente in modo che la latenza per gli utenti in quella regione sia minima. Se è presente un server in India, per gli utenti indiani la latenza delle richieste di dati servite da quel server sarà minima, rispetto a tutte le richieste che passano attraverso il server di origine situato negli Stati Uniti.

Pensa a cosa accadrebbe senza questo: tutte le persone in India che vogliono guardare un film su Netflix invierebbero richieste fino al data center degli Stati Uniti. Dal punto di vista geografico, la distanza da percorrere per i dati è lunga. Il tempo di risposta sarebbe elevato e si verificherebbe il buffering. Ma con un edge server a Mumbai o Chennai, quella distanza crolla quasi a zero.

Fig 1.2: CDN Netflix: contenuto distribuito dall'origine ai server Edge/PoP a livello globale, servito agli utenti vicini

Termini chiave di questo esempio, questi sono un vocabolario importante che utilizzerai durante la tua carriera:

  • CDN (rete per la distribuzione dei contenuti): una rete di server distribuita a livello globale che memorizza nella cache e distribuisce contenuti da posizioni geograficamente più vicine all'utente finale. Netflix ha un proprio CDN (chiamato Open Connect). Altri fornitori CDN includono Cloudflare, Akamai, Fastly, AWS CloudFront.
  • Edge Location/Edge Server/Edge Computing: Ogni volta che vedi la parola "edge" in contesti infrastrutturali, significa fondamentalmente un server più vicino all'utente invece di un server centralizzato o di origine. Il "bordo" è il bordo della rete, vicino agli utenti finali.
  • PoP (punto di presenza): Un PoP è solo un termine di fantasia che sostanzialmente indica una regione particolare in cui sono presenti più server periferici. Una raccolta di più server edge concentrati in una particolare regione è chiamata PoP. Ad esempio, Netflix potrebbe avere un PoP a Mumbai composto da 10-20 server edge.
  • Server di origine: il server master/primario in cui risiedono i dati canonici effettivi. I server periferici ottengono i loro contenuti da qui, li memorizzano nella cache locale e servono gli utenti dalla propria copia.
  • TTL (Tempo di vivere): una durata configurata sul contenuto memorizzato nella cache, dopo la quale viene considerato obsoleto. Quando il TTL scade, l'edge server deve recuperare il contenuto dal server di origine per ottenere una nuova copia. Le aziende stabiliscono una "durata equa", questo contenuto dovrebbe essere memorizzato nella cache solo per le prossime ore perché dopo potrebbe avere una nuova versione.
Caching intelligente di Netflix / Non tutto viene memorizzato nella cache ovunque

Netflix non memorizza nella cache tutti i suoi dati in tutte le edge location. Ciò comporterebbe costi enormi e richiederebbe anche molte risorse. Invece, usano algoritmi di machine learning, analisi delle tendenze, dati regionali in tempo realee molti altri calcoli complessi per decidere cosa sottoinsieme di dati da memorizzare nella cache in ciascuna edge location specifica. Un server a Mumbai potrebbe memorizzare film famosi di Bollywood e spettacoli indiani di tendenza, mentre un server a Tokyo memorizza anime e drammi J. Si tratta di caching intelligente, regionale e basato sui dati, non di replica a forza bruta.

La CDN non è solo per lo streaming video. Piattaforme come Vercello utilizza la stessa identica strategia per servire risorse web statiche, pacchetti JavaScript, file HTML, CSS, immagini, dal bordo più vicino all'utente richiedente. Quando distribuisci un'app Next.js su Vercel, questa viene automaticamente distribuita alla loro rete edge globale. Ecco perché le implementazioni Vercel si caricano quasi istantaneamente, indipendentemente da dove ti trovi nel mondo. Stesso principio, stesso meccanismo, diverso tipo di contenuto.

Esempio 3: Twitter / X (Argomenti di tendenza)

Prendiamo una piattaforma chiamata X, precedentemente nota come Twitter. Puoi applicare questo esempio a qualsiasi piattaforma di social media, Facebook, LinkedIn, YouTube, implementano tutte lo stesso tipo di strategia.

Se hai familiarità con il funzionamento di Twitter, c'è una sezione chiamata Argomenti di tendenza. Ciò che fa Twitter è identificare gli argomenti di tendenza in base a analizzando milioni e miliardi di tweet in tempo reale. Analizza tutti i tweet che le persone fanno in tutto il mondo, estrae modelli e tendenze e calcola ciò che è di tendenza.

Perché questo calcolo è costoso

Questo calcolo è molto costoso. Implica:

  • Algoritmi basati sull'apprendimento automatico per l'elaborazione del linguaggio naturale, il clustering di argomenti e il rilevamento delle tendenze
  • Grandi quantità di GPU e infrastrutture pesanti
  • Elaborando terabyte di dati, stiamo parlando di analizzare i tweet di milioni e miliardi di persone in tutto il mondo

Cosa succede senza memorizzazione nella cache

Immagina se Twitter facesse tutti questi calcoli ogni volta che un utente accedeva alla sezione delle tendenze. Se anche la metà dei miliardi di utenti di Twitter tentassero di accedere alla sezione delle tendenze e ogni utente attivasse questo costoso calcolo, il server non sarebbe in grado di gestirlo, si bloccherebbe minuti o secondi. Ci sono miliardi di persone e se ogni singola richiesta attiva l'intera pipeline di ML, è impossibile da sostenere.

Cosa fa realmente Twitter

Per evitare di eseguire calcoli così pesanti per ogni richiesta, Twitter memorizza nella cache gli argomenti di tendenza. Ogni pochi minuti, e ovviamente non conosciamo l'algoritmo esatto o la durata esatta utilizzata da Twitter, ma facciamo una stima approssimativa per il bene di questo esempio: ogni pochi minuti, Twitter prende tutti questi dati da diverse regioni, esegue diversi algoritmi di apprendimento automatico e algoritmi di rilevamento delle tendenze a un livello molto elevato, quindi memorizza i risultati in un archivio di valori-chiave in memoria come Redis.

Quando gli utenti richiedono la sezione delle tendenze, invece di calcolarla di nuovo, semplicemente prende i dati dalla cache e li invia all'utente. Questo è il motivo per cui nel momento in cui apri il telefono ottieni i dati immediatamente, non vedi alcun tipo di tempo di caricamento significativo. Se disponi di una connessione Internet generalmente veloce, l'intera interazione dell'interfaccia utente è molto veloce.

Perché gli argomenti di tendenza sono sicuri da memorizzare nella cache

Affinché una tendenza cambi in una particolare regione, supponiamo che nel tuo paese siano in corso le elezioni e che le elezioni siano l'argomento di tendenza, non è qualcosa che è soggetto a cambiamenti in pochi secondi o minuti. Per lo meno rimarrà nella sezione delle tendenze per un paio d'ore o un paio di giorni. Poiché questi dati sono non modificato dinamicamente minuto per minuto, è molto sicuro memorizzarlo nella cache. Il TTL può essere impostato su pochi minuti o anche di più senza alcuna notevole perdita di freschezza per l'utente.

Il modello: riconoscere quando memorizzare nella cache

Dopo questi tre esempi, ora dovresti vedere chiaramente lo schema. Ogni volta che si verifica una situazione in cui si tratta di:

  • Facendo molti calcoli pesanti: come gli algoritmi di ranking di Google o il rilevamento delle tendenze basato su ML di Twitter, non vuoi ricalcolare per ogni singola richiesta
  • Invio di grandi quantità di dati a molti utenti: come Netflix che invia terabyte di contenuti video a livello globale, non vuoi servire sempre da un'unica posizione centralizzata

Questi sono i due scenari comuni in cui entra in gioco la memorizzazione nella cache. Riconoscere uno di questi in una discussione sulla progettazione del sistema e la memorizzazione nella cache è quasi sempre parte della soluzione.

04 / LIVELLO DI RETE

Cache a livello di rete

I due principali casi d'uso a livello di rete di cui si occupano gli ingegneri backend sono la memorizzazione nella cache CDN e DNS.

4.1: CDN (rete per la distribuzione di contenuti)

L'idea centrale della CDN è quella di memorizzare nella cache i contenuti su server geograficamente più vicini agli utenti finali. Qualsiasi server posizionato vicino all'utente al "bordo" della rete è chiamato an Nodo Edge, Server Edge o Edge Computing.

Come scorre una richiesta CDN

Le decisioni di routing della CDN considerano più parametri:

  • Posizione geografica dell'utente: trova il PoP più vicino
  • Condizioni della rete: un utente con una connessione lenta potrebbe essere indirizzato verso un PoP con contenuti a risoluzione inferiore (es. 480p anziché 1080p)
  • Carico del server: evita il routing verso un edge server sovraccarico

4.2: Cache DNS

DNS (Domain Name System) traduce nomi di dominio leggibili dall'uomo (come example.com) negli indirizzi IP che i browser utilizzano per connettersi ai server. Questo processo di risoluzione, senza memorizzazione nella cache, lo è profondamente ricorsivo e lento.

Perché gli array sono più veloci per l'accesso sequenziale

Un'importante conseguenza pratica della memorizzazione nella cache della CPU: quando inizi a attraversare un array in sequenza, i file della CPU algoritmi di prefetch/predittivi rilevare il modello sequenziale e caricare l'intero array (o una parte di grandi dimensioni) nella cache L1/L2 in modo proattivo. Questo è il motivo for i cicli sugli array sono estremamente veloci, i dati sono già nella cache nel momento in cui la CPU ne ha bisogno.

RAM vs disco: perché la RAM è più veloce (la fisica)

Questo è il motivo fondamentale perché i database in memoria come Redis sono molto più veloci dei database basati su disco come PostgreSQL o MySQL. Comprendere l'effettiva differenza hardware è importante, non è magia, è fisica e ingegneria.

Come funziona l'archiviazione su disco rigido

In un tradizionale disco rigido (HDD), è presente una sorta di testa meccanica che ruota attorno al disco. Quando vuoi leggere i dati, il disco gira, la testa si sposta sulla traccia giusta e così trova fisicamente i dati. È un funzionamento meccanico. Pensaci, un braccio fisico letterale deve spostarsi in una posizione su un piatto rotante. Questo movimento meccanico richiede tempo, millisecondi, che in termini informatici è un'eternità.

Come funziona la RAM

La memoria ad accesso casuale è fondamentalmente diversa. Ha un sacco di condensatori e transistor e attraverso l'uso di segnali elettrici combinato con accesso diretto basato sull'indirizzo, può accedere a qualsiasi posizione della memoria con un singolo segnale elettrico. Non c'è movimento fisico, nessuna ricerca, nessuna rotazione. Si accede ai dati inviando un segnale elettrico a uno specifico indirizzo di memoria, e ciò avviene quasi alla velocità dell'elettricità stessa.

Anche per questo si chiama Memoria ad accesso casuale, lo fa non importa da quale direzione provi ad accedere ai dati. La velocità e il tempo sono quasi costanti indipendentemente da dove si trovano i dati nella memoria. Se accedi all'indirizzo 0x0001 o indirizzo 0xFFFF, il tempo di recupero è essenzialmente lo stesso. Questa proprietà si chiama O(1) tempo di accesso nella terminologia delle strutture dati.

Confrontalo con un disco rigido: l'accesso ai dati in sequenza (dall'indirizzo 0 a 100) è veloce perché la testa non deve muoversi molto. Ma accedere ai dati in modo casuale (saltando dall'indirizzo da 0 a 9000 a da 200 a 7000) è estremamente lento perché la testa deve cercare fisicamente ogni volta posizioni diverse. Ecco perché gli HDD preferiscono modelli di accesso sequenziale.

Il compromesso fondamentale

Quando si tratta di memoria ad accesso casuale, stiamo facendo affari non volatilità e capacità di velocità. Questo è il compromesso dichiarato chiaramente. La RAM è incredibilmente veloce ma:

  • È volatile. Ogni volta che spegni il dispositivo, qualunque dato sia memorizzato nella RAM, scompare. Si cancella da solo. Ricomincia da capo ogni volta che avvii il computer. Ciò è dovuto al modo in cui funzionano i condensatori, che necessitano di una fornitura costante di elettricità per mantenere il loro stato. Tagliamo il potere, lo Stato scompare.
  • Ha una capacità limitata. Anche se abbiamo velocità a nostra disposizione con la RAM, non ne abbiamo in abbondanza. Il costo di produzione della RAM su larga scala significa che i server hanno molta meno RAM rispetto allo storage su disco.

Questo è il motivo per cui tu non può sostituire completamente un disco rigido o un tradizionale sistema di archiviazione basato su disco con RAM. Hanno il loro ruolo, sono veloci quando si tratta di accesso e recupero dei dati, ma non sostituiscono l'archiviazione secondaria. La memorizzazione dei dati nella memoria secondaria lo è permanente, non volatile. Non importa se il tuo programma vi accede o meno, se il tuo computer è acceso o spento, i dati persistono lì perché sta scrivendo fisicamente i dati sul disco.

Archiviazione primaria e secondaria/Riepilogo

Memoria primaria (RAM): Accesso ai dati molto veloce, capacità limitata, volatile (perdita di dati allo spegnimento). Utilizzato per i dati che devono essere elaborati in questo momento o recuperati immediatamente.

Memoria secondaria (HDD/SSD): Accesso ai dati più lento, capacità abbondante, non volatile (i dati persistono). Utilizzato per l'archiviazione permanente di tutti i tuoi dati.

Come Redis unisce entrambi i mondi

Tecnologie come Redis e Memcached utilizzano questa memoria ad accesso casuale (memoria primaria/memoria principale) per archiviare i propri dati, ecco perché le operazioni di accesso ai dati da questi database sono molto veloci. Ma per quanto riguarda la persistenza? Che dire del fatto che la RAM perde dati allo spegnimento?

Dietro le quinte, per la persistenza, queste tecnologie fanno uso anche dello storage secondario. Con una sorta di meccanismo, all'avvio del programma, prende i dati dalla memoria secondaria e li carica nuovamente nella memoria principale, in modo da avere la persistenza dei dati. Ma quando effettivamente recuperi i dati o li modifichi, ciò accade con la memoria primaria. Il database in memoria è responsabile dell'implementazione di questo livello di persistenza, che si tratti degli snapshot RDB di Redis o del registro AOF (Append-Only File).

06 / DATABASE IN MEMORIA

Database NoSQL con valori-chiave in memoria

Tornando al contesto dello sviluppo backend, tecnologie come Redis, Memcached, e se parliamo di tecnologie Cloud allora AWS ElastiCache: entrano in gioco questi. Forniscono un qualche tipo di spazio di archiviazione e tale spazio di archiviazione si basa sulla memoria primaria (RAM). Questo è il motivo per cui le operazioni di accesso ai dati da questi database sono molto veloci.

Chiamiamo queste tecnologie Database NoSQL con valori-chiave in memoria. Quel nome è composto da quattro parti e ognuna ti dice qualcosa di importante:

In memoria

Rispetto ai database tradizionali come PostgreSQL o MySQL, questi lo sono non memorizzato su disco. La memoria si basa sulla RAM (memoria primaria). Questo è il motivo per cui le operazioni di accesso ai dati sono estremamente veloci, abbiamo appena capito nella sezione hardware esattamente perché la RAM è ordini di grandezza più veloce dell'accesso basato su disco. Redis legge e scrive sulla RAM, non sul disco.

Valore-chiave

Rispetto ai tradizionali database relazionali che hanno uno schema molto rigido, devi creare tabelle, creare righe, definire colonne con tipi, ecc., qui la struttura dei dati è molto semplice. Sì chiavi e valori. Hai una chiave particolare e per quella chiave puoi memorizzare qualsiasi cosa, può essere una lista, un oggetto JSON, una stringa, un numero, un hash, un set. Diverse tecnologie offrono diversi tipi di dati, ma l'interfaccia è sempre: dammi una chiave, ti darò il suo valore.

NoSQL

Loro non imporre la rigidità dei database SQL tradizionali. Nessuno schema, nessun join, nessuna query complessa. L'API è volutamente semplice. In Redis, essenzialmente hai SET key value e GET key come operazioni principali. Non è complesso come le query SQL con aggregazione, GRUPPO BY, ecc., l'accesso è piuttosto semplice.

Banca dati

Nonostante siano "solo" un archivio di valori-chiave, si tratta di database completi con funzionalità come scadenza basata su TTL, opzioni di persistenza, messaggistica pub/sub, scripting Lua (Redis), clustering e replica. L'etichetta di "database" è guadagnata, gestiscono i dati in modo affidabile, non solo come una cache effimera.

Perché la semplicità del valore-chiave è una caratteristica, non una limitazione

Potresti chiederti: perché dovrei utilizzare un database senza query complesse? La risposta è questa tutta quella complessità che non hai sono le prestazioni che ottieni. Quando Redis riceve un comando GET, cerca letteralmente semplicemente una tabella hash in memoria. Non è prevista l'analisi delle query, né la pianificazione delle query, né l'I/O del disco, né l'attraversamento dell'indice. È una ricerca di memoria O(1), ecco perché Redis può eseguire milioni di operazioni al secondo.

Questo è ciò di cui ti occuperai come ingegnere di backend, prendi qualunque libreria compatibile sia disponibile nel tuo linguaggio di programmazione corrispondente (Node.js ha node-redis o ioredis, Vai ha go-redis, Python ha redis-py) e, a seconda di ciò, usi semplicemente la libreria. Fornisci una chiave, fornisci un valore, lo memorizzi. E quando vuoi recuperarlo, fornisci la chiave e ottieni il valore. È piuttosto semplice, non presenta complessità come query SQL e aggregazione. Ma tutta questa familiarità tecnica con come funziona la tecnologia dietro le quinte, quali sono i componenti principali, ti aiuta a dare un senso al tutto e a prendere decisioni migliori.

Come Redis gestisce la persistenza

Redis utilizza due meccanismi principali per garantire che i dati non vadano persi al riavvio del processo:

  • Istantanee RDB (database Redis).: A intervalli configurati (ad esempio ogni 5 minuti o quando si sono verificate N scritture), Redis effettua un fork del processo e scrive l'intero set di dati in memoria su un file binario .rdb file su disco. All'avvio, Redis carica nuovamente questo file in memoria. Riavvio veloce, ma potresti perdere fino a N minuti di dati.
  • AOF (file di sola aggiunta): ogni operazione di scrittura viene registrata in un file di sola aggiunta su disco. Al riavvio, Redis ripete tutte queste operazioni per ricostruire lo stato in memoria. Perdita di dati prossima allo zero, ma riavvio più lento e il file diventa più grande nel tempo (Redis lo compatta periodicamente tramite uno sfondo riscrivere processo).
  • Entrambi insieme: Redis consiglia di utilizzare sia RDB che AOF in produzione per il miglior equilibrio tra prestazioni e durata.

L'intuizione chiave: i dati vengono sempre letti e scritti nella RAM durante il normale funzionamento. Il disco è coinvolto solo per la persistenza (salvataggio dello stato per il ripristino). Il percorso caldo, il percorso seguito da ogni richiesta dell'utente, non tocca mai il disco.

07 / STRATEGIE

Strategie di memorizzazione nella cache

Esistono due strategie principali di memorizzazione nella cache che incontrerai nello sviluppo quotidiano del backend. Rispondono a diverse domande: quando popoli la cache? e quando lo aggiorni?

Strategia 1

Caching lento (Cache-Aside)

La cache viene popolata solo quando i dati vengono richiesti per la prima volta. Non viene eseguita la precompilazione proattiva.

Strategia 2

Caching write-through

Ogni scrittura nel database viene scritta contemporaneamente nella cache. La cache è sempre fresca.

Strategia 1: caching lento (cache-aside)

Fig 5.1: Caching lento (Cache-Aside): popolato al primo errore

Caratteristiche del Lazy Caching:

  • La cache viene popolata solo quando i dati vengono effettivamente richiesti, senza alcuna precompilazione sprecata
  • La prima richiesta di dati comporta sempre un errore nella cache (latenza leggermente superiore per il primo utente)
  • Rischio di dati obsoleti, se il DB sottostante cambia, il valore memorizzato nella cache può essere obsoleto fino alla scadenza del TTL o all'invalidazione manuale
  • Semplice da implementare e molto comune nella pratica

Strategia 2: memorizzazione nella cache write-through

Ogni volta che un'operazione di scrittura (POST, PUT, PATCH) modifica i dati nel database, si verifica la stessa modifica applicati contemporaneamente alla cache all'interno dello stesso flusso di esecuzione della chiamata API.

Vantaggio

La cache lo è sempre fresco. Non fornisci mai dati obsoleti perché la cache viene aggiornata esattamente nello stesso momento del database.

Compromesso

Ogni operazione di scrittura porta spese generali aggiuntive: è necessario aggiornare atomicamente (o quasi atomicamente) sia il database che la cache. Ciò aumenta la latenza delle operazioni di scrittura. Se le operazioni di scrittura sono molto frequenti, ciò può diventare un collo di bottiglia.

Necessita di cache sempre aggiornata (dati finanziari, inventario)Scrivi attraverso

08 / POLITICHE DI SFRATTO

Politiche di sfratto

Qualcos'altro di cui dovremmo essere consapevoli quando lavoriamo con cache in memoria come Redis è il file politica di sfratto. Cosa significa? Innanzitutto capiamo il problema.

Perché è necessario lo sfratto

Quando si dispone di una cache e, come già sappiamo, le cache in memoria come Redis utilizzano la memoria primaria (RAM), che ha una capacità limitata rispetto alla memoria secondaria, è abbastanza ovvio che a un certo punto si esaurirà la memoria. Sia che tu stia eseguendo Redis sul tuo server e la RAM si riempia, o che tu stia utilizzando un servizio gestito come AWS ElastiCache che ha un limite di archiviazione, ad un certo punto raggiungerai il limite.

A quel punto devi decidere: vuoi conservare nuovo dati nella cache, ma non c'è spazio. Devi farlo eliminare qualcosa di vecchio per fare spazio a qualcosa di nuovo. E ovviamente, come abbiamo già discusso nella parte iniziale di questo argomento, la cache è solo un sottoinsieme dei dati, i dati a cui si accede frequentemente archiviati in una posizione diversa e più veloce. Le parole chiave su cui concentrarsi: a sottoinsieme dello storage primario. Non possiamo archiviare tutta la memoria primaria nella cache. Quindi dobbiamo decidere cosa resta e cosa va.

La questione centrale dello sfratto

Quale pezzo di dati memorizzato nella cache è meno prezioso mantenere? Sfrattalo, fai spazio ai nuovi dati che hanno una priorità più alta. Diverse politiche di sfratto rispondono a questa domanda in modo diverso.

  • NESSUN SFRATTO
    Nessuna politica di sfratto configurata. Questa è l'impostazione predefinita se non hai configurato alcuna politica di sfratto. Cosa succede quando la cache è piena e provi a inserire nuovi dati? Ottieni semplicemente un errore: la memoria è piena, operazione rifiutata. Ciò non ha molto senso per un caso d'uso della cache, ma esiste come configurazione perché ci sono situazioni in cui si desidera controllare esplicitamente la dimensione della cache e non eliminare mai i dati in modo silenzioso. Per un caso d'uso reale della memorizzazione nella cache, dovresti sempre configurare una delle policy seguenti.
  • LRU
    Usato meno di recente. L'algoritmo controlla quali dati erano accesso meno recente. Tiene traccia di quando è stata l'ultima volta che è stato effettuato l'accesso a una determinata chiave.

    Esempio dettagliato dalla lezione: Diciamo che abbiamo 4 chiavi nella cache, Chiave 1, Chiave 2, Chiave 3, Chiave 4, e la memoria è ora piena. Il database tiene traccia dell'ultimo accesso a ciascuna chiave:
    • Chiave 1, accesso effettuato oggi
    • Chiave 2, accesso effettuato oggi
    • Chiave 3, accessibile oggi
    • Tasto 4, accesso ieri
    Ora la chiave 5 vuole entrare nella cache. Con la politica di sfratto LRU, Redis verifica qual è il file con accesso più vecchio punto dati. Poiché ieri è stato effettuato l'accesso alla chiave 4 e oggi è stato effettuato l'accesso a tutte le altre, seleziona la chiave 4: "tu uscirai e la chiave 5 entrerà". Si tratta dello sfratto utilizzato meno di recente.

    Quando usarlo: LRU è la politica di sfratto più comunemente utilizzata. Funziona bene per i carichi di lavoro in cui è probabile che si accederà nuovamente presto ai dati a cui si è effettuato l'accesso di recente, il che è vero per la maggior parte delle applicazioni del mondo reale (località temporale).
  • LFU
    Usato meno frequentemente. Invece di tracciare quando è stato effettuato l'ultimo accesso a una chiave, tracce LFU quante volte in totale è stato eseguito l'accesso a ciascuna chiave. La chiave con il numero di accessi più basso verrà sfrattata.

    Esempio dettagliato dalla lezione: Dimentica il tempo, diciamo che abbiamo 4 chiavi e la chiave 5 vuole entrare. Ogni chiave ha un contatore di frequenza di accesso:
    • Chiave 1, accessibile 5 volte finora
    • Chiave 2, accesso 10 volte finora
    • Tasto 3, accesso 6 volte finora
    • Tasto 4, accesso 23 volte finora
    La chiave 5 arriva e ha bisogno di spazio. LFU controlla quale sia la chiave meno frequentemente utilizzato, quello con la frequenza più bassa. È stato effettuato l'accesso alla chiave 1 solo 5 volte, il minimo. Gli altri tasti vengono utilizzati più frequentemente. Quindi seleziona la chiave 1: "tu uscirai, la chiave 5 entrerà".

    Quando usarlo: LFU funziona meglio di LRU quando la tua applicazione ha un insieme stabile di articoli "caldi" che sono sempre popolari (come un catalogo di prodotti in cui i primi 100 prodotti ricevono l'80% del traffico). LRU potrebbe sfrattare un elemento importante a cui non è stato possibile accedere nell'ultimo minuto, mentre LFU lo manterrebbe a causa della sua elevata frequenza a lungo termine.
  • BASATO su TTL
    TTL volatile (sfratto basato sul tempo di vita). In Redis puoi configurare un TTL, un time-to-live, per chiavi diverse individualmente. Quando la cache è piena e deve eliminare qualcosa, con questa policy controlla quali chiavi hanno il file TTL rimanente più basso: ovvero quale chiave scadrà comunque prima.

    Esempio di procedura dettagliata: Stesso scenario, 4 chiavi, la chiave 5 vuole entrare, la cache è piena. Ogni chiave ha un TTL:
    • Chiave 1, scade tra 3 ore
    • Chiave 2, scade tra 45 minuti
    • Chiave 3, scade tra 2 ore
    • Chiave 4, scade tra 10 minuti (a breve scadenza)
    Arriva la chiave 5. La policy seleziona la Chiave 4, scadrà comunque tra 10 minuti, quindi potremmo anche sfrattarla adesso e fare spazio alla Chiave 5. La logica: "questa chiave sta per sparire presto a prescindere, quindi lasciala andare adesso."

    Nota: TTL viene utilizzato anche indipendentemente dallo sfratto per far scadere semplicemente automaticamente i dati non aggiornati. Hai impostato una chiave con SETEX weather_delhi "25 degC" 3600 e dopo 3600 secondi (1 ora), Redis lo elimina automaticamente. Non è mai necessario pulirlo manualmente. Questa è una delle funzionalità Redis più utili per la memorizzazione nella cache delle risposte API esterne.

09 / CASI D'USO

Casi d'uso di Redis nello sviluppo backend

Ora che abbiamo tutte le basi teoriche, diamo un'occhiata ai casi d'uso concreti in cui Redis e i database in memoria vengono utilizzati in un tipico flusso di lavoro di ingegneria backend. Queste sono le situazioni che incontrerai nei progetti reali.

9.1: Caching delle query del database

Uno dei casi d'uso principali. Supponiamo che tu abbia una query SQL che ha molti JOIN, tenta di unire più tabelle, esegue molte aggregazioni e alla fine termina con alcune righe. Si tratta di un'operazione ad alta intensità di calcolo perché hai un set di dati di grandi dimensioni (diciamo milioni e milioni di righe) e hai notato attraverso il monitoraggio che questa particolare API che chiama questa particolare query del database viene colpita abbastanza frequentemente, forse è la tua pagina di destinazione o una pagina dashboard che vengono colpite da molti utenti.

Cosa succede al tuo database senza memorizzazione nella cache? Ogni singolo utente che accede a quella pagina attiva lo stesso costoso JOIN multi-tavolo. Con mille utenti simultanei, stai facendo mille query identiche e costose al database. Ciò comporta un carico enorme sul server DB e aumenta la latenza della risposta API per tutti.

Cosa fai con la memorizzazione nella cache: Prendi quel particolare risultato della query, mettilo nella cache con un po' di TTL (diciamo 1 ora) e da quel momento in poi, quando arriva la richiesta successiva, controlli se il risultato è presente nella cache. Se sì, servilo da lì. Altrimenti esegui il calcolo una volta, memorizzalo nella cache e restituiscilo. Ogni volta che si verifica una modifica ai dati sottostanti, è possibile invalidare manualmente la cache o eliminarla e la richiesta successiva la ricalcolerà di nuovo.

L'esempio della pagina del prodotto Amazon

Questa è una delle migliori illustrazioni del mondo reale. Immagina che ci sia una vendita in corso per un MacBook su Amazon. Se Amazon non memorizzasse nella cache i dettagli di quel prodotto MacBook, durante il periodo dei saldi milioni di utenti visiterebbero quella particolare pagina web. Recuperare l'immagine del MacBook, tutte le descrizioni dei prodotti, le specifiche, le recensioni, queste sono tutte operazioni del database.

Con milioni di utenti simultanei in vendita, il database riceverebbe un milione di richieste identiche per gli stessi identici datie ciò comporta un carico significativo sul database senza alcun motivo, perché le informazioni come i dettagli del prodotto per un MacBook non cambiano molto spesso. Descrizioni dei prodotti, immagini, specifiche, questi sono dati statici. Potrebbero cambiare una volta al mese, se è così. Questo li rende un eccellente candidato per la memorizzazione nella cache.

Pertanto Amazon memorizza nella cache i dati statici come i dettagli dei prodotti e i prezzi in modo che possano ridurre il carico sul database e il database possa effettivamente svolgere il lavoro importante, come gestire le transazioni di pagamento, gli aggiornamenti dell'inventario e la gestione degli ordini, invece di spendere tutta la sua capacità servendo sempre la stessa pagina statica dei dettagli del prodotto.

Caching dei profili dei social media

Anche le piattaforme di social media come Twitter e Facebook memorizzano nella cache i dati del profilo utente. Pensaci, i dati del profilo utente non sono qualcosa che cambia molto spesso. Forse un paio di volte all'anno. Questo è il motivo per cui memorizzano nella cache i dati del profilo utente in modo che ogni volta che i dati vengono recuperati vengano serviti dalla cache anziché dal database.

Ora immagina se si tratta del profilo sui social media di qualche celebrità. Quella particolare pagina e quella particolare API per recuperare i dettagli del profilo utente di quella celebrità potrebbero essere visitate normalmente mille volte al giorno, o se hanno un film in uscita, forse un milione di volte al giorno. In tal caso, caricare tutto quel carico sul database non ha assolutamente senso, poiché le informazioni sul profilo utente sono piuttosto statiche per la maggior parte del tempo. Può fornire quel contenuto dalla cache e, anche se l'utente apporta alcune modifiche al proprio profilo, è possibile invalidare la cache e inserire la nuova voce. Si tratta di un'operazione con un numero elevato di operazioni di lettura e scritture molto rare, lo scenario ideale per la memorizzazione nella cache.

Il modello ad alta lettura

Ogni volta che abbiamo a operazione di lettura pesante e la scrittura è piuttosto rara, possiamo utilizzare la memorizzazione nella cache. La memorizzazione nella cache delle query del database è uno dei principali esempi di utilizzo di tecnologie come Redis o database in memoria. Il modello: le letture sono frequenti, i dati cambiano raramente, il calcolo è costoso -> memorizzalo nella cache.

9.2: Archiviazione dei token di sessione

Se hai guardato il video di autenticazione in questa playlist, potresti esserne a conoscenza. In un tipico flusso di autenticazione, dopo un'autenticazione riuscita, a il token di sessione viene generato per quel particolare utente e quel token di sessione è archiviato in una sorta di spazio di archiviazione.

Idealmente, è archiviato in Redis o in un database in memoria, non nel database relazionale principale. Ecco perché:

Ogni volta che l'utente effettua una richiesta o una chiamata API a qualsiasi endpoint sul tuo server, devi farlo convalidare quel token di sessione: recupera le informazioni sulla sessione e controlla se sono valide. Se non utilizzassi Redis, dovresti recuperarlo dal tuo database per ogni singola chiamata API. E come già sai, recuperare i dati dalla RAM (Redis) è molto più veloce che recuperare i dati da un database.

Considera cosa succede su larga scala: se hai 100.000 utenti attivi simultanei, ciascuno dei quali effettua più chiamate API al minuto, si tratta potenzialmente di milioni di query di database al minuto solo per la convalida della sessione, query che restituiscono esattamente gli stessi dati (la sessione è valida, l'ID utente è X) per lo stesso token di sessione ancora e ancora. Ciò comporta un carico non necessario sul database e aggiunge latenza a ogni singolo endpoint API nella tua applicazione.

Con Redis: il token di sessione è la chiave, i dati di sessione dell'utente (ID utente, autorizzazioni, metadati) sono il valore. La convalida è una singola GET session:token_id, una ricerca RAM O(1) che richiede nanosecondi. La sessione scade naturalmente anche tramite TTL, quindi non sono necessari lavori di pulizia.

9.3: Caching della risposta dell'API esterna

Nel tuo backend, stai utilizzando alcune API esterne, diciamo alcune API meteorologiche, e stai prendendo le informazioni da queste e facendo una sorta di calcolo per servire il tuo frontend. Ora ogni volta che il tuo frontend effettua una richiesta alla tua API, se non utilizzi la memorizzazione nella cache, fai anche un'altra richiesta all'API meteo per recuperare i dati meteorologici.

Se hai molti utenti e stanno effettuando più chiamate API, finirai per effettuare migliaia di chiamate API a questa API esterna. Le API esterne solitamente hanno:

  • Limiti di tariffa: ad es. 1000 richieste all'ora. Raggiungi quel limite e ogni richiesta successiva fallisce finché la finestra non si ripristina.
  • Prezzo per chiamata: molte API addebitano un costo per richiesta. Fai un milione di chiamate invece di mille e la tua bolletta aumenta proporzionalmente.
  • Latenza di rete: ogni chiamata HTTP esterna aggiunge tempo di andata e ritorno della rete al tempo di risposta della tua API, rendendo la tua API più lenta.

In questo caso i dati meteorologici non sono dati in tempo reale, nel senso che cambiano ogni secondo. I dati meteorologici non cambiano ogni secondo o minuto, ecco perché è un tipo di dati che lo è sicuro da memorizzare nella cache. Cosa fai: recuperi le informazioni dall'API meteo, le metti nella cache in Redis con un TTL di 1 ora e per la successiva 1 ora tutte le richieste dal tuo frontend utilizzeranno i dati meteorologici memorizzati nella cache. Dopo un'ora, la cache si invalida automaticamente e la prossima volta che arriva una richiesta recupererai nuovi dati meteorologici, li rimetterai nella cache con un nuovo TTL e li restituirai. Per l'ora successiva, tutte le richieste utilizzano nuovamente la nuova versione memorizzata nella cache.

Quando la memorizzazione nella cache dell'API esterna è appropriata

Chiediti: quanto spesso questi dati cambiano effettivamente in modo significativo? Meteo -> ogni ora. Tassi di cambio -> ogni pochi minuti. Prezzi delle azioni -> ogni secondo (troppo volatile per essere memorizzato nella cache). Titoli di notizie -> ogni ora. La risposta determina il tuo TTL. Se i dati cambiano più lentamente della velocità del traffico, memorizzali nella cache.

9.4: Limitazione della velocità

Un ultimo caso d'uso che mi viene in mente, poiché stiamo parlando di limitazione della velocità, anche il meccanismo di limitazione della velocità viene implementato la maggior parte delle volte utilizzando una tecnologia come Redis o qualsiasi cache in memoria.

Il modo in cui viene implementata la limitazione della velocità: di solito è una sorta di middleware che si trova da qualche parte nel mezzo della pipeline delle richieste, ecco perché si chiama middleware. Prima che la richiesta venga passata al percorso o al controller, passa prima attraverso questo middleware del limite di velocità.

Come funziona il middleware di limitazione della velocità passo dopo passo

Il middleware prende un'intestazione dalla richiesta in entrata, una sorta di intestazione che fornisce l'indirizzo IP dell'utente. Di solito l'intestazione è qualcosa del genere X-Forwarded-For. Questa intestazione viene utilizzata principalmente per implementare la limitazione della velocità per scoprire l'indirizzo IP pubblico del client da qualunque parte provenga la richiesta. Questo di solito viene aggiunto da un proxy inverso come Nginx o qualunque cosa tu stia utilizzando.

Il compito di questo middleware è:

  1. Estrai il X-Forwarded-For intestazione dalla richiesta in entrata per ottenere l'indirizzo IP del client
  2. Controlla Redis per un contatore associato a quell'indirizzo IP per la finestra temporale corrente (ad esempio, al minuto)
  3. Incrementa il contatore di 1
  4. Se il contatore supera il limite configurato (ad esempio, 50 richieste al minuto), bloccare la richiesta e restituire lo stato HTTP 429 Too Many Requests
  5. Se è inferiore al limite, passa la richiesta al gestore del percorso effettivo

Diciamo che la condizione è: un determinato cliente può effettuare solo 50 richieste in 1 minuto. Quindi ogni volta che arriva una richiesta:

  • Richiesta 1: controlla la chiave su Redis rate_limit:10.0.0.1:<current_minute> -> non trovato -> imposta su 1 -> consenti
  • Richiesta 2: chiave trovata, il valore è 1 -> incrementa a 2 -> 2 <= 50 -> consenti
  • Richiesta 3: il valore è 2 -> incrementa a 3 -> consenti
  • ... allo stesso modo 4, 5, 6 ... fino a 50 ...
  • Richiesta 51: il valore è 50 -> incremento a 51 -> 51 > 50 -> blocco, ritorno 429

Il TTL sulla chiave è impostato su 1 minuto. Dopo 1 minuto, la chiave scade automaticamente, il contatore si azzera e il client può effettuare nuovamente richieste. Questa è una finestra pulita e automatica in cui non è necessario alcun codice di pulizia.

Fig 7.1: Rate Limiting: il middleware legge l'IP -> incrementa il contatore Redis -> blocca alla 51a richiesta

Perché Redis e non un database relazionale per la limitazione della velocità

Questa è una domanda giusta. È possibile archiviare il contatore in PostgreSQL o MySQL, ha un'archiviazione persistente e possiamo recuperare i dati. Questo è possibile. Ma la differenza è: estrarre i dati da un database relazionale richiede più tempo. Anche una differenza di 20 o 30 millisecondi ha un impatto significativo sulla latenza dell'API, poiché la limitazione della velocità viene eseguita su ogni singola richiesta.

Se lo archiviassimo in un database relazionale, per ogni richiesta effettueremo una chiamata al database. A sua volta, in primo luogo, la latenza verrà aumentata per quella particolare API poiché stiamo effettuando una chiamata al database inutilmente per ogni richiesta. In secondo luogo, aumenta anche il carico sul nostro database, diciamo che ci sono mille utenti che fanno 100 richieste al minuto. Si tratta di 100.000 query di database al minuto solo per gli incrementi del contatore di limitazione della velocità. Il tuo database sarà inondato solo dal sovraccarico del livello di limitazione della velocità.

Questo è il motivo per cui vogliamo separarli, per due motivi. Innanzitutto, renderlo il più veloce possibile in modo da poter ridurre al minimo la latenza delle API. In secondo luogo, per ridurre il carico del database. Questo è il motivo per cui ogni volta che parliamo di implementare la limitazione della velocità, utilizziamo database in memoria come Redis invece di archiviarli nei nostri database relazionali. L'atomica di Redis INCR Il comando è particolarmente adatto: incrementa una chiave di 1 in una singola operazione atomica, senza condizioni di competizione, senza necessità di transazioni o blocchi.

10.1: Caching lento (Cache-Aside) in Go

cache_aside.go / Go + github.com/redis/go-redis/v9 
package main

import (
    "context"
    "encoding/json"
    "fmt"
    "time"

    "github.com/redis/go-redis/v9"
)

type Product struct {
    ID    string `json:"id"`
    Name  string `json:"name"`
    Price float64 `json:"price"`
}

var rdb = redis.NewClient(&redis.Options{
    Addr: "localhost:6379",
})

// GetProduct implements Cache-Aside (Lazy) caching.
// 1. Check Redis first
// 2. On miss, fetch from DB, store in cache, return
func GetProduct(ctx context.Context, productID string) (*Product, error) {
    cacheKey := "product:" + productID

    // Step 1: Try cache first (Cache Hit path)
    cached, err := rdb.Get(ctx, cacheKey).Result()
    if err == nil {
        var product Product
        json.Unmarshal([]byte(cached), &product)
        fmt.Println("[CACHE HIT]", productID)
        return &product, nil
    }

    // Step 2: Cache Miss, fetch from database (expensive operation)
    fmt.Println("[CACHE MISS] fetching from DB...", productID)
    product, err := fetchFromDatabase(productID) // simulate DB call
    if err != nil {
        return nil, err
    }

    // Step 3: Store in cache with a 1-hour TTL
    data, _ := json.Marshal(product)
    rdb.Set(ctx, cacheKey, data, 1*time.Hour)

    return product, nil
}

// Write-Through: update DB and cache simultaneously
func UpdateProduct(ctx context.Context, product *Product) error {
    // Step 1: Update in database
    if err := updateInDatabase(product); err != nil {
        return err
    }

    // Step 2: Write-through, update cache immediately
    cacheKey := "product:" + product.ID
    data, _ := json.Marshal(product)
    rdb.Set(ctx, cacheKey, data, 1*time.Hour)

    fmt.Println("[WRITE-THROUGH] DB + cache updated for", product.ID)
    return nil
}

10.2: Middleware di limitazione della velocità in Go

rate_limiter.go / Go + go-redis 
package middleware

import (
    "context"
    "fmt"
    "net/http"
    "time"

    "github.com/redis/go-redis/v9"
)

const (
    maxRequests = 50
    windowTime  = 1 * time.Minute
)

func RateLimitMiddleware(rdb *redis.Client) http.HandlerFunc {
    return func(w http.ResponseWriter, r *http.Request) {
        ctx := context.Background()

        // Extract client IP from X-Forwarded-For header
        // (set by reverse proxy like Nginx or Caddy)
        clientIP := r.Header.Get("X-Forwarded-For")
        if clientIP == "" {
            clientIP = r.RemoteAddr
        }

        // Redis key: per IP, per minute window
        key := fmt.Sprintf("rate_limit:%s:%d", clientIP, time.Now().Unix()/60)

        // INCR is atomic, no race condition even with concurrent requests
        count, err := rdb.Incr(ctx, key).Result()
        if err != nil {
            http.Error(w, "Internal Server Error", http.StatusInternalServerError)
            return
        }

        // Set TTL on first request of this window (key is new)
        if count == 1 {
            rdb.Expire(ctx, key, windowTime)
        }

        // Check if limit exceeded
        if count > maxRequests {
            w.Header().Set("Retry-After", "60")
            http.Error(w, "429 Too Many Requests", http.StatusTooManyRequests)
            return
        }

        // Proceed to actual handler
        w.Header().Set("X-RateLimit-Remaining", fmt.Sprintf("%d", maxRequests-count))
    }
}

10.3: Decoratore di memorizzazione nella cache in Python

cache.py / Python + redis-py + FastAPI 
import json
import functools
import redis
from fastapi import FastAPI

app = FastAPI()

# Connect to Redis
r = redis.Redis(host="localhost", port=6379, decode_responses=True)

def cache_result(ttl: int = 3600):
    """
    Decorator that implements lazy (cache-aside) caching.
    ttl: time-to-live in seconds (default 1 hour)
    """
    def decorator(func):
        @functools.wraps(func)
        async def wrapper(*args, **kwargs):
            # Build cache key from function name + args
            cache_key = f"{func.__name__}:{args}:{kwargs}"

            # Step 1: Check cache (Cache Hit)
            cached = r.get(cache_key)
            if cached:
                print(f"[CACHE HIT] {cache_key}")
                return json.loads(cached)

            # Step 2: Cache Miss, execute the actual function
            print(f"[CACHE MISS] calling {func.__name__}...")
            result = await func(*args, **kwargs)

            # Step 3: Store in Redis with TTL
            r.setex(cache_key, ttl, json.dumps(result))

            return result
        return wrapper
    return decorator


# Usage: apply cache decorator to any route handler
@app.get("/products/{product_id}")
@cache_result(ttl=3600)  # cache for 1 hour
async def get_product(product_id: str):
    # Expensive DB query, only runs on cache miss
    product = await fetch_from_db(product_id)
    return product


# TTL-based API Response Caching (e.g. weather)
@app.get("/weather/{city}")
async def get_weather(city: str):
    cache_key = f"weather:{city}"

    # Check cache (TTL = 1 hour, weather doesn't change every minute)
    cached = r.get(cache_key)
    if cached:
        return {"source": "cache", "data": json.loads(cached)}

    # Miss: call external weather API (costs money / rate limited)
    weather_data = await call_weather_api(city)

    # Store for 1 hour
    r.setex(cache_key, 3600, json.dumps(weather_data))

    return {"source": "api", "data": weather_data}

10.4: Gestione delle sessioni con Redis (Python)

session.py / Python + redis-py 
import uuid
import json
import redis
from datetime import timedelta

r = redis.Redis(host="localhost", port=6379, decode_responses=True)

def create_session(user_id: str, user_data: dict) -> str:
    """Create a session after successful login. Store in Redis."""
    session_id = str(uuid.uuid4())
    session_key = f"session:{session_id}"

    # Store session data with 24-hour TTL
    # TTL ensures sessions auto-expire, no manual cleanup needed
    r.setex(
        session_key,
        timedelta(hours=24),
        json.dumps({"user_id": user_id, **user_data})
    )

    return session_id  # returned to client as cookie/token


def get_session(session_id: str) -> dict | None:
    """
    Validate session on every authenticated API request.
    Redis O(1) lookup, microseconds, not milliseconds.
    """
    session_key = f"session:{session_id}"
    data = r.get(session_key)

    if not data:
        return None  # session expired or invalid

    # Optionally: refresh TTL on activity (sliding window)
    r.expire(session_key, timedelta(hours=24))

    return json.loads(data)


def delete_session(session_id: str):
    """Logout, delete session from Redis immediately."""
    r.delete(f"session:{session_id}")
