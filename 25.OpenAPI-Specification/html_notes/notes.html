Il problema risolto da OpenAPI

Ogni API inizia come un'idea tra due ingegneri. All'inizio il contratto risiede in un thread Slack o in un file di markdown e funziona, finché non funziona più. Deriva è la modalità di errore universale: Alice aggiunge un campo, il client di Bob si interrompe ed entrambi discutono su cosa fa effettivamente l'API. Un file di markdown è una conversazione; una conversazione va alla deriva.

L'unico cambiamento

Sostituisci "documentiamo l'API" con "let's spec l'API." Una specifica è un file che un computer può analizzare. Un documento è un file che un essere umano legge e ignora. La differenza è la differenza tra un contratto in vita e una pagina wiki morta.

L'anatomia di una specifica OpenAPI

Una specifica OpenAPI è un singolo file YAML o JSON. Al centro ci sono queste chiavi:

openapi: 3.1.0
info:
  title: Bookstore API
  version: 1.0.0
servers:
  - url: https://api.example.com/v1
paths:
  /books:
    get:
      operationId: listBooks
      ...
components:
  schemas:
    Book: ...
ChiaveScopoObbligatorio
openapiVersione specifica (ad es. 3.1.0)Sì
infoTitolo, descrizione, versione, contattoSì
serversURL di base per ambienteNo
pathsOgni endpoint e metodo HTTPSì
componentsSchemi riutilizzabili, schemi di sicurezzaNo

Definizione di endpoint, schemi e codici di stato

I parametri risiedono nell'URL (in: path, in: query, in: header) o nell'organismo della richiesta. Le risposte sono codificate in base al codice di stato.

parameters:
  - name: bookId
    in: path
    required: true
    schema:
      type: string
  - name: page
    in: query
    schema:
      type: integer
      default: 1
requestBody:
  required: true
  content:
    application/json:
      schema:
        $ref: '#/components/schemas/CreateBook'
Perché i componenti sono importanti

Senza components, ogni risposta e ogni corpo della richiesta dovrebbero incorporare lo schema completo. Con components, a Book è definito una volta e viene fatto riferimento ovunque con $ref: '#/components/schemas/Book'. Ciò mantiene le specifiche ASCIUTTE e coerenti.

Design-First o Code-First

Il design innanzitutto: scrivere le specifiche prima del codice. Il contratto viene concordato in anticipo e sia i team frontend che backend lo implementano. Prima il codice: scrivi prima il codice del server e genera la specifica da esso: la specifica è sempre sincronizzata perché è derivata, non scritta a mano.

FattoreIl design innanzituttoPrima il codice
Dimensione della squadra3+ ingegneriSolo/piccola squadra
Stabilità dell'APIContratto stabileIn rapida evoluzione
Consumatori esterniSìInterno
Velocità di iterazioneIniziale più lentaPiù veloce
L'ibrido è il punto debole

Scrivere prima le specifiche per il contratto iniziale (design-first), implementare il server nel codice (code-first) e utilizzare un controllo CI che convalidi le specifiche generate rispetto alle specifiche scritte a mano. Il meglio di entrambi i mondi.

Interfaccia utente spavalda e documentazione interattiva

Servire le specifiche Interfaccia utente spavalda e ogni parte interessata ottiene un sito di documentazione live e interattivo. Gli utenti possono esplorare gli endpoint, provarli e vedere risposte di esempio, tutte generate automaticamente dalle specifiche.

Generazione del codice

Strumenti come openapi-generator, orval, e swagger-typescript-api leggere le specifiche e produrre SDK client tipizzati, stub di server e tipi TypeScript per ogni lingua. Una specifica guida documentazione, test, client e stub.

Mantenere le specifiche sincronizzate

Aggiungi la convalida CI che invia le richieste definite nelle specifiche e verifica che le risposte corrispondano agli schemi. Linting le specifiche con spectral o openapi-lint. Rileva la deriva confrontando la specifica generata con quella canonica. Versione delle specifiche insieme al codice in Git.

Punto di partenza consigliato

Se stai avviando una nuova API, prova code-first con FastAPI (Pitone) o NestJS (Script dattiloscritto). Entrambi generano una specifica OpenAPI valida dal tuo codice con zero configurazione. Aggiungi l'interfaccia utente Swagger per documenti interattivi e una fase di convalida CI per individuare le derive.
